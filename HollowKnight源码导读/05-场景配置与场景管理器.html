第 5 章　场景配置与场景管理器

第 4 章讲场景"怎么换"，本章聚焦每个场景"靠什么描述自己"。《空洞骑士》把一个场景的全部静态配置收在一个挂着 HK 版 SceneManager 的物体上，再配合相机锁区、动态边界和附加场景加载器，构成完整的场景组织方式。

5.1 同名陷阱：两个 SceneManager

读源码时第一个要分清的名字：SceneManager 在游戏里有两个所指。

  • UnityEngine.SceneManagement.SceneManager——Unity 引擎的场景 API（LoadSceneAsync、UnloadScene 等）
  • SceneManager（全局命名空间，本教程称 HK SceneManager）——Team Cherry 写的场景配置组件，每个场景一个

源码里同一个文件中两者会同时出现，引擎调用写全限定名，HK 组件直接用 sm 字段。GameManager 的 sm 属性指向的是 HK SceneManager。

5.2 HK SceneManager：场景的配置档案

它是一个 [Serializable] MonoBehaviour，字段几乎全是 Inspector 配置，可以按六个维度分组：

维度代表字段作用
身份sceneType、mapZone声明场景类型（GAMEPLAY/MENU…）和所属地图区域，是全局判断的依据
环境isWindy、isTremorZone、environmentType风、震动、脚步环境类型（灰尘/草/骨/金属/水），影响粒子与音效
色彩saturation、red/green/blueChannel、darknessLevel色彩校正曲线、饱和度、黑暗等级
光照defaultColor、defaultIntensity、heroLightColor环境光与主角光源颜色
音频atmosCue、musicCue、四个 Snapshot氛围/音乐 Cue 与混音快照
边界/映射borderPrefab、sceneBordersMask、manualMapTrigger场景边界生成与地图登记开关

Start 里的配置应用流程

场景激活后，HK SceneManager 的 Start 按固定顺序把配置推给各子系统，这段代码是理解"场景如何影响全局表现"的主线：

写入 RenderSettings"] B --> C["3. 主角光源 heroLight 颜色"] C --> D["4. 登记场景访问

// 音乐的感染替换：十字路变化后同一场景换用不同 MusicCue
MusicCue cue = this.musicCue;
if (gm.playerData.crossroadsInfected && infectedMusicCue != null)
{
    cue = infectedMusicCue;
}
gm.AudioManager.ApplyMusicCue(cue, musicDelayTime, musicTransitionTime, applySnapshot: false);

注意它不直接调用 PlayMakerFSM，而是通过 FSMUtility 定位场景里 Tag 为 "Vignette" 的黑暗控制 FSM 并写入黑暗等级——再次体现"配置组件通过工具类间接操作 FSM"的模式。

5.3 CameraLockArea：相机锁区

一个场景常被切成多个相机房间，每个房间由一个 CameraLockArea（Trigger Collider）描述四向边界。主角进出 Trigger 时驱动相机锁定与释放。

进入时：记录从哪条边进来

public void OnTriggerEnter2D(Collider2D otherCollider)
{
    if (!IsInApplicableGameState() || !otherCollider.CompareTag("Player")) return;
    heroPos = otherCollider.transform.position;
    // 用 ±1 容差判断主角靠近哪条边，设置 camTarget.enteredLeft/Right/Top/Bot
    if (heroPos.x > leftSideX - 1f && heroPos.x < leftSideX + 1f)
        camTarget.enteredLeft = true;
    // ...
    cameraCtrl.LockToArea(this);
}

为什么要记录进入方向？

相机从一个锁区移动到下一个时，需要知道主角是从哪条边进来的，才能决定相机是横向平移还是纵向平移，避免镜头斜向滑动。entered/exited 四组布尔标记就是相机过渡动画的方向输入，由 CameraTarget 承载。

停留与退出

  • OnTriggerStay2D 持续调用 LockToArea，防止多个锁区重叠时锁被别的区域抢走
  • OnTriggerExit2D 记录退出边并调用 ReleaseLock
  • OnDisable 兜底释放，避免组件被禁用后相机永久锁住

边界默认值的约定：ValidateBounds 里 -1 是"未指定"哨兵值，会被替换成默认值（14.6 / 8.3 或相机极限）。四个边界全为 0 才判定为配置错误。读这类代码要先识别哨兵值，否则会把 -1 当成真实坐标。

5.4 场景边界的动态生成

HK SceneManager 不把边界写死在场景里，而是监听 ForceCameraAspect.ViewportAspectChanged，在宽高比变化时按位掩码 sceneBordersMask 动态实例化 borderPrefab：

// 右边界：位置随场景宽度和宽高比偏移量调整
transform.SetPosition2D(gm.sceneWidth + x / 2f - num, gm.sceneHeight / 2f);
transform.localScale = new Vector2(x, gm.sceneHeight + x * 2f);

宽高比变化（超宽屏、窗口拉伸）时，边界位置和长度都要跟着变，否则不同比例下会出现漏边。这是为多分辨率适配做的设计，也解释了为什么边界用代码生成而不是摆放。

5.5 附加场景：条件加载与预加载

除了主场景，游戏还会按需 additive 加载小场景，由两个组件分工：

SceneAdditiveLoadConditional：数据驱动的条件加载器

它在 OnEnable 里跑一组测试——PlayerData 布尔测试、整数比较（六种 TestType）、PersistentBool 测试、门口触发校验——全部通过才加载主附加场景，否则加载备选场景或不加载：

switch (intTest.testType)
{
    case IntTest.TestType.Less: flag2 = playerDataInt < num; break;
    case IntTest.TestType.More: flag2 = playerDataInt > num; break;
    // Equal / NotEqual / LessOrEqual / MoreOrEqual
}

场景切换期间 loadInSequence=true，这些加载器先登记，由 SceneLoad 第 7 阶段（LoadBoss）统一 LoadAll 顺序执行，避免多个 additive 加载同时竞争。Boss 场景的附加内容主要走这条路径。

ScenePreloader：相邻场景的后台预加载

它在场景运行时就把相邻场景以 allowSceneActivation=false 预加载到 0.9，挂起等待；SceneLoad 开始时先 FinishPendingOperations 激活它们，管线结束时 Cleanup 卸载。这是用内存换取进门时的加载速度。

组件加载时机典型用途
SceneAdditiveLoadConditional切换序列中按条件加载Boss 附加场景、状态相关内容
ScenePreloader当前场景运行时提前加载相邻房间预取，缩短进门等待

5.6 子场景命名后缀

GameManager.GetBaseSceneName 会剥离一组子场景后缀（如 _b 等），把同一场景的拆分版本归并到基础名。这与 SaveDataUpgradeHandler 里的场景拆分逻辑（一个大场景被拆成两个）对应。读场景名时要意识到：磁盘上的场景名和逻辑上的场景名可能差一个后缀，存档与地图按基础名归并。

思考与练习

  1. 列出区分两个 SceneManager 的方法，并在 GameManager 中找出分别使用二者的代码位置。
  2. 追踪 CameraLockArea 从主角进入到相机完成锁定的调用链，说明 enteredLeft 这类标记最终被谁消费。
  3. 解释场景边界为什么要监听宽高比变化动态生成，固定摆放 在什么情况下会出问题。
  4. 对比 SceneAdditiveLoadConditional 与 ScenePreloader 的代价（内存/IO/时机），各举一个适合它们的场景。
