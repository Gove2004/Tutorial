第 15 章　UI 与地图系统

本章拆解 UIManager 如何统管菜单与游戏内界面，GameMap 如何用层级化物体和 PlayerData 数据驱动地图显示，以及库存界面的组织方式。

15.1 UIManager：UI 总控

UIManager 是一个 2151 行的大管理器，持有所有菜单屏幕、滑块、按钮、画布的引用，负责 UI 状态切换、菜单导航、暂停界面和设置。它和 GameManager 是协作关系：GameManager 管游戏状态，UIManager 管对应状态下显示什么界面。

15.2 UIState 与 SetState

UI 整体状态由 UIState 枚举描述，SetState 是切换入口：

public void SetState(UIState newState)
{
    if (newState != uiState)
    {
        if (uiState == UIState.PAUSED && newState == UIState.PLAYING)
            UIClosePauseMenu();
        else if (uiState == UIState.PLAYING && newState == UIState.PAUSED)
            UIGoToPauseMenu();
        else
            switch (newState)
            {
                case UIState.INACTIVE: DisableScreens(); break;
                case UIState.MAIN_MENU_HOME:
                    if (Platform.Current.EngagementState == EngagementStates.Engaged)
                        UIGoToMainMenu();
                    else
                        UIGoToEngageMenu();
                    break;
                case UIState.LOADING:
                case UIState.PLAYING:
                case UIState.CUTSCENE:
                    DisableScreens(); break;
            }
        uiState = newState;
    }
}

注意 UI 状态与游戏状态联动：暂停/恢复有专门的成对处理，进入主菜单前还会检查平台的 EngagementState（主机平台的用户登录状态）。SetState 只决定"该显示哪个屏幕"，具体开关由 UIGoToXxx / DisableScreens 完成。

15.3 屏幕体系：CanvasGroup 与 MenuScreen

每个界面是一个 CanvasGroup 或 MenuScreen，UIManager 字段区持有全部引用：

public Canvas UICanvas;
public CanvasGroup modalDimmer;
public CanvasScaler canvasScaler;
public CanvasGroup mainMenuScreen;
public CanvasGroup saveProfileScreen;
public MenuScreen optionsMenuScreen;
public MenuScreen audioMenuScreen;
public MenuScreen videoMenuScreen;
public MenuAudioSlider masterSlider;
public SaveSlotButton slotOne;
// ...数十个屏幕与控件

用 CanvasGroup 而非单独的 Canvas 来组织界面，是因为它能整体控制一个界面组的 alpha、交互和射线阻挡，切换界面就是启用/禁用对应 CanvasGroup，轻量且便于做淡入淡出。

菜单导航：UIGoToXxx 模式

方法清单里有大量命名统一的导航方法：

public void UIGoToMainMenu() { ... }
public void UIGoToAudioMenu() { ... }
public void UIGoToVideoMenu(bool rollbackRes = false) { ... }
public void UIGoToPauseMenu() { ... }
public void UIClosePauseMenu() { ... }
public void UIShowQuitGamePrompt() { ... }

每个方法负责"进入/离开某界面"的具体操作（开关 CanvasGroup、设置默认选中项、播放音效）。这种显式方法比通用跳转表更直观，但方法数量多，是菜单层级复杂的直接体现。

15.4 Canvas 与分辨率适配

if (UICanvas.worldCamera == null)
    UICanvas.worldCamera = GameCameras.instance.mainCamera;
// CanvasScaler 负责不同分辨率/宽高比下的缩放
// 主机平台还有 overscan（过扫描）、brightness 等菜单调整

UI 是屏幕空间画布，由 CanvasScaler 按参考分辨率缩放，保证不同屏幕尺寸下布局一致；worldCamera 指向 GameCameras 的主相机。HollowKnightInputModule 是自定义输入模块，处理手柄/键盘的菜单导航。

15.5 GameMap：层级化、数据驱动的地图

GameMap（1343 行）管理世界地图和区域地图。地图不是运行时绘制的，而是预先搭好的层级 GameObject：区域 → 房间 → 图钉，运行时按 PlayerData 决定显示哪些。

flowchart TB M["GameMap"] --> A["各区域 GameObject
areaCrossroads / areaGreenpath ..."] A --> R["房间 GameObject（按场景名）"] R --> P["图钉 pin_blue_health / pin_dream_tree ..."] PD["PlayerData"] -->|"scenesMapped / hasQuill / hasPinXxx"| M

SetupMap：按数据决定可见性

public void SetupMap(bool pinsOnly = false)
{
    foreach (区域 in transform)
        foreach (房间 in 区域)
        {
            // 没买该房间地图、且不是全图模式：不显示
            if (!pd.scenesMapped.Contains(房间.name) && !pd.mapAllRooms)
                continue;
            if (pd.hasQuill && !pinsOnly)
                房间.SetActive(true);          // 有羽毛笔才显示房间布局
            foreach (图钉 in 房间)
            {
                // 幼虫图钉：遇到过且买了对应图钉才显示
                if (图钉.name == "pin_blue_health"
                    && pd.scenesEncounteredCocoon.Contains(房间.name)
                    && pd.hasPinCocoon)
                    图钉.SetActive(true);
                // 梦之树图钉类似处理
            }
        }
}

地图显示的三层数据条件

  • 房间是否已购买地图（scenesMapped）
  • 是否有羽毛笔（hasQuill）决定能否画出房间布局
  • 各类图钉是否已遇到对应对象、是否购买了图钉（hasPinXxx）

所有可见性都查 PlayerData，地图物体本身是静态预制的，逻辑只负责开关。这是数据驱动 UI 的典型范式。

世界地图：平移边界与区域开关

public void WorldMap()
{
    string zone = gm.GetCurrentMapZone();
    shadeMarker.SetActive(true);
    dreamGateMarker.SetActive(true);
    dreamerPins.SetActive(true);
    SetupMapMarkers();
    panMinX = -1.44f; panMaxX = 4.55f;   // 地图平移范围
    if (pd.mapAbyss) areaAncientBasin.SetActive(true);
    // 各区域按探索进度启用
}

平移边界（panMin/Max）限制地图拖动范围，阴影标记、梦门、梦境者图钉等特殊标记按进度显示。SetCompassPoint 计算罗盘方向，GetDoorValues 处理房间间的门位对齐。

15.6 库存界面：FSM 编排 + 专用组件

背包/库存界面没有单一的大控制器，而是由 PlayMaker FSM 编排页面切换，配合各专用小组件：

组件职责
CharmItem / CharmIconList护符槽位与图标，CharmItem 记录护符编号
InvCharmBackboard / SelectCharmBackboard护符背板与装备选择
JournalList / JournalEntryStats猎人日志列表与条目统计
MapMarkerMenu / MapMarkerButton地图标记（自定义图钉）菜单
 
public class CharmItem : MonoBehaviour
{
    public int listNumber;
    public int GetListNumber() => listNumber;
    public void SetListNumber(int n) => listNumber = n;
}

这些组件都很薄，只承载本控件的数据和简单逻辑，页面流转和与 PlayerData 的交互由 FSM 完成——延续了整个工程"薄 C# 组件 + FSM 编排"的双轨风格。

15.7 设计权衡

收益代价
CanvasGroup 切换轻量；地图静态预制 + 数据驱动，无需运行时绘制；组件薄、易复用；分辨率适配统一 UIManager 体量大、导航方法多；UI 流程分散在 FSM 与 C# 两处，追踪需跨体系；字符串场景名/图钉名无编译期检查

思考与练习

  2. 为什么用 CanvasGroup 而非多个 Canvas 组织界面？它对界面切换和淡入淡出有什么好处。
  3. 梳理 GameMap 显示一个房间及其图钉需要满足哪些 PlayerData 条件。
  4. 解释地图为什么做成静态预制物体 + 数据开关，而不是运行时绘制，权衡是什么。
  5. 分析库存界面"FSM 编排 + 薄组件"的组织方式，它与工程整体双轨架构如何呼应。
