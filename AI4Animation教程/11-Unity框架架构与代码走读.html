11　Unity 框架架构与代码走读

本章基于仓库当前 master 分支的真实目录结构，讲解 Unity 版的工程组织、编辑器工作流与运行时组件。 阅读时建议对照仓库代码，而不是把它当作抽象概念。

11.1 仓库目录的真实结构

主仓库的 AI4Animation/ 目录下，一个原生插件目录加七个按年份/会议命名的项目目录：

AI4Animation/
├── Plugins/                  # 原生 Eigen 插件（x86 / x86_64）
│   ├── Libraries/            # 编译好的原生 dll
│   └── Source/Eigen/         # C# 包装层
├── SIGGRAPH_2017/            # PFNN（Original + Adam 两个 Demo）
├── SIGGRAPH_2018/            # MANN 四足
├── SIGGRAPH_Asia_2019/       # NSM 场景交互
├── SIGGRAPH_2020/            # 局部运动相位
├── SIGGRAPH_2022/            # DeepPhase
├── SIGGRAPH_2024/            # 类别码本匹配
└── （当前 master 未包含 2021 NAL 的工程目录，仅在 README 中提供论文入口）
需要注意的事实

当前 master 分支中没有 SIGGRAPH_2021 工程目录。引用或复现 NAL 时，应以 README 链接的论文为准， 不要假设仓库里有对应 Unity 工程。各年份项目是独立的 Unity 工程，并非一个共用工程内的不同场景。

11.2 2017：单体脚本时代

最早的 PFNN 工程结构简单直接。Unity 工程的 Assets/ 下核心逻辑集中在两个 C# 脚本：

  • BioAnimation_Original.cs：论文原始实现，包含数据处理、网络推理、轨迹混合、IK 与场景绘制的全部逻辑
  • BioAnimation_Adam.cs：社区改进版，对应不同的优化器与参数设置

这种"一个大脚本包办一切"的写法便于论文复现，但模块边界模糊、难以扩展。后续年份的项目逐步把它拆分成 实体、组件与系统式的结构。

11.3 原生矩阵运算：Eigen 插件

Plugins/ 目录提供编译好的 Eigen（C++ 线性代数库）原生二进制，分 x86 与 x86_64 两套， Source/Eigen/ 是对应的 C# 包装层。Unity 通过 P/Invoke 调用原生库完成矩阵运算， 避免在纯 C# 中实现高性能线性代数。

工程含义

这也解释了为什么早期仓库强绑定 Windows 平台与特定 CPU 架构——原生 dll 是平台相关的。迁移到其他平台时， 需要重新编译原生插件，或改用纯托管实现。

11.4 编辑器工作流：菜单与 Inspector

从 2020 项目的 ReadMe 可以确认，数据处理通过 Unity 顶部 AI4Animation 菜单下的三类工具完成：

菜单分组工具职责
ImporterBVH Importer批量导入原始 BVH，生成 Unity 内的运动资产
ToolsMotionProcessor按管线（如 Quadruped Pipeline）自动处理原始动捕，含相位/接触/特征
ExporterMotion Exporter导出训练数据，可配置 Frame Shifts、Frame Buffer、Write Mirror

场景侧由一个挂载 MotionEditor 组件的空 GameObject 承载，目标帧率等参数在 Inspector 的 Editor Settings 中配置（例如 30 Hz）。

11.5 训练与权重的对接方式

2020 项目的训练仍在 Unity 外部完成，流程在 ReadMe 中有明确记录：

1

用 Motion Exporter 导出训练数据，写入工程内 DeepLearning/ 目录

2

把数据放入 DeepLearning/Models/ExpertModel/ 的数据集目录，运行外部 main.py 开始训练

3

训练产出二进制权重，把训练目录路径填入角色 ExpertModel 组件的 Inspector 字段，点击 Play 即可运行

预训练权重统一放在 DeepLearning/Weights。到 2024 项目，外部训练已切换为 PyTorch，Unity 侧通过 ONNX 加载模型——工程内可以看到 ONNXTraining 示例与对应的 C# 脚本。

11.6 ECS 风格的运行时架构

11.8 常见工程陷阱

踩坑清单
  • 架构不匹配：原生 dll 分 x86/x64，Unity 工程的目标架构必须与插件一致，否则运行时找不到入口
  • 帧率不一致：处理数据时的目标帧率（如 30 Hz）与特征窗口假设必须一致，混用时窗口长度会错位
  • 镜像开关：导出时 Write Mirror 决定数据是否翻倍，训练与推理的特征布局要对应
  • 路径硬编码：ExpertModel 依赖 Inspector 中的目录路径，换机器或移动工程后需要重新指定

本章小结

  • Unity 版由原生 Eigen 插件与七个独立年份工程组成，当前 master 不含 2021 工程目录
  • 2017 为单体脚本，后续演进为 ECS 风格的实体/组件/更新循环；矩阵运算依赖平台相关的原生 dll
  • 编辑器通过 Importer/Tools/Exporter 三类菜单工作，外部 main.py 训练后把路径填回 ExpertModel
  • 2024 工程以 PyTorch + ONNX 为核心，Examples 覆盖 IK、KDTree、MeshCollider、ONNX 等模块
