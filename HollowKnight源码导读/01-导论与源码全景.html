第 1 章　导论与源码全景

在打开任何一个源文件之前，先弄清楚"手里这份东西到底是什么"。这决定了你应该用什么预期去读它——哪些东西是开发者的真实意图，哪些只是反编译工具的产物，哪些地方信息已经永久丢失。

1.1 这份源码的来源

Unity 游戏编译后，C# 代码会被编译成 .NET 程序集（DLL），放在游戏数据目录下。《空洞骑士》的对应位置是：

hollow_knight_Data/Managed/Assembly-CSharp.dll

其中 Assembly-CSharp.dll 装着游戏自有代码，PlayMaker.dll、UnityEngine.*.dll 等是引擎与第三方库。反编译工具（ILSpy、dnSpy 等）把这些 DLL 的 IL（中间语言）重新翻译成 C# 源码，就得到了本教程的教材。工程文件 Solution.sln 里的引用路径留下了反编译者机器上的痕迹：

<HintPath>D:\SteamLibrary\steamapps\common\Hollow Knight\hollow_knight_Data\Managed\UnityEngine.CoreModule.dll</HintPath>

版本锚点：1.5.12459

这个数字在源码里反复出现：GameManager.saveFormatVersion、DesktopPlatform 写入的版本化文件名 user1_1.5.12459.dat、存档升级逻辑记录的系统版本号。它对应《空洞骑士》Godmaster（神居）版本线的发布格式。读源码时以这个版本为准，更早版本（1.0–1.4）的类结构和存档格式与本教材存在差异。

1.2 反编译代码的六个典型特征

下面这些特征会贯穿全书，提前认识它们可以避免大量误读。

特征一：注释和原始局部变量名永久丢失

编译后的 IL 不保留注释，也不保留未被反射/序列化使用的局部变量名。反编译器只能按类型自动命名，所以你会大量看到这样的局部变量：

  • num、num2、num3……——整型或浮点局部变量
  • flag、flag2……——布尔局部变量
  • text、text2……——字符串局部变量
  • obj、obj2……——对象引用

注意区分：类的字段和 public 方法名是保留的（Unity 序列化和反射依赖它们），所以 HeroController.dashSpeed 这样的字段名是开发者起的真名，而方法体里的 int num = 0; 是工具生成的。读代码时字段名承载的信息密度远高于局部变量名。

特征二：游戏自有代码位于全局命名空间

游戏的绝大多数类（GameManager、HeroController、HealthManager……）没有命名空间，直接处于全局命名空间下；而枚举被收在 GlobalEnums 命名空间，第三方库各有自己的命名空间：

内容命名空间
游戏自有类（约 800 个根目录文件）全局（无 namespace）
32 个枚举文件GlobalEnums
PlayMaker 自定义动作HutongGames.PlayMaker.Actions
输入库InControl

另外你会看到 namespace GlobalEnums; 这种文件作用域命名空间写法，这是 C# 10 语法，是反编译工具的输出风格，不是当年开发者的原始写法（游戏开发时主流是 C# 6）。

特征三：迭代器协程被高质量还原

C# 的 yield return 协程在 IL 里会被编译成名为 <方法名>d__N 的状态机类。本教材使用的反编译器把它们成功还原回了 IEnumerator 迭代方法，所以你读不到尖括号类名，看到的是接近手写的协程代码，例如 GameManager 里的 BeginSceneTransitionRoutine。这是这份源码质量较高的一个标志，但要知道底层运行时它仍然是一个状态机对象。

特征四：显式的 base. 与 Object. 前缀

反编译器倾向于把所有隐式调用写全，于是出现大量 base.transform、base.gameObject、Object.DontDestroyOnLoad、Object.FindObjectOfType。这里的 Object 是 UnityEngine.Object，不是 C# 的 System.Object，阅读时自动忽略这些前缀即可。

特征五：发布版调试代码被主动剥离

开发版里的作弊菜单、调试钩子在发布构建中被条件编译或直接清空。CheatManager.cs 是最直观的标本：

public static bool IsCheatsEnabled => false;   // 硬编码关闭

public void DrawGUI()
{
    // 方法体被掏空，250 行的类只剩骨架
}

同类现象还有 GameManager.RecordGameComplete() 的空方法体。看到空方法不要以为这个机制不存在——它在开发版里有完整实现，只是发布版移除了。

特征六：属性与字段的边界被模糊

反编译器有时把编译器自动生成的属性后备字段（backing field）直接展开，有时保留属性。你会同时看到 public static GameManager instance { get; ... } 这样的完整属性和大量裸 public 字段。Unity 序列化只认字段，所以需要在 Inspector 里配置的东西一律是字段，这也是判断字段用途的线索。

1.3 阅读这份源码的正确心态

先读结构，再读实现。面对一个 140KB 的类（HeroController 有 4000 多行），不要从第一行开始硬啃。先看字段、再看 public 方法清单、最后挑一个具体调用链深入。本教程每一章都按这个顺序组织。

不要期待解释性文字。没有注释、没有设计文档，所有"为什么"都要靠调用关系和数据流向反推。当你发现某个布尔字段在十几个地方被读写，把这些位置串起来，它的真实语义才会浮现。

信任字段名，警惕局部变量名。cState.dashing 是可信的语义；方法体里的 num 是什么，需要结合它参与的表达式判断。

1.4 全书的分析框架

本教程对每个子系统都用同一套四问来拆解，你也可以把它用在任何一个没覆盖到的类上：

1
它持有什么数据？——字段和它们的序列化方式（Inspector 配置 / 运行时状态 / 存档字段）。
2
它的生命周期由谁驱动？——Awake/Start/Update，还是协程、事件、PlayMaker FSM。
3
它和谁通信？——直接引用、静态单例、FSM 事件、C# event/delegate。
4
数据从哪里来、到哪里去？——沿着一条真实操作（进门、受击、存档）走完整条链路。

思考与练习

  1. 打开 CheatManager.cs，列出三处能证明"发布版功能被剥离"的证据，并思考为什么反编译器还能看到类的骨架。
  2. 在 GameManager.cs 中找出 5 个 num 或 flag 命名的局部变量，根据它们参与的表达式给它们各起一个有意义的名字。
  3. 解释为什么反编译后类的字段名得以保留、而方法内的局部变量名丢失（提示：Unity 序列化与反射机制）。
  4. 用自己的话说明：为什么不能把反编译源码等同于开发者的原始工程？至少列出三点差异。
