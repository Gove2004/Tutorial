第九章：Web 性能优化

性能是用户体验的核心维度。研究表明，页面加载时间每增加 1 秒，转化率下降 7%，跳出率增加 16%。本章将系统讲解现代 Web 性能优化的核心技术——从 Google 定义的 Core Web Vitals 指标，到 Lazy Loading、Code Splitting、Service Worker 缓存策略等实战手段。

核心概念：Web 性能指标体系

现代 Web 性能优化围绕三个维度展开：加载速度（用户多久看到内容）、交互性（用户多久能交互）、视觉稳定性（页面在加载过程中是否跳动）。Google 将这些维度量化为 Core Web Vitals 指标。

9.1 Core Web Vitals：LCP、CLS、INP

Core Web Vitals 是 Google 定义的一组用户中心性能指标，直接影响搜索引擎排名和用户体验评估。

指标全称衡量什么优秀值合格值需改进
LCPLargest Contentful Paint最大内容块渲染时间≤ 2.5s≤ 4.0s> 4.0s
INPInteraction to Next Paint用户交互到下次绘制的延迟≤ 200ms≤ 500ms> 500ms
CLSCumulative Layout Shift页面加载过程中的布局偏移总量≤ 0.1≤ 0.25> 0.25

9.1.1 LCP（最大内容块渲染时间）

LCP 衡量视口内最大内容元素（通常是图片、视频或大块文本）渲染完成的时间。它是用户感知页面加载速度的核心指标。

// 测量 LCP
const lcpObserver = new PerformanceObserver((list) => {
    const entries = list.getEntries();
    const lastEntry = entries[entries.length - 1];
    console.log('LCP:', lastEntry.startTime, 'ms');
    console.log('LCP 元素:', lastEntry.element);
});
lcpObserver.observe({ type: 'largest-contentful-paint', buffered: true });

// 优化 LCP 的策略
// 1. 预加载关键资源


// 2. 压缩图片（WebP/AVIF 格式）
// 3. 使用 CDN 加速静态资源
// 4. 服务端渲染 (SSR) 或静态站点生成 (SSG)
// 5. 避免渲染阻塞的 JavaScript
// 6. 关键 CSS 内联，非关键 CSS 异步加载

9.1.2 CLS（累计布局偏移）

CLS 衡量页面在加载过程中元素的意外位移总和。布局偏移会让用户点击错目标、阅读迷失，是最令人沮丧的体验问题之一。

// 测量 CLS
const clsObserver = new PerformanceObserver((list) => {
    for (const entry of list.getEntries()) {
        console.log('CLS score:', entry.value);
        console.log('Sources:', entry.sources);
        // entry.sources 列出导致本次偏移的具体元素
    }
});
clsObserver.observe({ type: 'layout-shift', buffered: true });

9.1.3 INP（交互到下次绘制）

INP 取代了之前的 FID（First Input Delay），衡量用户在页面加载后所有交互的响应时间。它不仅关注第一次交互，还关注整页生命周期内的所有交互。

// 测量 INP
const inpObserver = new PerformanceObserver((list) => {
    const entries = list.getEntries();
    // INP 是所有交互延迟的第 98 百分位数
    const inpValue = entries.reduce((max, entry) =>
        Math.max(max, entry.duration), 0);
    console.log('INP:', inpValue, 'ms');
});
inpObserver.observe({ type: 'event', buffered: true,
    entryTypes: ['event'] });

// 优化 INP 的策略
// 1. 减少主线程阻塞
// 2. 使用 Web Worker 处理计算密集型任务
// 3. 避免长任务（>50ms）
// 4. 使用 requestIdleCallback 安排低优先级任务
// 5. 优化事件处理器，避免同步 DOM 操作
📊 性能数据：根据 Web Almanac 2024 报告，全球桌面端 LCP 中位数为 3.8 秒，移动端为 6.2 秒。这意味着超过一半的网站 LCP 未达标（≤ 2.5s）。CLS 中位数为 0.12，勉强合格。优化空间巨大。

9.2 Lazy Loading：按需加载

Lazy Loading 的核心思想是：只在需要时才加载资源。这包括图片懒加载、组件懒加载、路由懒加载等多个层面。

9.2.1 图片懒加载

<!-- 原生懒加载（无需 JS） -->
<img src="photo.jpg" loading="lazy" alt="风景照片" width="800" height="600">

<!-- IntersectionObserver 方式（更灵活） -->
<img data-src="photo.jpg" alt="风景照片" class="lazy">

<script>
const lazyImages = document.querySelectorAll('img.lazy');
const imageObserver = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
        if (entry.isIntersecting) {
            const img = entry.target;
            img.src = img.dataset.src;
            img.classList.remove('lazy');
            imageObserver.unobserve(img);  // 只加载一次
        }
    });
}, {
    rootMargin: '200px 0px'  // 视口外 200px 就开始预加载
});

lazyImages.forEach(img => imageObserver.observe(img));
</script>

9.3 Code Splitting：代码分割

Code Splitting 将单个巨大的 JavaScript bundle 拆分为多个较小的 chunk，按需加载。这是现代前端工程化的核心技术。

9.3.1 分割策略

// 1. 路由级分割 (Route-level)
// 每个页面/路由对应一个 chunk
const routes = [
    { path: '/', component: Home },           // home.js
    { path: '/about', component: About },     // about.js
    { path: '/dashboard', component: Dashboard }, // dashboard.js
];

// 2. 组件级分割 (Component-level)
// 重型组件（图表、编辑器）单独打包
const Chart = lazy(() => import('./Chart'));
const Editor = lazy(() => import('./Editor'));

// 3. 第三方库分割 (Vendor chunk)
// 将 React、Lodash 等公共依赖提取为独立 chunk
// webpack.config.js:
module.exports = {
    optimization: {
        splitChunks: {
            chunks: 'all',
            cacheGroups: {
                vendor: {
                    test: /[\\/]node_modules[\\/]/,
                    name: 'vendors',
                    chunks: 'all',
                },
            },
        },
    },
};

// 4. 预加载 vs 预取
// preload: 在当前页面需要时使用（高优先级）
<link rel="preload" href="/dashboard.js" as="script">

// prefetch: 未来可能需要时使用（低优先级，空闲时下载）
<link rel="prefetch" href="/admin.js" as="script">

9.3.2 分割效果对比

# 优化前：单个 bundle
dist/bundle.js    2.5 MB  # 首屏必须加载全部内容

# 优化后：多个 chunk
dist/home.js      150 KB  # 首页
dist/about.js      45 KB  # About 页
dist/vendors.js   380 KB  # 公共依赖（可长期缓存）
dist/dashboard.js 220 KB  # 仪表盘（路由懒加载）

# 效果:
# - 首页首屏 JS 从 2.5MB 降至 150KB + 380KB (vendors 可缓存)
# - 实际首次加载: 150KB (home) + 380KB (vendors, 缓存命中则为 0)
# - 第三方用户首次加载: 150KB (home) + 0 (vendors 缓存命中)

9.4 Service Worker：离线优先与缓存策略

Service Worker 是一个运行在后台的独立线程，可以拦截和代理网络请求。它是 PWA（Progressive Web App）的核心技术。

9.4.1 缓存策略模式

策略工作流程适用场景优缺点
Cache First先查缓存，命中则返回；否则请求网络并缓存静态资源（CSS/JS/图片）快但有过期风险
Network First先请求网络，成功则缓存并返回；失败则返回缓存动态数据（API 响应）数据新鲜但依赖网络
Stale While Revalidate先返回缓存，同时后台更新缓存内容型页面平衡速度与新鲜度
Network Only只通过网络获取实时数据（天气、股票）永远最新但无离线能力
Cache Only只从缓存读取离线应用完全离线但可能过期
 
// Service Worker 缓存策略实现
self.addEventListener('fetch', (event) => {
    const url = new URL(event.request.url);

    // 静态资源：Cache First
    if (url.pathname.startsWith('/static/')) {
        event.respondWith(
            caches.match(event.request)
                .then(cached => {
                    if (cached) return cached;  // 命中缓存
                    const fetchPromise = fetch(event.request)
                        .then(response => {
                            caches.open('v1').then(cache => cache.put(event.request, response));
                            return response;
                        });
                    return fetchPromise;
                })
        );
    }

    // API 请求：Network First
    if (url.pathname.startsWith('/api/')) {
        event.respondWith(
            fetch(event.request)
                .then(response => {
                    const clone = response.clone();
                    caches.open('api-v1').then(cache => cache.put(event.request, clone));
                    return response;
                })
                .catch(() => caches.match(event.request));  // 网络失败时用缓存
        );
    }
});

9.4.2 Service Worker 性能收益

指标无 SWSW + Cache First改善
LCP (首次访问)3.5s2.8s-20%
LCP (二次访问)N/A0.3s-89% (缓存命中)
网络请求数8512 (仅 API)-86%
流量消耗2.5MB150KB-94%
弱网体验不可用可用 (离线缓存)功能可用
💡 关键洞察：Service Worker 的最大价值不在首次访问（只能带来 10-20% 的改善），而在回访用户的体验。二次访问时，静态资源全部命中缓存，LCP 可以从 3.5s 降到 0.3s，改善近 90%。

9.5 Performance API：精确性能监控

Performance API 提供了浏览器内置的性能测量工具，让我们可以精确量化页面的各项指标。

9.5.1 Navigation Timing API

// 获取详细的导航性能数据
const nav = performance.getEntriesByType('navigation')[0];

console.log({
    // 时间线分解 (单位: ms)
    dnsLookup:     nav.domainLookupEnd - nav.domainLookupStart,
    tcpConnect:    nav.connectEnd - nav.connectStart,
    tlsHandshake:  nav.secureConnectionStart ? nav.connectEnd - nav.secureConnectionStart : 0,
    ttfb:          nav.responseStart - nav.requestStart,        // Time to First Byte
    domParse:      nav.domContentLoadedEventEnd - nav.domInteractive,
    domReady:      nav.domComplete - nav.domContentLoadedEventEnd,
    loadComplete:  nav.loadEventEnd - nav.fetchStart,
});

// 关键指标阈值:
// TTFB < 200ms: 优秀 (服务器响应快)
// TTFB < 800ms: 合格
// TTFB > 1.5s: 需要优化 (可能是数据库慢查询、CDN 配置问题)

9.5.2 Resource Timing API

// 分析每个资源的加载性能
const resources = performance.getEntriesByType('resource');
resources.forEach(res => {
    console.log(`${res.name}:`);
    console.log(`  大小: ${res.transferSize / 1024} KB`);
    console.log(`  耗时: ${res.duration.toFixed(2)}ms`);
    console.log(`  缓存: ${res.transferSize === 0 ? 'Memory Cache' : 'Network'}`);
    console.log(`  类型: ${res.initiatorType}`);
});

// 找出最慢的资源
const slowest = resources
    .sort((a, b) => b.duration - a.duration)
    .slice(0, 5);
console.log('Top 5 最慢资源:', slowest.map(r => r.name));

9.5.3 自定义性能标记

// 标记关键业务操作
performance.mark('user-login-start');
await loginUser(credentials);
performance.mark('user-login-end');
performance.measure('login-duration', 'user-login-start', 'user-login-end');

// 上报性能数据
const measures = performance.getEntriesByType('measure');
measures.forEach(m => {
    // 上报到性能监控平台
    sendToAnalytics({
        metric: m.name,
        value: m.duration,
        category: 'performance',
    });
});

9.7 本章小结

本章系统讲解了 Web 性能优化的核心技术：

  • Core Web Vitals：LCP（≤2.5s）、CLS（≤0.1）、INP（≤200ms）是三大核心指标。
  • Lazy Loading：IntersectionObserver + loading="lazy" 按需加载，可减少 70% 传输量。
  • Code Splitting：路由级 + 组件级分割，将 2.5MB bundle 拆分为按需加载的小 chunk。
  • Service Worker：缓存策略（Cache First / Network First）让回访用户 LCP 降低 89%。
  • Performance API：Navigation Timing + Resource Timing + 自定义标记实现精确监控。
