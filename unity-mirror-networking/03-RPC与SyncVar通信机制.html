第 3 章：RPC 与 SyncVar — 服务器-客户端通信机制

如果说 NetworkIdentity 是对象的身份证，NetworkServer/Client 是管理器， 那么 RPC 和 SyncVar 就是网络中的语言。 本章将系统讲解 Mirror 提供的所有通信方式，以及它们各自的设计意图和适用场景。

Mirror 96 API 更新
本章已全面适配 Mirror 96.x。主要变化包括： [Command]/[ClientRpc] 方法前缀（Cmd/Rpc）从必需变为可选； SyncVar hook 签名统一为双参数 (T oldValue, T newValue)； [ServerCallback]/[ClientCallback] 语义修正（与 [Server]/[Client] 相同，仅日志行为不同）； 新增 requiresAuthority 和 includeOwner 选项； hasAuthority 已更名为 isOwned。

3.1 RPC 的本质：远程过程调用

RPC（Remote Procedure Call）的核心思想很简单：在 A 机器上调用方法，但实际执行在 B 机器上。

在单机开发中，你直接调用方法：

// 单机：直接调用
enemy.TakeDamage(50);  // 同一进程内，立即执行

在网络中，你不能这样做——敌人可能在另一台机器上。Mirror 的 RPC 机制帮你把这段调用 "打包"成网络消息，发送到目标机器再执行：

客户端                          服务器
  |                                |
  |--- CmdAttack() --------------->|  (序列化消息 + 发送)
  |                                |--- PerformAttack()  (反序列化 + 执行)
  |<<< RpcPlayEffect() ------------|  (结果广播)

3.2 [Command]：客户端 → 服务器

[Command] 是最常用的 RPC 类型。它允许客户端向服务器发送请求。

public class PlayerController : NetworkBehaviour
{
    // [Command] 方法前缀 Cmd 在 Mirror 96 中是可选的（旧版为必需）
    // 但保留前缀仍然是推荐约定——便于在代码中区分 RPC 和普通方法
    [Command]
    public void CmdAttack()
    {
        // 这段代码在服务器上执行
        Debug.Log($"玩家 {connectionToClient} 发起了攻击");

        // 执行攻击逻辑
        PerformAttack();

        // 通知所有客户端攻击结果
        RpcPlayAttackEffect();
    }

    // Mirror 96 也允许不加前缀（不推荐，但合法）
    [Command]
    public void AttackNoPrefix()
    {
        // 同样合法，但代码可读性下降
    }
}
Mirror 96 命名约定变化
在 Mirror 96 之前，[Command] 方法必须以 Cmd 开头， [ClientRpc] 方法必须以 Rpc 开头，否则编译报错。

Mirror 96 将此约束改为可选——Mirror 通过特性（Attribute）而非方法名前缀来识别 RPC。 但作为代码规范，强烈建议保留前缀，因为：
  • 代码可读性：CmdAttack 一眼就能看出是客户端→服务器的调用
  • 团队协作：前缀是通用的网络编程约定
  • 搜索友好：grep "Cmd" 可以快速找到所有 Command 方法
[Command] 的执行流程：
1. 客户端调用 CmdAttack()
2. Mirror 拦截调用，序列化为网络消息
3. 通过 Transport 发送到服务器
4. 服务器反序列化，在对应的 NetworkBehaviour 实例上执行方法体
5. 服务器端的 isServer 为 true，逻辑在服务端运行

3.2.1 requiresAuthority 选项

默认情况下，[Command] 要求调用方客户端拥有此对象的控制权（isOwned == true）。 如果没有控制权，调用会被静默丢弃。但在某些场景下，你需要让没有控制权的客户端也能调用 Command—— 例如世界中的交互物体（按钮、宝箱）：

public class InteractableObject : NetworkBehaviour
{
    // requiresAuthority = false 允许任何客户端调用此 Command
    // 适用于：不归属于特定玩家的对象，如场景中的门、宝箱、开关
    [Command(requiresAuthority = false)]
    public void CmdInteract(uint interactorNetId)
    {
        // 即使调用方不拥有此对象，Command 也能执行
        // 注意：此时需要通过参数传入交互者的 netId 来识别是谁触发的
        if (NetworkServer.spawned.TryGetValue(interactorNetId, out var identity))
        {
            Debug.Log($"{identity.name} 与 {name} 交互");
            OpenChest();
        }
    }
}

3.2.2 Command 的 sender 参数

当使用 requiresAuthority = false 时，你可能需要知道是哪个客户端发送的 Command。 Mirror 96 支持在 Command 方法中添加一个可选的 NetworkConnectionToClient sender = null 参数， Mirror 会自动填充发送方连接：

[Command(requiresAuthority = false)]
public void CmdPickupItem(int itemId, NetworkConnectionToClient sender = null)
{
    // sender 由 Mirror 自动填充——指向发起此 Command 的客户端连接
    if (sender != null)
    {
        Debug.Log($"客户端 {sender.connectionId} 请求拾取物品 {itemId}");
        // 验证 + 执行逻辑
    }
}
参数位置规则：NetworkConnectionToClient sender = null 必须是方法的最后一个参数， 且必须有默认值 = null。Mirror 会在服务器端自动注入实际的连接对象。 这个参数对调用方是透明的——客户端调用时不传此参数。

3.2.3 Command 的参数限制

由于参数需要被序列化为网络消息，[Command] 方法的参数有严格限制：

类型支持说明
基本类型✅int, float, bool, string, byte 等
Vector3 / Quaternion✅Mirror 内置支持
Enum✅序列化为底层整型
NetworkIdentity✅序列化为 netId
GameObject（带 NetworkIdentity）✅序列化为 netId
自定义 struct（实现 NetworkMessage）✅需可序列化
class（非 NetworkBehaviour）❌无法可靠序列化
数组✅支持，但注意大小——大数组消耗带宽
返回值❌Command 是单向的，不能返回数值

3.2.4 [Server] 和 [ServerCallback]：方法执行端验证

除了 [Command]，Mirror 还提供了 [Server] 和 [ServerCallback] 特性。 它们的作用是确保方法只在服务器端执行——如果在客户端调用，直接跳过不执行。

Mirror 96 语义修正（重要）
旧版教程常将 [ServerCallback] 描述为"跳过网络层的本地调用"——这是完全错误的。

实际语义：
  • [Server]：如果当前不是服务器，不执行并输出一条警告日志
  • [ServerCallback]：如果当前不是服务器，不执行但不输出警告
两者行为完全相同，唯一区别是是否在 Console 中打印警告。 它们都不是 RPC——不会发送网络消息，只是本地的方法守卫（guard）。 
public class WeaponSystem : NetworkBehaviour
{
    // [Server]：非服务器调用时跳过 + 打印警告
    [Server]
    public void ServerReload()
    {
        // 只有服务器端才会执行到这里
        // 如果客户端调用了此方法，会跳过并打印警告
        ammo = maxAmmo;
    }

    // [ServerCallback]：非服务器调用时跳过 + 不打印警告
    // 适合在 Unity 回调方法（如 OnTriggerEnter）中使用
    // 因为这些回调在所有端都会触发，不需要看到满屏警告
    [ServerCallback]
    void OnTriggerEnter(Collider other)
    {
        // 只在服务器端执行碰撞处理
        if (other.CompareTag("Pickup"))
        {
            CollectPickup(other.gameObject);
        }
    }

    // 同理：
    // [Client]：非客户端调用时跳过 + 打印警告
    // [ClientCallback]：非客户端调用时跳过 + 不打印警告
    [ClientCallback]
    void Update()
    {
        // 只在客户端执行（服务器跳过，不打印警告）
        if (!isOwned) return;
        HandleInput();
    }
}
选择指南：[Command] vs [Server]
• [Command]：客户端通过网络请求服务器执行某操作。消息会发送到服务器，服务器能知道是谁发的。
• [Server] / [ServerCallback]：方法只在服务器本地执行。不发网络消息，通常用于 Unity 回调或服务器内部逻辑。

简单记忆：[Command] = 跨网络请求；[Server] = 本地守卫。

3.3 [ClientRpc]：服务器 → 所有客户端

当服务器需要通知所有客户端某个事件发生时，使用 [ClientRpc]：

public class PlayerController : NetworkBehaviour
{
    // [ClientRpc] 方法前缀 Rpc 在 Mirror 96 中是可选的
    [ClientRpc]
    public void RpcPlayShootEffect(Vector3 direction)
    {
        // 这段代码在每个客户端上执行
        // 通常只修改视觉/听觉表现，不改游戏逻辑
        Instantiate(shootPrefab, transform.position, Quaternion.identity);
        AudioSource.PlayClipAt(shootClip, transform.position);
    }

    // 服务器端调用
    public void OnShot(Vector3 direction)
    {
        // ... 服务器执行攻击逻辑 ...

        // 通知所有客户端播放射击特效
        RpcPlayShootEffect(direction);
    }
}

3.3.1 includeOwner 选项

默认情况下，[ClientRpc] 会发送给所有已连接的客户端，包括拥有此对象的客户端（Owner）。 如果你不需要 Owner 收到此 RPC（因为 Owner 可能已经在本地处理了），可以使用 includeOwner = false：

public class PlayerController : NetworkBehaviour
{
    [ClientRpc(includeOwner = false)]
    public void RpcShowDamageIndicator(int targetNetId, int damage)
    {
        // 只在其他客户端上执行，拥有此对象的客户端不会收到
        // 适合：Owner 已经在本地直接显示了伤害，不需要再通过 RPC 重复处理
        if (NetworkClient.spawned.TryGetValue(targetNetId, out var identity))
        {
            DamageUI.Show(identity.transform.position, damage);
        }
    }
}
includeOwner = false 的使用场景：
• Owner 已经在本地处理了视觉效果（如本地摄像机震动），不需要 RPC 重复
• 减少不必要的网络消息（Owner 的那条消息省了）
• 注意：在 Host 模式下，Owner 也是服务器，使用此选项时 RPC 不会在 Host 客户端执行

3.4 [TargetRpc]：服务器 → 指定客户端

当你只想通知某一个特定客户端时，使用 [TargetRpc]：

public class InventorySystem : NetworkBehaviour
{
    // [TargetRpc] 可以接受一个 NetworkConnection 参数来指定目标客户端
    // Mirror 96 中：第一个参数如果是 NetworkConnection 类型，则作为目标连接
    [TargetRpc]
    public void TargetUpdateInventoryUI(NetworkConnection target, ItemData[] items)
    {
        // 只在 target 指定的客户端上执行
        UpdateUI(items);
    }

    // 服务器端调用
    public void RefreshInventory(NetworkConnectionToClient conn)
    {
        ItemData[] myItems = GetItems();
        // 只发给 conn 这个特定客户端
        TargetUpdateInventoryUI(conn, myItems);
    }
}
TargetRpc 的 Connection 参数规则：
• 如果方法的第一个参数是 NetworkConnection 类型，它被用作目标连接，不会被序列化发送
• 如果第一个参数不是 NetworkConnection，Mirror 会默认发送给拥有此对象的客户端连接
• 调用时，NetworkConnection 参数由服务器端传入，其他参数会被序列化

3.6 SyncVar：状态同步

RPC 用于"通知"——告诉其他机器"发生了某件事"。SyncVar 用于"同步"——让某个变量的值在所有机器上一致。

public class HealthSystem : NetworkBehaviour
{
    // 服务器修改 health 后，新值自动同步到所有客户端
    // hook 指定一个回调方法，在值变化时被调用
    [SyncVar(hook = nameof(OnHealthChanged))]
    public int health = 100;

    // Mirror 96 中，hook 方法签名必须是双参数：(旧值, 新值)
    // 旧值 = 变更前的 SyncVar 值
    // 新值 = 变更后的 SyncVar 值
    void OnHealthChanged(int oldHealth, int newHealth)
    {
        UpdateHealthBar(newHealth);

        // 可以利用旧值做差值动画
        int delta = newHealth - oldHealth;
        if (delta < 0)
            ShowDamageIndicator(-delta);
    }

    // 服务器端：扣血
    public void TakeDamage(int amount)
    {
        if (!isServer) return;

        health -= amount;  // 修改 SyncVar → 自动同步
        // hook 方法在所有客户端（以及服务器自己）上自动被调用

        if (health <= 0)
            Die();
    }
}
Mirror 96 SyncVar Hook 签名变化
在 Mirror 96 中，SyncVar hook 方法必须是双参数签名：(T oldValue, T newValue)。

旧写法（已过时）： 
// ❌ 单参数 hook 在 Mirror 96 中不再被支持
[SyncVar(hook = "OnHealthChanged")]
public int health = 100;
void OnHealthChanged(int newHealth) { ... }  // 编译报错
正确写法： 
// ✅ 双参数 hook
[SyncVar(hook = nameof(OnHealthChanged))]
public int health = 100;
void OnHealthChanged(int oldHealth, int newHealth) { ... }
hook 还支持使用 nameof() 运算符引用方法名（比字符串更安全，支持重构）。

3.6.1 SyncVar 的工作原理

很多人误以为 SyncVar 是"变量值通过网络即时发送"。实际上它的机制更精细：

1

服务器修改 SyncVar 字段

Mirror 在内部标记该 SyncVar 为"脏"（dirty），并记录新值。 同时在服务器端也调用 hook 方法（旧值 → 新值）。

2

每帧打包变更

服务器在每个同步间隔（通常每帧或每几帧）将所有"脏"SyncVar 打包到一个状态快照中发送。 如果同一 SyncVar 在一帧内被修改多次，只发送最终值。

3

客户端应用变更

客户端收到后，将旧值保存，设置新值，然后调用 hook 方法（旧值 → 新值）。 hook 在值已经被设置之后才调用。

关键理解：SyncVar 的变化不是"即时发送"的。它们在服务器批量打包后发送。 这意味着 SyncVar 同步有一帧的延迟（在 60fps 下约 16ms）。 对于大多数场景这个延迟完全可以接受，但对于高精度同步需求需要考虑这一点。

另外，Mirror 96 会对 SyncVar 做去重——如果一帧内修改了同一个 SyncVar 多次，只发送最后一次的值， hook 也只调用一次。这比手动发 RPC 高效得多。

3.6.2 SyncVar Hook 的调用时机

理解 hook 在何时被调用至关重要：

调用场景调用位置oldValuenewValue
服务器修改 SyncVar服务器修改前的值修改后的新值
客户端收到同步消息客户端客户端之前持有的旧值服务器发来的新值
对象 Spawn 时（初始同步）客户端类型的默认值（如 0, null）服务器发来的初始值
Hook 在 Spawn 时的行为：当对象在客户端 Spawn 时，SyncVar 的初始值从服务器同步过来。 此时 hook 也会被调用，oldValue 是该类型的默认值（如 int 的 0、string 的 null）。 你可以利用这一点在 Spawn 时初始化 UI——不需要在 OnStartClient 中额外读取 SyncVar 值。

3.6.3 SyncVar 的限制

限制原因替代方案
不能是 static静态变量不属于实例，无法逐实例同步改用实例变量
不能是 readonlyMirror 需要通过反射修改字段值去掉 readonly
复杂对象序列化有限只能序列化基础类型和简单结构体用 SyncList 或自定义消息
不支持 List/Dictionary集合类型需要特殊处理用 SyncList（见第 5 章）
高频更新影响性能每个 SyncVar 变化都要序列化合并多个值或使用 NetworkTransform

3.7 RPC vs SyncVar：什么时候用哪个？

这是新手最常问的问题。判断标准很简单：

选择准则

用 RPC，如果：你想告诉其他机器"做一件事"（动作/事件驱动）。
例如："射击"、"跳跃"、"拾取物品"、"开始动画"。

用 SyncVar，如果：你想让其他机器"知道一个状态"（状态驱动）。
例如："当前血量"、"当前弹药"、"是否隐身"、"队伍分数"。

实际项目中，两者经常配合使用：

public class PlayerStats : NetworkBehaviour
{
    // SyncVar：同步"当前值"——hook 自动更新 UI
    [SyncVar(hook = nameof(OnHealthChanged))]
    public int currentHealth = 100;

    [SyncVar(hook = nameof(OnAmmoChanged))]
    public int currentAmmo = 30;

    // Command：客户端请求开火
    [Command]
    public void CmdRequestFire()
    {
        if (currentAmmo <= 0) return;

        // 服务器执行开火逻辑
        currentAmmo--;  // 修改 SyncVar → 自动同步 + 调用 hook

        // Rpc：通知客户端播放特效（事件型，不适合 SyncVar）
        RpcPlayFireEffect();
    }

    [ClientRpc]
    public void RpcPlayFireEffect()
    {
        // 所有客户端播放枪口火焰
        PlayMuzzleFlash();
    }

    // hook：值变化时自动更新 UI
    void OnHealthChanged(int oldHealth, int newHealth)
    {
        healthBar.SetHealth(newHealth);
    }

    void OnAmmoChanged(int oldAmmo, int newAmmo)
    {
        ammoText.text = $"弹药: {newAmmo}";
    }
}

3.8 带宽优化：减少 RPC 和 SyncVar 的开销

在网络游戏中，带宽是有限资源。每一个 RPC 调用和 SyncVar 变更都在消耗带宽。 以下是实用的优化策略：

3.8.1 合并多个值为一个 RPC

// ❌ 低效：多次 RPC 调用，每条都有头部开销
RpcSetPosition(x, y, z);
RpcSetRotation(rx, ry, rz, rw);
RpcSetScale(sx, sy, sz);

// ✅ 高效：一次 RPC 传递所有数据
RpcSetTransform(position, rotation, scale);

// 更好的方案：使用 NetworkTransform 组件自动处理变换同步
// 无需手写任何 RPC

3.8.2 条件同步：只在值变化时发送

public class PositionTracker : NetworkBehaviour
{
    Vector3 lastSyncedPosition;
    float syncThreshold = 0.1f;

    void Update()
    {
        if (!isOwned) return;

        float distance = (transform.position - lastSyncedPosition).sqrMagnitude;
        if (distance > syncThreshold * syncThreshold)
        {
            // 只有移动超过阈值才发送
            CmdReportPosition(transform.position);
            lastSyncedPosition = transform.position;
        }
    }

    [Command]
    void CmdReportPosition(Vector3 pos)
    {
        // 服务器验证后更新位置
        // NetworkTransform 会自动处理后续同步
        transform.position = pos;
    }
}

3.8.3 使用 SyncVar 而非手动 RPC 同步常量状态

如果一个值需要在服务器修改后自动同步给所有人，SyncVar 比手动发 RPC 更高效—— 因为 Mirror 会对 SyncVar 做批量处理和去重：

// ❌ 手动同步：每次修改都发一条 RPC
public void SetScore(int score)
{
    this.score = score;
    RpcUpdateScore(score);  // 即使一帧内改了 10 次也发 10 条
}

// ✅ SyncVar：Mirror 会自动合并同帧变更
[SyncVar]
public int score = 0;

public void AddScore(int amount)
{
    if (!isServer) return;
    score += amount;  // 一帧内加 10 次，只发 1 条更新消息
}

3.9 消息可靠性

Mirror 的 Transport 层决定了消息的可靠性。不同的 Transport 有不同的保证：

Transport可靠性适用场景
KCP Transport（默认）可靠 + 有序大多数游戏，平衡性能和可靠性
UnityTransport可配置（可靠/不可靠虚拟连接）需要 Unity 生态集成
Simple Web Transport可靠（WebSocket）浏览器端客户端

对于位置同步等高频数据，建议使用 NetworkTransform 组件—— 它内置了插值（Interpolation）和预测（Extrapolation），无需手动处理丢包。 对于必须保证送达的消息（如伤害、得分），SyncVar 和 RPC 会通过可靠通道传输。

Mirror 96 传输层变化：Mirror 96 的 Transport 是抽象类（非接口）， 方法名为 ServerSend / ClientSend， 事件为 OnServerConnected / OnClientData 等。 如果你自定义 Transport，需要继承 Transport 抽象类。

3.10 实战：一个完整的战斗系统示例

让我们把 RPC 和 SyncVar 组合起来，实现一个真实的战斗系统：

public class CombatSystem : NetworkBehaviour
{
    [SyncVar(hook = nameof(OnHealthChanged))]
    public int health = 100;

    [SyncVar(hook = nameof(OnStateChanged))]
    public CombatState state = CombatState.Idle;

    [SyncVar] public int comboCount;

    [SerializeField] float attackCooldown = 0.5f;
    [SerializeField] int attackDamage = 20;
    float lastAttackTime;

    public enum CombatState { Idle, Attacking, Blocking, Stunned }

    // 客户端请求攻击
    [Command]
    public void CmdAttack()
    {
        if (Time.time - lastAttackTime < attackCooldown) return;
        if (state != CombatState.Idle) return;

        state = CombatState.Attacking;  // SyncVar → 自动同步 + 调用 hook
        lastAttackTime = Time.time;

        // 服务器端查找附近的敌人并造成伤害
        Collider[] hits = Physics.OverlapSphere(transform.position, 2f);
        foreach (var hit in hits)
        {
            if (hit.TryGetComponent<CombatSystem>(out var target) && target != this)
            {
                target.TakeDamage(attackDamage, connectionToClient);
            }
        }

        // 通知所有客户端播放攻击动画
        RpcPlayAttackAnimation();

        // 攻击结束后恢复状态（Invoke 在服务器端运行）
        Invoke(nameof(ResetState), 0.3f);
    }

    // 服务器端调用：对目标造成伤害
    [Server]
    public void TakeDamage(int amount, NetworkConnectionToClient attacker = null)
    {
        // [Server] 确保只有服务器端执行
        // attacker 参数可选，用于记录伤害来源
        health -= amount;
        if (health <= 0)
        {
            Die();
            // 给攻击者加分
            if (attacker != null)
                ScoreManager.Instance.AddScore(attacker, 100);
        }
    }

    // 只给特定客户端显示伤害数字（视觉效果）
    [TargetRpc]
    public void TargetShowDamageNumber(NetworkConnection target, Vector3 position, int damage)
    {
        // 只在 target 指定的客户端上执行
        DamageNumberPool.Show(position, damage);
    }

    [ClientRpc]
    void RpcPlayAttackAnimation()
    {
        animator.SetTrigger("Attack");
        audioSource.PlayOneShot(attackClip);
    }

    // SyncVar hook：值变化时自动调用
    void OnHealthChanged(int oldHealth, int newHealth)
    {
        healthBar.SetHealth(newHealth);

        // 利用差值做伤害飘字动画
        if (newHealth < oldHealth)
        {
            int damage = oldHealth - newHealth;
            ShowLocalDamageIndicator(damage);
        }

        if (newHealth <= 0)
        {
            PlayDeathEffect();
        }
    }

    void OnStateChanged(CombatState oldState, CombatState newState)
    {
        // 根据状态切换动画
        animator.SetInteger("State", (int)newState);
    }

    [Server]
    void ResetState()
    {
        state = CombatState.Idle;
    }

    void Die()
    {
        // 服务器端死亡逻辑
        RpcOnDeath();
        NetworkServer.Destroy(gameObject);
    }

    [ClientRpc]
    void RpcOnDeath()
    {
        animator.SetTrigger("Die");
    }
}

3.11 调试 RPC 和 SyncVar

3.11.1 追踪 RPC 调用链

当 RPC 没有按预期触发时，常见原因和调试方法：

public class PlayerController : NetworkBehaviour
{
    void Update()
    {
        if (!isOwned) return;

        if (Input.GetKeyDown(KeyCode.Space))
        {
            // 调试 Command 前检查前置条件
            Debug.Log($"[Debug] isServer={isServer}, isClient={isClient}, " +
                      $"isOwned={isOwned}, netId={netId}");

            // 确保对象已 Spawn 且有有效连接
            if (connectionToServer == null)
            {
                Debug.LogError("connectionToServer 为 null！对象可能未正确 Spawn 或客户端未连接。");
                return;
            }

            CmdJump();
        }
    }

    [Command]
    void CmdJump()
    {
        // 在服务器端加日志确认收到
        Debug.Log($"[Server] 收到 CmdJump from netId={netId}");
        // 执行逻辑...
    }
}
Command 不执行的常见原因：
  • 客户端没有此对象的 isOwned（authority）—— 使用 requiresAuthority = false 或修正权限
  • 对象尚未 Spawn（netId == 0）—— 等待 OnStartClient 后再调用
  • connectionToServer 为 null —— 客户端尚未连接或对象不是网络对象
  • 调用了 base.Method() 而非实例方法 —— 确保 RPC 方法不是 static

3.11.2 观察 SyncVar 同步

SyncVar 的 hook 方法本身就是最好的调试入口。你也可以在 hook 中添加日志：

public class DebugSyncVar : NetworkBehaviour

    {
        Debug.Log($"[SyncVar] {name} 的 debugValue: {oldValue} → {newValue} " +
                  $"(isServer={isServer}, isClient={isClient})");

    }

3.12 本章小结

机制方向用途Mirror 96 变化
[Command] 客户端 → 服务器 客户端请求服务器执行操作 Cmd 前缀可选；新增 requiresAuthority 选项
[ClientRpc] 服务器 → 所有客户端 广播事件 Rpc 前缀可选；新增 includeOwner 选项
[TargetRpc] 服务器 → 指定客户端 定向通知 自动识别 NetworkConnection 参数
[Server] / [ServerCallback] 本地守卫（非 RPC） 确保方法只在服务器执行 语义修正：两者行为相同，仅日志不同
[SyncVar] 服务器 → 客户端 状态自动同步 Hook 签名统一为双参数 (T, T)

核心原则：动作用 RPC，状态用 SyncVar；客户端只发请求，服务器做决定。

下一章，我们将学习 Spawn 系统——网络对象如何在服务器和客户端之间正确生成和管理。

  3. 推理题：如果在 Awake() 中调用 CmdXXX()，会发生什么？ 为什么？应该在哪个生命周期方法中调用？
  4. Mirror 96 变化题：[ServerCallback] 的真正含义是什么？ 它和 [Command] 有什么本质区别？
参考答案：
1) ① CmdFire() Command → ② 服务器内部逻辑（Raycast 等） → ③ RpcPlayMuzzleFlash() ClientRpc → ④ TargetRpcShowBlood(hitConn) TargetRpc → ⑤ [SyncVar] int score（自动同步 + hook 更新 UI）

2) 两个错误：① SyncVar 不支持 List<GameObject>—— 应使用 SyncList 存储物品 ID；② Hook 方法签名错误——Mirror 96 要求双参数 (int oldHealth, int newHealth)，单参数会编译报错。

3) Awake 时网络未初始化，connectionToServer 为 null，netId 为 0， Command 调用会被 Mirror 静默丢弃。应在 OnStartClient（客户端）或 OnStartServer（服务器）之后调用。

4) [ServerCallback] 是本地方法守卫，确保方法只在服务器端执行， 非服务器调用时跳过且不打印警告。它不是 RPC——不走网络，不序列化消息。 [Command] 才是真正的远程过程调用——通过网络发送消息到服务器。 两者完全不同：[ServerCallback] = 本地判断；[Command] = 跨网络请求。
