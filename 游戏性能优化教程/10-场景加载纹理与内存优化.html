场景加载、纹理与内存优化

模块二 · 优化策略实战 ｜ 对应原文策略 8、9、14 及内存管理

本章把三个与“数据何时进入内存”相关的策略放在一起，它们共同回答两个问题：如何让资源加载不造成帧尖峰，以及如何避免内存被用不到的数据占满。

10.1 场景加载优化（策略 8）

场景加载有三个优化方向：离线分析、异步加载、空间划分与加载优先级。一次性同步加载整个场景会让主线程长时间阻塞，产生明显的加载卡顿甚至 ANR。正确流程是：

flowchart LR A["离线分析场景物件"] --> B["空间划分区块"] B --> C["按距离/重要性计算加载优先级"] C --> D["异步分帧加载"] D --> E["由近到远平滑显示"] style A fill:#f5eefb,stroke:#8e44ad,color:#14395a style D fill:#e7f3ff,stroke:#007acc,color:#14395a
  • 异步加载把读取与实例化摊到多帧，单帧只处理一小部分，避免主线程被占满。
  • 由近到远显示：玩家身边的内容先出现，远处物件随后淡入，配合距离阈值让加载行为难以被察觉。
  • 优先级要动态更新，玩家快速转向或传送时，新方向的物件应立即提权。

10.2 Mipmap 与纹理优化（策略 9）

Mipmap 为纹理预生成多级缩小版本：物体离远或被斜看时，采样更小的层级，既减少远处摩尔纹/锯齿，又降低缓存未命中带来的带宽开销。代价是纹理内存约增加三分之一。

原文针对视角相对固定的游戏进一步优化：相邻帧视野变化很小时，不必重复生成大量相似的纹理数据，按实际视野变化决定是否更新层级，从而同时降低纹理生成开销、内存占用与 CPU 计算。实践中还应：

  • 使用硬件压缩格式（移动端 ASTC/ETC2），并按用途选择合适的 Mipmap 策略（UI 2D 贴图通常不需要 Mipmap）。
  • 控制纹理最大尺寸，分辨率永远不超过实际显示需要。
  • 关注 Mipmap 剥离（Mipmap Stripping）与流式纹理（Texture Streaming），按距离只加载需要的层级。

10.3 Model 元素延迟加载（策略 14）

部分数据接口在调用时会把完整的 Model 元数据一次性载入内存，但运行逻辑往往只用到其中少数字段。原文的原则是：需要什么加载什么，什么时候需要什么时候加载。

手段效果
首次访问时才加载（懒加载）不访问就不产生 IO 与内存
只加载实际需要的字段避免整表/整对象载入
延迟加载低频属性把冷数据推迟到真正使用
减少启动阶段加载缩短启动时间、降低启动内存峰值

C# 中可直接用 System.Lazy<T> 表达首次访问语义：

using System;

public class HeroModel
{
    private readonly Lazy detail;
    private readonly Lazy skins;

    public HeroModel(Func detailFactory, Func skinFactory)
    {
        detail = new Lazy(detailFactory);
        skins = new Lazy(skinFactory);
    }

    public HeroDetail Detail => detail.Value;
    public HeroSkinLibrary Skins => skins.Value;
}

10.4 内存管理：池化与碎片

引擎层内存管理通常由对象池、内存池与内存分配器组成。运行中频繁 new / destroy 会产生两个问题：分配本身的 CPU 成本，以及反复分配释放导致的内存碎片——空闲内存总量够，但没有连续大块可分配。

  • 对象池：回收对象而不是销毁，再次需要时复用，避免重复实例化与 GC。
  • 内存池：预分配固定大小块，分配/归还都是 O(1)，且不产生碎片。
  • 分配器：按生命周期选择不同分配策略，短生命周期对象用线性/栈分配，长生命周期用通用堆。

一个通用对象池实现：

using System.Collections.Generic;
using UnityEngine;

public class GameObjectPool
{
    private readonly Stack available = new Stack();
    private readonly GameObject prefab;
    private readonly Transform root;

    public GameObjectPool(GameObject prefab, Transform root, int preload)
    {
        this.prefab = prefab;
        this.root = root;

        for (int i = 0; i < preload; i++)
        {
            GameObject instance = Create();
            instance.SetActive(false);
            available.Push(instance);
        }
    }

    public GameObject Get()
    {
        GameObject instance = available.Count > 0 ? available.Pop() : Create();
        instance.SetActive(true);
        return instance;
    }

    public void Release(GameObject instance)
    {
        instance.SetActive(false);
        instance.transform.SetParent(root, false);
        available.Push(instance);
    }

    private GameObject Create()
    {
        return Object.Instantiate(prefab, root);
    }
}
池化的常见误用：
  • 取出对象时未重置状态（血量、位置、协程残留），导致脏数据 bug。
  • 池只增不减、预分配过大，长期占用内存反而更糟，应设置容量上限与回收策略。
  • 把创建成本极低、生命周期简单的对象也塞进池，徒增复杂度。

练习与思考

基础练习对象池接入

把项目中频繁生成的子弹/特效改为对象池，用 Profiler 对比改造前后的 GC Alloc 与实例化耗时。

思考题懒加载边界

懒加载是否适用于所有数据？请分析在战斗中首次访问触发同步 IO 会带来什么风险，以及如何规避。

进阶挑战池容量治理

为对象池增加容量上限与闲置超时回收，使池大小随实际使用量自适应，而不是只增不减。

本章小结

  • 场景加载走离线分析、空间划分、优先级、异步分帧、由近到远显示的完整流程。
  • Mipmap 用空间换带宽与画质，视角固定时可按视野变化减少重复纹理生成。
  • Model 延迟加载用懒加载只载入需要的字段，降低启动内存峰值。
