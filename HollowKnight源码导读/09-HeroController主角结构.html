第 9 章　HeroController 主角结构（上）

主角是整个游戏交互的中心，HeroController 则是承载主角逻辑的巨型控制器——5600 多行，从移动参数、物理状态到攻击、施法、死亡全部管。本章先拆解它的静态结构：调参常量、组件构成、状态容器、生命周期；第 10 章再深入输入处理和具体动作机制。

9.1 一个类，两种状态语言

读 HeroController 前先分清它内部两套并行的状态表达：

hero_state（ActorStates 枚举）cState（HeroControllerStates）
类型枚举，9 个值[Serializable] 类，约 50 个布尔字段
语义主角当前的宏观运动状态，互斥各维度的并行状态标记，可同时为真
取值grounded、idle、running、airborne、wall_sliding、hard_landing、dash_landing、no_input、previousdashing、attacking、onGround、facingRight、invulnerable、focusing…

为什么需要两套？

宏观运动状态是互斥的（你不能同时 grounded 又 airborne），用一个枚举表达最清晰；但很多状态是正交、可叠加的（可以同时 dashing + facingRight + invulnerable），无法用单个枚举表达，于是用一组布尔。SetState 切换枚举主状态，cState 布尔则在各动作方法里独立置位。

9.2 调参常量区：数据驱动的移动手感

类开头是上百个 public 常量字段，全部大写命名，按动作分组：

public float RUN_SPEED;
public float JUMP_SPEED;
public int   JUMP_STEPS;          // 跳跃持续帧数
public float DASH_SPEED;
public float DASH_TIME;
public float DASH_COOLDOWN;
public float WALLSLIDE_SPEED;
public float DEFAULT_GRAVITY;
public float ATTACK_DURATION;
// 水下、冲刺、二段跳、骨钉蓄力等各有一组

这些数值不在代码里写死，而是在 Inspector 配置，让策划能独立调手感而不改逻辑。注意区分两类：速度类是 float（每秒位移），而 JUMP_STEPS、DASH_QUEUE_STEPS 这类是 int（帧数/步数），配合协程按帧计数。带 _CH 后缀的是对应护符（Charm）生效时的替换值。

物理与碰撞：私有组件

rb2d 和 col2d 是私有字段，通过 GetComponent 获取，外部不直接操作主角刚体。所有移动都经 HeroController 内部方法改 rb2d.linearVelocity，这保证了对主角运动的集中控制。

受击与攻击的判定分离

  • HeroBox 是主角身上的受击 Trigger，负责检测伤害源并回调 TakeDamage；它有静态开关 inactive，进场/过场时整体关闭受击
  • NailSlash 是骨钉攻击的判定对象，五个方向各一个，配合独立的 PlayMaker FSM 控制挥砍动画与命中窗口
// HeroBox 识别两类伤害源：FSM 版与组件版
if (FSMUtility.ContainsFSM(other.gameObject, "damages_hero")) { /* 读 FSM 伤害值 */ }
DamageHero component = other.GetComponent();
if (component != null && (!cState.shadowDashing || !component.shadowDashHazard))
{ /* 应用伤害，暗影冲刺可穿过特定危险 */ }

9.4 cState 状态容器与反射访问

HeroControllerStates 是一个 [Serializable] 类，字段覆盖主角全部正交状态：

[Serializable]
public class HeroControllerStates
{
    public bool facingRight;
    public bool onGround;
    public bool dashing;
    public bool attacking;
    public bool invulnerable;
    public bool focusing;
    public bool nearBench;
    // ... 约 50 个
}

它和 PlayerData 一样提供反射字符串访问，供 FSM 按名查询：

public bool GetState(string stateName)
{
    FieldInfo field = GetType().GetField(stateName);
    if (field != null)
        return (bool)field.GetValue(HeroController.instance.cState);
    Debug.LogError("HeroControllerStates: Could not find bool named" + stateName);
    return false;
}

同样的反射模式第三次出现（PlayerData、HeroControllerStates、FSM 变量），这是全工程一致的架构选择：让数据驱动的 PlayMaker 能用字符串访问 C# 状态。代价也相同——拼写错误只能在运行时暴露。

9.5 生命周期：Awake / Start / Update

Awake：单例去重与引用装配

private void Awake()
{
    if (_instance == null)
    {
        _instance = this;
        DontDestroyOnLoad(this);
    }
    else if (this != _instance)
    {
        Destroy(gameObject);
        return;
    }
    SetupGameRefs();
    SetupPools();
}

这是第 3 章讲过的手写单例模式：静态字段 + DontDestroyOnLoad + 重复实例销毁。Awake 里还会 SetupPools 预建特效对象池。

Start：容错定位与场景判断

Start 里有大量"字段为空就手动定位"的兜底逻辑，是反编译代码里值得注意的防御性写法：

if (superDash == null)
{
    Debug.Log("SuperDash came up null, locating manually");
    superDash = FSMUtility.LocateFSM(gameObject, "Superdash");
}

随后判断当前是否游戏场景：是则启用 vignette、发送 heroInPosition；否则把主角移到 y=-2000 并关闭重力（菜单场景下主角藏在屏幕外）。

Update：每帧的结构

private void Update()
{
    if (Time.frameCount % 10 == 0) Update10();   // 每 10 帧一次的低频逻辑
    current_velocity = rb2d.linearVelocity;
    FallCheck();
    FailSafeChecks();
    // 脚步声/特效、落地计时、受击硬直处理……
    if (hero_state != ActorStates.no_input)
        LookForInput();   // 输入驱动的动作（第 10 章）
}

两个工程细节：用 frameCount % 10 把不需要每帧跑的检查（Update10）节流到 10 帧一次，降低开销；FailSafeChecks 是兜底检测，防止主角卡在异常状态（如卡在墙里、状态标记不一致）。这种"主逻辑 + 看门狗"的组合在大型控制器里很常见。

9.6 SetupGameRefs：集中的引用装配

private void SetupGameRefs()
{
    if (cState == null) cState = new HeroControllerStates();
    gm = GameManager.instance;
    animCtrl = GetComponent();
    rb2d = GetComponent();
    col2d = GetComponent();
    audioCtrl = GetComponent();
    inputHandler = gm.GetComponent();
    proxyFSM = FSMUtility.LocateFSM(gameObject, "ProxyFSM");
    // ...
    gm.UnloadingLevel += OnLevelUnload;
    acceptingInput = true;
}

引用获取分两类：同物体组件用 GetComponent，跨系统用其他单例（GameManager.instance）。末尾订阅 gm.UnloadingLevel 事件，场景卸载时收到回调——再次体现事件解耦。

9.7 巨型控制器的权衡

好处代价
主角状态集中、可读字段齐全；调试时一处能看到全部信息；避免多组件间状态同步问题 5600 行单文件、职责过载；改动易产生回归；新人难以整体把握；状态布尔多，组合爆炸难推理

团队用"子 FSM 分担表现、独立组件（HeroBox/NailSlash）分担判定、cState 集中状态"来缓解，但核心运动逻辑仍收在一个类里。这是动作游戏常见的务实选择——主角逻辑高度耦合，强行拆分会带来更多跨组件通信成本。

思考与练习

  1. 区分 hero_state 与 cState，说明为什么一套枚举不够、还要一组并行布尔。
  2. 列出 HeroController 上的物理、受击、攻击组件，说明受击判定（HeroBox）和攻击判定（NailSlash）为什么分开。
  3. 解释 Update 里 frameCount % 10 的作用，哪些逻辑适合放进 Update10 而不是每帧执行？
  4. 结合 cState 的反射 GetState，说明它与 PlayerData 反射访问共享的架构动机和共同风险。
