02　ECS 核心概念：Entity、Component、System 与 Chunk

这一章把 ECS 的四个核心构件一次讲透：Entity、Component、System，以及把它们串起来的 Archetype 和 Chunk。理解了 Chunk 的内存布局，你就掌握了 ECS 性能模型的全部根基。

2.1 Entity：一个编号，不是对象

定义

Entity 是一个轻量级的标识，运行时表现为一个只含 Index 和 Version 两个整型字段的结构体。它不持有任何数据，也没有任何方法。你不能给 Entity“加字段”，数据全部存放在它关联的组件里。

这是和 OOP 最大的决裂点。一个 GameObject 自带 Transform、名字、激活状态、组件列表，是个有内容的对象；而 Entity 更像数据库里的一行主键——它唯一的职责是把“散落的各组件数据”归拢到同一个身份下。

两个字段各有分工：

  • Index：实体在内部存储中的位置索引。
  • Version：版本号。实体被销毁后，它的 Index 会被复用，Version 随之递增，这样手里还握着旧引用的代码不会误操作到新实体上。
别和 EntityId 搞混：Unity 6.5 引入的 EntityId 是一个 64 位结构体，用于 GameObject 与实体之间的互操作标识（替代旧的 InstanceID 机制）。ECS 内部用来标识实体的仍然是 Entity（Index + Version）。两个名字像，作用域不同，第十章讲混合工作流时会再碰到 EntityId。

2.2 Component：只放数据的 struct

最常用的组件类型是实现 IComponentData 的结构体。规则很严格：只包含数据字段，不写任何逻辑方法。

using Unity.Entities;

public struct Health : IComponentData
{
    public float Current;
    public float Max;
}

public struct MovementSpeed : IComponentData
{
    public float Value;
}

对照 OOP：EnemyBase 类里的字段和方法是焊在一起的；ECS 把它们拆成独立的组件，实体按需组合。一个实体可以同时拥有 Health、MovementSpeed、LocalTransform，也可以只有其中两个。组合替代继承，这是 ECS 复用能力的来源——不需要为“会移动但不会攻击的敌人”再写一个子类。

纪律：组件字段默认使用非托管类型（float、int、float3、其他 struct）。需要字符串用 FixedString，需要数组用 DynamicBuffer，需要引用引擎资源用 UnityObjectRef<T>。第六章逐一讲。

2.3 System：行为的唯一居所

数据和行为分离后，行为放在 System 里。一个 System 每帧（或按指定时机）执行，通过查询找出拥有特定组件组合的所有实体，然后批量处理它们。第四章会完整写一个 System，这里先建立概念：System 不属于任何一个实体，它“俯视”整个 World 里的数据。

三者的关系可以用一句话记住：Entity 是编号，Component 是数据，System 是处理数据的函数。

2.4 Archetype：组件组合的唯一指纹

定义

Archetype（原型）是一个实体所拥有的组件类型集合的唯一组合。拥有完全相同组件类型集合的实体属于同一个 Archetype，哪怕组件里的数值不同。

举例：

  • 实体 A、B 都有 LocalTransform + MovementSpeed + Health → 属于同一个 Archetype；
  • 实体 C 有 LocalTransform + MovementSpeed，没有 Health → 属于另一个 Archetype；
  • 给 A 动态加上一个 Stunned 组件 → A 离开原 Archetype，进入第三个 Archetype。

Archetype 不是你手动创建的，而是 ECS 在实体组件组合首次出现时自动建立的。它的意义在于：查询“所有拥有 Health 的实体”时，引擎可以直接按 Archetype 筛选，而不是逐个实体检查。

2.5 Chunk：性能模型的核心

光有 Archetype 还不够，关键是数据在内存里怎么放。每个 Archetype 由若干个 Chunk（内存块，默认 16 KB）组成，同一个 Archetype 的实体数据写进这些 Chunk，Chunk 写满就再分配一个。

Chunk 内部采用 SoA（Structure of Arrays，数组结构）布局：不是把每个实体的组件打包在一起，而是把同一种组件的所有实例排成一段连续数组：

flowchart TB
    subgraph CHUNK["一个 16KB Chunk（Archetype: LocalTransform + MovementSpeed + Health）"]
        direction TB
        T["LocalTransform 数组（连续）
[T0][T1][T2][T3] ..."]
        M["MovementSpeed 数组（连续）
[M0][M1][M2][M3] ..."]
        H["Health 数组（连续）
[H0][H1][H2][H3] ..."]
    end

回忆第一章讲的缓存行：当一个 System 只想读取所有实体的 MovementSpeed 时，它遍历的是 Chunk 内一段紧密排列的同构数组，CPU 预取器可以高效地把后续数据连续搬进缓存，几乎没有浪费。这就是 ECS 性能优势落地的物理位置——不是玄学，是内存布局。

同一个实体的各组件在 Chunk 内通过相同的数组下标关联（第 0 个 Transform、第 0 个 Speed、第 0 个 Health 属于同一个实体）。System 遍历 Chunk 时按下标同步推进即可。

由此推出两条设计直觉：
  • 组件越精简越好。一个大组件里塞十几个字段，会让只需要其中一个字段的查询把整段数据拉进缓存，稀释 SoA 的收益。把按不同频率、不同用途访问的数据拆成小组件。
  • Archetype 数量要可控。每种组件组合都对应独立的 Chunk 序列，过度碎片化的组合会让每个 Chunk 都填不满，产生空隙，并增加查询要扫描的 Chunk 数。

2.6 一次结构变更在底层发生了什么

给实体增删组件叫结构变更（structural change）。因为 Archetype 由组件组合决定，结构变更意味着实体要换 Archetype，而不同 Archetype 的 Chunk 布局完全不同，所以 ECS 必须把这个实体的组件数据从旧 Chunk 搬到新 Archetype 的 Chunk 里，原位置留下空洞并在后续整理。

flowchart LR
    E["实体 A"] -->|"添加 Stunned 组件"| Q["匹配新 Archetype"]
    Q --> P["在新 Archetype 的 Chunk 中分配位置"]
    P --> C["拷贝 A 的全部组件数据"]
    C --> D["旧 Chunk 位置释放"]

这解释了第一章埋的伏笔：为什么结构变更昂贵且不能在并行 Job 里随手做——移动数据、重排 Chunk 都需要同步点，会卡住其他 Job。所以 ECS 提供 EntityCommandBuffer 把变更记录下来、在安全时机统一回放（第七章详解）。日常设计中，能用“数值变化”表达的状态（如 Health.Current 归零）就不要滥用组件增删；确实需要开关式状态时，优先用零内存开销的 Enableable Component（第六章）。

2.7 World：实体与系统的容器

World 是一个隔离的运行环境，拥有自己的 EntityManager、实体集合和 System 集合。默认情况下游戏启动时会创建一个默认 World，你写的 System 默认都进这里。实体和系统按 World 隔离，不同 World 之间互不可见。

初学者暂时只需要和默认 World 打交道。显式创建额外 World 的场景通常是：独立的模拟沙箱、编辑器预览世界（在第三章的 Baking 阶段你会在 Hierarchy 里看到 Editor World）、客户端/服务器分世界等。

本章小结

  • Entity 是 Index + Version 的编号，不存数据、没有方法；EntityId 是 GameObject 互操作层的 64 位标识，别混淆。
  • IComponentData 是只含数据的非托管 struct，组件组合替代类继承。
  • Archetype 是组件类型组合的唯一指纹，同 Archetype 的实体住在同一组 16KB Chunk 中。
  • Chunk 内 SoA 布局让同类组件数据连续排列，是缓存友好与高性能的物理来源。
  • 结构变更会导致实体在 Archetype 间搬迁，成本高，需经 ECB 排队执行。
  • World 是实体与系统的隔离容器，初学阶段只接触默认 World。
