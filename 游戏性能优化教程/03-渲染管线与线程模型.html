渲染管线与线程模型

模块一 · 基础与度量 ｜ 理解指标背后的执行过程

第 2 章建立了指标语言，本章回答这些指标在程序里是怎么产生的：一帧之内 CPU 和 GPU 分别执行哪些阶段，任务如何分布到多个线程，以及怎样判断瓶颈落在哪一侧。这些认知是后面所有优化策略的“地图”。

3.1 一帧的生命周期

游戏主循环以目标帧率反复执行“更新 → 渲染”。CPU 负责逻辑与构建渲染命令，GPU 负责真正的并行图形计算，两者通过命令缓冲区异步协作。

sequenceDiagram participant MT as 主线程 participant RT as 渲染线程 participant W as Worker 线程 participant GPU as GPU MT->>W: 并行任务（动画/剔除/粒子） W-->>MT: 结果汇合（同步点） MT->>MT: 游戏逻辑/物理/动画状态 MT->>RT: 生成渲染命令 RT->>GPU: 提交 Draw Call GPU->>GPU: 顶点处理→光栅化→片元着色 GPU->>GPU: 深度测试/混合→帧缓冲 GPU-->>RT: 完成（缓冲交换）

注意图中的同步点：Worker 任务必须在主线程进入下一阶段前汇合，渲染线程与 GPU 之间也需要缓冲交换。如果某一侧耗时过长，另一侧就会空等——这就是后面要讲的线程等待问题。

3.2 渲染管线：剔除 → 绘制

原文把渲染管线拆成剔除管线与绘制管线两大段，这个划分直接对应一批优化点。

剔除阶段：决定“不画什么”

剔除越早、越准确，后面的绘制成本越低。常见剔除类型包括：

  • Frustum Culling（视锥剔除）：丢弃摄像机视野外的物体，最基础的剔除。
  • Occlusion Culling（遮挡剔除）：被不透明物体完全挡住的物体不提交。
  • 地形剔除 / Group Culling：按地形块或成组对象整体剔除，减少逐对象判断。
  • 光照剔除 / 反射剔除：只保留对当前画面有贡献的光源与反射探针。

绘制阶段：把可见对象画出来

典型顺序为：动态网格构建 → 深度图 / 阴影绘制 → 不透明物体 → 半透明物体 → 排序与合批 → 提交。其中不透明物体通常由前到后绘制以利用深度测试减少 Overdraw；半透明物体必须由后到前绘制并做混合，无法靠深度测试剔除，这正是粒子与 UI 容易产生 Overdraw 的原因。

对应到优化策略：剔除阶段的优化包括自定义合批、遮挡与分组剔除、减少不必要的 Camera Culling；绘制阶段的优化包括合批、特效分级、阴影替代、管线裁剪。学完本章再看模块二，会清楚每个策略作用在管线的哪个位置。

3.3 线程模型的三个演进阶段

flowchart TB subgraph S1["阶段一：单线程"] A1["主线程：业务逻辑 → 引擎逻辑 → 渲染管线 → 渲染提交"] end subgraph S2["阶段二：拆出渲染线程"] B1["主线程：业务逻辑 + 引擎逻辑"] B2["渲染线程：渲染提交"] B1 --> B2 end subgraph S3["阶段三：多 Worker 并行"] C1["主线程：调度与汇总"] C2["渲染线程"] C3["Worker：动画/剔除/粒子等可并行任务"] C1 --> C3 C1 --> C2 end S1 --> S2 --> S3

现代移动设备都是多核 CPU，把可并行的工作（动画蒙皮、距离剔除、粒子更新）拆到 Worker 线程，是榨干硬件的关键。但这里有两个必须建立的认知：

  • 并行不是万能：存在无法绕过的串行段与同步点。如果主线程的串行逻辑已经占满帧预算，增加 Worker 不会让帧变快——这就是并行计算中的“阿姆达尔定律”：加速比受限于串行部分的比例。
  • 线程间有等待成本：锁竞争、数据同步、线程通信的缓存一致性都会产生开销。网络同步、逻辑与表现分离时尤其要关注跨线程数据搬运。

3.4 判定 CPU 瓶颈还是 GPU 瓶颈

定位瓶颈的第一步，是确认帧时间耗在 CPU 侧还是 GPU 侧。两者的优化手段几乎不通用，判错方向会白费力气。

判定方式CPU Bound 的表现GPU Bound 的表现
Profiler 时间线CPU 各线程总和先触及预算，GPU 仍有空档（等待 CPU）GPU 段先耗尽预算，CPU 在等待 Gfx 完成
降低渲染分辨率帧时间几乎不变帧时间明显下降（填充/采样压力减轻）
减少场景对象 / 逻辑帧时间明显下降变化不明显
关闭后处理 / 阴影变化小明显改善
快速实验法：在受控场景里分别做两个极端实验——把渲染分辨率降到最低（几乎只省 GPU），再把可见对象与逻辑压到最少（主要省 CPU）。观察哪个实验让帧时间下降更多，就能快速确定方向，再用 Profiler 精确定位。

3.5 为什么不能只盯单个函数

新手看 Profiler 时常做的事，是按耗时排序找到最“贵”的函数然后优化它。但帧时间是多线程协作加等待的总和：一个函数本身耗时不高，却可能因为持有锁导致其他线程阻塞；Worker 线程出现大片空闲，可能是主线程派发任务太晚。因此分析时既要看单点耗时，也要看线程时间线里的空洞、等待与同步点。模块四会把这套方法系统化。

附：用 ProfilerMarker 标注自定义阶段

Unity 默认采样看不到业务自定义阶段，可用标记把自己的系统暴露到 Profiler 时间线，便于和渲染、动画阶段对照：

using Unity.Profiling;
using UnityEngine;

public class MarkeredSystem : MonoBehaviour
{
    static readonly ProfilerMarker gameplayMarker =
        new ProfilerMarker("MyGameplay.Tick");
    static readonly ProfilerMarker cullingMarker =
        new ProfilerMarker("MyGameplay.CustomCulling");

    void Update()
    {
        using (gameplayMarker.Auto())
        {
            TickGameplay();
        }

        using (cullingMarker.Auto())
        {
            RunCustomCulling();
        }
    }

    private void TickGameplay() { }
    private void RunCustomCulling() { }
}

练习与思考

思考题线程空洞

在 Profiler 时间线里，你发现 Worker 线程在一帧的前半段全部空闲，后半段才开始执行动画任务。请给出至少两种可能的原因，并思考这种情况下直接优化 Worker 上的函数是否有效。

实践任务瓶颈判定实验

在你自己的工程中设计 3.4 节的两个受控实验，记录实验前后的 CPU 与 GPU 帧时间，写出判定结论，并说明你选择的观察指标为什么能区分两类瓶颈。

本章小结

  • 一帧由 CPU（逻辑、剔除、命令构建）与 GPU（顶点、光栅化、片元、混合）异步协作完成，中间存在同步点。
  • 渲染管线分剔除与绘制两段；剔除决定不画什么，绘制按不透明/半透明不同规则处理。
  • 线程模型从单线程演进到渲染线程再到多 Worker，但受串行段、锁与同步点约束。
  • 用分辨率与对象数量两个受控实验，可快速判定 CPU Bound 还是 GPU Bound。
