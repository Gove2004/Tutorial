CI/CD 与持续交付

CI/CD 是软件工程的"高速公路"——它让代码从提交到上线的整个过程自动化、可预测、可追溯。

没有 CI/CD 的团队，部署就像"跳崖"：几个月积累的代码，一次性推到生产环境，然后祈祷一切正常。有了 CI/CD，部署变成"散步"：每天多次小步部署，出问题随时回滚。

CI vs CD vs CICD

这三个缩写经常被混用，但它们代表不同的概念：

CI/CD 流水线 代码提交 │ ▼ ┌─────────────────────────────────────────────────────┐ │ CI (Continuous Integration) │ │ 每次提交自动触发： │ │ 1. 拉取代码 │ │ 2. 安装依赖 │ │ 3. 运行 lint │ │ 4. 运行测试 │ │ 5. 构建产物 │ └─────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────┐ │ CD (Continuous Delivery) │ │ 在 CI 的基础上增加： │ │ 6. 部署到 staging 环境 │ │ 7. 运行集成测试 │ │ 8. 人工审批 → 决定是否部署到生产 │ └─────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────┐ │ Continuous Deployment (全自动) │ │ 在 CD 的基础上去掉： │ │ 8. 人工审批 → 自动部署到生产 │ └─────────────────────────────────────────────────────┘

CI/CD 的核心价值

价值说明没有 CI/CD 的后果
快速反馈 代码提交后几分钟就知道有没有问题 问题在几天后才被发现，修复成本是原来的 10 倍
降低风险 小步部署，每次变更很小 "发布日"变成"恐慌日"，一次部署上千个变更
可重复性 每次部署的流程完全相同 "在我机器上是好的"——环境不一致
可追溯性 每个版本都有完整的构建日志和测试报告 出了问题不知道是哪个提交导致的

Pipeline 设计

一个典型的 CI/CD pipeline 包含以下阶段：

典型 CI/CD Pipeline Stage 1: Lint → 检查代码风格（秒级） Stage 2: Build → 编译/打包（分钟级） Stage 3: Unit Test → 单元测试（分钟级） Stage 4: Integration → 集成测试（分钟级） Stage 5: Security Scan → 安全扫描（分钟级） Stage 6: Deploy Staging → 部署到测试环境（分钟级） Stage 7: E2E Test → 端到端测试（分钟级） Stage 8: Deploy Prod → 部署到生产环境（人工审批）

关键原则：越快越好。每个阶段都应该尽快失败（fail-fast）。如果 lint 都过不了，就没必要跑测试了。

CI/CD 工具选型

工具类型特点适用场景
GitHub Actions 托管式 与 GitHub 深度集成，YAML 配置，社区 Actions 丰富 GitHub 项目首选
GitLab CI 托管/自托管 .gitlab-ci.yml，内置容器注册表，完整的 DevOps 平台 GitLab 项目首选
Jenkins 自托管 插件生态最丰富，完全可控，但运维成本高 大型企业、合规要求高的场景
CircleCI 托管式 配置简洁，缓存和并行执行能力强 中小团队，追求快速上手
Argo CD 自托管 (GitOps) 声明式 K8s 部署，Git 作为唯一真相源 Kubernetes 环境

实战：GitHub Actions Pipeline

# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install ruff
      - run: ruff check .
      - run: ruff format --check .

  test:
    needs: lint
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: test
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: pytest --cov=app --cov-report=xml

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:${{ github.sha }} .
      - run: docker push myapp:${{ github.sha }}

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: kubectl set image deployment/myapp myapp=myapp:${{ github.sha }}

  deploy-production:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    if: github.ref == 'refs/heads/main'
    steps:
      - run: kubectl rollout restart deployment/myapp

部署策略

部署到生产环境不是"一键切换"那么简单。部署策略决定了新版本如何替换旧版本，以及出问题怎么办。

1. 蓝绿部署 (Blue-Green)

蓝绿部署 Blue (v1.0) Green (v2.0) ┌──────────┐ ┌──────────┐ │ Running │ │ Ready │ │ Production│ │ Staging │ └──────────┘ └──────────┘ │ │ └──────┬───────────┘ ▼ 流量切换 (瞬间完成) ┌──────────┐ │ v2.0 │ ← Green 现在在生产 └──────────┘ │ ▼ (如果出问题) 瞬间切回 Blue (v1.0)

蓝绿部署的核心是两套完全相同的环境，一套运行旧版本，一套准备好新版本。切换流量是瞬间完成的，回滚也是瞬间的。

2. 金丝雀部署 (Canary)

金丝雀部署 Step 1: 5% 流量 → v2.0 (金丝雀实例) Step 2: 监控指标 (错误率、延迟、CPU) Step 3: 如果正常 → 逐步增加流量 5% → 25% → 50% → 100% Step 4: 如果异常 → 立即回滚

金丝雀部署的核心是渐进式放量。先让一小部分用户用新版本，观察指标正常后再逐步扩大。

3. 特性开关 (Feature Toggle)

特性开关 代码提交 │ ├─→ 部署到生产 (v2.0 代码已上线，但功能关闭) │ ├─→ 对内部用户开启 (Alpha) │ ├─→ 对 10% 用户开启 (Beta) │ └─→ 对所有用户开启 (Feature Live) 好处：代码可以随时部署，功能可以随时开关

环境管理

一个成熟的 CI/CD 体系需要多个环境：

环境用途数据变更频率
Local开发者本地开发Mock / 种子数据每天多次
CI自动化测试临时 / 重置每次提交
Staging预发布验证脱敏的生产数据每天数次
Production真实用户使用真实数据按需发布
常见陷阱：Staging 环境和 Production 环境不一致（数据库版本不同、配置不同、依赖版本不同），导致"staging 没问题，上线就崩"。
对策：用 Docker / Kubernetes 保证环境一致性。代码在任何环境跑出来的镜像应该是一样的。

回滚策略

再好的部署也会出问题。关键是出问题后多快能恢复。

策略做法恢复时间
自动回滚监控到错误率飙升，自动回滚到上一个版本几分钟
手动回滚运维人员发现异常后手动触发15-30 分钟
特性开关不开启新功能的入口，代码还在但不生效秒级

本章小结

  • CI = 自动测试和构建，CD = 自动部署，Continuous Deployment = 全自动
  • Pipeline 应该 fail-fast，每个阶段都应该是独立的、快速的
  • 部署策略：蓝绿部署（瞬间切换）、金丝雀（渐进放量）、特性开关（代码在线但功能关闭）
  • 环境一致性是 CI/CD 成功的关键前提
  • 回滚策略必须提前设计，不能等问题发生了再想
