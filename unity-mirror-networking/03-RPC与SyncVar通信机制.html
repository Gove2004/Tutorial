第 3 章：RPC 与 SyncVar — 服务器-客户端通信机制

如果说 NetworkIdentity 是对象的身份证，NetworkServer/Client 是管理器， 那么 RPC 和 SyncVar 就是网络中的语言。 本章将系统讲解 Mirror 提供的所有通信方式，以及它们各自的设计意图和适用场景。

3.1 RPC 的本质：远程过程调用

RPC（Remote Procedure Call）的核心思想很简单：在 A 机器上调用方法，但实际执行在 B 机器上。

在单机开发中，你直接调用方法：

// 单机：直接调用
enemy.TakeDamage(50);  // 同一进程内，立即执行

在网络中，你不能这样做——敌人可能在另一台机器上。Mirror 的 RPC 机制帮你把这段调用 "打包"成网络消息，发送到目标机器再执行：

客户端                          服务器
  |                                |
  |--- CmdTakeDamage(50) --------->|  (序列化消息 + 发送)
  |                                |--- enemy.TakeDamage(50)  (反序列化 + 执行)
  |<<< ClientRpc_UpdateHealth() ---|  (结果回传)

3.2 [Command]：客户端 → 服务器

[Command] 是最常用的 RPC 类型。它允许客户端向服务器发送请求。

public class PlayerController : NetworkBehaviour
{
    [Command]
    public void CmdAttack()
    {
        // 这段代码在服务器上执行
        Debug.Log($"玩家 {connectionToServer.player.netId} 发起了攻击");

        // 执行攻击逻辑
        PerformAttack();

        // 通知所有客户端攻击结果
        RpcOnAttack();
    }

    // 注意：[Command] 方法名必须以 Cmd 开头（约定）
    // 注意：不能是 static
    // 注意：不能有 return value（ RPC 是 fire-and-forget ）
}
[Command] 的执行流程：
1. 客户端调用 CmdAttack()
2. Mirror 拦截调用，序列化为 RpcAttackMessage
3. 通过 Transport 发送到服务器
4. 服务器反序列化，在对应的 NetworkBehaviour 实例上执行 CmdAttack()
5. 服务器端的 isServer 为 true，所以逻辑在服务端运行

3.2.1 Command 的参数限制

由于参数需要被序列化为网络消息，[Command] 方法的参数有严格限制：

类型支持说明
基本类型✅int, float, bool, string, byte 等
Vector3 / Quaternion✅Mirror 内置支持
Enum✅序列化为底层整型
NetworkIdentity✅序列化为 netId
自定义 struct✅需可序列化
class（非 NetworkBehaviour）❌无法可靠序列化
数组 / List⚠️支持固定大小数组，List 需小心大小
返回值❌Command 是单向的，不能返回数值

3.2.2 [ServerCallback]：被废弃的 Command 替代方案

Mirror 后期版本引入了 [ServerCallback] 作为 Command 的补充：

public class WeaponSystem : NetworkBehaviour
{
    // [Command] 会经过网络序列化 → 服务器反序列化 → 执行
    // [ServerCallback] 跳过网络层，直接在服务器执行
    // 适用于"本地客户端请求服务器执行"的场景

    [ServerCallback]
    public void ServerOnlyMethod()
    {
        // 只在服务器执行，不走网络
        // 只能在 hasAuthority 的客户端上调用
    }

    void Update()
    {
        if (hasAuthority && Input.GetKeyDown(KeyCode.Space))
        {
            // 本地客户端直接调用，不经过网络
            ServerReloadWeapon();
        }
    }
}
Command vs ServerCallback 的选择：
• [Command]：需要经过网络层，服务器能收到消息、做验证、记录日志。适合"客户端请求服务器执行某事"。
• [ServerCallback]：不走网络序列化，性能更好，但服务器无法区分请求来自哪个客户端（因为是本地调用）。适合"本地客户端帮服务器做预处理"。

新手建议统一用 [Command]——它更透明、更容易调试。

3.3 [ClientRpc]：服务器 → 所有客户端

当服务器需要通知所有客户端某个事件发生时，使用 [ClientRpc]：

public class PlayerController : NetworkBehaviour
{
    [ClientRpc]
    public void RpcPlayShootEffect(Vector3 direction)
    {
        // 这段代码在每个客户端上执行
        // 通常只修改视觉/听觉表现，不改游戏逻辑
        Instantiate(shootPrefab, transform.position, Quaternion.identity);
        AudioSource.PlaySound(shootClip);
    }

    // 服务器端调用
    public void OnShot(Vector3 direction)
    {
        // ... 服务器执行攻击逻辑 ...

        // 通知所有客户端播放射击特效
        RpcPlayShootEffect(direction);
    }
}

3.3.1 Rpc 参数限制

与 Command 相同，Rpc 方法的参数也需要可序列化。 另外注意：Rpc 方法不需要 Cmd/Rpc 前缀约定——只要在服务器上调用， Mirror 就会自动将其作为 Rpc 发送给客户端。

3.4 [TargetRpc]：服务器 → 指定客户端

当你只想通知某一个特定客户端时，使用 TargetRpc：

public class InventorySystem : NetworkBehaviour
{
    // 服务器告诉"拥有这个背包的玩家"更新 UI
    [TargetRpc]
    public void TargetUpdateInventoryUI(List<string> items)
    {
        // 只在目标客户端上执行
        UpdateUI(items);
    }

    // 服务器端调用
    public void RefreshInventory(NetworkConnection target)
    {
        List myItems = GetMyItems();
        TargetUpdateInventoryUI(myItems);  // 只发给 target 这个客户端
    }
}

3.6 SyncVar：状态同步

RPC 用于"通知"——告诉其他机器"发生了某件事"。SyncVar 用于"同步"——让某个变量的值在所有机器上一致。

public class HealthSystem : NetworkBehaviour
{
    // 服务器修改 health 后，新值自动同步到所有客户端
    [SyncVar(hook = "OnHealthChanged")]
    public int health = 100;

    // hook 方法会在每次 health 值变化时自动调用
    // 这让你可以在同步时触发 UI 更新、动画等
    void OnHealthChanged(int newHealth)
    {
        UpdateHealthBar(newHealth);
    }

    // 服务器端：扣血
    public void TakeDamage(int amount)
    {
        if (!isServer) return;

        health -= amount;  // 修改 SyncVar → 自动同步
        // OnHealthChanged 在每个客户端自动被调用

        if (health <= 0)
            Die();
    }
}

3.6.1 SyncVar 的工作原理

很多人误以为 SyncVar 是"变量值通过网络发送"。实际上它的机制更精细：

1

服务器修改 SyncVar 字段

Mirror 在序列化时会跟踪哪些 SyncVar 发生了变化。

2

每帧打包变更

服务器每帧将所有发生变化的 SyncVar 打包到一个状态快照中发送。

3

客户端应用变更

客户端收到后，按顺序应用变更，并调用 hook 方法。

关键理解：SyncVar 的变化不是"即时发送"的。它们在服务器每帧结束时批量打包， 然后通过 UpdateVars 消息发送给客户端。这意味着 SyncVar 同步有一帧的延迟（在 60fps 下约 16ms）。 对于大多数场景这个延迟完全可以接受，但对于高精度同步需求需要考虑这一点。

3.6.2 SyncVar 的钩子（Hook）机制

Hook 方法是 SyncVar 最有价值的特性之一。它让你在值变化时自动执行回调：

[SyncVar(hook = nameof(OnArmorChanged))]
public int armor = 0;

// hook 方法签名必须是：void HookName(旧值, 新值)
void OnArmorChanged(int oldArmor, int newArmor)
{
    Debug.Log($"护甲从 {oldArmor} 变为 {newArmor}");

    // 可以计算差值做增量动画
    float delta = newArmor - oldArmor;
    AnimateArmorChange(delta);
}

3.6.3 SyncVar 的限制

限制原因替代方案
不能是 static静态变量不属于实例，无法逐实例同步改用实例变量
不能是 readonlyMirror 需要通过反射修改字段值去掉 readonly
复杂对象序列化有限只能序列化基础类型和简单结构用自定义消息
高频更新影响性能每个 SyncVar 变化都要序列化合并多个值为一组发送
初始值问题客户端 Spawn 时同步的是初始值在 OnStartClient 中手动设置

3.7 RPC vs SyncVar：什么时候用哪个？

这是新手最常问的问题。判断标准很简单：

选择准则

用 RPC，如果：你想告诉其他机器"做一件事"（动作/事件驱动）。
例如："射击"、"跳跃"、"拾取物品"、"开始动画"。

用 SyncVar，如果：你想让其他机器"知道一个状态"（状态驱动）。
例如："当前血量"、"当前弹药"、"是否隐身"、"队伍分数"。

实际项目中，两者经常配合使用：

public class PlayerStats : NetworkBehaviour
{
    // SyncVar：同步"当前值"
    [SyncVar(hook = "OnHealthChanged")]
    public int currentHealth = 100;

    [SyncVar(hook = "OnAmmoChanged")]
    public int currentAmmo = 30;

    // Command：客户端请求开火
    [Command]
    public void CmdRequestFire()
    {
        if (currentAmmo <= 0) return;

        // 服务器执行开火逻辑
        currentAmmo--;  // 修改 SyncVar → 自动同步给所有客户端
        currentHealth -= CalculateDamage();

        // Rpc：通知客户端播放特效
        RpcPlayFireEffect();
    }

    [ClientRpc]
    public void RpcPlayFireEffect()
    {
        // 所有客户端播放枪口火焰
        PlayMuzzleFlash();
    }
}

3.8 带宽优化：减少 RPC 和 SyncVar 的开销

在网络游戏中，带宽是有限资源。每一个 RPC 调用和 SyncVar 变更都在消耗带宽。 以下是实用的优化策略：

3.8.1 合并多个值为一个 RPC

// ❌ 低效：多次 RPC 调用，每条都有头部开销
RpcSetPosition(x, y, z);       // 第一次
RpcSetRotation(rx, ry, rz, rw); // 第二次
RpcsetScale(sx, sy, sz);       // 第三次

// ✅ 高效：一次 RPC 传递所有数据
RpcSetTransform(position, rotation, scale);

3.8.2 条件同步：只在值变化时发送

public class PositionTracker : NetworkBehaviour
{
    Vector3 lastSyncedPosition;
    float syncThreshold = 0.1f;

    void Update()
    {
        if (!isLocalPlayer) return;

        float distance = (transform.position - lastSyncedPosition).sqrMagnitude;
        if (distance > syncThreshold * syncThreshold)
        {
            // 只有移动超过阈值才发送
            CmdReportPosition(transform.position);
            lastSyncedPosition = transform.position;
        }
    }

    [Command]
    void CmdReportPosition(Vector3 pos)
    {
        // 服务器收到后广播
        RpcUpdatePosition(pos);
    }

    [ClientRpc]
    void RpcUpdatePosition(Vector3 pos)
    {
        targetTransform.position = pos;
    }
}

3.8.3 使用 SyncVar 而非手动 RPC 同步常量状态

如果一个值需要在服务器修改后自动同步给所有人，SyncVar 比手动发 RPC 更高效—— 因为 Mirror 会对 SyncVar 做批量处理和去重：

// ❌ 手动同步：每次修改都发一条 RPC
public void SetScore(int score)
{
    this.score = score;
    RpcUpdateScore(score);  // 即使一帧内改了 10 次也发 10 条
}

// ✅ SyncVar：Mirror 会自动合并同帧变更
[SyncVar]
public int score = 0;

public void AddScore(int amount)
{
    if (!isServer) return;
    score += amount;  // 一帧内加 10 次，只发 1 条更新消息
}

3.9 消息可靠性：哪些 RPC 需要保证送达？

Mirror 默认使用可靠的传输（TCP 或 KCP），所有 RPC 都会保证送达。 但在某些场景下你可能需要不可靠传输（允许丢包以换取更低延迟）：

// Mirror 支持 unreliable RPC
// 在 NetworkServer.Send 中可以指定 channelId
// Reliable (channel 0): 保证送达，可能乱序（UDP 时）
// Unreliable (channel 1): 不保证送达，保持顺序

// 高频位置同步（每帧 30-60 次）→ 用 unreliable
// 伤害计算（每秒几次）→ 用 reliable

// 手动发送 unreliable 消息
NetworkServer.SendToAll(msgType, message, channelId: 1);
不可靠传输的语义："不可靠"不代表"没用"。对于位置同步这类高频数据， 最新的值永远比"确保送达但过期"的值更有价值。如果一帧的位置数据丢了， 下一帧（几毫秒后）的新位置会覆盖它——玩家几乎感知不到差异。

3.10 实战：一个完整的战斗系统示例

让我们把 RPC 和 SyncVar 组合起来，实现一个真实的战斗系统：

public class CombatSystem : NetworkBehaviour
{
    [SyncVar(hook = nameof(OnHealthChanged))]
    public int health;

    [SyncVar(hook = nameof(OnStateUpdated))]
    public CombatState state;

    [SyncVar] public int comboCount;

    float lastAttackTime;
    float attackCooldown = 0.5f;

    enum CombatState
    {
        Idle,
        Attacking,
        Blocking,
        Stunned
    }

    // 客户端请求攻击
    [Command]
    public void CmdAttack()
    {
        if (Time.time - lastAttackTime < attackCooldown) return;
        if (state != CombatState.Idle) return;

        state = CombatState.Attacking;  // SyncVar → 自动同步
        lastAttackTime = Time.time;

        // 对目标造成伤害
        if (target != null && target.TryGetComponent(out HealthSystem hs))
        {
            hs.TakeDamage(attackDamage);
        }

        // 通知所有客户端播放攻击动画
        RpcPlayAttackAnimation();

        // 攻击结束后恢复状态
        Invoke(nameof(ResetState), 0.3f);
    }

    [TargetRpc]
    public void TargetShowDamageNumber(NetworkConnection conn, Vector3 position, int damage)
    {
        // 只给特定客户端显示伤害数字（视觉效果）
        DamageNumberPool.Show(position, damage);
    }

    [ClientRpc]
    void RpcPlayAttackAnimation()
    {
        animator.SetTrigger("Attack");
        audioSource.PlayOneShot(attackClip);
    }

    void OnHealthChanged(int oldVal, int newVal)
    {
        healthBar.SetHealth(newVal);
        if (newVal <= 0 && isLocalPlayer)
        {
            RpcOnDeath();
        }
    }

    void OnStateUpdated(CombatState oldState, CombatState newState)
    {
        // 可以根据状态切换不同的行为
    }

    [ClientRpc]
    void RpcOnDeath()
    {
        animator.SetTrigger("Die");
        GetComponent<Collider>.enabled = false;
    }

    void ResetState()
    {
        state = CombatState.Idle;
    }
}

3.11 调试 RPC 和 SyncVar

3.11.1 追踪 RPC 调用链

当 RPC 没有按预期触发时，可以用以下方式调试：

// 在服务器端拦截所有 RPC 调用
NetworkServer.RegisterHandler<RpcMessage>(msg =>
{
    Debug.Log($"[RPC-Debug] 收到来自 {msg.connectionId} 的消息: {msg.messageType}");
    Debug.Log($"[RPC-Debug] 调用堆栈: {System.Environment.StackTrace}");
}, replace: true);

// 在客户端检查 NetworkIdentity 的 connectionToServer
if (identity.connectionToServer == null)
{
    Debug.LogWarning($"[RPC-Debug] 对象 {name} 没有连接到服务器！");
    // 这通常意味着客户端还没完成连接就尝试调用 Command
}

3.11.2 观察 SyncVar 同步

Mirror 提供了观察 SyncVar 变化的工具方法：

public class DebugSyncVar : NetworkBehaviour
{
    [SyncVar]
    public int debugValue = 0;

    // Mirror 自动生成 GetSyncVarGameObject / GetSyncVarString 等方法
    // 你也可以手动检查同步状态
    void OnSyncEvent()
    {
        // 在 SyncVar 同步后调用
        Debug.Log($"SyncVar 已同步: debugValue = {debugValue}");
    }
}

3.12 本章小结

本章我们系统学习了 Mirror 的通信机制：

  • [Command]：客户端向服务器发请求——"我想做某事"
  • [ClientRpc]：服务器向所有客户端广播——"发生了某事"
  • [TargetRpc]：服务器向指定客户端发消息——"这件事只告诉你"
  • [SyncVar]：状态自动同步——"我的值是 X"
  • [ServerCallback]：本地调服务器的捷径——性能优化用

核心原则：动作用 RPC，状态用 SyncVar；客户端只发请求，服务器做决定。
