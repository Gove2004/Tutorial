动态自适应与特效分级

模块二 · 优化策略实战 ｜ 对应原文策略 4、7、10

前面的 LOD 与设备分档是“静态”的：进游戏定好档位后基本不变。但同一场战斗内部，压力也在剧烈波动——清兵线时 CPU 很闲，五人团战瞬间同屏单位、技能、特效全部拉满。动态自适应要解决的，是让画质随实时压力波动，把有限的帧预算集中到团战这种关键场景。

7.1 战斗性能动态自适应

核心思路是把战斗强度划分为低、中、高（可更多档），不同档位驱动不同的表现系统。当战斗强度升高时，逐步关闭或降低非关键表现：

表现项低强度中强度高强度（团战）
描边全开仅主角关闭
阴影实时简化面片/关闭
非关键特效正常降密度裁剪低优先级
UI 特效 / 音效完整精简关闭非关键
特效质量档位高中低

战斗强度如何度量

档位不能凭空设定，需要一个可计算的强度信号。常见输入包括：同屏活跃单位数、近几秒技能/特效触发数、当前粒子总数，以及最直接的——近期 CPU 帧时间是否逼近预算。实践中通常把这些信号加权成一个强度分数，再映射到档位。

用帧时间做兜底反馈：基于单位数的预测可能失准（比如特效特别重的技能），加入“帧时间持续超预算就强制升档”的反馈回路，能保证系统在意外压力下仍然保命。

7.2 特效动态裁剪：五级分类

要裁剪特效，先得知道哪些能裁、哪些不能动。原文按重要程度把特效分为五级：

等级类型裁剪优先级
Level 1氛围感特效（环境飘尘、光晕）最先裁
Level 2光感特效高
Level 3强化手感特效（打击火花）中
Level 4关键设计特效（技能核心表现）低
Level 5功能提示特效（命中、范围警示）不裁（承载信息）

高压力场景按等级从低到高裁剪，Level 5 承载玩法信息，关闭会让玩家无法判断技能范围，原则上保留。这体现了资源倾斜逻辑：牺牲装饰性表现，保住信息与核心手感。

7.3 粒子离线裁剪：治 Overdraw

粒子贴图通常是带大量透明区域的方形图，透明像素虽然不产生有效视觉，但默认仍可能进入渲染管线、参与光栅化，白白推高 Overdraw。原文的方案是把这部分处理搬到离线：

flowchart LR A["原始粒子纹理"] --> B["离线分析 Alpha 通道"] B --> C["提取有效像素区域"] C --> D["凸包计算最小多边形"] D --> E["生成裁剪顶点数据"] E --> F["运行时直接使用，跳过透明区"] style A fill:#fdecea,stroke:#e53935,color:#14395a style D fill:#e7f3ff,stroke:#007acc,color:#14395a

对有效像素点集求凸包（Convex Hull），得到一个能包住所有不透明像素的最小多边形，运行时用这组顶点替代原始矩形，透明区域不再参与绘制。这是一次性的资产预处理，运行时零额外计算。

展开：为什么用凸包而不是精确像素轮廓

精确沿像素边缘会产生大量顶点和凹多边形，顶点处理成本与排序复杂度上升；凸包以少量顶点换取大部分 Overdraw 收益，且凸多边形渲染稳定。对粒子这类边缘柔软、常带羽化的效果，凸包是性价比最高的近似。

7.4 工程实现：带冷却的自适应状态机

自适应系统最大的体验风险是档位频繁横跳：强度在阈值附近波动时，特效反复出现/消失比一直低档更刺眼。因此除了滞回，还要加切换冷却时间，两次换档之间强制间隔。

using UnityEngine;

public enum CombatTier { Low, Medium, High }

public class AdaptiveQuality : MonoBehaviour
{
    [SerializeField] private int mediumThreshold = 6;
    [SerializeField] private int highThreshold = 10;
    [SerializeField] private float switchCooldown = 1.5f;
    [SerializeField] private float frameBudgetMs = 16.6f;

    private CombatTier tier = CombatTier.Low;
    private float lastSwitch;
    private float overBudgetSince;

    public void Evaluate(int activeUnits, float currentFrameMs)
    {
        if (Time.unscaledTime - lastSwitch < switchCooldown) return;

        CombatTier target = tier;

        if (activeUnits >= highThreshold)
        {
            target = CombatTier.High;
        }
        else if (activeUnits >= mediumThreshold)
        {
            target = CombatTier.Medium;
        }
        else
        {
            target = CombatTier.Low;
        }

        if (currentFrameMs > frameBudgetMs)
        {
            overBudgetSince += Time.deltaTime;
            if (overBudgetSince > 0.5f && tier != CombatTier.High)
            {
                target = CombatTier.High;
            }
        }
        else
        {
            overBudgetSince = 0f;
        }

        if (target != tier)
        {
            Apply(target);
            tier = target;
            lastSwitch = Time.unscaledTime;
        }
    }

    private void Apply(CombatTier next)
    {
        switch (next)
        {
            case CombatTier.Low:
                QualitySettings.shadowDistance = 40f;
                break;
            case CombatTier.Medium:
                QualitySettings.shadowDistance = 20f;
                break;
            case CombatTier.High:
                QualitySettings.shadowDistance = 0f;
                break;
        }
    }
}

7.5 玩家感知边界

  • 避免在玩家正注视某个特效时把它消失，裁剪优先作用于视野边缘和新触发的特效。
  • 能用“降低密度/缩放”软降级的，就不要硬开关，平滑过渡更难被察觉。
  • 任何降级都要记录日志，方便事后对照“某档关闭了什么”，排查表现问题。

练习与思考

基础练习特效分级标注

为项目中 10 个特效按五级分类打标，并写出在 High 档下哪些会被裁剪、哪些必须保留，说明理由。

思考题反馈兜底

为什么单靠“同屏单位数”预测强度会失准？请举出一个单位数不多但 GPU 压力很大的场景，并说明帧时间反馈如何兜底。

进阶挑战软降级

把示例中的硬开关改造成带过渡的缩放/淡入淡出降级，并验证切换瞬间不再出现突变。

本章小结

  • 动态自适应按战斗强度实时调整表现，把帧预算集中到团战；强度信号结合单位数与帧时间反馈。
  • 特效五级分类决定裁剪顺序，承载玩法信息的功能提示特效不裁。
  • 粒子离线裁剪用 Alpha 分析 + 凸包生成有效顶点，运行时零成本降低 Overdraw。
  • 自适应状态机必须带滞回与切换冷却，并优先用软降级减少玩家感知。
