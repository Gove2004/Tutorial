03 主循环与进程系统

Rain World 没有用 Unity 的场景（Scene）来切换主菜单、游戏、过场，而是自建了一套“进程”系统：一个长生命周期的管理器持有若干可替换的进程对象，每个进程独立负责自己的逻辑与渲染。本章拆解这套系统的三个核心角色，以及进程之间如何切换。

3.1 三个核心角色

类性质职责
RainWorldMonoBehaviour挂载在场景中的 Unity 入口，持有 processManager、progression、options、shaders 等全局对象，由 Unity 每帧驱动
ProcessManager普通 C# 类持有当前主进程 currentMainLoop、旁支进程列表、进程切换队列、黑屏与对话框，负责进程的创建与切换
MainLoopProcess抽象类所有进程的基类，实现固定时间步长，定义 Update / GrafUpdate 等生命周期方法

驱动关系非常直接：Unity 每帧调用 RainWorld.Update()，后者在初始化完成后调用 processManager.Update(Time.deltaTime)，管理器再驱动当前进程。

// RainWorld.cs
if (processManagerInitialized)
{
    processManager.Update(Time.deltaTime);
}

3.2 固定 40 FPS 时间步长

这是进程系统里最精巧的部分。游戏逻辑以固定频率 40 FPS 推进，与显示器刷新率无关；渲染则在两个逻辑帧之间插值。全部秘密在 MainLoopProcess.RawUpdate：

public virtual void RawUpdate(float timeDelta)
{
    if (processActive)
    {
        timeStacker += timeDelta;
        if (timeStacker > 0.25f)   // 防止掉帧严重时疯狂补帧
        {
            timeStacker = 0.25f;
        }
        int num = 0;
        while (timeStacker >= 1f / 40f && num < 2)
        {
            Update();
            timeStacker -= 1f / 40f;
            num++;
        }
        GrafUpdate(timeStacker);   // 用剩余时间做插值渲染
    }
}

逐行理解：

  • timeStacker 是时间累加器，把真实帧的 deltaTime 攒起来。
  • 每攒够 1/40 秒，就触发一次逻辑 Update()，并扣掉对应时间。
  • 一帧最多补 2 次（num < 2），且累加器封顶 0.25 秒，避免卡顿后“死亡螺旋”式地无限补帧。
  • GrafUpdate(timeStacker) 拿到的是不足一个逻辑步的剩余时间，归一化后正好落在 0 到 1/40 之间，用作插值系数。

为什么要固定步长

Rain World 的物理是自研的位置型积分，对更新频率极其敏感。固定步长能保证任何机器上的物理结果一致、可复现，这对生态模拟、存档确定性和竞速公平性都很重要。代价是高刷新率屏幕不会让逻辑更快，只是画面更平滑。

GrafUpdate 如何插值：渲染时用 timeStacker * 40f 得到 0~1 的插值系数，在 lastPos 与 pos 之间取值。这就是为什么 BodyChunk 要同时保存 lastLastPos、lastPos、pos 三个历史位置。

3.3 进程 ID 与进程工厂

进程的类型用 ProcessID 标识，它是一个 ExtEnum（可扩展枚举），因此模组可以注册自己的进程。原版定义了 30 多个进程，常见的有：

ProcessID对应进程类用途
MainMenuMainMenu主菜单
GameRainWorldGame游戏内主进程
InitializationInitializationScreen启动初始化画面
SleepScreen / DeathScreen / StarveScreenSleepAndDeathScreen睡眠、死亡、饿死画面
GhostScreen / KarmaToMaxScreenGhostEncounterScreen回声遭遇、业力提升
RegionSelect / OptionsMenuRegionSelectMenu / OptionsMenu区域选择、选项
SlideShowSlideShow过场幻灯片
FastTravelScreenFastTravelScreen快速旅行

新进程不是用反射创建的，而是在 PostSwitchMainProcess 里用一长串 if-else 工厂式分派：

if (ID == ProcessID.Game)
{
    currentMainLoop = new RainWorldGame(this);
}
else if (ID == ProcessID.MainMenu)
{
    currentMainLoop = new MainMenu(this, ...);
}
else if (ID == ProcessID.SleepScreen || ID == ProcessID.DeathScreen)
{
    currentMainLoop = new SleepAndDeathScreen(this, ID);
}
// ... 其余进程

3.4 进程切换的三阶段

进程切换不是瞬间完成的，而是借黑屏淡入淡出分阶段进行，确保旧进程被干净关闭、新进程被安全创建。完整流程如下：

flowchart LR
    A["请求切换
RequestMainProcessSwitch"] --> B["淡出 0→1
黑屏渐显"]
    B --> C["PreSwitch
关闭旧进程/释放资源"]
    C --> D["模组 finalization"]
    D --> E["PostSwitch
工厂创建新进程"]
    E --> F["淡入 1→0
黑屏消失"]

阶段一：请求与淡出

调用 RequestMainProcessSwitch 时，如果当前有对话框，请求会先进入 _processSwitchQueue 排队；否则直接进入 ActualProcessSwitch，记录 upcomingProcess 并启动黑屏。随后每帧 fadeToBlack 递增：

fadeToBlack += deltaTime / blackFadeTime;
if (fadeToBlack > 1f)
{
    PreSwitchMainProcess(upcomingProcess);
    processAfterModFinalization = upcomingProcess;
    upcomingProcess = null;
}

阶段二：PreSwitch，关闭旧进程

PreSwitchMainProcess 负责收尾：隐藏开发者界面、销毁附加可视化对象、根据情况调用 ShutDownProcess() 或 PauseProcess()、释放音频与 Futile 资源、重置输入处理器。

if (currentMainLoop.pauseProcessOnNextComplete)
{
    currentMainLoop.PauseProcess();
}
else
{
    currentMainLoop.ShutDownProcess();
}
if (!currentMainLoop.pauseProcessOnNextComplete && pendingProcess == null)
{
    soundLoader.ReleaseAllUnityAudio();
    AssetManager.HardCleanFutileAssets();
}

阶段三：模组 finalization 与 PostSwitch

切换黑屏期间会运行模组 finalization（让模组在新进程启动前完成初始化），完成后 PostSwitchMainProcess 用工厂创建新进程，随后 fadeToBlack 递减、黑屏移除，新进程开始运行。

为什么切换要夹在黑屏中间：旧进程销毁与新进程创建会产生大量资源释放与加载，若在画面可见时进行会出现对象凭空消失/出现。黑屏把这些“脏动作”全部遮住，同时给资源加载留出时间，是体验与稳定性的双重保障。

3.5 旁支进程与对话框

除了主进程，ProcessManager 还维护 sideProcesses 列表。旁支进程同样被 RawUpdate 驱动，但不占据主进程位置，典型代表：

  • MenuMicrophone：菜单环境麦克风/音频处理，进出游戏时按需增删。
  • Dialog 系列：对话框作为旁支进程独立运行，因此能浮在任意主进程之上。

对话框通过 dialogStack 管理，ShowNextDialog 在条件满足时把栈顶对话框取出并加入旁支进程。这也解释了为什么请求切换时若有对话框，切换要排队——避免对话框与进程切换互相干扰。

3.6 进程的生命周期方法

MainLoopProcess 定义了一组可重写的生命周期钩子，子类按需实现：

方法调用时机
Init进程创建后初始化
Update每个固定逻辑步（40 FPS）
GrafUpdate每个渲染帧，做插值
ShutDownProcess进程被彻底关闭时
PauseProcess / ResumeProcess进程被挂起（保留）/恢复时

注意 pendingProcess 机制：某些进程（如睡眠、死亡）可以被挂起保留而非销毁，恢复时通过 pendingProcess 直接拿回，避免重复构建。

3.7 常见陷阱

陷阱一：在 Update 里写与帧率相关的假设

Update 永远以 40 FPS 调用，不要在里面乘 Time.deltaTime，也不要假设它和渲染帧率一致。需要平滑表现的逻辑放到 GrafUpdate 并用 timeStacker。

陷阱二：误以为进程切换是同步的

调用 RequestMainProcessSwitch 后当前进程不会立刻停止，黑屏淡出需要若干帧。切换后要执行的逻辑不能写在调用点之后，应放进新进程的 Init，或利用进程提供的回调。

陷阱三：混淆 ShutDown 与 Pause

ShutDown 会销毁进程并释放资源，Pause 只挂起保留状态。判断该用哪个，看进程是否需要稍后原样恢复（如临时过场），错用会导致状态丢失或资源泄漏。

3.8 练习与思考

  1. 假设显示器在 144 Hz 下运行，结合 RawUpdate 说明：一帧渲染中 timeStacker 大约是多少？一帧内最多会触发几次 Update？
  2. 在 ProcessManager 中追踪一次从主菜单进入游戏的完整路径，写出依次经过的方法名与 fadeToBlack 的变化。
  3. 思考：若把 timeStacker 的 0.25 秒上限和“每帧最多补 2 次”去掉，在游戏严重卡顿（如掉帧到 5 FPS）时会发生什么？这两个保护分别解决什么问题？

本章小结

  • RainWorld 是 Unity 入口，ProcessManager 管理进程，MainLoopProcess 是进程基类，三者构成自驱动的进程系统。
  • 逻辑以固定 40 FPS 时间步长推进，GrafUpdate 用剩余时间插值，保证物理一致、画面平滑。
  • 进程 ID 是可扩展枚举，新进程在 PostSwitch 中工厂式创建。
  • 切换经淡出、PreSwitch 关闭、模组 finalization、PostSwitch 创建、淡入五阶段，黑屏遮住资源变化。
  • 旁支进程承载音频与对话框，进程可 ShutDown 或 Pause/Resume。
