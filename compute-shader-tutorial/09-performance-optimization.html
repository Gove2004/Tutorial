性能优化实战

你的 Compute Shader 跑对了，但不够快。怎么办？本章教你系统地分析性能瓶颈、定位热点、实施优化。内容包括 Warp 级分析、Bank Conflict 消除、指令级优化、Occupancy 调优和 Profiler 使用。

优化方法论：先测量，再优化

性能优化的第一原则：不要猜，测量。没有 Profiling 数据的优化只是在写小说。

优化流程：
1. 建立基准（Baseline）：当前实现的性能数据
2. Profiling：用工具定位瓶颈
3. 假设：你认为哪个环节最慢？
4. 测量验证：只优化你假设的那一环
5. 回归验证：确认确实提升了，没有引入新问题
6. 重复 2-5，直到达到目标性能

Warp 分析：理解 GPU 的真实执行

GPU 的调度单位是 Warp（32 线程），不是线程，不是 Group。优化必须从 Warp 层面理解。

Warp 状态机

每个 Warp 在任何时刻处于以下状态之一：

  [EXECUTING] ←── 正在执行指令（最好的状态）
       │
       ├──→ [MEM_WAIT] ── 等待内存返回（最坏的状态）
       │         │
       │         └──→ [EXECUTING]（数据到了）
       │
       └──→ [IDLE] ── 没有指令可执行（Warp 被调度器丢弃）
                 │
                 └──→ [EXECUTING]（下一个 Warp 被激活）

GPU 的性能取决于：有多少 Warp 处于 EXECUTING 状态。
理想：所有 SM 的所有 Warp 都在 EXECUTING。
现实：很多时间在 MEM_WAIT 和 IDLE 之间摆动。

通过 Warp 效率诊断问题

Warp 状态可能的原因优化方向
IDLE 过高Occupancy 不足，SM 上 Warp 太少增加每组线程数，减少寄存器使用
MEM_WAIT 过高全局内存访问过多，缓存命中率低用 Shared Memory，合并内存访问
STALL_BRANCH 过高分支发散重构代码消除分支，用数学函数替代
STALL_MEM_DEPENDENCY 过高指令依赖链太长增加指令级并行，用不同线程处理不同数据

Bank Conflict 深度分析

Bank Conflict 是 Shared Memory 最常见的性能陷阱。让我们用一个具体例子量化它的代价。

Bank Conflict 的代价

假设 32 Banks，每 Bank 每次服务 1 个请求：

无冲突：32 个线程同时访问 32 个不同 Bank
  → 1 个事务完成，32 周期

2 路冲突：32 个线程访问同一 Bank 的不同地址
  → 32 次访问被分成 16 组，每组 2 个线程
  → 2 个事务完成，64 周期（2x 慢）

32 路冲突：32 个线程访问同一个 Bank 的同一地址
  → 虽然地址相同可以广播，但如果地址不同：
  → 32 个事务完成，1024 周期（32x 慢）

检测 Bank Conflict

Nsight Compute 提供 sm__throughput.st_bank_conflict_pipe_low.sum`pipe metric：

# 查询 Bank Conflict 率
ncu -k MyKernel --metrics sm__throughput.st_bank_conflict_pipe_low.sum ./my_app

# 如果返回值 > 0，说明有 Bank Conflict
# 理想值 = 0

消除 Bank Conflict 的实战技巧

// ❌ 有冲突：32 个线程访问 shared[0..31]，每个占 4 字节
// Bank 0: shared[0], shared[32], shared[64]...
// Bank 1: shared[1], shared[33], shared[65]...
// Warp 0 的 32 个线程访问 shared[0..31] → 每个 Bank 1 次访问 → 无冲突 ✅

// 但是！如果访问模式是 shared[tid * 2]：
// 线程 0 → shared[0] (Bank 0)
// 线程 1 → shared[2] (Bank 1)
// 线程 2 → shared[4] (Bank 2)
// ...
// 线程 16 → shared[32] (Bank 0) ← 和线程 0 冲突！
// 线程 17 → shared[34] (Bank 1) ← 和线程 1 冲突！
// → 16 路 Bank Conflict！

// ✅ 修复：加 padding
SharedMemory float shared[32][33];  // 每行 33 个 float
// 线程 i 访问 shared[i][0]
// 线程 i+16 访问 shared[i+16][0]
// 偏移 = (i+16) * 33 = i*33 + 528
// 528 % 32 = 16 → 不同 Bank，无冲突

Occupancy 调优

Occupancy = 一个 SM 上实际驻留的 Warp 数 / 最大可能的 Warp 数。高 Occupancy 意味着更好的延迟隐藏。

限制 Occupancy 的因素

资源RTX 4090 上限/SM每个 Warp 消耗最大 Warp 数
Shared Memory164 KB取决于 Shader 声明164KB / sharedPerWarp
Registers65K / SMperThreadRegs × 3265K / (perThreadRegs × 32)
Block/SM最大 32 个 Block—32 × (threadsPerBlock / 32)

计算 Occupancy 的实战方法

// 假设：
// numthreads(256, 1, 1) = 256 线程 = 8 Warp
// 每个线程使用 64 个寄存器
// 每个 Warp 使用 64 × 32 = 2048 个寄存器
// SM 有 65536 个寄存器
// 最大 Warp 数 = 65536 / 2048 = 32 Warp
// 每个 Block 8 Warp → 最多 4 个 Block 同时驻留
// Occupancy = 4 × 8 / 32 = 100% ✅

// 但如果每个线程用 128 个寄存器：
// 每个 Warp 128 × 32 = 4096
// 最大 Warp 数 = 65536 / 4096 = 16 Warp
// 每个 Block 8 Warp → 最多 2 个 Block
// Occupancy = 2 × 8 / 16 = 100% ✅ (刚好填满)

// 如果每个线程用 256 个寄存器：
// 每个 Warp 256 × 32 = 8192
// 最大 Warp 数 = 65536 / 8192 = 8 Warp
// 每个 Block 8 Warp → 最多 1 个 Block
// Occupancy = 1 × 8 / 8 = 100% ✅
// 但只有一个 Block 时，如果一个 Block 在等内存，整个 SM 就 IDLE 了
// → 实际性能可能很差！
Occupancy ≠ 性能：100% Occupancy 是必要的，但不是充分的。如果你的 Shader 内存带宽饱和了，增加 Occupancy 只会增加上下文切换的开销。先解决内存瓶颈，再优化 Occupancy。

指令级优化

减少指令数

// ❌ 低效：重复计算
float result = sin(x) * sin(x) + cos(x) * cos(x);

// ✅ 高效：利用数学恒等式
float result = 1.0;  // sin² + cos² = 1

// ❌ 低效：多次除法
float a = x / divisor;
float b = y / divisor;
float c = z / divisor;

// ✅ 高效：除法是慢指令（~20 周期），换成乘法
float invDivisor = rcp(divisor);  // rcp ≈ 7 周期
float a = x * invDivisor;
float b = y * invDivisor;
float c = z * invDivisor;

用数学函数替代分支

// ❌ 分支：导致 Warp 发散
if (x > 0)
    result = x;
else
    result = -x;

// ✅ 无分支：abs() 是单指令
result = abs(x);

// ❌ 分支
if (x > threshold)
    result = 1.0;
else
    result = 0.0;

// ✅ 无分支：step() 或 smoothstep()
result = step(threshold, x);

利用 Warp-level 原语（SM 6.0+）

// WaveReadLaneAt：Warp 内线程间交换数据（无 Shared Memory）
// 比 Shared Memory + Barrier 快得多

[numthreads(32, 1, 1)]  // 正好一个 Warp
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    float local = sharedData[tid.x];

    // 广播 local 到 Warp 内所有线程
    // 比 GroupMemoryBarrier + 每个线程读更快
    float broadcast = __shfl_sync(0xFFFFFFFF, local, 0);

    // SM 6.0+ HLSL 等效：
    // 用 WaveActiveAllEqual / WaveReadLaneFirst 等
}

内存访问模式优化

合并内存访问（Coalesced Access）

全局内存访问的效率取决于 Warp 内线程的访问模式：

访问模式内存事务效率
线程 i 访问地址 i（连续）1 个事务100% ✅
线程 i 访问地址 i×2（跨步 2）2 个事务50%
线程 i 访问地址 random()（随机）32 个事务3% ❌
 
// ❌ 随机访问：每个线程访问全局数组的不同位置
uint idx = hash(tid.x);  // 哈希函数 → 随机索引
result[tid.x] = globalArray[idx] * 2;

// ✅ 顺序访问：每个线程访问连续位置
result[tid.x] = globalArray[tid.x] * 2;

// ⚠️ 有时随机访问不可避免：如何用 Shared Memory 缓解？
// 1. 每个线程先把随机读的数据加载到 Shared Memory
// 2. 在 Shared Memory 中做重排（Sort/Transpose）
// 3. 从 Shared Memory 顺序读取

用 Texture 缓存做随机读优化

如果随机读的访问模式有空间局部性（相邻线程读相近的地址），用 Texture SRV 而非 Buffer SRV。Texture 缓存针对空间局部性做了优化：

// Texture2D 有专用的 L1 纹理缓存
// 对于空间局部性好的随机访问，Texture SRV 比 Buffer SRV 快 2-4x
Texture2D<float4> dataTexture : register(t0);

// 线程 (x, y) 读 dataTexture[int2(x, y)]
// 线程 (x+1, y) 读 dataTexture[int2(x+1, y)]
// → 空间局部性好 → Texture 缓存命中率高

Profiler 实战：一个完整的优化案例

让我们用真实的 Profiling 数据演示完整的优化流程：

项目：1024×1024 图像的 5×5 高斯模糊

【第 0 轮】基线性能：
  PIX 报告：
  - Dispatch 时间：12.4 ms
  - Instruction Throughput：1.8（>1.0，说明有 stalls）
  - Warp State：MEM_WAIT 45%, EXECUTING 40%, IDLE 15%
  → 诊断：内存等待占比太高

【第 1 轮】优化：加入 Shared Memory Tile
  - Dispatch 时间：8.1 ms（↓35%）
  - Warp State：MEM_WAIT 20%, EXECUTING 70%, IDLE 10%
  → 改善显著，但还有空间

【第 2 轮】优化：Separable Blur（拆成水平+垂直）
  - Dispatch 时间：5.3 ms（↓35%）
  - Warp State：MEM_WAIT 12%, EXECUTING 82%, IDLE 6%
  → 采样次数从 25 降到 10

【第 3 轮】优化：用 rcp() 替代除法
  - Dispatch 时间：5.0 ms（↓6%）
  → 边际收益递减

结论：从 12.4ms 到 5.0ms，优化了 60%。
     主要收益来自 Shared Memory + Separable Blur。
     指令级优化只贡献了微小的改善。

优化检查清单

Compute Shader 性能检查清单

按优先级从高到低检查：

  1. 内存访问：是否合并了全局内存访问？是否用了 Shared Memory 减少全局读取？
  2. Bank Conflict：Nsight 报告有 Bank Conflict 吗？Shared Memory 布局有 padding 吗？
  3. 分支发散：Warp 内有分支吗？能用数学函数替代吗？
  4. Occupancy：寄存器使用是否太多？Shared Memory 是否太大限制了 Block 数？
  5. 指令效率：有没有可以用 rcp/abs/step 替代的操作？
  6. Barrier 频率：有没有不必要的 Barrier？Barrier 是否可以在循环外？
  7. Dispatch 开销：如果每次只 Dispatch 一小块数据，CPU 开销可能超过 GPU 收益

本章小结

  • 性能优化必须先 Profiling，后动手
  • Warp 状态分布（EXECUTING/MEM_WAIT/IDLE）是最直接的诊断指标
  • Bank Conflict 用 padding 消除，Occupancy 用寄存器/Shared Memory 调优
  • 数学函数替代分支是零成本优化
  • 合并内存访问比什么都重要
  • 优化收益递减——先解决大头问题
