项目管理与度量

项目管理不是"画甘特图、开周会"。它是在约束条件下交付价值的能力——约束包括时间、预算、人力、技术风险。好的项目管理让团队在有限的资源下做出最大的影响。

项目管理的三重约束

范围 (Scope) ╱ ╲ ╱ ╲ ╱ ╲ ╱ 质量 ╲ ╱──────────╲ ╱ ╲ ╱ 时间 ─── 成本 ╲ ╱ ╲ ─────────────────────────

三重约束（Iron Triangle）的核心思想：你不可能同时改变任何一个角而不影响其他两个。

  • 想加快进度？→ 要么加人（成本↑），要么砍功能（范围↓）
  • 想降低成本？→ 要么延长期限（时间↑），要么减少功能（范围↓）
  • 想加功能？→ 要么加时间，要么加钱

估算与排期

估算是一切计划的基础。但估算是软件工程中最难的事情之一——因为你既不了解任务的真实复杂度，也不了解团队的实际速度。

估算方法

方法做法精度适用场景
类比估算 跟类似项目对比 低（±50%） 早期规划、粗略估计
三点估算 最乐观 + 最悲观 + 最可能，加权平均 中（±25%） 单个任务的估算
敏捷故事点 相对估算（这个任务是那个任务的 2 倍大） 中（±20%） 迭代规划、Backlog 排序
Planning Poker 团队一起估算，讨论分歧 中高（±15%） 团队共识、知识共享

三点估算公式

期望值 E = (乐观 + 4 × 最可能 + 悲观) / 6
标准差 σ = (悲观 - 乐观) / 6

示例：
乐观：3 天
最可能：5 天
悲观：12 天

E = (3 + 4×5 + 12) / 6 = 5.83 天
σ = (12 - 3) / 6 = 1.5 天

结论：有 68% 的概率在 4.3 ~ 7.3 天内完成

敏捷估算：故事点与 Velocity

敏捷团队用故事点 (Story Points) 估算任务的相对复杂度，而不是绝对时间。然后用 Velocity（速率） 衡量每个 Sprint 能完成多少故事点。

Sprint 1: 完成 21 点
Sprint 2: 完成 19 点
Sprint 3: 完成 23 点
Sprint 4: 完成 20 点
─────────────────────
平均 Velocity ≈ 21 点/Sprint

剩余 Backlog: 140 点
预计 Sprint 数: 140 / 21 ≈ 7 个 Sprint
如果每个 Sprint 2 周 → 约 14 周
常见陷阱：把故事点直接等同于人天。故事点是相对复杂度，不是时间。一个 8 点的任务不一定是 4 点任务的两倍工作量——它可能在复杂度、风险和不确定性上都更高。

风险管理

风险管理不是"等出了问题再救火"，而是提前识别可能的风险，评估影响，制定应对策略。

风险矩阵

风险可能性影响等级应对策略
核心开发人员离职 中 极高 高 知识共享、文档化、交叉培训
第三方 API 变更 中 高 高 抽象接口层、准备备选方案
性能不达标 低 高 中 早期性能测试、性能基准
UI 设计稿反复修改 高 低 低 设计评审确认、冻结期

风险的四种应对策略

  • 规避 (Avoid)：改变计划消除风险。例如：不用新技术，用团队熟悉的方案。
  • 转移 (Transfer)：把风险转给别人。例如：买保险、签 SLA、用云服务代替自建。
  • 缓解 (Mitigate)：降低可能性或影响。例如：多做测试、加监控、写预案。
  • 接受 (Accept)：承认风险存在，准备应急资金/时间。适用于低概率低影响的风险。

敏捷看板 (Kanban Board)

看板是可视化管理工作流的工具。它的核心是限制在制品 (WIP, Work In Progress)——一次只做少数的几件事。

Kanban Board 待办 (Backlog) 进行中 (Doing) 已完成 (Done) ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Ticket 1 │ │ Ticket 3 │ │ Ticket 5 │ │ Ticket 2 │ ──→ │ Ticket 4 │ ──→ │ Ticket 6 │ │ Ticket 3 │ └──────────┘ └──────────┘ │ Ticket 4 │ WIP ≤ 2 交付给用户 │ Ticket 5 │ └──────────┘ WIP 限制：每列最多 2 个任务

限制 WIP 的好处：减少上下文切换，提高交付速度。当"进行中"的列满了，团队成员就不能再接新任务，而是要先帮别人完成已有的任务。

代码度量 (Code Metrics)

度量是"用数据驱动决策"的基础。代码度量帮助我们客观地评估代码质量，而不是凭感觉说"这段代码写得不错"。

核心代码度量指标

指标定义健康范围说明
圈复杂度 线性独立路径的数量 ≤ 10（函数） 复杂度越高，越难测试和理解
代码行数 文件的物理行数 ≤ 300（文件） 文件太长通常意味着职责过多
耦合度 与其他模块的依赖数量 越少越好 高耦合意味着改一处动全身
圈复杂度 函数/类的圈复杂度之和 类 ≤ 50 类的方法太多也意味着职责过多
测试覆盖率 被测试覆盖的代码比例 ≥ 80% 但不是越高越好——关注有意义的覆盖

圈复杂度详解

圈复杂度 (Cyclomatic Complexity) 衡量的是一个函数的"分支数量"。每增加一个 if/for/while/catch，复杂度 +1。

# 圈复杂度 = 1（没有分支）
def calculate_sum(numbers):
    total = 0
    for n in numbers:
        total += n
    return total

# 圈复杂度 = 4（3 个分支）
def classify_score(score):
    if score >= 90:          # +1
        return "A"
    elif score >= 80:        # +1
        return "B"
    elif score >= 60:        # +1
        return "C"
    return "F"                # 基础 1

# 圈复杂度 = 8（7 个分支）
def process_order(order):
    if order.is_valid():     # +1
        if order.has_stock(): # +1
            if order.can_pay(): # +1
                if order.is_vip(): # +1
                    discount = 0.2
                else:
                    discount = 0.1
                payment = process_payment(order, discount) # +1
                if payment.success: # +1
                    ship(order)
    return None
    # 圈复杂度 = 8，建议拆分为多个小函数

团队度量

除了代码度量，还有一些团队层面的度量指标可以帮助你了解项目的健康度：

指标定义用途
燃尽图 (Burndown Chart) 剩余工作量随时间的变化 跟踪 Sprint 进度
累积流图 (CFD) 各状态累积的任务数 发现瓶颈（哪一列堆积了最多任务）
Lead Time 从创建到交付的总时间 衡量交付效率
Cycle Time 从开始开发到交付的时间 衡量开发效率
Bug 逃逸率 生产环境发现的 bug 数 / 总 bug 数 衡量测试质量

本章小结

  • 项目管理是在三重约束（范围、时间、成本）之间做权衡
  • 估算用相对方法（故事点）比绝对方法（人天）更准确
  • 风险管理要提前识别、评估、制定应对策略
  • 看板的核心是限制 WIP，减少上下文切换
  • 代码度量（圈复杂度、耦合度、覆盖率）帮助客观评估代码质量
  • 团队度量（Lead Time、Cycle Time、Bug 逃逸率）帮助优化流程
