02 总体架构鸟瞰

本章先不深入任何单个机制，而是给出一张完整的“地图”：Rain World 由哪些层、哪些子系统构成，它们如何继承、如何在一帧内协作。读完本章，你应该能在脑中建立起后续每一章的坐标。

2.1 分层架构总览

Rain World 在 Unity 之上自建了一整套框架。自底向上可以分成五层，外加一个横切所有层的模组系统：

    subgraph MOD["横切层：模组系统（ModManager / ExtEnum / MonoMod）"]

    L4["世界层：World · AbstractRoom · AbstractPhysicalObject（抽象 / 现实双层）"]
    L3["实体与 AI 层：PhysicalObject · Creature · ArtificialIntelligence · PathFinder"]
    L2["物理层：BodyChunk · BodyChunkConnection · 瓦片碰撞 · FPhysics"]
    L1["渲染与框架层：Futile · FStage · FNode · FSprite · FAtlas · IDrawable"]
    L5 --> L4 --> L3 --> L2
    L3 --> L1
    L2 --> L1

这张图里有两个关键事实需要先记住：世界层是“抽象/现实”双层的，而物理层与渲染层是分离的——物理决定位置，渲染只负责把位置画出来。

2.3 两条并行的继承主干

Rain World 最容易让新人困惑的地方，是同一个“东西”在抽象层和现实层各有一个类。理解这两条并行主干，是理解整个工程的钥匙。

抽象层继承树（逻辑状态）

flowchart TD
    AWE["AbstractWorldEntity"] --> APO["AbstractPhysicalObject"]
    APO --> AC["AbstractCreature"]
    APO --> AOBJ["其他抽象物品（如 AbstractDataPearl）"]
    AR["AbstractRoom"] -.持有.-> AWE
    W["World"] -.持有.-> AR

现实层继承树（物理与表现）

flowchart TD
    UD["UpdatableAndDeletable"] --> PO["PhysicalObject"]
    PO --> CR["Creature"]
    CR --> PL["Player"]
    CR --> LZ["Lizard"]
    CR --> SC["Scavenger / Vulture / Centipede ..."]
    PO --> ROCK["Rock / Spear / Weapon 等物品"]
    PO -.关联.-> GM["GraphicsModule（表现对象）"]
    CR -.关联.-> AI["ArtificialIntelligence（决策对象）"]

核心概念：抽象对象与现实对象的双向绑定

每个 AbstractPhysicalObject 通过 realizedObject 字段引用它的现实对象；每个 PhysicalObject 通过 abstractPhysicalObject 字段反向引用。房间被加载时调用 Realize() 生成现实对象，房间被卸载时调用 Abstractize() 把状态收回抽象层。两者是同一份逻辑实体在不同“分辨率”下的两种形态。

2.4 一帧的生命周期

把驱动链从 Unity 一路追到具体对象，一帧的完整生命周期如下。这是一条固定的调用链，后续所有章节的细节都挂在这条链上：

sequenceDiagram
    participant U as Unity 引擎
    participant RW as RainWorld.Update
    participant PM as ProcessManager.Update
    participant ML as MainLoopProcess.RawUpdate
    participant RO as Room / 实体
    U->>RW: 每帧调用（Time.deltaTime）
    RW->>PM: processManager.Update(deltaTime)
    PM->>ML: currentMainLoop.RawUpdate(dt)
    Note over ML: 时间累加器，按 40FPS 触发
    ML->>ML: Update()（逻辑，可多次）
    ML->>RO: 抽象房间/世界/房间/实体依次更新
    ML->>ML: GrafUpdate(timeStacker)（插值渲染）
    PM->>PM: sideProcesses 各 RawUpdate（音乐/对话框等）

这里有两个值得强调的设计：一是逻辑更新（Update）与渲染更新（GrafUpdate）分离，渲染时用 timeStacker 在前后两帧位置之间插值，保证画面平滑；二是主进程与旁支进程并存，音乐、对话框等作为 sideProcess 独立更新，不依附于当前主进程。

2.5 贯穿全局的五条设计哲学

把具体机制暂时抛开，Rain World 的所有代码几乎都在反复体现下面五条原则。先建立这个认知，后面读代码时会不断“对上号”。

哲学一：双层世界，离屏不暂停

世界不是以玩家所在房间为边界存在的。抽象层维护整个区域所有房间的实体状态，玩家看不见的生物依然在抽象层移动、觅食、避雨、迁徙。这让生态系统具有“真实在运转”的感觉，也让房间可以随时卸载以节省性能。

哲学二：组合优于继承

生物的能力几乎不靠深层继承，而靠组合：一只生物 = 物理对象 + 图形模块 + AI 对象 + 寻路器 + 状态对象，AI 内部再组合十几个 AIModule。新增能力通常是新增/替换一个模块，而不是改继承树。这也是 DLC 能在不破坏原版的前提下大量扩展的原因。

哲学三：数据与表现分离

物理层只算位置和速度，GraphicsModule 只读这些数据去画精灵，两者通过接口（IDrawable）解耦。同一份逻辑可以换不同的表现，表现层被剔除（culling）时逻辑照常运行。

哲学四：固定时间步长 + 分帧预算

逻辑以固定 40 FPS 推进，与渲染帧率解耦；昂贵的寻路、AI 地图计算被拆成小步，通过资源分配器（PathfinderResourceDivider）在所有生物间按帧分摊预算。这是用确定性换稳定性的典型工程取舍。

哲学五：模组优先，类型可扩展

所有类型 ID 都用可扩展枚举（ExtEnum）而非普通 enum，模组可以安全注册新值；连官方 DLC 都被实现成“预装模组”，走与第三方完全相同的加载管线。这套设计从一开始就把可扩展性当成了一等公民。

一个检验标准：当你读完后续章节，不妨回到本章，对照这五条哲学，看能否为每一条举出具体的类与方法。如果能，说明你已经从“记住名词”进阶到“理解设计”了。

2.6 练习与思考

  1. 用 IDE 类型层次图核对本章的两条继承主干，各找出 5 个本章未列出的具体子类（如某种生物、某种物品）。
  2. 在 RainWorld.cs 与 ProcessManager.cs 中找到 processManager.Update(Time.deltaTime) 与 currentMainLoop.RawUpdate 的调用点，亲手走一遍 2.4 的调用链。
  3. 思考：为什么 Rain World 选择“抽象/现实双层”而不是像多数 Unity 游戏那样只在玩家附近激活对象？这种设计在性能和复杂度上各有什么代价？（提示：结合房间卸载与生态连续性）

本章小结

  • 架构自底向上分为渲染框架、物理、实体 AI、世界、进程五层，模组系统横切所有层。
  • 抽象层与现实层是两条并行继承主干，通过 Realize / Abstractize 双向绑定。
  • 一帧由 Unity 驱动，经 RainWorld → ProcessManager → MainLoopProcess，逻辑与渲染分离、主进程与旁支进程并存。
  • 五条设计哲学：双层世界、组合优先、数据表现分离、固定步长与分帧预算、模组优先。
