04 - Unity DOTS 架构全景

DOTS（Data-Oriented Technology Stack）不是单一的技术，而是一套相互配合的技术栈。本章梳理 Unity 从 2015 年到 2026 年的 DOTS 演进历程，详解 Hub 架构中每个 Package 的职责，以及 World 隔离的设计哲学。

4.1 DOTS 的完整演进史

DOTS 不是一夜之间出现的，它是 Unity 团队花了近十年逐步构建的结果。理解这段历史对于把握 DOTS 的设计决策至关重要。

4.1.1 阶段一：前 DOTS 时代（2015 之前）

在 DOTS 出现之前，Unity 的游戏逻辑完全基于 MonoBehaviour。每个 GameObject 都是一个独立的对象，组件（Component）是挂载在 GameObject 上的类。

// 2015 年之前的典型 Unity 代码
public class PlayerController : MonoBehaviour
{
    public float speed = 5f;
    public int health = 100;

    void Update()
    {
        transform.position += transform.forward * speed * Time.deltaTime;
    }
}

这种模式的问题在实体数量增长时暴露无遗：

  • GC 压力：每个 MonoBehaviour 都是引用类型，创建 10000 个实体 = 10000 个 GC 对象。
  • 缓存不友好：GameObject 的数据分散在堆上，遍历时需要大量随机内存访问。
  • 单线程瓶颈：Update 模式天然串行，无法利用多核。
  • 虚函数开销：MonoBehaviour 是类，虚函数调用阻止了编译器内联优化。

4.1.2 阶段二：Entities 0.0 - 初步尝试（2017）

Unity 在 2017 年推出了第一个实验性的 Entities 包（版本号 0.0.x），引入了 Entity 和 Component 的概念，但 API 非常不稳定：

Entities 0.0 架构（2017）： [MonoBehaviour Authoring] │ ▼ [EntityManager.CreateEntity()] │ ▼ [ComponentDataObject<T>] ← 需要通过 GetComponentData() 读取 │ ▼ [ComponentSystem] ← 继承自 ComponentSystem │ ▼ [foreach (var entity in GetAllEntities())] ← 手动遍历 { var pos = GetComponentData<Position>(entity); // 没有 SIMD，没有 Burst，没有 Jobs }

这一版本的主要问题：

  • API 频繁变更，每次小版本更新都需要重写大量代码。
  • 没有 Burst 编译支持，System 运行在 Mono JIT 上。
  • 没有 Job System 集成，无法并行化。
  • ComponentDataObject 的存取方式繁琐且容易出错。

4.1.3 阶段三：Entities 0.11 - 第一次重大重构（2019）

2019 年，Unity 发布了 Entities 0.11，这是 DOTS 的第一个"可用"版本。引入了大量新 API 和架构改进：

Entities 0.11 架构（2019）： [IComponentData] ← 值类型，无虚函数 [SystemBase] ← 替代 ComponentSystem，更简洁的 API [BurstCompile] ← 可选的 Burst 编译支持 [IJobChunk] ← 新的并行 Job 接口 [EntityCommandBuffer] ← 统一的实体创建/销毁/修改 [Hybrid Renderer] ← 将 ECS 数据渲染到 GameObject 上 [Translation] ← 替代 transform，用 Position + Rotation 代替 [Baker<T>] ← 烘焙管线，将 MonoBehaviour 转为 IComponentData

关键改进：

  • IComponentData 取代 ComponentDataObject：不再需要通过 EntityManager 逐个存取组件，而是直接在 Job 中通过引用访问。
  • Burst 集成：System 可以用 [BurstCompile] 标记，享受 SIMD 优化。
  • IJobChunk：新的并行接口，直接操作 Chunk 级别的内存块。
  • EntityCommandBuffer：统一了实体创建/销毁/修改的操作方式。

4.1.4 阶段四：Entities 1.x - 稳定化（2021-2022）

2021 年发布的 Entities 1.x 系列标志着 DOTS API 的相对稳定。这一版本最大的变化是引入了 Entities 1.0 的版本号跳跃（从 0.17 直接到 1.0），原因是：

  1. API 已经稳定，不再需要 0.x 系列的"实验性"标识。
  2. Unity 决定将 DOTS 作为正式产品路线，而非实验性功能。
  3. 包管理器版本号需要反映成熟度。

1.x 版本的主要新增功能：

功能版本说明
ISystem / SystemAPI1.0新的 System 声明方式，更简洁的组件访问
Shared Component Data1.0优化相同组件数据的实体分组
Chunk Component Data1.0Chunk 级别的共享组件
Hybrid Renderer V21.2GPU Instancing 原生支持，性能大幅提升
Job Component System1.0IJobChunk 和 IJobParallelForTransform 标准化
Entities Graphics1.0GPU 端的材质/网格管理

4.1.5 阶段五：Entities 2.x - 当前形态（2023+）

2023 年开始，Unity 将 DOTS 生态统一到了 Entities 2.x 系列。这一代最重要的变化是：

为什么从 1.x 跳到 2.x？

Unity 在 2023 年底宣布将 DOTS 相关包统一到 2.x 版本号。主要原因包括：(1) 新的 ISystem 声明方式（非泛型、非继承）彻底改变了 System 的编写方式；(2) Job System 和 Burst 深度集成到核心管线；(3) Hybrid Renderer V2 成为默认渲染后端；(4) 多个子系统的 API 进行了不兼容的重构。

2.x 的核心变化：

// 旧版（1.x）System 声明
public partial class MySystem1x : SystemBase
{
    protected override void OnUpdate()
    {
        Dependencies.Complete();
        var ecb = commandBufferSystem.CreateCommandBuffer();
        foreach (var (pos, vel) in SystemAPI.Query<RefRO<Position>, RefRO<Velocity>>())
        {
            // 需要手动管理 ECB 生命周期
        }
        ecb.Playback(entityManager);
    }
}

// 新版（2.x）System 声明
public partial struct MySystem2x : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        // 不再需要 Dependencies.Complete()
        // ECB 自动管理
        foreach (var (pos, vel) in SystemAPI.Query<RefRO<Position>, RefRO<Velocity>>().WithAll<Health>())
        {
            pos.ValueRW += vel.ValueRW * SystemAPI.Time.DeltaTime;
        }
    }
}

4.2 Hub 架构：DOTS 的六大支柱

DOTS 不是一个单一的 Package，而是多个 Package 协同工作的生态系统。Unity 将这些 Package 统称为 "DOTS Hub"。

DOTS Hub 架构总览： ┌──────────────────────────────────────────────────────────────┐ │ Unity DOTS Hub │ ├────────────┬────────────┬────────────┬───────────────────────┤ │ Entities │ Burst │ Jobs │ Collections │ │ (ECS) │ (Compiler) │ (Scheduler)│ (Containers) │ │ │ │ │ │ │ World │ LLVM │ Thread │ NativeArray │ │ Archetype │ SIMD │ Pool │ NativeList │ │ Chunk │ Inlining │ Barrier │ NativeHashMap │ │ Query │ Vectorize │ Handle │ NativeQueue │ ├────────────┴────────────┴────────────┴───────────────────────┤ │ 扩展层（可选） │ │ Hybrid Renderer V2 │ Translation │ Baking │ Entities Graphics│ └──────────────────────────────────────────────────────────────┘

4.2.1 Entities（核心 ECS 引擎）

Entities 是 DOTS 的心脏，负责：

  • Entity 管理：创建、销毁、查询实体。Entity 只是一个 64-bit ID（Generation ID + Index）。
  • Component 存储：将 IComponentData 存储在 Archetype/Chunk 结构中。
  • Query 系统：基于组件类型组合的高效查询引擎。
  • System 生命周期：ISystem 的注册、排序和执行调度。
  • EntityCommandBuffer：异步的实体操作缓冲，用于 Job 安全的数据修改。

4.2.2 Burst（编译器）

Burst 是 Unity 定制的 JIT 编译器，它将 C# 代码（IL）转换为高度优化的原生机器码：

  • LLVM 后端：使用 LLVM 编译器基础设施进行代码生成和优化。
  • SIMD 向量化：自动将标量循环转换为 SIMD 指令（SSE/AVX/NEON）。
  • Loop Unrolling：自动展开循环以减少分支开销。
  • Function Inlining：激进的函数内联，消除函数调用开销。

4.2.3 Jobs（并行框架）

Job System 提供线程安全的并行执行框架：

  • JobHandle：依赖关系追踪，确保 Job 按正确的顺序执行。
  • NativeContainer：线程安全的容器基类，提供读写检查和 Dispose 管理。
  • Work Stealing：动态负载均衡，空闲线程自动从繁忙线程"偷取"工作。
  • Thread Pool：预创建的线程池，避免频繁创建/销毁线程的开销。

4.2.4 Collections（安全集合）

Collections 提供了专为 Job System 设计的线程安全集合类型：

  • NativeArray<T>：连续的、Job 安全的数组。
  • NativeList<T>：动态增长的列表。
  • NativeHashMap<K,V>：哈希表（注意：Job 中只支持单线程写入）。
  • NativeQueue<T>：队列。
  • NativeMultiHashMap<K,V>：支持一个 Key 对应多个 Value 的哈希表。

4.2.5 Mathematics

Mathematics 包提供了 SIMD 友好的数学类型和运算：

  • float3 / float4 / float3x3 / float4x4：SIMD 向量和矩阵类型。
  • Unity.Mathematics.noise：Perlin noise、Simplex noise 等程序化噪声。
  • Unity.Mathematics.random：PCG 随机数生成器。
  • Unity.Mathematics.math：SIMD 化的数学函数库（sin, cos, sqrt, lerp 等）。

4.3 Package 依赖关系图

DOTS 的各个 Package 之间存在严格的依赖关系。理解这些关系对于排查编译错误和版本冲突非常重要：

Package 依赖关系图（箭头表示"依赖"方向）： Entities 2.x ├── Burst (≥ 1.8.0) ← Entities 的 System 需要 Burst 编译 ├── Jobs (≥ 3.3.0) ← EntityCommandBuffer 内部使用 Job ├── Collections (≥ 3.3.0) ← NativeArray, ECB 等 ├── Mathematics (≥ 3.3.0) ← float3, float4x4 等类型 └── Hybrid Renderer V2 ← 可选，用于渲染 Burst ├── LLVM (内置) ← Burst 自带 LLVM 编译器 └── Il2Cpp Optimizer ← 与 IL2CPP 后端的集成 Jobs └── Collections ← NativeContainer 基类 Collections └── (无外部依赖) ← 纯 C# + intrinsics Mathematics └── (无外部依赖) ← 纯数学库，可独立使用
⚠️ 版本冲突：DOTS Package 之间版本耦合紧密。如果你手动更新了 Entities 包但没有同步更新 Burst/Jobs/Collections，可能会导致编译错误或运行时崩溃。始终通过 Package Manager 统一更新所有 DOTS 相关包。

4.4 World 概念与隔离

4.4.1 World 是什么

World 是 DOTS 中最高级别的隔离单元。每个 World 拥有自己独立的：

  • EntityManager：实体的创建、销毁和查询。
  • Scene：Entity 组成的逻辑场景。
  • System Set：注册的 ISystem 及其执行顺序。
  • Job Scheduler 上下文：Job 执行的调度环境。

不同 World 之间的 Entity 完全隔离——你不能在一个 World 中直接查询另一个 World 的 Entity。

// 创建和使用自定义 World
using Unity.Entities;

// 获取默认 World（Unity 启动时自动创建）
World defaultWorld = World.DefaultGameObjectInjectionWorld;

// 创建全新的 World
var customWorld = new World("MyCustomWorld");

// 在自定义 World 中创建 EntityManager
var entityManager = customWorld.GetOrCreateSystem<EntityManagerSystem>();

// 在自定义 World 中注册 System
customWorld.GetOrCreateSystem<MovementSystem>();
customWorld.GetOrCreateSystem<RenderingSystem>();

// 运行指定 World 的 Systems
customWorld.Update();

// 销毁 World（释放所有 Entity 和 System）
customWorld.Dispose();

4.4.2 为什么需要 World 隔离

World 隔离有几个重要的应用场景：

场景目的说明
多场景加载内存管理每个场景一个 World，卸载场景时直接 Dispose World
热重载开发效率在单独的 World 中测试修改后的 System，不影响主世界
仿真环境测试/AI训练并行运行多个 World，每个 World 是不同的仿真实例
服务端/客户端网络同步服务器 World 和客户端 World 独立运行
VR/AR渲染隔离左右眼分别在不同的 World 中渲染

4.4.3 World 的生命周期

// World 的完整生命周期示例
using Unity.Entities;
using UnityEngine;

public class WorldLifecycleExample : MonoBehaviour
{
    World simulationWorld;

    void Start()
    {
        // 1. 创建 World
        simulationWorld = new World("Simulation World");

        // 2. 注册 System
        var moveSystem = simulationWorld.GetOrCreateSystem<MovementSystem>();
        var renderSystem = simulationWorld.GetOrCreateSystem<RenderingSystem>();

        // 3. 创建 Entity
        var entityManager = simulationWorld.EntityManager;
        var archetype = entityManager.CreateArchetype(typeof(Position), typeof(Velocity));
        var entities = entityManager.Instantiate archetype, 100);

        // 4. 运行 Simulation
        simulationWorld.Update();  // 调用所有注册的 System
    }

    void OnDestroy()
    {
        // 5. 清理
        simulationWorld.Dispose();  // 释放所有 Entity、System、NativeArray
    }
}

4.5 从 0.x 到 2.x：为什么 Unity 要跳这么大版本号

Unity 从 Entities 0.17 直接跳到 1.0，后来又跳到 2.x，这背后有多重考量：

4.5.1 0.x 到 1.0 的变化（2021）

4.5.2 1.x 到 2.x 的变化（2023+）

📌 迁移建议：如果你正在维护旧版 0.x 或 1.x 的项目，Unity 提供了 Migration 工具可以帮助部分自动转换。但对于全新项目，直接从 2.x 开始是最明智的选择。

本章小结

本章我们梳理了 Unity DOTS 从 2015 年至今的完整演进历程。DOTS 不是某个单一的技术，而是 Entities（ECS 引擎）、Burst（编译器）、Jobs（并行框架）、Collections（安全集合）、Mathematics（数学库）以及一系列扩展 Package 构成的完整技术栈。理解每个 Package 的职责和它们之间的依赖关系，是使用好 DOTS 的基础。World 隔离机制则为多场景、热重载、仿真测试等高级场景提供了底层支持。
