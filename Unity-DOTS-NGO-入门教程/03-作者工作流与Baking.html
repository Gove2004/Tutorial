03　作者工作流与 Baking：GameObject 如何变成实体

第二章讲的实体和组件是运行时概念，但你不可能在编辑器里直接“摆放一个实体”——编辑器里只有 GameObject。Baking（烘焙）就是连接这两个世界的桥梁：你照旧用 GameObject 做内容，构建或进入播放模式时，引擎把它们转换成实体数据。这一章把整条工作流跑通。

3.1 为什么需要 Baking，而不是直接用场景

Unity 的核心场景系统与 ECS 运行时不兼容：场景里的对象是 GameObject，而 ECS 要的是 Chunk 里连续排列的组件数据。Unity 的解法是引入子场景（Sub Scene）——一个嵌套在普通场景里的特殊场景单元。子场景里的 GameObject 会经过 Baking 生成实体，运行时加载的是烘焙产物而不是原始 GameObject。

这样设计同时保住了两边的好处：

  • 编辑期：场景搭建、Inspector 调参、预制体、Gizmos 等成熟工作流全部保留；
  • 运行时：拿到的是高性能、可流式加载、可 Burst 处理的实体数据。

3.2 三个核心角色

Authoring Component（作者组件）

一个普通 MonoBehaviour，挂在子场景的 GameObject 上，字段在 Inspector 里暴露给策划和你自己调整。它只在编辑期存在，运行时不会被使用。

Baker（烘焙器）

继承 Baker<TAuthoring> 的类，重写 Bake 方法，负责把对应 Authoring 组件的数据翻译成一个或多个实体组件。子场景里每个 Authoring 实例都会触发一次 Bake。

Entity Baking Preview

选中子场景里的 GameObject 时，Inspector 底部出现的预览区，实时显示这个 GameObject 烘焙后会得到哪些组件，是验证 Baker 是否正确的第一现场。

3.3 环境准备

Unity 6.4 及以上版本中，Entities、Collections、Mathematics、Entities Graphics 已转为随编辑器分发的核心包。操作上：

  1. 使用 Unity 6.4 或更高版本新建项目（建议用 URP 模板，Entities Graphics 与 URP 配合最顺）。
  2. 打开 Package Manager，确认 Entities 与 Entities Graphics 已启用；若项目里没有，通过包管理器添加。
  3. 新建一个脚本文件夹，后续组件、Authoring、Baker、System 都放这里。建议用 Assembly Definition 管理程序集，引用 Unity.Entities、Unity.Transforms 等——这是 DOTS 项目的标准组织方式。
版本核对习惯：网上大量 DOTS 教程基于 0.5x 预览版或 Entities 1.x，API 差异极大（比如旧的 ConvertToEntity、Entities.ForEach 都已不存在）。本教程只使用 6.x 的现行 API，你在别处查资料时先确认版本号，避免把废弃写法抄进项目。

3.4 完整实操：会旋转的 Cube

步骤一：创建子场景

  1. 打开一个普通场景，在 Hierarchy 窗口右键。
  2. 选择 New Sub Scene → Empty Scene，命名为 ECS_Example 并保存。

步骤二：在子场景里放一个 Cube

选中子场景节点，通过 GameObject → 3D Object → Cube 创建一个 Cube。此时它还只是普通 GameObject，但引擎已经能对它做烘焙预览。选中 Cube，滚动到 Inspector 底部，能看到 Entity Baking Preview 区域，里面列出了默认烘焙出的组件（如 LocalToWorld 等）。

步骤三：定义运行时组件

using Unity.Entities;

// 运行时组件：只存数据，单位是弧度/秒
public struct RotationSpeed : IComponentData
{
    public float RadiansPerSecond;
}

步骤四：写 Authoring 组件与 Baker

using Unity.Entities;
using Unity.Mathematics;
using UnityEngine;

// 作者组件：编辑器里以“度/秒”为单位配置，符合日常直觉
public class RotationSpeedAuthoring : MonoBehaviour
{
    public float DegreesPerSecond = 360.0f;
}

// 烘焙器：每个 RotationSpeedAuthoring 实例触发一次
class RotationSpeedBaker : Baker<RotationSpeedAuthoring>
{
    public override void Bake(RotationSpeedAuthoring authoring)
    {
        // GetEntity 取得该 GameObject 对应的实体；
        // TransformUsageFlags.Dynamic 表示实体会移动，需要 LocalTransform 组件
        var entity = GetEntity(authoring, TransformUsageFlags.Dynamic);

        var component = new RotationSpeed
        {
            // 编辑期用角度，运行时用弧度，转换在烘焙期一次性完成
            RadiansPerSecond = math.radians(authoring.DegreesPerSecond)
        };

        AddComponent(entity, component);
    }
}

把 RotationSpeedAuthoring 挂到子场景里的 Cube 上，回到 Inspector 的 Entity Baking Preview，现在能看到实体多出了 RotationSpeed 组件，且 RadiansPerSecond 已经是换算后的弧度值（360 度约等于 6.28）。

步骤五：观察编辑器世界

Hierarchy 窗口里会出现 Editor World 节点，展开能看到当前烘焙出的实体，点开可在 Inspector 查看实体的运行时组件。这是不进入播放模式就能调试 ECS 数据的入口。

3.5 TransformUsageFlags：告诉引擎你需要变换做什么

GetEntity 的第二个参数决定烘焙器为实体生成哪些变换相关组件。常用取值：

TransformUsageFlags.ManualOverride
取值含义与典型用途
TransformUsageFlags.None不需要任何变换。纯逻辑实体（如生成器、全局配置、游戏状态）用它，避免无意义的变换组件。
TransformUsageFlags.Dynamic实体位置/旋转会变化，需要 LocalTransform。会移动的角色、子弹、Cube 都用它。
TransformUsageFlags.Renderable需要被渲染，实体将获得渲染所需的 LocalToWorld 相关数据。
你要完全手动控制变换组件，跳过自动处理，属于进阶用法。
新手高频错误：给不需要移动的逻辑实体用了 Dynamic，或给要移动的实体用了 None 导致 System 查不到 LocalTransform。写 Baker 时先问自己：这个实体需要渲染吗？会移动吗？再选标志。

3.6 Baker 里的其他常用操作

除了 GetEntity 和 AddComponent，Baker 还支持这些模式，后续章节会逐个用到：

  • 引用另一个 GameObject：对被引用的物体调用 GetEntity(otherGameObject) 拿到它烘焙后的实体，用于建立实体间引用（如生成器引用预制体）。
  • 添加 DynamicBuffer：用 AddBuffer<T> 烘焙可变长数据，第六章讲。
  • Blob 资产：用 AddBlobAsset 挂载不可变的大块原生数据，第六章讲。
  • 声明依赖：DependsOn 用于跟踪外部资源，资源变化时触发增量重新烘焙。

增量烘焙

Baking 分两种：全量烘焙处理整个子场景；增量烘焙只重新处理被直接修改或依赖发生变化的组件。这也是为什么在 Inspector 里改一个数值，预览能快速更新而不必重算全部。Baker 必须是确定性的——同样的输入永远得到同样的输出，不要在 Bake 里依赖随机数或运行时状态。

3.7 故障排查：Baker 不生效怎么办

展开：Entity Baking Preview 里看不到自定义组件

按顺序排查：① Authoring 脚本是否真的挂在子场景内部的 GameObject 上（放在子场景外的普通物体不会烘焙）；② Baker 类的泛型参数是否与 Authoring 类型一致；③ 控制台是否有编译错误，编译失败时整个烘焙不会更新；④ Bake 方法里是否正确调用了 AddComponent。

展开：进入播放模式后什么都没有

确认物体在子场景内且子场景已保存；检查子场景组件的加载设置；进入播放模式后在 Hierarchy 的运行时 World 节点里确认实体是否存在，以区分是“没烘焙出来”还是“烘焙出来但渲染/逻辑没工作”。

展开：改了 Baker 代码但预览不变

等待脚本编译完成后再看；若仍异常，可对该子场景触发重新烘焙或重启编辑器。先确认控制台没有遗留报错。

思考与练习

  1. 把 Cube 的 TransformUsageFlags.Dynamic 改成 None，观察 Entity Baking Preview 里少了哪些组件，解释原因。
  2. 在子场景里再放三个 Cube，其中两个挂 Authoring、一个不挂，预测进入播放模式后各实体的组件差异。
  3. 新建一个不渲染、不移动的“游戏配置”Authoring（比如全局敌人数量），为它写 Baker，选择正确的 TransformUsageFlags。
  4. 用自己的话描述 Authoring、Baker、运行时组件三者的职责边界，以及为什么 Authoring 不应该在运行时被引用。

本章小结

  • Baking 是编辑期 GameObject 到运行时实体的单向转换，发生在子场景内。
  • Authoring 是只在编辑期使用的 MonoBehaviour，Baker 负责把它的数据翻译成实体组件。
  • Entity Baking Preview 与 Editor World 是不进播放模式就能验证烘焙结果的工具。
  • TransformUsageFlags 决定实体获得哪些变换组件，按“是否渲染、是否移动”选择。
  • Baker 要保持确定性，增量烘焙依赖这一性质。
