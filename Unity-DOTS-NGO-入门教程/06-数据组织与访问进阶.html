06　数据组织与访问进阶

掌握了查询和 Job，这一章补齐真实项目里反复用到的一组数据工具：随机访问、可变长数据、零成本开关、不可变资产与引擎资源引用。每一个都对应一个明确的 OOP 旧需求，注意它们各自的替代关系。

6.1 ComponentLookup：跨实体随机访问

第四章在循环里用 SystemAPI.GetComponent 读目标实体，每次调用都有查找开销。批量场景下正确的工具是 ComponentLookup<T>——它像一张以实体为键的组件索引表，构造一次，反复查询：

using Unity.Burst;
using Unity.Entities;
using Unity.Mathematics;
using Unity.Transforms;

[BurstCompile]
public partial struct LookupMoveSystem : ISystem
{
    [BurstCompile]
    public void OnUpdate(ref SystemState state)
    {
        float dt = SystemAPI.Time.DeltaTime;

        // 只读 Lookup，true 表示只读，利于并行
        var targets = SystemAPI.GetComponentLookup<LocalTransform>(isReadOnly: true);

        foreach (var (transform, speed, target) in
            SystemAPI.Query<RefRW<LocalTransform>,
                          RefRO<MovementSpeed>,
                          RefRO<MoveTarget>>())
        {
            if (targets.TryGetComponent(target.ValueRO.Entity, out var targetTransform))
            {
                float3 direction = math.normalize(
                    targetTransform.Position - transform.ValueRO.Position);
                transform.ValueRW.Position += direction * speed.ValueRO.Value * dt;
            }
        }
    }
}

Lookup 也可以作为字段放进 IJobEntity，由安全系统自动处理依赖。判断实体是否拥有该组件用 HasValue(entity)；需要可选的读写引用时，用 TryGetRefRW / TryGetRefRO（旧的 GetRefRWOptional 已在 1.4 弃用）。

6.2 DynamicBuffer：实体上的可变长数据

OOP 里往对象上挂一个 List<T> 很自然，ECS 的对应物是 DynamicBuffer。先定义元素类型：

using Unity.Entities;

// 一个缓冲元素，比如伤害记录
public struct DamageEvent : IBufferElementData
{
    public float Amount;
    public int SourceId;
}

Baker 里通过 AddBuffer 初始化，运行时用 GetBuffer 取出并像列表一样操作：

// 运行时读写
var buffer = SystemAPI.GetBuffer<DamageEvent>(entity);
buffer.Add(new DamageEvent { Amount = 10f, SourceId = 2 });

for (int i = 0; i < buffer.Length; i++)
{
    // 处理 buffer[i]
}
buffer.Clear();

缓冲数据存在 Chunk 之外的原生内存，容量不足时自动重定位，因此不破坏 Chunk 的固定布局。它也能作为字段传入 Job 并行处理。典型用途：待处理事件队列、路径点、技能目标列表、帧输入历史。

6.3 Tag Component：零大小的标记

一个不含任何字段、实现 IComponentData 的 struct 就是 Tag 组件，占用零字节，只用于表达“是否属于某一类”，配合 WithAll/WithNone 过滤：

public struct AliveTag : IComponentData { }
public struct StunnedTag : IComponentData { }

用 Tag 替代 OOP 里的布尔标志位或类型枚举，查询可以直接按 Archetype 快速筛选，而不必逐个读取字段。但注意：增删 Tag 仍然是结构变更，频繁切换的状态应该用下面的 Enableable Component。

6.4 Enableable Component：零成本的开关

让组件同时实现 IEnableableComponent，就可以在不改变 Archetype、不移动 Chunk 数据的情况下启用/禁用它：

using Unity.Entities;

public struct Cooldown : IComponentData, IEnableableComponent
{
    public float Remaining;
}

// 切换启用状态，不触发结构变更
SystemAPI.SetComponentEnabled<Cooldown>(entity, false);
bool isActive = SystemAPI.IsComponentEnabled<Cooldown>(entity);
这是高频切换状态的首选方案。被禁用的组件默认不会出现在查询结果里，效果等同于“临时移除”，但没有任何数据搬迁成本。冷却、眩晕、行为开关、死亡标记等反复变化的状态都适合用它。

6.5 BlobAsset：不可变的原生数据资产

“Blob”指不可变（immutable）的非托管数据，一旦构建就只读，可被 Burst 访问、无 GC、可在多个实体间共享。典型用途是烘焙期确定的配置表、网格数据、曲线等。用 BlobBuilder 构建：

using Unity.Entities;

public struct EnemyConfig
{
    public BlobArray<float> HealthPerLevel;
    public float BaseSpeed;
}

public struct EnemyConfigReference : IComponentData
{
    public BlobAssetReference<EnemyConfig> Config;
}

在 Baker 中构建并挂载：

class ConfigBaker : Baker<EnemyConfigAuthoring>
{
    public override void Bake(EnemyConfigAuthoring authoring)
    {
        var builder = new BlobBuilder(Allocator.Temp);
        ref var root = ref builder.ConstructRoot<EnemyConfig>();

        var array = builder.Allocate(
            ref root.HealthPerLevel, authoring.HealthValues.Length);
        for (int i = 0; i < array.Length; i++)
            array[i] = authoring.HealthValues[i];
        root.BaseSpeed = authoring.Speed;

        var reference = builder.CreateBlobAssetReference<EnemyConfig>(
            Allocator.Persistent);
        builder.Dispose();

        AddBlobAsset(ref reference, out _);
        AddComponent(new EnemyConfigReference { Config = reference });
    }
}

运行时通过 Config.Value.HealthPerLevel[i] 读取。Blob 内部可用 BlobArray、BlobString、BlobPtr 组织嵌套结构。因为只读，它能安全地被并行 Job 同时访问。

6.6 UnityObjectRef：在实体上引用引擎资源

当实体确实需要引用材质、网格、ScriptableObject 等托管引擎对象时，用 UnityObjectRef<T> 而不是直接持有引用（直接持有会让组件变成托管组件，6.6 已弃用）：

using Unity.Entities;
using UnityEngine;

public struct VisualReference : IComponentData
{
    public UnityObjectRef<Material> Material;
    public UnityObjectRef<Mesh> Mesh;
}

通过 .Value 访问实际对象。注意：访问托管对象的那部分代码无法 Burst 编译，通常把这类引用限制在需要和引擎对象交互的少数系统里，纯模拟逻辑保持非托管。对于没有非托管等价物的类型（如 AnimationCurve），官方建议把它放进一个 ScriptableObject，再用 UnityObjectRef 引用。

6.7 Singleton：全局唯一数据

OOP 里的单例管理器，在 ECS 里表达为“只有一个实体拥有某组件”，用 Singleton API 访问：

// 读取唯一配置实体的数据
var config = SystemAPI.GetSingleton<GameSettings>();
var configEntity = SystemAPI.GetSingletonEntity<GameSettings>();

// Job 中也可通过 GetSingleton 取初始值

前提是该组件确实只存在于一个实体上，否则会报错。这比自己写一个静态 Instance 更符合 ECS 数据流，也能被安全系统跟踪。

6.8 实体预制体与运行时实例化

Baker 里把一个 GameObject 预制体转成实体预制体引用，运行时用 EntityManager 实例化：

public struct Spawner : IComponentData
{
    public Entity Prefab;
    public int Count;
}

// Baker 中：预制体本身用 Dynamic 标志
AddComponent(new Spawner
{
    Prefab = GetEntity(authoring.Prefab, TransformUsageFlags.Dynamic),
    Count = authoring.Count
});

// 运行时批量生成（主线程）
var spawner = SystemAPI.GetSingleton<Spawner>();
for (int i = 0; i < spawner.Count; i++)
{
    Entity instance = state.EntityManager.Instantiate(spawner.Prefab);
    // 设置初始位置等
}

在 Job 里不能直接调用 EntityManager，需要用 ECB 的 Instantiate，这正是第七章的内容。

6.9 工具选型速查

OOP 旧需求ECS 工具
按对象引用查另一个对象的数据ComponentLookup
对象上的 List 字段DynamicBuffer（IBufferElementData）
类型/分类布尔标记Tag Component（不常变）/ Enableable（常变）
只读配置表、共享资产BlobAssetReference
引用材质、SO 等引擎对象UnityObjectRef
单例管理器Singleton 组件实体

思考与练习

  1. 用 ComponentLookup 重写第五章练习里的并行移动 Job，把 Lookup 作为 Job 字段传入并标注只读。
  2. 实现一个技能系统：用 DynamicBuffer 存待释放的技能请求，系统每帧处理后 Clear。
  3. 给一个敌人设计“死亡”状态，分别用 Tag 增删和 Enableable Component 实现，对比两者是否触发结构变更。
  4. 用 BlobAsset 构建一张等级→血量配置表，在 System 中按等级读取，验证无 GC 分配。

本章小结

  • ComponentLookup 提供高效的跨实体随机访问，支持只读标记与 TryGet 系列方法。
  • DynamicBuffer 替代托管 List，数据存于 Chunk 外原生内存，可传入 Job。
  • Tag 是零字节分类标记；Enableable Component 在不搬迁数据的前提下做开关，是高频状态首选。
  • BlobAsset 是不可变、可共享、可 Burst 的只读资产；UnityObjectRef 安全引用托管引擎资源。
  • Singleton 组件实体替代静态单例；实体预制体经 Instantiate 生成。
