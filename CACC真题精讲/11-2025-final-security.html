第二届总决赛安全赛道：分布式广播 Q1–Q5

第二天是安全赛道，主题是分布式可靠广播，5 题共 500 分。 所有选手在同一份框架代码上实现协议：每个实例是一个节点，节点之间用 TCP 互发 JSON 消息。 题面来自选手「我就是蓬蒿人」的记录，属于 B 级，接口细节以现场为准。

与算法题的根本区别

算法题是「输入 → 输出」，这题是「多个进程互相发消息 → 系统级性质」。 评测不看某一次输出，而是检查整个执行过程是否满足安全性（safety）与活性（liveness）。 所以「本地跑通」不等于「能得分」——必须理解每条性质对应哪个断言。

框架接口

接口作用
broadcast(msg)把消息发给所有节点（应用层语义上的广播）
deliver(msg)向本地应用层「提交」一条消息（提交后不可撤销）
send_to(target, msg)点对点发送
send_to_all(msg)向所有节点发送（底层）
verify(msg)校验消息签名
SHA256(x)哈希
encode(m, n, msg) / decode(pairs)纠删码：把消息切成 n 块，任意 m 块可还原

应用层的回调签名是 (const std::string& msg_id, const json& data)。 每条消息必须包含 type（字符串）与 signature（字符串）， 发送前用「node_id + 内容/哈希」签名，接收方必须 verify 通过才处理。

题目已经把消息处理串行化了，所以不需要加锁；但多条消息可能并发传播， 去重和状态更新的顺序仍要自己保证。

Q1：Best-Effort Broadcast（尽力广播）

要满足的三条性质

  • 有效性：诚实节点 broadcast 的消息，最终被所有诚实节点 deliver。
  • 不重复性：同一条消息至多被 deliver 一次。
  • 不创造性：不得 deliver 从未被 broadcast 过的消息。

最简实现：

// 收到应用层 broadcast 请求
void onBroadcast(const string& id, const json& data) {
    // 记录「我已 broadcast 过」，用于去重
    if (broadcast_set.count(id)) return;
    broadcast_set.insert(id);
    json msg = makeMsg("send", id, data);   // 附带签名
    send_to_all(msg);
}

// 收到类型为 "send" 的消息
void onSend(const string& id, const json& data, const string& from) {
    if (!verify(msg)) return;               // 签名不合法直接丢弃
    if (delivered.count(id)) return;        // 已提交过，不重复
    delivered.insert(id);
    deliver(id, data);                      // 立即提交
}

Q1 在无拜占庭节点的前提下成立：消息不会丢（TCP），所以「发过就一定收到」。 一旦有恶意节点伪造消息，Q1 的三条性质就会崩——这正是 Q2 要解决的问题。

Q2：Authenticated Echo Broadcast（认证回声广播）

参数：n = 3f + 1，其中最多 f 个恶意节点。要求：即使有恶意节点，诚实节点也不会提交恶意消息， 且诚实节点之间最终达成一致。

协议流程

1

收到 send

若这条消息是第一次见到，向所有节点发一条 echo(msg, src)（带签名），且同一消息只 echo 一次。

2

收到 echo

按 (msg, src) 去重记录：echo_from_nodes[msg] 里 src 对应的槽位若为空，填入；否则忽略。

3

提交条件

当某条 msg 的 echo_from_nodes 中不同 src 的数量达到 2f + 1 时，deliver。

// 收到 send
void onSend(id, data, src) {
    if (!verify(msg)) return;
    if (echoed.count(id)) return;          // 同一消息只 echo 一次
    echoed.insert(id);
    send_to_all(makeEcho(id, data, src));
}

// 收到 echo
void onEcho(id, data, src) {
    if (!verify(msg)) return;
    // 每个 (msg, src) 只记录第一次
    if (echo_from_nodes[id].count(src)) return;
    echo_from_nodes[id].insert(src);

    if (!delivered.count(id) &&
        (int)echo_from_nodes[id].size() >= 2 * f + 1) {
        delivered.insert(id);
        deliver(id, data);
    }
}
为什么是 2f + 1，不是 f + 1

恶意节点可以伪造任意多份「echo」，但它不能伪造别人的签名。 如果有 2f+1 个不同 src 的合法 echo，那么其中至少有 f+1 个来自诚实节点—— 这保证了消息确实被足够多的诚实节点见过，而不是恶意节点自导自演。

选手踩过的坑

  • 重复 echo：同一条消息收到多次 send（不同节点转发），每次都 echo，会被评测判「不满足不重复性」或浪费带宽。必须按 msg_id 去重。
  • 槽位重复计数：同一个 src 发两次 echo，若都计数，2f+1 的门槛会被恶意节点用少量节点刷到。必须按 (msg, src) 去重。
  • 忘记 verify：直接把未验证的消息计入 echo 集合，等于允许伪造。

Q3：Byzantine Reliable Broadcast（拜占庭可靠广播）

Q2 有一个理论缺陷：如果恶意节点在不同的诚实节点那里凑出了不同的 2f+1 集合， 不同诚实节点可能提交不同的消息（或提交与不提交不一致）。 Q3 在 echo 之上再加一层 ready，把「提交」变成全体一致的决策。

1

echo 达到 2f+1 时，不提交，先发 ready

向所有节点广播 ready(msg)。注意：每个节点对同一 msg 只发一次 ready。

2

维护 ready 集合

收到 ready 后按 (msg, src) 去重记录。

3

提交条件

某 msg 的 ready 数量达到 f + 1 时，deliver。

// 收到 echo
void onEcho(id, data, src) {
    if (!verify(msg)) return;
    if (echo_from_nodes[id].count(src)) return;
    echo_from_nodes[id].insert(src);

    if (!readySent.count(id) &&
        (int)echo_from_nodes[id].size() >= 2 * f + 1) {
        readySent.insert(id);
        send_to_all(makeReady(id, data));
    }
}

// 收到 ready
void onReady(id, data, src) {
    if (!verify(msg)) return;
    if (ready_from_nodes[id].count(src)) return;
    ready_from_nodes[id].insert(src);

    if (!delivered.count(id) &&
        (int)ready_from_nodes[id].size() >= f + 1) {
        delivered.insert(id);
        deliver(id, data);
    }
}
两层门槛的含义
层门槛作用
echo2f + 1证明消息真的被足够多节点见过（排除伪造）
readyf + 1只要有 f+1 个节点认为「该提交」，就足以推动全体达成一致（f 个恶意节点无法阻止）

选手记录：Q1–Q3 全部 AC。这三题是「照着协议写」，真正的难点在于去重和 verify 的顺序。

Q4：优化认证回声广播

Q4 移除拜占庭节点（只剩崩溃故障），要求把每个节点占用的空间降下来。 题面给出参数 m：encode(m, n, msg) 把消息切成 n 块，任意 m 块可 decode 还原。

核心思路：纠删码

不再让每个节点保存完整消息，而是只保存自己那一块。需要还原时，向其他节点收集任意 m 块， 用 decode 拼回原文。空间从 O(消息大小) 降到 O(消息大小 / m)。

  • 签名用哈希：不要对原始数据签名（数据大，传输贵），用 SHA256(数据块) 或消息 id 签名。
  • 块与消息 id 绑定：每块要能对应回 msg_id，否则 decode 时凑不齐。
  • 重传策略：某些块丢失时，按块编号向邻居请求，凑够 m 块即可。

选手记录：Q4 十个测试点挂了 1 个。说明方向对，边界（比如 m = n、或块数不足时的重试）没处理干净。

Q5：优化拜占庭可靠广播

Q5 把 Q4 的纠删码叠加到 Q3 的拜占庭协议上，要求同时满足可靠性与空间约束。 因为块可能被恶意节点篡改，需要逐块验证——这就是 Merkle Tree 的用场。

1

构造 Merkle Tree

把消息切成 n 块，叶子是 SHA256(块)，逐层两两哈希到根。根哈希就是这条消息的「指纹」。

2

传播根哈希 + 块

签名只需覆盖根哈希（短），块可单独传输。接收方用 Merkle 证明验证「这块属于该根」。

3

凑够 m 块后 decode

还原完整消息，再走 Q3 的 echo/ready 流程。恶意节点提供的坏块会在 Merkle 校验时被丢弃。

选手记录：Q5「直接开 -O3 也过了 9/10」。这说明 Q5 的性能瓶颈主要在校验与哈希， 开优化能顶一部分；但最后一个点多半是某个边界条件没过。

安全题最容易被忽略的三件事
  • 先 verify 再入账：任何进入状态集合的消息，必须先通过签名校验。顺序反了，恶意节点可以污染状态。
  • 去重键要完整：(msg_id) 去重防重复提交，(msg_id, src) 去重防同一节点刷票，两者都要。
  • 不要假设消息有序：虽然框架串行化了回调，但不同消息的到达顺序仍然不确定，状态机要能处理任意顺序。

把五题串起来看

题故障模型空间核心机制分值
Q1无故障O(1)send + 去重提交~100
Q2f 个拜占庭O(1)echo 达 2f+1 提交~100
Q3f 个拜占庭O(1)echo 2f+1 → ready f+1 → 提交~100
Q4崩溃O(1/m)纠删码 + 哈希签名~100
Q5f 个拜占庭O(1/m)纠删码 + Merkle + Q3~100

分值是按 500 分均分的推测，选手记录没有给出每题的具体分值。

本章小结

  • 安全赛道考的是协议正确性，不是算法复杂度。
  • Q1 → Q2 → Q3 是逐步加层：去重提交 → echo 2f+1 → ready f+1。
  • Q4、Q5 用纠删码把空间降到 O(1/m)，Q5 再加 Merkle Tree 抵抗坏块。
  • 所有消息先 verify 再入状态集合，去重键要区分「消息」和「消息 + 发送者」。
