09 - Hybrid ECS 与 GameObject 集成

现实中的项目很少能完全使用 DOTS。大多数情况下，你需要在传统的 MonoBehaviour + GameObject 架构和 ECS 之间架起桥梁。本章深入讲解 Authoring + Baker 转换管线、Hybrid Renderer V2 的渲染机制，以及什么时候该用 Hybrid、什么时候该全 DOTS。

9.1 Authoring + Baker 转换管线

Authoring + Baker 是 Unity 提供的从 MonoBehaviour 到 IComponentData 的自动转换机制。它在场景烘焙（Bake）阶段将传统的 GameObject 组件"翻译"为 ECS 组件。

9.1.1 转换管线的三个阶段

Authoring → Baker → ECS 转换管线： 阶段 1: Authoring（编辑器阶段） ┌─────────────────────────────────────────────┐ │ MonoBehaviour 脚本 │ │ - 可序列化字段 [SerializeField] │ │ - 继承 IConvertGameObjectToEntity │ │ - 在 Inspector 中配置参数 │ │ - 运行时不存在（仅在编辑器中使用） │ └─────────────────────────────────────────────┘ ↓ Convert() 阶段 2: Baker（烘焙阶段） ┌─────────────────────────────────────────────┐ │ Baker<T> 类 │ │ - 继承 Baker<MyAuthoringComponent> │ │ - Override Bake() 方法 │ │ - 读取 Authoring 组件的数据 │ │ - 添加到 GameObjectEntity 的 Archetype │ │ - 可以添加多个 IComponentData │ │ - 可以添加 ISharedComponentData │ │ - 可以添加 ChunkComponentData │ └─────────────────────────────────────────────┘ ↓ 烘焙结果 阶段 3: ECS Runtime（运行时阶段） ┌─────────────────────────────────────────────┐ │ Entity + IComponentData │ │ - 纯数据，无行为 │ │ - 存储在 Archetype/Chunk 中 │ │ - 由 System 处理 │ │ - MonoBehaviour 脚本已被移除 │ └─────────────────────────────────────────────┘

9.1.2 完整的转换示例

// === 阶段 1: Authoring ===
// 这个脚本挂在 GameObject 上，在 Inspector 中配置参数
public class ShipAuthoring : MonoBehaviour, IConvertGameObjectToEntity
{
    [SerializeField] private float maxSpeed = 10f;
    [SerializeField] private float acceleration = 5f;
    [SerializeField] private int hitPoints = 100;
    [SerializeField] private MeshRenderer renderer;

    // Convert 在烘焙阶段被调用（不是在运行时！）
    public void Convert(Entity entity, EntityManager dstManager,
                        GameObjectConversionSystem conversionSystem)
    {
        // 将 MonoBehaviour 中的数据转换为 IComponentData
        dstManager.AddComponentData(entity, new ShipStats
        {
            MaxSpeed = maxSpeed,
            Acceleration = acceleration
        });

        dstManager.AddComponentData(entity, new Health
        {
            Current = hitPoints,
            Maximum = hitPoints
        });

        // 添加标签组件
        dstManager.AddComponent(entity);

        // 注意：不要在 Convert 中添加 MonoBehaviour
        // 也不要在这里创建 GameObject
    }
}

// === 阶段 2: Baker（可选，用于更复杂的转换） ===
// 大多数情况下 Convert 就够了，但 Baker 提供更精细的控制
public class ShipBaker : Baker<ShipAuthoring>
{
    public override void Bake(ShipAuthoring authoring)
    {
        // GetEntity() 返回当前 GameObject 对应的 Entity
        var entity = GetEntity(TransformUsageFlags.Dynamic);

        // 读取 Authoring 组件的数据
        AddComponent(entity, new ShipStats
        {
            MaxSpeed = authoring.maxSpeed,
            Acceleration = authoring.acceleration
        });

        // SharedComponent：相同值的实体共享数据
        if (authoring.renderer != null)
        {
            var material = authoring.renderer.sharedMaterial;
            AddSharedComponent(entity, new ShipMaterial
            {
                Material = material
            });
        }

        // ChunkComponent：整个 Chunk 共享的数据
        // 适用于同一批次的实体
        AddComponent(entity, new TeamId { Value = authoring.teamId });

        // 依赖转换：将 Transform 转换为 ECS 坐标
        // 这是由 Translation Component 自动处理的
        base.Bake(authoring);
    }
}

// === 阶段 3: 运行时组件数据 ===
public struct ShipStats : IComponentData
{
    public float MaxSpeed;
    public float Acceleration;
}

public struct Health : IComponentData
{
    public float Current;
    public float Maximum;
}

public struct ShipTag : IMarkerComponent { }

public struct ShipMaterial : ISharedComponentData
{
    public Material Material;
}

public struct TeamId : IComponentData
{
    public int Value;
}

9.1.3 TransformUsageFlags 详解

转换管线中的一个关键概念是 TransformUsageFlags，它决定了 GameObject 的 Transform 数据如何转换为 ECS 的坐标组件：

Flag含义适用场景
None不使用 Transform不需要位置的实体（如粒子特效）
NonStationary位置可变，旋转/缩放固定移动但不变形的物体
Stationary位置固定，不更新静态场景物体
RenderSync位置可变，与渲染同步需要渲染的实体
Dynamic位置、旋转、缩放都可变大多数游戏实体
 
// 选择合适的 TransformUsageFlags
var entity = GetEntity(TransformUsageFlags.Dynamic);
// 实体位置会在每一帧被 System 更新
// Hybrid Renderer 会读取最新的 Position 数据进行渲染

var entity2 = GetEntity(TransformUsageFlags.Stationary);
// 实体位置固定不变，不会添加到更新列表中
// 性能更好，但不能移动

var entity3 = GetEntity(TransformUsageFlags.RenderSync);
// 位置和旋转在 Simulation 阶段更新
// 在 Rendering 阶段同步到渲染管线
// 适合需要动画但不需要物理的物体

9.2 GameObjectUtility：桥接工具

除了 Authoring + Baker，Unity 还提供了一些工具类来桥接 GameObject 和 ECS：

9.2.1 GameObjectConversionUtility

// 手动将一个 GameObject 转换为 Entity
using Unity.Entities;
using Unity.Transforms;

// 方法 1：通过 ConversionScene
var scene = GameObjectConversionSettings.FromWorld(defaultWorld, null);
var conversionSystem = World.GetOrCreateSystem<GameObjectConversionSystem>();
var entity = conversionSystem.Convert(gameObject);

// 方法 2：直接创建 Entity 并添加组件
var entityManager = World.DefaultGameObjectInjectionWorld.EntityManager;
var entity = entityManager.CreateEntity();
entityManager.SetComponentData(entity, new Translation
{
    Value = new float3(0, 0, 0)
});
entityManager.SetComponentData(entity, new Rotation
{
    Value = quaternion.identity
});

// 方法 3：从 GameObject 复制 Transform 数据
var translation = gameObject.GetComponent<Translation>();
entityManager.SetComponentData(entity, new Translation
{
    Value = translation.Position
});

9.2.2 GameObjectEntity

GameObjectEntity 是一个特殊的组件，它将 GameObject 本身转换为 Entity。使用这个组件后，GameObject 的 Transform 会自动转换为 Translation/Rotation/Scale 组件：

// 添加 GameObjectEntity 组件后：
// 1. GameObject 的 Transform → Translation + Rotation + Scale
// 2. GameObject 的名称 → Entity Name 组件
// 3. GameObject 的子对象 → 通过 Parent 组件关联
// 4. 所有实现了 IConvertGameObjectToEntity 的组件 → 自动转换

// 这意味着你可以：
// - 在编辑器中用 GameObject 搭建场景
// - 运行时自动转换为 Entity
// - 用 ECS System 处理所有逻辑
// - 用 Hybrid Renderer 渲染

9.3 Hybrid Renderer V2

Hybrid Renderer V2 是 Unity 将 ECS 数据驱动传统 Unity 渲染管线的核心 Package。它允许你使用 ECS 的组件数据来控制 GameObject 的渲染。

9.3.1 渲染管线架构

Hybrid Renderer V2 架构： ┌──────────────────────────────────────────────────────────────┐ │ ECS System Layer │ │ - MovementSystem 更新 Position 组件 │ │ - AnimationSystem 更新 Bone 组件 │ ├──────────────────────────────────────────────────────────────┤ │ Hybrid Renderer V2 Layer │ │ │ │ 1. Extractor System │ │ - 读取所有实体的 Translation/Rotation/Scale │ │ - 读取 MeshRenderer / SkinnedMeshRenderer 组件 │ │ - 生成 RenderMesh / RenderSkinnedMesh 数据 │ │ │ │ 2. GPU Instancing │ │ - 相同材质的实体合并为 Instanced Draw Call │ │ - 10000 个相同模型的实体 → 1 个 Draw Call │ │ - 通过 RenderMeshArray 管理材质变体 │ │ │ │ 3. Submesh Mapping │ │ - 将 IComponentData 映射到 GPU Buffer │ │ - Per-instance data (Transform, Color, etc.) │ │ │ ├──────────────────────────────────────────────────────────────┤ │ Unity Render Pipeline (URP/HDRP/Built-in) │ │ - 接收 GPU Buffer 数据 │ │ - 执行实际的光栅化和着色 │ └──────────────────────────────────────────────────────────────┘ 关键优化： - GPU Instancing：相同材质合并 Draw Call - Frustum Culling：剔除视野外的实体 - LOD：根据距离自动切换细节级别 - Occlusion Culling：遮挡剔除

9.3.2 RenderMesh 与 RenderMeshArray

// RenderMesh：单个实体的网格渲染数据
using Unity.Rendering;

// 在 Baker 中设置
var renderMesh = new RenderMesh
{
    mesh = myMesh,
    material = myMaterial
};
AddComponent(entity, renderMesh);

// RenderMeshArray：批量管理的网格渲染数据
// 当有大量相同/相似网格的实体时，使用 RenderMeshArray 更高效
var array = new RenderMeshArray();
array.Add(meshA, materialA);
array.Add(meshB, materialB);
array.Add(meshC, materialC);

// 将 RenderMeshArray 赋值给实体
var renderMeshTag = new RenderMeshTag { Array = array };
AddComponent(entity, renderMeshTag);

// Hybrid Renderer 会自动将相同材质的实体合并为 Instanced Draw Call
// 10000 个相同材质的实体 → 1 个 Draw Call
// 10000 个不同材质的实体 → 10000 个 Draw Call（性能差）

9.4 Hybrid vs Full DOTS：决策矩阵

这是项目架构中最关键的决策之一。以下是详细的决策矩阵：

维度Full DOTSHybrid ECS
实体数量> 10,000< 10,000
性能要求极致性能，需要 SIMD性能一般，传统方式够用
团队技能熟悉 ECS/Job/Burst主要熟悉 MonoBehaviour
第三方插件少依赖或已适配 DOTS大量使用传统 Unity 插件
UI 系统自定义或用 UI Toolkit + ECSUGUI 直接可用
动画系统DOTS Animation PackageMecanim 直接可用
物理系统PhysX DOTS / Bullet3 DOTSUnity PhysX 直接可用
开发速度较慢（学习曲线陡）较快（渐进式迁移）
调试难度高（Burst 编译后难调试）中（可以用 Profiler 直接看）

9.4.1 渐进式迁移策略

如果你的项目已经从 MonoBehaviour 开始，可以采用渐进式迁移：

1

Phase 1：混合共存

保持大部分逻辑在 MonoBehaviour 中，将性能热点（如大量单位的移动计算）迁移到 ECS。使用 GameObjectEntity + Authoring 桥接。

2

Phase 2：系统级迁移

将整个 System（如战斗系统、AI 系统）迁移到 ECS。保留 UI、音频等非性能敏感部分在 MonoBehaviour 中。

3

Phase 3：全 DOTS

当性能成为瓶颈或实体数量达到数万级别时，考虑全面迁移到 DOTS。此时团队已经积累了 ECS 开发经验。

9.5 性能对比：Hybrid vs Full DOTS

以下是同一场景（10000 个移动的单位）在不同架构下的性能对比：

指标MonoBehaviourHybrid ECSFull DOTS
Update 耗时45 ms8 ms2 ms
Draw Call1000050（Instancing）50（Instancing）
GC Alloc/frame256 KB64 KB0 KB
内存占用120 MB85 MB45 MB
10 万实体 Update无法运行40 ms15 ms

关键观察：

  • Hybrid ECS 已经比纯 MonoBehaviour 快了 5-6 倍，因为 ECS System 的 SoA 布局和 Burst 编译带来了巨大收益。
  • Full DOTS 比 Hybrid 再快 2-3 倍，因为消除了 GameObject 和 MonoBehaviour 的开销。
  • Draw Call 方面 Hybrid 和 Full DOTS 相同，因为都使用了 Hybrid Renderer V2 的 GPU Instancing。
  • GC 方面 Full DOTS 为零，因为所有数据都是值类型和 NativeContainer。

9.6 常见问题与陷阱

9.6.1 Baker 中的常见错误

// ❌ 错误 1：在 Baker 中创建新的 GameObject
public class BadBaker : Baker<MyAuthoring>
{
    public override void Bake(MyAuthoring authoring)
    {
        var newGO = GameObject.CreatePrimitive(PrimitiveType.Cube);
        // 绝对不行！Baker 运行在编辑器线程，不能修改场景
    }
}

// ✅ 正确：只添加 ComponentData
public class GoodBaker : Baker<MyAuthoring>
{
    public override void Bake(MyAuthoring authoring)
    {
        var entity = GetEntity(TransformUsageFlags.Dynamic);
        AddComponent(entity, new MyComponentData { Value = authoring.value });
    }
}

// ❌ 错误 2：在 Convert 中访问运行时数据
public class BadAuthoring : MonoBehaviour, IConvertGameObjectToEntity
{
    public void Convert(Entity entity, EntityManager dstManager,
                        GameObjectConversionSystem conversionSystem)
    {
        // 这些在烘焙时是 null 或默认值！
        var health = GetComponent<Health>().Current;  // 可能是 0
        var pos = transform.position;                   // 可能是初始位置
    }
}

// ✅ 正确：使用 [SerializeField] 的编辑器数据
public class GoodAuthoring : MonoBehaviour, IConvertGameObjectToEntity
{
    [SerializeField] private float maxHealth = 100f;  // 编辑器中设置的值

    public void Convert(Entity entity, EntityManager dstManager,
                        GameObjectConversionSystem conversionSystem)
    {
        // 使用序列化字段的值
        dstManager.AddComponentData(entity, new Health { Current = maxHealth });
    }
}

9.6.2 Hybrid Renderer 的性能陷阱

// ❌ 陷阱 1：每个实体使用不同的材质
// 10000 个实体 × 10000 种材质 = 10000 个 Draw Call
foreach (var entity in entities)
{
    AddComponent(entity, new RenderMesh { Material = uniqueMaterial });
}

// ✅ 解决：使用 RenderMeshArray + GPU Instancing
var array = new RenderMeshArray();
for (int i = 0; i < 10; i++)
{
    array.Add(mesh, sharedMaterials[i]);
}
foreach (var entity in entities)
{
    AddComponent(entity, new RenderMeshTag { Array = array });
}
// 10000 个实体 × 10 种材质 = 10 个 Draw Call

// ❌ 陷阱 2：频繁修改材质
// 每次修改材质都会导致新的 Draw Call

// ✅ 解决：使用 MaterialPropertyBlock 或在 Shader 中通过参数控制变化

本章小结

Hybrid ECS 是现实世界中最重要的架构模式。它允许你在传统 MonoBehaviour 和 ECS 之间自由切换，用 Authoring + Baker 管线将 GameObject 自动转换为 Entity，用 Hybrid Renderer V2 将 ECS 数据驱动渲染管线。理解转换管线的三个阶段、TransformUsageFlags 的选择、以及 Hybrid vs Full DOTS 的决策矩阵，是做出正确架构决策的基础。
