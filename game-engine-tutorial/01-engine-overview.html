第一章：游戏引擎架构全景

学习目标：理解游戏引擎的本质——它到底是什么？和框架有什么区别？引擎内部有哪些子系统？这些子系统如何协作？本章建立全局认知，为后续章节深入每个子系统打下基础。

引擎 vs 框架 vs 库：本质区别

在开始编写引擎之前，我们必须明确一个根本问题：游戏引擎到底是什么？ 这个定义看似简单，但实践中经常有人把引擎、框架、库混为一谈。三者的本质区别在于控制权的归属。

维度 库（Library） 框架（Framework） 引擎（Engine）
控制权 你的代码调用库 框架调用你的代码（好莱坞原则） 引擎调度一切，你写内容
侵入性 低——只引入需要的部分 中——需要遵循框架约定 高——整个项目围绕引擎构建
典型例子 stb_image、glm SFML、Raylib Unreal、Godot、自研引擎
修改能力 不可修改 有限扩展 完全可控
学习曲线 陡峭（API 多） 中等（学框架范式） 极陡（学整个系统）

库：工具箱

库是最小的代码复用单元。你主动调用它，它被动返回结果。比如 stb_image.h 只有一个函数 stbi_load()，你传给它图片路径，它返回像素数据。你不需要理解它怎么解码 PNG，也不需要遵循任何约定——直接调用即可。库的粒度最小，但最灵活。

框架：骨架

框架反转了控制流。不是你的代码调用框架，而是框架调用你的代码。这就是著名的「好莱坞原则」：「不要给我们打电话，我们会给你打电话。」比如 SFML 框架会调用你编写的 update() 和 render() 函数。你需要按照框架的约定来组织代码，但框架处理了窗口创建、事件循环、生命周期管理等基础设施。

引擎：完整的工业流水线

引擎是最高层级的抽象。它不仅提供代码结构，还提供内容创作工具（编辑器）、运行时系统（渲染、物理、音频）、开发工作流（调试器、性能分析器）。在引擎中，你主要是在「使用」引擎提供的功能，而不是「指挥」引擎做什么。Unreal Engine 中你写蓝图或 C++ 脚本，引擎负责调度所有子系统。

核心区分标准：如果你可以随意替换某个部分而不影响其他部分，那是库；如果你需要遵循特定结构才能使用，那是框架；如果你几乎不能替换任何核心部分，只能在其生态内工作，那就是引擎。

引擎架构全景

一个完整的游戏引擎由多个子系统组成。这些子系统既独立又相互依赖，构成了引擎的「身体器官」。

渲染子系统

将场景图描述的世界转换为屏幕上的像素。这是引擎中最复杂、计算量最大的子系统，涉及 GPU 驱动、着色器编译、帧缓冲区管理、后处理效果等。现代引擎的渲染管线可以产生电影级画质，也可能仅为移动端做极简渲染——取决于目标平台。

物理引擎

模拟真实世界的物理行为：重力、碰撞、摩擦力、关节约束。物理引擎分为两个层次——碰撞检测（Collision Detection，判断物体是否相交）和刚体动力学（Rigid Body Dynamics，计算碰撞后的运动变化）。常用算法包括 SAT（分离轴定理）、GJK（Gilbert-Johnson-Keerthi）、EPA（Expanding Polytope Algorithm）。

音频系统

管理所有声音的播放、混合和空间化。3D 音频根据物体与摄像机的距离和方向动态调整音量、频率和多普勒效应。高级引擎还支持音频 occlusion（遮挡）和 reverb（混响），即声音穿过墙壁时会衰减，在洞穴中会有回声。

场景图

游戏世界中所有对象的层次化组织结构。场景图决定了物体的父子关系、局部坐标与世界坐标的转换、可见性裁剪等。它是连接渲染、物理、音频等子系统的「中枢神经」——所有子系统都从场景图中获取数据。

资源管理

负责所有外部数据的加载、缓存、引用计数和卸载。包括纹理、模型、音频、脚本等资源。优秀的资源管理器需要处理异步加载（避免卡顿）、资源流送（大场景按需加载）、热重载（开发时实时生效）等复杂问题。

输入系统

将硬件输入（键盘、鼠标、手柄、触摸屏）转化为引擎可理解的事件。跨平台输入系统需要处理不同操作系统的差异（如 Windows 的 WM_KEYDOWN 和 macOS 的 NSEvent），并提供输入映射（Input Mapping）机制让玩家自定义按键。

网络模块

处理多人游戏的网络通信，包括状态同步、预测、插值、延迟补偿等。对于单机游戏来说这个模块可能很简单，但对于在线游戏，网络模块的复杂度甚至超过渲染子系统。

单体架构 vs 模块化架构

引擎的子系统如何组织在一起，直接决定了引擎的可维护性、可扩展性和性能。主要有两种架构风格。

单体架构（Monolithic Engine）

所有子系统紧密耦合在一个代码库中。Unreal Engine 是典型代表——渲染、物理、音频、UI 全部在同一个仓库中，彼此直接调用。

优势 劣势
子系统间调用开销极小（直接函数调用） 修改一个子系统可能影响所有其他子系统
数据访问路径最短（共享内存） 编译时间长（全量编译）
API 设计一致，开发者体验好 难以剥离单个子系统用于其他项目
便于全局优化（如批量渲染 + 物理） 团队规模受限（代码冲突频繁）

模块化架构（Modular Engine）

每个子系统作为独立的模块存在，通过明确的接口通信。Godot Engine 是典型代表——渲染、物理、音频各自独立编译，通过信号（Signal）和节点（Node）机制通信。

优势 劣势
模块间松耦合，易于替换和升级 模块间接口调用带来额外开销
可按需启用/禁用模块 接口设计不当会导致模块间数据不一致
支持热加载单个模块 编译速度快但链接复杂度高
不同项目可复用相同模块 全局优化难度较大
架构选择的真相：没有绝对正确的架构。单体架构适合追求极致性能的大型项目（如 AAA 游戏），模块化架构适合需要快速迭代和多项目复用的中型项目。你的选择应该基于团队规模、项目周期和目标平台，而不是技术偏好。

游戏引擎发展史

理解引擎的历史演变，能帮助我们理解为什么现代引擎长这样。每一次技术突破都催生了新的架构范式。

1993

Doom Engine

Id Software 的 John Carmack 创造了 BSP（Binary Space Partitioning）树用于可见性裁剪，实现了世界上第一个真正意义的「引擎」——游戏逻辑与渲染完全分离。Doom 的 WAD 文件格式是现代 Asset Pipeline 的雏形。

1998

Unreal Engine 1

Epic Games 引入了可视化脚本系统（后来的 Blueprint）、材质编辑器、关卡编辑器。首次将「编辑器工具链」作为引擎的核心组成部分，而不仅仅是代码运行时代码。

2004

Source Engine

Valve 的 Source 引擎引入了物理系统（Havok 集成）、粒子系统、布料模拟。第一次将物理效果从纯数值计算变为玩家可直观感知的视觉表现。

2014

Unreal Engine 4

全面转向 PBR（Physically Based Rendering）渲染管线、蓝图可视化脚本、Lumen 全局光照的前身技术。UE4 确立了「功能即服务」（Features-as-a-Service）的引擎交付模式。

2022

Unreal Engine 5

Nanite（虚拟几何体）和 Lumen（动态全局光照）彻底改变了渲染方式。引擎开始拥抱「无限细节」的理念——不再需要 LOD、不再需要手动烘焙光照。

引擎选型指南

当你准备开发一个游戏项目时，面临的首要决策就是：用什么引擎？这没有标准答案，但有清晰的决策框架。

方案 适合场景 不适合场景 开发效率 性能上限
自研引擎 特殊需求（如 VR 定制、嵌入式设备）、学习目的 商业游戏、团队 < 5 人、时间紧迫 极低（6-18 个月搭建基础） 极高（完全针对项目优化）
Unreal Engine 3A 品质、FPS/TPS、开放世界 2D 游戏、超轻量级移动应用 高（蓝图降低门槛） 极高
Unity 跨平台、手游、独立游戏、VR/AR 超大型开放世界（内存压力） 很高（C# + 丰富 Asset Store） 中高
Godot 2D 优先、轻量级 3D、开源项目 高端 3D 画面、AAA 级渲染 高（GDScript 上手快） 中
自定义框架 特殊渲染需求、学术研究 常规游戏开发 极低 取决于实现

自研引擎的决策树

点击展开：你是否真的需要自研引擎？
  1. 你的项目有特殊的技术需求吗？
    • 否 → 使用现有引擎（UE/Unity/Godot）
    • 是 → 继续
  2. 这个特殊需求能被现有引擎的插件/扩展满足吗？
    • 是 → 使用现有引擎 + 定制插件
    • 否 → 继续
  3. 你有至少 2 名以上的资深 C++ 工程师吗？
    • 否 → 考虑 Unity 或 Godot（C# / GDScript 更友好）
    • 是 → 继续
  4. 项目周期是否允许 6 个月以上的基础设施搭建？
    • 否 → 使用现有引擎
    • 是 → 可以考虑自研引擎

结论：90% 的商业项目都不需要自研引擎。自研引擎的主要价值在于学习和控制力，而非生产力。

代码示例：引擎启动循环

让我们从一个最简单的引擎启动循环开始，理解引擎的基本运行模式。这个示例展示了引擎的核心结构——初始化、主循环、清理。

#include <memory>
#include <chrono>
#include <thread>
#include <functional>

// 引擎核心——管理所有子系统的生命周期
class Engine {
public:
    using Clock = std::chrono::steady_clock;
    using Duration = std::chrono::duration<float>;

    Engine(const char* name, uint32_t width, uint32_t height)
        : m_name(name), m_running(false), m_deltaTime(0.0f)
    {
        // 1. 按依赖顺序初始化子系统
        // 底层优先：内存 → 日志 → OS抽象
        m_memory = std::make_unique<MemoryManager>(128_MB);
        m_logger = std::make_unique<Logger>("engine.log");
        m_os = std::make_unique<OSAbstraction>();

        // 中间层：输入 → 资源 → 场景
        m_input = std::make_unique<InputManager>(*m_os);
        m_resourceMgr = std::make_unique<ResourceManager>(*m_memory);
        m_scene = std::make_unique<SceneGraph>();

        // 顶层：渲染 → 物理 → 音频
        m_renderer = std::make_unique<Renderer>(width, height, *m_os);
        m_physics = std::make_unique<PhysicsWorld>();
        m_audio = std::make_unique<AudioSystem>();

        m_logger->info("{} initialized successfully", m_name);
    }

    // 启动引擎主循环
    int run()
    {
        m_running = true;
        auto lastFrame = Clock::now();

        while (m_running) {
            // 计算帧时间（固定时间步长用于物理）
            auto now = Clock::now();
            m_deltaTime = std::chrono::duration_cast<Duration>(now - lastFrame).count();
            lastFrame = now;

            // 处理输入事件
            m_input->pollEvents();

            // 更新场景图（变换传播、脏标记清理）
            m_scene->update(m_deltaTime);

            // 物理模拟（在渲染前执行）
            m_physics->step(m_deltaTime);

            // 渲染（读取场景图和物理世界状态）
            m_renderer->render(*m_scene, *m_physics);

            // 音频更新（根据物体位置更新空间音频）
            m_audio->update(*m_scene);

            // 交换前后缓冲区
            m_renderer->swapBuffers();
        }

        return shutdown();
    }

private:
    int shutdown()
    {
        m_running = false;
        // 按初始化逆序销毁
        m_audio.reset();
        m_physics.reset();
        m_renderer.reset();
        m_scene.reset();
        m_resourceMgr.reset();
        m_input.reset();
        m_os.reset();
        m_logger.reset();
        m_memory.reset();
        m_logger->info("{} shut down cleanly", m_name);
        return 0;
    }

    std::string m_name;
    bool m_running;
    float m_deltaTime;

    // 子系统指针（实际项目中用智能指针或对象池）
    std::unique_ptr<MemoryManager> m_memory;
    std::unique_ptr<Logger> m_logger;
    std::unique_ptr<OSAbstraction> m_os;
    std::unique_ptr<InputManager> m_input;
    std::unique_ptr<ResourceManager> m_resourceMgr;
    std::unique_ptr<SceneGraph> m_scene;
    std::unique_ptr<Renderer> m_renderer;
    std::unique_ptr<PhysicsWorld> m_physics;
    std::unique_ptr<AudioSystem> m_audio;
};

// 使用示例
int main()
{
    Engine engine("MyGameEngine", 1920, 1080);
    return engine.run();
}

关键设计要点

  • 初始化顺序：必须从底层到顶层。OS 抽象层最先初始化（因为其他子系统依赖它），最后销毁。
  • 主循环结构：输入 → 场景更新 → 物理 → 渲染 → 音频 → 缓冲交换。这个顺序很重要——物理必须在渲染前完成，因为渲染需要读取物理世界的位置数据。
  • Delta Time：每帧的时间差，用于使物理模拟和游戏逻辑与帧率无关。
  • 子系统依赖：渲染依赖场景图和物理世界，音频依赖场景图，输入不依赖任何其他子系统。

本章小结

本章核心知识点回顾：
  1. 引擎 vs 框架 vs 库：区别在于控制权的归属——谁调用谁。
  2. 引擎六大子系统：渲染、物理、音频、场景图、资源管理、输入。
  3. 单体 vs 模块化：没有最优解，只有最适合项目规模和需求的解。
  4. 引擎发展史：从 Doom 的 BSP 到 UE5 的 Nanite，每一次突破都改变了游戏规则。
  5. 引擎选型：90% 的项目应该使用现有引擎，自研引擎主要用于学习和特殊需求。
  6. 引擎启动循环：初始化 → 主循环（输入→场景→物理→渲染→音频）→ 清理。
