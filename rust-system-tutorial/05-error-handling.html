第五章：错误处理

在系统编程中，错误处理往往占据了代码量的 30%-50%。Rust 通过类型系统强制你在编译期处理所有可能的错误路径，这比运行时 panic 或静默忽略错误要可靠得多。本章将深入探讨 Rust 的错误处理模式、工具链和设计哲学。

为什么 Rust 的错误处理如此重要？

在 C 语言中，错误码被忽略是最常见的 bug 来源。在 C++ 中，异常虽然提供了统一的错误处理机制，但引入了运行时开销和 noexcept 规范的复杂性。Rust 用类型系统强制你处理每一个错误，同时保持零运行时开销。

5.1 Result vs Panic：何时使用哪个

Rust 有两种主要的错误处理策略：Result（可恢复错误）和 panic!（不可恢复错误）。选择的关键在于错误是否属于程序的正常控制流。

场景 使用 Result 使用 panic!
用户输入无效 ✅ 返回 Err ❌
文件不存在 ✅ 返回 Err ❌
网络请求超时 ✅ 返回 Err ❌
数组越界 ⚠️ 取决于上下文 ✅ 调试模式 panic
内部逻辑矛盾 ❌ ✅ unreachable!()
内存不足 ❌ ✅ alloc::handle_alloc_error() 
use std::num::ParseIntError;

// 可恢复错误：使用 Result
fn parse_port(input: &str) -> Result<u16, ParseIntError> {
    input.parse()
}

// 不可恢复错误：使用 panic
fn get_element_unchecked<T>(slice: &[T], index: usize) -> &T {
    if index < slice.len() {
        &slice[index]
    } else {
        panic!(
            "Index {} out of bounds for slice of length {}",
            index,
            slice.len()
        );
    }
}

// 内部逻辑错误：使用 unreachable!
enum Command {
    Start,
    Stop,
}

impl Command {
    fn execute(&self) -> bool {
        match self {
            Command::Start => true,
            Command::Stop => false,
        }
    }

    fn as_str(&self) -> &str {
        match self {
            Command::Start => "start",
            Command::Stop => "stop",
        }
    }

    // 如果枚举只定义了 Start 和 Stop，这里永远不可能到达
    fn debug_name(&self) -> &str {
        match self {
            Command::Start => "START",
            Command::Stop => "STOP",
        }
        // 编译器知道这是 exhaustive match，不需要 unreachable!
    }
}

5.1.1 panic! 的展开策略

Rust 的 panic 有两种处理模式：

模式 行为 适用场景 设置方式
Unwind（默认） 逐帧展开栈，调用 drop GUI 应用、服务器 Cargo.toml 中配置
Abort 立即终止进程 嵌入式、追求最小体积 panic = "abort" 
# Cargo.toml
[profile.release]
panic = "unwind"  # 或 "abort"

# 性能影响：abort 模式可以减小二进制文件大小约 5-10%
# 因为不需要 unwind 表（unwind tables）

5.2 thiserror：库作者的工具

thiserror 是一个 derive macro，用于简化自定义错误类型的定义。它是编写 Rust 库时的首选方案：

// Cargo.toml
// [dependencies]
// thiserror = "2"

use thiserror::Error;

#[derive(Error, Debug)]
pub enum NetworkError {
    #[error("connection timed out after {timeout_ms}ms")]
    Timeout { timeout_ms: u64 },

    #[error("failed to resolve DNS for {hostname}: {reason}")]
    DnsFailure { hostname: String, reason: String },

    #[error("HTTP error: status={status}, body={body}")]
    HttpError { status: u16, body: String },

    #[error(transparent)]
    Io(#[from] std::io::Error),

    #[error("invalid URL: {0}")]
    InvalidUrl(#[from] url::ParseError),
}

// 自动实现 Display（#[error(...)]）、Debug（#[derive(Debug)]）、
// Source（#[source]）和 From（#[from]）trait
impl NetworkError {
    pub fn is_timeout(&self) -> bool {
        matches!(self, NetworkError::Timeout { .. })
    }

    pub fn status_code(&self) -> Option<u16> {
        match self {
            NetworkError::HttpError { status, .. } => Some(*status),
            _ => None,
        }
    }
}

5.2.1 thiserror 的宏展开

理解 thiserror 做了什么有助于你更好地使用它：

// 你写的：
#[derive(Error, Debug)]
pub enum ParseError {
    #[error("not a number: {0}")]
    NotNumber(String),
}

// thiserror 展开为：
pub enum ParseError {
    NotNumber(String),
}

impl std::fmt::Debug for ParseError { ... }  // 自动生成

impl std::fmt::Display for ParseError {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        match self {
            ParseError::NotNumber(s) => write!(f, "not a number: {}", s),
        }
    }
}

impl std::error::Error for ParseError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        None
    }
}
为什么库要用 thiserror？：thiserror 的 #[error] 属性决定了 Display 的输出格式。库作者需要精确控制错误消息的国际化、版本稳定性等。thiserror 让你在定义错误类型时就确定这些信息，无需手动实现每个 trait。

5.3 Anyhow：应用代码的工具

anyhow 提供了灵活的错误包装能力，适合应用程序而非库：

// Cargo.toml
// anyhow = "1"

use anyhow::{Context, Result, bail};

async fn fetch_config(url: &str) -> Result<String> {
    // 使用 ? 自动包装错误
    let response = reqwest::get(url)
        .await
        .context(format!("failed to fetch config from {}", url))?;

    // 使用 .context() 添加上下文信息
    let body = response.text()
        .await
        .context("failed to read response body")?;

    // 使用 bail! 提前返回
    if body.is_empty() {
        bail!("config file is empty");
    }

    Ok(body)
}

// 链式上下文
fn read_and_parse(path: &str) -> Result<Config> {
    let content = std::fs::read_to_string(path)
        .with_context(|| format!("failed to read config file: {}", path))?;

    let config: Config = serde_json::from_str(&content)
        .with_context(|| "failed to parse config as JSON")?;

    Ok(config)
}

5.3.1 Context vs WithContext

方法 参数类型 错误消息 性能
.context(msg) impl Display 立即求值 无论是否有错误都会格式化
.with_context(f) impl FnOnce() -> S 延迟求值 仅在错误时调用闭包 
// ❌ 不推荐：即使成功也会格式化字符串
let result = do_something()
    .context(format!("operation failed at step {}", step_num))?;

// ✅ 推荐：只在失败时格式化
let result = do_something()
    .with_context(|| format!("operation failed at step {}", step_num))?;

5.4 错误传播模式

5.4.1 ? 运算符的展开

? 运算符在编译时被展开为 match 表达式：

// 使用 ? 的简写
fn read_file(path: &str) -> Result<String> {
    let content = std::fs::read_to_string(path)?;
    Ok(content)
}

// 等价的手写展开
fn read_file_expanded(path: &str) -> Result<String> {
    let content = match std::fs::read_to_string(path) {
        Ok(val) => val,
        Err(err) => return Err(err.into()),  // .into() 做类型转换
    };
    Ok(content)
}

// 注意：? 末尾的 ; 和没有 ; 的区别
fn example() -> Result<()> {
    let data = read_file("test.txt")?;  // 如果有错误，return Err(...)
    let data2 = read_file("test2.txt")?;  // 继续传播
    Ok(())
}

5.4.2 错误转换（Error Conversion）

// 将具体错误转换为通用错误
use std::io;
use std::num::ParseIntError;

fn parse_number(s: &str) -> io::Result<i32> {
    s.parse::<i32>()
        .map_err(|e: ParseIntError| io::Error::new(io::ErrorKind::InvalidInput, e))
}

// 或者使用 ? 自动转换（需要 From 实现）
fn parse_number_auto(s: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let n: i32 = s.parse()?;  // ? 自动调用 .into()
    Ok(n)
}

5.4.3 错误链（Error Chain）

当一个错误由另一个错误引起时，Rust 通过 std::error::Error::source() 方法建立错误链：

use thiserror::Error;

#[derive(Error, Debug)]
enum AppError {
    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),

    #[error("parse error: {0}")]
    Parse(#[from] std::num::ParseIntError),

    #[error("config error: {0}")]
    Config(String),
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = std::fs::read_to_string("config.txt")
        .map_err(|e| AppError::Io(e))?;

    let port: u16 = config.trim().parse()
        .map_err(|e: std::num::ParseIntError| AppError::Parse(e))?;

    println!("Port: {}", port);
    Ok(())
}

5.5 错误处理的性能考量

Rust 的 Result 类型在编译后与 C 风格的错误码（errno）具有相同的性能特征：

// Result 的内存布局（单字段变体优化）
// Ok(i32) 和 Err(std::io::Error) 在释放后大小相同

fn main() {
    println!("size of Result<i32, io::Error>: {}",
        std::mem::size_of::<Result<i32, std::io::Error>>());  // 16 字节
    println!("size of i32: {}", std::mem::size_of::<i32>());  // 4 字节
    println!("size of io::Error: {}", std::mem::size_of::<std::io::Error>());  // 12 字节
    // Result 大小 = max(4, 12) + discriminant = 12 + 4 = 16 字节
}

// 性能对比（10^9 次 Result 操作，Release 模式）：
// Result::Ok:  ~1ns（与直接返回值相同）
// Result::Err:  ~2ns（额外的一次分支预测）
// C errno:     ~1ns
// 差距：在现代 CPU 上几乎可以忽略

Result 的内存布局

enum Result<T, E> {
    Ok(T),
    Err(E),
}

内存布局（discriminant + 最大变体）：
┌────────────────────┬────────────────────┐
│ discriminant (1 byte) │  Ok: 0 / Err: 1   │
├────────────────────┼────────────────────┤
│ T (if Ok)          │  最多 8 字节 (SSA)  │
│ E (if Err)         │  最多 8 字节 (SSA)  │
└────────────────────┴────────────────────┘

SSA (Single Small Scalar Optimization):
当 T 或 E 是小标量类型时，直接嵌入 discriminant，
不需要额外包装。Result<u64, io::Error> 大小 = 16 字节。

5.6 自定义错误类型的设计原则

use thiserror::Error;

// 原则 1：错误类型应该反映领域模型
#[derive(Error, Debug)]
pub enum DatabaseError {
    #[error("connection failed: {0}")]
    Connection(#[from] std::io::Error),

    #[error("query execution failed: {0}")]
    Query(String),

    #[error("constraint violation: {constraint}")]
    ConstraintViolation { constraint: String },

    #[error("deadlock detected")]
    Deadlock,
}

// 原则 2：提供辅助方法
impl DatabaseError {
    pub fn is_recoverable(&self) -> bool {
        matches!(self, DatabaseError::Connection(_) | DatabaseError::Deadlock)
    }

    pub fn retry_after(&self) -> Option<std::time::Duration> {
        match self {
            DatabaseError::Deadlock => Some(std::time::Duration::from_millis(100)),
            _ => None,
        }
    }
}

// 原则 3：向上层暴露通用错误，向下层使用具体错误
// 库的公共 API 使用具体错误类型
// 应用层的 main 函数可以转换为 anyhow::Error
fn main() -> Result<(), Box<dyn std::error::Error>> {
    run().map_err(|e| e.into())
}

fn run() -> Result<(), DatabaseError> {
    let conn = connect("localhost:5432")?;
    let rows = conn.query("SELECT * FROM users")?;
    Ok(())
}

5.7 实战：完整的错误处理模式

use thiserror::Error;

#[derive(Error, Debug)]
enum CliError {
    #[error("configuration error: {0}")]
    Config(#[from] ConfigError),

    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),

    #[error("network error: {0}")]
    Network(#[from] NetworkError),
}

#[derive(Error, Debug)]
enum ConfigError {
    #[error("file not found: {path}")]
    FileNotFound { path: String },

    #[error("parse error at line {line}: {reason}")]
    Parse { line: usize, reason: String },
}

#[derive(Error, Debug)]
enum NetworkError {
    #[error("connection refused: {host}:{port}")]
    ConnectionRefused { host: String, port: u16 },

    #[error("timeout after {ms}ms")]
    Timeout { ms: u64 },
}

// 主函数：将所有错误转换为 anyhow::Error
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = load_config("config.yaml")
        .map_err(|e| CliError::Config(e))?;

    let client = NetworkClient::new(&config.host, config.port)
        .map_err(|e| CliError::Network(e))?;

    let data = client.fetch("/")?;
    println!("{}", data);

    Ok(())
}

5.8 本章小结

关键要点
  • Result vs panic：可恢复错误用 Result，不可恢复错误用 panic
  • thiserror：库作者的首选，轻量、编译快、类型安全
  • anyhow：应用代码的首选，灵活的上下文包装
  • ? 运算符：自动错误传播和类型转换（.into()）
  • 性能：Result 与 C errno 性能相当，现代 CPU 分支预测几乎零开销
  • 错误链：source() 方法连接相关错误，便于调试
