第二章：DNS 与网络层

在浏览器内部结构中，网络层扮演着"快递员"的角色——它负责把请求送到服务器，再把响应安全地送回来。但在这看似简单的过程中，隐藏着 DNS 解析、TCP 握手、TLS 加密、HTTP 协议等多个复杂环节。本章将逐一拆解。

2.1 DNS 解析：从域名到 IP 地址

DNS（Domain Name System）是将人类可读的域名（如 example.com）转换为机器可读的 IP 地址（如 93.184.216.34）的系统。没有 DNS，你每次访问网站都需要记住一串数字。

2.1.1 递归查询 vs 迭代查询

DNS 查询有两种模式，理解它们的区别对优化网络性能至关重要：


递归查询（Recursive Query）—— 浏览器发起的查询
─────────────────────────────────────────────────
浏览器                          本地 DNS 服务器
  │                               │
  │  "example.com 的 IP 是什么？"  │
  ├──────────────────────────────►│
  │                               │
  │  "IP 是 93.184.216.34"        │
  │◄──────────────────────────────┤
  │                               │
  ▼  浏览器拿到 IP，发起 HTTP 请求

本地 DNS 服务器需要自己完成后续的迭代查询（见下方）
            

迭代查询（Iterative Query）—— DNS 服务器之间的查询
─────────────────────────────────────────────────
本地 DNS 服务器 → 根服务器 → .com 权威服务器 → example.com 权威服务器
    │                  │               │                    │
    │  "我不知道"       │               │                    │
    │─────────────────►│               │                    │
    │                  │ "找 .com"     │                    │
    │                  │──────────────►│                    │
    │                  │               │ "我不知道"          │
    │                  │               │───────────────────►│
    │                  │               │                    │
    │                  │               │ "IP 是 93.184..."   │
    │                  │               │◄───────────────────┘
    │                  │               │
    │                  │◄──────────────┤
    │◄─────────────────┤               │
    │  最终结果         │               │
💡 为什么浏览器用递归查询？

递归查询让浏览器只需要发一次请求就能拿到结果。如果让每个浏览器都自己完成完整的迭代查询，那将是巨大的网络负担。递归查询的本质是将复杂性封装在 DNS 服务器层。

2.1.2 DNS 缓存层级

DNS 查询的结果会被缓存在多个层级，每一层都有各自的 TTL（Time To Live）：

缓存层级 典型 TTL 命中率 查询耗时
浏览器缓存 60s - 30min 高（同源域名复用） < 0.1ms
操作系统缓存 系统配置（通常 2-24h） 中高 ~0.5ms
路由器/ISP 缓存 TTL 值 中 5-30ms
公共 DNS（1.1.1.1 / 8.8.8.8） 自定义 TTL 中 10-50ms
权威 DNS 服务器 记录配置的 TTL N/A 20-100ms

2.1.3 CDN 与 DNS

CDN（内容分发网络）利用 DNS 的智能调度能力，将用户请求导向最近的服务器。当你的 DNS 查询到达权威服务器时，服务器会根据你的 IP 地理位置返回最近的边缘节点 IP。

# 使用 dig 命令查看 DNS 解析过程
$ dig example.com +trace
; <> DiG 9.18.12 <> example.com +trace
;; Got answer:
;; ->>>HEADER<<- opcode: QUERY, status: NOERROR
;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.		300	IN	A	93.184.216.34

# 查看 CDN 返回的不同 IP
$ dig cdn.example.com
;; ANSWER SECTION:
cdn.example.com.	60	IN	A	104.16.132.229  # 可能是边缘节点 IP

2.2 TCP 三次握手与四次挥手

DNS 解析得到 IP 地址后，浏览器需要建立 TCP 连接。TCP（Transmission Control Protocol）通过三次握手确保双方都能可靠地通信。


TCP 三次握手
────────────
客户端                          服务器
  │                               │
  │  SYN (seq=100)               │
  │──────────────────────────────►│
  │                               │  收到 SYN，分配资源
  │  SYN+ACK (seq=300, ack=101)  │
  │◄──────────────────────────────┤
  │                               │  收到 SYN+ACK
  │  ACK (seq=101, ack=301)      │
  │──────────────────────────────►│
  │                               │
  ▼  连接建立，可以开始传输数据

TCP 四次挥手
────────────
客户端                          服务器
  │                               │
  │  FIN (seq=100)               │
  │──────────────────────────────►│
  │                               │  收到 FIN，关闭写方向
  │  ACK (seq=300, ack=101)      │
  │◄──────────────────────────────┤
  │                               │  数据传完了
  │  FIN+ACK (seq=301, ack=101)  │
  │◄──────────────────────────────┤
  │                               │
  │  ACK (seq=101, ack=302)      │
  │──────────────────────────────►│
  │                               │
  ▼  连接完全关闭

2.2.1 为什么需要三次握手？

三次握手的根本原因是为了防止已失效的连接请求报文段突然又传送到了服务端，因而产生错误。

  1. 客户端 → 服务器：客户端发送 SYN 包，服务器收到后知道"客户端能发送，服务器能接收"。
  2. 服务器 → 客户端：服务器回复 SYN+ACK 包，客户端收到后知道"服务器能接收，客户端能发送"。
  3. 客户端 → 服务器：客户端回复 ACK 包，服务器收到后知道"客户端确认收到了我的 SYN+ACK"。

经过三次握手，双方都确认了彼此的收发能力，连接才算真正建立。

🚀 性能优化：TCP Fast Open (TFO)

TCP Fast Open 允许在三次握手的同时发送数据，将建立连接和发送第一个请求合并为一步。对于已知客户端的重复访问，可以将 RTT 减少一半。

2.3 TLS 1.3 握手：安全的加密通道

现代浏览器几乎都使用 HTTPS，这意味着在 HTTP 之前还需要完成 TLS 握手。TLS（Transport Layer Security）为数据传输提供加密和完整性保护。


TLS 1.3 握手（简化版，1-RTT）
─────────────────────────────
客户端                          服务器
  │                               │
  │  ClientHello                  │
  │  (支持的 cipher suites,       │
  │   key_share, ...)            │
  │──────────────────────────────►│
  │                               │
  │  ServerHello                  │
  │  (选择的 cipher suite,        │
  │   key_share, ...)            │
  │◄──────────────────────────────┤
  │                               │
  │  EncryptedExtensions          │
  │──────────────────────────────►│
  │                               │
  │  Certificate + ...            │
  │◄──────────────────────────────┤
  │                               │
  │  Finished                     │
  │──────────────────────────────►│
  │                               │
  ▼  加密通道建立，可以发送 HTTP 请求

TLS 1.2 需要 2-RTT，TLS 1.3 优化为 1-RTT

2.3.1 前向保密（Forward Secrecy）

TLS 1.3 强制使用前向保密（Perfect Forward Secrecy, PFS）。这意味着每次会话使用临时密钥交换（ECDHE），即使服务器的长期私钥在未来泄露，也无法解密过去的通信。

前向保密
即使长期密钥（如服务器 RSA 私钥）泄露，过去所有会话的通信内容也不会被解密。这是通过在每次握手时使用临时 Diffie-Hellman 密钥交换实现的。

2.4 HTTP 缓存策略

HTTP 缓存是浏览器性能优化的核心手段之一。合理的缓存策略可以减少 50%-80% 的网络请求量，显著提升页面加载速度。

2.4.1 强缓存（Force Cache）

强缓存阶段，浏览器直接使用本地缓存，完全不向服务器发送请求。控制强缓存的头部字段：

# 场景：静态资源（带 hash 的文件名）
Cache-Control: public, max-age=31536000, immutable
# public: 允许 CDN 和代理服务器缓存
# max-age=31536000: 缓存有效期 1 年（365 * 24 * 3600 秒）
# immutable: 浏览器在有效期内不会重新验证

# 场景：API 接口（需要实时数据）
Cache-Control: no-store
# 完全不缓存，每次请求都从服务器获取最新数据

# 场景：首页 HTML（短时间有效）
Cache-Control: max-age=60, must-revalidate
# 60 秒内使用缓存，过期后向服务器验证

2.4.2 协商缓存（Negotiated Cache）

强缓存失效后，浏览器向服务器发送请求，通过协商缓存决定是否使用本地副本：

Last-Modified / If-Modified-Since ETag / If-None-Match
原理 文件修改时间 文件唯一标识符（哈希值）
精度 秒级 字符级（精确匹配）
性能 服务器需要计算修改时间 服务器需要计算哈希值（略贵）
可靠性 低（1 秒内的修改无法区分） 高（几乎不会误判）
推荐 作为 ETag 的补充方案 ✅ 优先使用 
# 协商缓存流程
# 第一次请求
GET /app.js HTTP/1.1
Host: example.com
▼
HTTP/1.1 200 OK
Content-Type: application/javascript
ETag: "abc123-def456"
Cache-Control: max-age=60

# 60 秒后再次请求
GET /app.js HTTP/1.1
Host: example.com
If-None-Match: "abc123-def456"
▼
HTTP/1.1 304 Not Modified
# 浏览器使用本地缓存的 app.js

2.5 连接复用与性能数据

2.5.1 HTTP 连接复用

HTTP/1.1 默认开启 Keep-Alive，允许在一个 TCP 连接上发送多个请求。HTTP/2 更进一步，支持多路复用——在同一个连接上并行发送多个请求，无需排队。

协议 连接数 请求方式 典型首屏加载时间
HTTP/1.1 + Keep-Alive 每个域名最多 6 个 串行（有队头阻塞） 3-5s
HTTP/2 多路复用 1 个连接 并行（无队头阻塞） 1.5-3s
HTTP/3 (QUIC) 1 个连接 并行 + 0-RTT 1-2s

2.5.2 关键性能数据

一次完整请求的时间分布（典型场景）

  1. DNS 查询：20-100ms（有缓存 < 1ms，无缓存 20-100ms）
  2. TCP 握手：1-3 RTT（~20-100ms，取决于网络延迟）
  3. TLS 握手：1 RTT（TLS 1.3）或 2 RTT（TLS 1.2）（~10-50ms）
  4. 服务器处理：取决于后端性能（通常 50-500ms）
  5. 内容传输：取决于文件大小和网络带宽
// 使用 Performance API 精确测量网络各阶段
function analyzeNetworkPerformance() {
  const nav = performance.getEntriesByType('navigation')[0];
  const dns = performance.getEntriesByName(nav.domainLookupStart, 'resource');

  console.log('=== 网络性能分析 ===');
  console.log(`DNS 解析:      ${(nav.domainLookupEnd - nav.domainLookupStart).toFixed(1)} ms`);
  console.log(`TCP 连接:      ${(nav.connectEnd - nav.connectStart).toFixed(1)} ms`);
  if (nav.secureConnectionStart) {
    console.log(`TLS 握手:      ${(nav.connectEnd - nav.secureConnectionStart).toFixed(1)} ms`);
  }
  console.log(`TTFB:          ${(nav.responseStart - nav.requestStart).toFixed(1)} ms`);
  console.log(`内容下载:      ${(nav.responseEnd - nav.responseStart).toFixed(1)} ms`);
}
⚠️ 连接池耗尽的陷阱

HTTP/1.1 中，浏览器对每个域名最多只保持 6 个并发连接。如果你的页面需要加载超过 6 个资源，多余的请求必须排队等待。这就是为什么推荐使用 HTTP/2——一个连接就能多路复用，不再受连接数限制。

2.6 本章小结

  • DNS 查询通过递归模式发起，经过多级缓存最终到达权威服务器，耗时通常在 20-100ms。
  • TCP 三次握手建立可靠连接，TLS 1.3 将加密握手优化到 1-RTT。
  • HTTP 缓存分为强缓存（Cache-Control）和协商缓存（ETag/Last-Modified），合理配置可减少大量网络请求。
  • 连接复用和协议升级（HTTP/1.1 → HTTP/2 → HTTP/3）是降低延迟的关键手段。
