软件测试

测试不是为了证明"代码能工作"，而是为了发现"代码哪里不能工作"。这是测试思维的第一原则。

Dijkstra 的名言："测试只能证明 bug 的存在，而不能证明 bug 不存在。" —— Edsger W. Dijkstra

测试的层次

软件测试不是"跑一下看看"。它是一个有层次的体系，每一层解决不同的问题：

测试金字塔 /\ / \ ← 端到端测试 (E2E) /____\ 数量少、速度慢、覆盖全 / \ /________\ ← 集成测试 / \ 中等数量、中等速度 /____________\ / \ ← 单元测试 /________________\ 数量多、速度快、粒度细 单元测试 > 集成测试 > E2E 测试 (数量最多) (数量最少)

1. 单元测试 (Unit Test)

单元测试是对最小的可测试代码单元进行测试——通常是一个函数或一个方法。它不依赖外部系统（数据库、网络、文件系统）。

import pytest

# 被测函数
def calculate_discount(price, membership, coupon=None):
    if membership == "gold":
        price *= 0.8
    elif membership == "silver":
        price *= 0.9

    if coupon == "SAVE10":
        price *= 0.9

    return round(price, 2)

# 测试用例
def test_gold_member_no_coupon():
    assert calculate_discount(100, "gold") == 80.0

def test_silver_member_with_coupon():
    assert calculate_discount(100, "silver", "SAVE10") == 81.0

def test_no_discount():
    assert calculate_discount(100, "normal") == 100.0

def test_negative_price():
    with pytest.raises(ValueError):
        calculate_discount(-50, "gold")

2. 集成测试 (Integration Test)

集成测试测试的是多个模块之间的协作。它验证模块之间的接口是否正确工作。

# 集成测试：测试 OrderService 和 PaymentGateway 的协作
def test_order_payment_integration():
    order_service = OrderService(payment_gateway=TestPaymentGateway())
    order = order_service.create_order(user_id=1, items=[...])

    result = order_service.pay(order.id, method="credit_card")

    assert result.status == "paid"
    assert order.status == "paid"
    # 验证支付记录被正确写入
    assert payment_log.exists(order_id=order.id)

3. 系统测试 (System Test)

系统测试是对完整系统进行测试，验证系统是否满足需求规格说明书中的所有要求。包括功能测试、性能测试、安全测试等。

4. 验收测试 (Acceptance Test)

验收测试是用户或客户确认系统是否满足他们的需求的测试。BDD (Behavior Driven Development) 是验收测试的一种流行方法。

Feature: 用户注册
  As a visitor
  I want to create an account
  So that I can place orders

  Scenario: 正常注册流程
    Given 我是一个未登录的访客
    And 我填写了有效的用户名、邮箱和密码
    When 我点击"注册"按钮
    Then 我应该看到"注册成功"的提示
    And 我应该收到一封验证邮件
    And 我应该能够用新账号登录

  Scenario: 邮箱已被注册
    Given 我已经用 "test@example.com" 注册过
    When 我尝试用相同的邮箱注册
    Then 我应该看到"邮箱已被注册"的错误提示

TDD：测试驱动开发

TDD (Test-Driven Development) 的核心思想是：先写测试，再写实现。

TDD 的三步循环

1

Red（红）

先写一个失败的测试。这个测试描述了你还不想写的功能。运行测试，确认它失败了。

2

Green（绿）

写最少的代码让测试通过。不要追求完美，只要能通过就行。

3

Refactor（重构）

在测试的保护下，重构代码让它变好。确保重构后测试仍然通过。

# TDD 实战示例：实现一个 LRU Cache

# Step 1: Red — 先写测试
def test_lru_cache_basic():
    cache = LRUCache(capacity=2)
    cache.put(1, "one")
    cache.put(2, "two")
    assert cache.get(1) == "one"
    assert cache.get(2) == "two"

def test_lru_cache_eviction():
    cache = LRUCache(capacity=2)
    cache.put(1, "one")
    cache.put(2, "two")
    cache.put(3, "three")  # 触发淘汰
    assert cache.get(1) is None  # key=1 被淘汰
    assert cache.get(2) == "two"
    assert cache.get(3) == "three"

def test_lru_cache_access_renews():
    cache = LRUCache(capacity=2)
    cache.put(1, "one")
    cache.put(2, "two")
    cache.get(1)  # 访问 key=1，使它成为最近使用的
    cache.put(3, "three")  # 淘汰的是 key=2（最不常用）
    assert cache.get(1) == "one"
    assert cache.get(2) is None
    assert cache.get(3) == "three"

# Step 2: Green — 写最简单的实现让它通过
class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.cache = {}
        self.order = []

    def put(self, key, value):
        if key in self.cache:
            self.order.remove(key)
        self.cache[key] = value
        self.order.append(key)
        if len(self.cache) > self.capacity:
            evicted = self.order.pop(0)
            del self.cache[evicted]

    def get(self, key):
        if key not in self.cache:
            return None
        self.order.remove(key)
        self.order.append(key)
        return self.cache[key]

# Step 3: Refactor — 用 OrderedDict 优化实现
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.cache = OrderedDict()

    def put(self, key, value):
        if key in self.cache:
            self.cache.move_to_end(key)
        self.cache[key] = value
        if len(self.cache) > self.capacity:
            self.cache.popitem(last=False)

    def get(self, key):
        if key not in self.cache:
            return None
        self.cache.move_to_end(key)
        return self.cache[key]
TDD 的好处：
  • 测试覆盖率天然接近 100%——因为你先写了测试
  • 设计更简洁——为了"好测试"，代码必须"好设计"
  • 重构有安全感——测试套件是你的安全网
  • 文档即测试——测试用例就是最好的使用文档

测试覆盖率

测试覆盖率衡量的是你的测试覆盖了多少代码。但它不是万能的——高覆盖率不代表没有 bug。

覆盖率类型说明例子
语句覆盖 每行代码至少执行一次 最基础，但不够
分支覆盖 每个 if/else 的两个分支都走到 比语句覆盖强
路径覆盖 每条可能的执行路径都走到 理论上最强，但实践中不可行（组合爆炸） 
def classify_grade(score):
    if score >= 90:
        return "A"
    elif score >= 80:
        return "B"
    elif score >= 60:
        return "C"
    else:
        return "F"

# 语句覆盖需要 4 个测试：90, 80, 60, 0
# 分支覆盖也需要 4 个测试（每个分支都走到）
# 但如果测试只写了 90 和 80，覆盖率显示 75%，漏掉了 else 分支

# 好的测试：
assert classify_grade(95) == "A"
assert classify_grade(85) == "B"
assert classify_grade(65) == "C"
assert classify_grade(30) == "F"
# 边界值也要测：
assert classify_grade(90) == "A"
assert classify_grade(89.9) == "B"  # 刚好低于 90
assert classify_grade(60) == "C"
assert classify_grade(59.9) == "F"

Mock 与 Stub

单元测试不应该依赖外部系统（数据库、网络、文件系统）。Mock 和 Stub 是用来隔离这些依赖的工具。

import pytest
from unittest.mock import MagicMock, patch

# 被测代码依赖外部服务
class OrderService:
    def __init__(self, db, payment_gateway):
        self.db = db
        self.payment_gateway = payment_gateway

    def create_order(self, user_id, items):
        order = self.db.insert("orders", {...})
        self.payment_gateway.charge(order.id, items)
        return order

# 测试时 Mock 依赖
def test_create_order_success():
    mock_db = MagicMock()
    mock_db.insert.return_value = {"id": 1, "status": "created"}

    mock_gateway = MagicMock()
    mock_gateway.charge.return_value = {"status": "paid"}

    service = OrderService(mock_db, mock_gateway)
    result = service.create_order(1, [{"name": "book", "price": 30}])

    assert result["status"] == "created"
    mock_gateway.charge.assert_called_once_with(1, [{"name": "book", "price": 30}])

# 或者用 patch 装饰器
@patch('myapp.services.PaymentGateway')
def test_create_order_with_real_mock(PaymentGatewayMock):
    instance = MagicMock()
    instance.charge.return_value = {"status": "paid"}
    PaymentGatewayMock.return_value = instance

    service = OrderService(MagicMock(), PaymentGatewayMock())
    ...

测试的常见误区

误区 1："测试写了但从来不加新的测试用例"——测试变成了摆设。
正确做法：每次修 bug 必须先写一个能复现 bug 的测试。
误区 2："测试覆盖率 100% 所以没有 bug"——覆盖率只说明代码被执行了，不代表逻辑正确。
正确做法：覆盖率是手段不是目标。关注测试的"断言质量"而非"行数覆盖"。
误区 3："测试是测试人员的事"——测试是全员责任。开发者写单元测试，QA 写集成和 E2E 测试。
正确做法：测试左移（Shift Left Testing）——越早发现 bug，修复成本越低。
误区 4："测试代码不重要"——测试代码也是代码，也需要维护。写烂的测试比不写测试更糟。
正确做法：测试代码也要 code review，也要遵循 DRY、单一职责等原则。

本章小结

  • 测试分为四层：单元测试、集成测试、系统测试、验收测试
  • 测试金字塔：单元测试最多，E2E 测试最少
  • TDD 先写测试再写实现，带来更好的设计和更高的测试覆盖率
  • Mock 和 Stub 用于隔离外部依赖，让单元测试真正"独立"
  • 测试覆盖率不是万能药——关注断言质量而非数字
  • 测试是全员责任，不是 QA 的专属工作
