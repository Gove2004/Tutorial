第 3 章　单例体系与启动流程

《空洞骑士》有一批贯穿整个游戏生命周期的管理器对象。本章拆解它们的单例实现方式、持久化机制，以及从游戏进程启动到主菜单出现的完整时序。

3.1 一个反直觉的发现：泛型 Singleton 是死代码

工程里存在一个写得相当完整的泛型单例基类 Singleton<T>，带线程锁、退出标记、重复实例检测：

public class Singleton : MonoBehaviour where T : MonoBehaviour
{
    private static T _instance;
    private static object _lock = new object();
    private static bool applicationIsQuitting = false;

    public static T instance { get { /* 锁内 FindObjectOfType，找不到就新建并 DontDestroyOnLoad */ } }

    public void Awake()
    {
        Debug.Log("TEST1 - AWAKE - " + GetInstanceID());  // 调试日志还没删
        // ...
    }
}

但对全工程做交叉引用搜索，没有任何一个类继承它：

// 搜索 ": Singleton<" 的结果为 0

这是一个典型的代码考古结论：Singleton<T> 是项目早期方案的遗留物（Awake 里残留的 TEST1 调试字符串是它试验性质的证据），后来团队转向每个管理器各自手写单例。读代码时不要被这个类误导，以为游戏的单例都走它的逻辑。

3.2 手写单例的统一模式

GameManager、HeroController、UIManager、GameCameras、SceneData、ObjectPool 等全部手写，但骨架高度一致，由三部分组成。

部件一：静态字段 + 懒查找属性

以 GameManager 为例：

public static GameManager _instance;

public static GameManager instance
{
    get
    {
        if (_instance == null)
        {
            _instance = UnityEngine.Object.FindObjectOfType<GameManager>();
            if (_instance == null)
                Debug.LogError("Couldn't find a Game Manager, make sure one exists in the scene.");
            else if (Application.isPlaying)
                UnityEngine.Object.DontDestroyOnLoad(_instance.gameObject);
        }
        return _instance;
    }
}

public static GameManager UnsafeInstance => _instance;

部件二：Awake 里的去重

private void Awake()
{
    if (_instance == null)
    {
        _instance = this;
        UnityEngine.Object.DontDestroyOnLoad(this);
        SetupGameRefs();
    }
    else if (this != _instance)
    {
        UnityEngine.Object.Destroy(base.gameObject);  // 场景里出现第二个，自我销毁
    }
    else
    {
        SetupGameRefs();
    }
}

懒查找属性和 Awake 构成双保险：无论外部先访问 instance 还是对象先 Awake，最终都只有一个实例，且一定被标记为 DontDestroyOnLoad。

部件三：三种访问语义的变体

HeroController 把访问方式拆成了三个静态入口，这个设计值得注意：

入口行为适用场景
instance找不到时输出 LogError正常游戏逻辑，主角理应存在
SilentInstance查找但不打错误日志启动早期、对象可能还没生成的场景
UnsafeInstance直接返回字段，不触发任何查找对性能敏感或需要判断"是否已存在"的场合

陷阱：FindObjectOfType 是成本不低的全场景扫描。手写单例把它放在 _instance == null 的分支里，正常情况下只执行一次；但如果你在大量物件的逻辑里反复访问一个尚未初始化的单例，就会触发多次扫描。判断单例是否存在时应使用 UnsafeInstance，而不是访问 instance。

3.3 DontDestroyOnLoad 与持久对象

被标记 DontDestroyOnLoad 的对象在场景切换时不会被卸载，它们共同构成游戏的"持久层"。核心成员包括：

  • GameManager——总控，持有 PlayerData、SceneData、gameState 等
  • GameCameras——主相机 + HUD 相机及相机控制器
  • UIManager——UI 画布与菜单系统
  • HeroController——主角对象（注意：主角是持久对象，不随场景重建）
  • CoreLoop——主线程调度器（见 3.5）
主角是持久对象这一点解释了很多设计：场景切换时 HeroController 不销毁，只是被移动到新场景的门口坐标（LeaveScene/EnterScene），所以主角的移动状态、输入队列在过门后可以延续。

3.4 事件委托：持久层的解耦手段

GameManager 不直接引用场景里的具体物件，而是暴露一组 C# event，让场景物件在 Awake/Start 时订阅、销毁时退订：

public event SavePersistentState SavePersistentObjects;
public event ResetSemiPersistentState ResetSemiPersistentObjects;
public event DestroyPooledObjects DestroyPersonalPools;
public event UnloadLevel UnloadingLevel;
public event RefreshLanguage RefreshLanguageText;
public event EnterSceneEvent OnFinishedEnteringScene;

例如 PersonalObjectPool 订阅 DestroyPersonalPools，在场景切换时收到通知清理自己注册的池对象。这样 GameManager 不需要知道场景里有哪些对象池，依赖方向是"场景物件知道管理器，管理器不知道具体物件"，这是全书反复出现的架构原则。

3.5 CoreLoop：主线程调度器

CoreLoop 用 [RuntimeInitializeOnLoadMethod] 在任何场景加载之前自动创建，提供两类调度能力：

方法作用
InvokeNext(Action)把动作排到下一帧执行（双缓冲列表，避免遍历中修改集合）
InvokeOnGameThread(Action) / InvokeSafe把其他线程（如平台回调、IO 线程）的动作 marshal 回 Unity 主线程执行

Unity 的 API 只能在主线程调用，而平台层的存档读写、成就回调往往来自后台线程，CoreLoop 就是它们回到主线程的统一通道。DesktopPlatform 里读取存档后的回调 CoreLoop.InvokeSafe(() => callback(...)) 就是实际用例。

3.6 完整启动时序

把上面的部件串起来，从进程启动到主菜单的时序如下：

sequenceDiagram participant Runtime as Unity 运行时 participant CL as CoreLoop participant SM as StartManager(启动场景) participant Plat as Platform participant Menu as Menu_Title Runtime->>CL: RuntimeInitializeOnLoadMethod 创建持久 CoreLoop Note over Runtime: 启动场景加载，StartManager.Awake SM->>Menu: LoadSceneAsync("Menu_Title") 但 allowSceneActivation=false SM->>Plat: SetSceneLoadState，等待共享数据挂载 alt 首次启动且未设语言 SM->>SM: 显示语言选择，等待确认 end SM->>Plat: 等待 IsSharedDataMounted SM->>Plat: 等待 IsPlayerPrefsLoaded SM->>Menu: allowSceneActivation=true，激活菜单场景 Note over Menu: 菜单场景中的 GameManager 等持久对象 Awake Menu->>Menu: 各自手写单例去重 + DontDestroyOnLoad

StartManager 用一个 allowSceneActivation 门控把菜单场景的加载和"平台数据是否就绪"解耦：场景资源可以先在后台加载完，但只有共享数据、PlayerPrefs 都准备好后才激活，避免菜单在数据未就绪时初始化出错误状态。这个门控模式在第 4 章的场景管线里还会以更复杂的形式出现。
