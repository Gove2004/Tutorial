编码实践

编码实践是软件工程中最"接地气"的部分。设计再漂亮，代码写得烂也白搭。这一章我们不讲语法，讲的是写出好代码的习惯和方法。

什么是"好代码"？

好代码不是"没有 bug 的代码"。好代码是别人能看懂、能修改、能扩展的代码。一句话总结：好代码是可维护的。

编码规范

编码规范不是"代码长得好看"，而是团队有一致的代码风格。当 10 个人在同一个项目里写代码，如果每个人的缩进、命名、文件结构都不一样，那维护成本会指数级增长。

规范的核心维度

维度说明工具支持
命名变量名、函数名、类名的风格IDE 内置
格式缩进、换行、空格Prettier / black / gofmt
文件结构模块如何组织、文件如何命名团队约定
注释什么时候写注释、写什么风格的注释ESLint / Pylint
错误处理异常怎么处理、日志怎么记代码审查

命名是软件工程中最被低估的技能

# 差的命名
def calc(a, b):
    return a * b

# 好的命名
def calculate_order_total(subtotal, tax_rate):
    return subtotal * (1 + tax_rate)

Bjarne Stroustrup（C++ 之父）说过："There are only two hard things in Computer Science: cache invalidation and naming things."

代码审查 (Code Review)

代码审查是保证代码质量的最有效手段之一。它的价值不仅仅是"找 bug"，更重要的是知识共享和质量文化。

代码审查的四个层次

层次检查什么谁来做
语法/格式缩进、分号、引号风格自动化工具（lint）
逻辑正确性算法是否正确、边界条件是否处理同行审查者
架构一致性是否符合设计、是否引入了不该有的依赖架构师 / Tech Lead
可读性命名是否清晰、注释是否到位、结构是否合理所有审查者
致命错误：把代码审查变成"挑错大会"——审查者逐行检查语法错误、缩进问题。这些应该交给 linter 去做。代码审查的重点应该是逻辑、架构、可读性。

代码审查的检查清单

  • [ ] 代码是否实现了需求？（功能正确性）
  • [ ] 有没有更简单的写法？（简洁性）
  • [ ] 命名是否清晰表达了意图？（可读性）
  • [ ] 异常和边界情况是否处理了？（鲁棒性）
  • [ ] 有没有硬编码的魔法数字/字符串？（可配置性）
  • [ ] 测试是否充分？（可测试性）
  • [ ] 有没有引入新的依赖？这个依赖值得吗？（依赖性）
  • [ ] 这段代码 6 个月后还能看懂吗？（可维护性）

重构 (Refactoring)

什么是重构？

重构是在不改变外部行为的前提下，改善代码的内部结构。它是"代码消毒"的过程——把烂代码慢慢变成好代码。

关键原则：小步重构。每次只做一个小改动，跑测试，确认没问题再做下一个。

常见代码异味 (Code Smells)

代码异味症状重构手法
过长函数 一个函数超过 20 行 提取函数（Extract Method）
过大类 一个类超过 500 行 提取类、提取接口
过长参数列表 函数参数超过 3 个 引入参数对象（Introduce Parameter Object）
发散式变化 一个类经常被不同原因修改 拆分类（Single Responsibility）
霰弹式修改 改一个需求要动多个文件 合并到同一模块
依恋情结 函数对某个局部变量的关注多于对自身所在类的关注 提取函数或引入类
数据泥团 同一组数据总是一起出现 提取为对象

重构实战示例

# 重构前：一个函数做了太多事
def process_order(data):
    # 验证
    if not data.get('items'):
        return None
    for item in data['items']:
        if item['quantity'] <= 0:
            return None

    # 计算
    total = 0
    for item in data['items']:
        price = item['price']
        qty = item['quantity']
        discount = 0.1 if item.get('is_vip') else 0
        total += price * qty * (1 - discount)

    # 格式化
    result = "Order total: $" + str(round(total, 2))

    # 记录日志
    print("Order processed")

    return result

# 重构后：职责分离
def validate_order(data):
    if not data.get('items'):
        return False
    for item in data['items']:
        if item['quantity'] <= 0:
            return False
    return True

def calculate_order_total(items):
    total = 0.0
    for item in items:
        discount = 0.1 if item.get('is_vip') else 0.0
        total += item['price'] * item['quantity'] * (1 - discount)
    return round(total, 2)

def format_order_result(total):
    return f"Order total: ${total}"

def process_order(data):
    if not validate_order(data):
        return None
    total = calculate_order_total(data['items'])
    logger.info("Order processed")
    return format_order_result(total)

技术债务 (Technical Debt)

技术债务是软件工程中最形象的比喻之一。它说的是：你选择了"快速但粗糙"的方案，未来需要花更多时间来偿还这个"债务"。

技术债务的分类

故意 vs 无意

  • 故意的：明知不好，但为了赶deadline 先这么写了。比如：硬编码配置、跳过测试、不用异常处理。
  • 无意的：不知道有更好的做法。比如：用了过时的 API、没注意到代码重复。

谨慎 vs 轻率

  • 谨慎的：权衡之后选择的短期方案，有明确的偿还计划。比如：MVP 阶段用 SQLite 而不是 PostgreSQL。
  • 轻率的：完全不负责任的代码。比如：不写注释、不处理异常、变量名全是 x/y/z。

技术债务的管理策略

策略做法适用场景
定期偿还 每个 Sprint 预留 20% 时间还债 成熟团队、长期维护的项目
重构驱动开发 写代码前先写测试，然后逐步重构 新功能开发
Boy Scout Rule 离开时让代码比你来时更好 任何团队文化
债务看板 用 Issue Tracker 记录技术债务，定期清理 大型项目
警惕：技术债务本身不是坏事——有时候"先跑起来再说"是正确的策略。危险的是不还债。当技术债务超过某个阈值，代码变得无法修改，新功能开发速度归零——这就是"停滞点"（Stagnation Point）。

编程习惯

每日编程习惯清单

  • 提交前跑测试：确保你没有破坏已有功能
  • 提交信息有意义：不要写 "fix" 或 "update"，写 "fix: 修复订单金额为负数时的计算错误"
  • 小步提交：每次提交只做一件事，方便回滚和审查
  • 每天至少读 30 分钟好代码：看优秀开源项目的源码，学别人的写法
  • 遇到 bug 先写复现测试：再修 bug，而不是直接改代码
  • 代码写完后问自己："如果我是第一次看到这个代码的人，能看懂吗？"

调试思维

调试不是"猜哪里错了然后试一下"。好的调试方法是系统性的：

1

复现问题

写一个最小化的测试用例，能稳定复现问题。如果做不到，说明你对问题的理解还不够。

2

隔离范围

二分法缩小问题范围。问题在左边还是右边？在上层还是下层？

3

定位根因

找到导致问题的具体代码行。不是"大概"，而是"精确到那一行"。

4

修复并验证

修完之后，跑一遍测试，确保没有引入回归。

本章小结

  • 编码规范让团队代码风格一致，减少认知负担
  • 代码审查是知识共享和质量控制的利器，但要用对重点
  • 重构是持续的过程，小步慢走比一次性大重构更可靠
  • 技术债务是必要的恶——可以借，但要还
  • 好的编程习惯（小步提交、有意义的 commit message、先写测试再修 bug）比任何工具都重要
