第 11 章　PlayMaker 状态机体系

《空洞骑士》的另一半逻辑运行在 PlayMaker 可视化状态机里。本章讲清 FSM 的核心概念、两类 Action 的区别、C# 与 FSM 如何双向通信，以及 FSMUtility 这个贯穿全工程的工具类。

11.1 核心概念：状态机的五个部件

部件含义
FSM有限状态机，一个独立的逻辑单元，挂在 GameObject 上（PlayMakerFSM 组件）
State（状态）FSM 在某一时刻处于一个状态，每个状态里挂若干 Action
Event（事件）状态切换的触发信号，由 Action 或外部代码发送
Action（动作）状态内执行的具体行为，本工程有 1140 个
Variable（变量）FSM 内部数据，FsmBool/FsmInt/FsmString 等包装类型

PlayMakerFSM 与 FSM 的区别

PlayMakerFSM 是 MonoBehaviour 组件，是 FSM 的载体；Fsm 是它内部的数据对象（通过 playMakerFSM.Fsm 访问），包含状态、事件、变量。一个 GameObject 可以挂多个 PlayMakerFSM，用 FsmName 区分。读代码时定位 FSM 用名字，读写变量用 FsmVariables。

11.2 Action 的两类：瞬时型与持续型

对 1140 个 Action 统计，约 524 个含 OnUpdate（持续型），其余是 OnEnter 后立即 Finish 的瞬时型。这个区分是理解 Action 生命周期的关键。

瞬时型：OnEnter + Finish

以 DecrementPlayerDataInt 为例，进入状态执行一次就结束：

[ActionCategory("PlayerData")]
public class DecrementPlayerDataInt : FsmStateAction
{
    public FsmOwnerDefault gameObject;
    public FsmString intName;

    public override void OnEnter()
    {
        GameObject target = Fsm.GetOwnerDefaultTarget(gameObject);
        GameManager gm = target.GetComponent();
        gm.DecrementPlayerDataInt(intName.Value);
        Finish();          // 立即结束，FSM 可切换到下一状态
    }
}

这类 Action 是薄封装：自身不含业务逻辑，只负责把 FSM 的调用转发给 C# 管理器。ActionCategory 特性把它归类到编辑器的 "PlayerData" 分组。

持续型：OnUpdate 每帧执行

ListenForDreamNail 进入后不 Finish，留在状态里每帧检测：

public override void OnEnter()
{
    gm = GameManager.instance;
    inputHandler = gm.GetComponent();
}
public override void OnUpdate()
{
    if (!gm.isPaused)
    {
        if (inputHandler.inputActions.dreamNail.WasPressed)
            Fsm.Event(wasPressed);          // 检测到输入，发事件触发切换
        if (inputHandler.inputActions.dreamNail.IsPressed)
            Fsm.Event(isPressed);
        // WasReleased / isNotPressed ...
    }
}

OnEnter 只做一次性的引用装配，OnUpdate 承担每帧逻辑，通过发事件让 FSM 决定是否切换。这类 Action 用于监听、计时、持续移动等需要跨帧的行为。

瞬时型持续型
入口OnEnterOnEnter（装配）+ OnUpdate（逻辑）
结束主动 Finish不 Finish，靠事件切换状态
典型用途写数据、调用管理器、设置字段监听输入、协程式计时、持续检测

11.3 FSMUtility：贯穿全工程的工具类

C# 代码操作 FSM 不直接拼组件调用，而是统一走静态类 FSMUtility，它的方法分四组：

public static PlayMakerFSM LocateFSM(GameObject go, string fsmName)
{
    List list = ObtainFsmList();
    go.GetComponents(list);
    PlayMakerFSM result = null;
    for (int i = 0; i < list.Count; i++)
        if (list[i].FsmName == fsmName) { result = list[i]; break; }
    ReleaseFsmList(list);
    return result;
}

列表池：避免每次 GetComponents 产生垃圾

注意 ObtainFsmList/ReleaseFsmList 这对方法：临时 List 从一个池里借、用完归还，而不是每次 new List。因为 FSM 定位可能在运行中频繁发生，反复分配临时列表会增加 GC 压力。这是为减少托管堆垃圾做的对象池化，容量上限 20。

变量读写的字符串约定

public static int GetInt(PlayMakerFSM fsm, string variableName)
{
    return fsm.FsmVariables.FindFsmInt(variableName).Value;
}
public static void SetInt(PlayMakerFSM fsm, string variableName, int value)
{
    fsm.FsmVariables.GetFsmInt(variableName).Value = value;
}

变量同样按字符串名查找，拼写错误的风险与反射一致。FSMUtility 还内嵌了几个抽象 Action 基类（CheckFsmStateAction 等），把常见的"判定布尔并发 true/false 事件"模式固化复用。

11.4 C# 与 FSM 的双向通信

Fsm.Event"| B["FSM 收事件切状态"] A -->|"FSMUtility.SetXxx

（薄封装）"| D["C# 管理器"] C -->|"反射读 PlayerData/cState"| D end

两个方向都不直接依赖对方的具体类型：C# 用 FSM 名字和事件名（字符串）操作 FSM；FSM 用 Action 调用 C# 公共接口。这种松散耦合让设计师能改 FSM 而不动 C#，程序员也能改管理器内部实现而不影响 FSM 资产。

11.5 约定大于配置

PlayMaker 体系大量依赖命名约定，读代码时要识别这些"魔法字符串"：

  • 持久化 FSM 必须含名为 "Activated"（布尔）或 "Value"（整数）的变量，FindFSMWithPersistentXxx 据此识别
  • 重置靠发送 "RESET" 事件；主角伤害事件是 "HeroCtrl-HeroDamaged" 这类固定字符串
  • FSM 名字（如 "Superdash"、"ProxyFSM"、"damages_hero"）是定位的唯一依据

约定的代价是没有编译期检查：改了 FSM 名字或变量名，所有引用它的 C# 字符串不会报错，只会在运行时静默失败。维护时改名要全局搜索对应字符串。

11.6 发布版的运行时剥离

HutongGames.PlayMaker 目录里的 UpdateHelper 在发布版被剥成空方法：

public class UpdateHelper
{
    public static void SetDirty(Fsm fsm)
    {
        // 发布版方法体为空，编辑器下的脏标记逻辑被移除
    }
}

这与第 1 章讲的调试代码剥离一致：编辑器专用的运行时机制在发布构建里被条件编译移除，只保留功能所需的最小部分。

11.7 架构权衡

收益代价
设计师可视化编排逻辑、无需写代码；状态切换显式清晰；数据驱动，迭代快 逻辑散落在大量 FSM 资产中，无法用 IDE 全局重构；字符串约定无编译期保障；调试链路跨 C#/FSM 两层

团队的边界划分很清晰：核心运动、底层系统用 C#（性能与类型安全），编排、触发、场景内容用 FSM（灵活与可视化）。理解这条边界，就知道一个新功能该落在哪一层。

思考与练习

  1. 区分 PlayMakerFSM 与 Fsm，说明一个物体上多个 FSM 如何被定位。
  2. 对比瞬时型与持续型 Action 的生命周期，各举一个适合它们的场景。
  3. 解释 FSMUtility 为什么用列表池，若每次 LocateFSM 都 new List 会有什么影响。
  4. 梳理 C# 与 FSM 的双向通信路径，说明这种松散耦合在改名时的风险。
  5. 找出工程中三个依赖命名约定的"魔法字符串"，分析改它们的连带影响。
