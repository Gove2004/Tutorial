需求工程

需求工程是软件工程的起点。它解决的是"我们要做什么？"这个问题。几乎所有项目失败的根源，都可以追溯到需求阶段出了问题。

关键事实：Standish Group 的 CHAOS Report 数据显示，约 18% 的项目彻底失败（花费超出预算 200% 或时间是预期的 3 倍以上），另有 45% 的项目存在不同程度的延期和超支。其中最常见的失败原因不是技术不够先进，而是需求不明确或频繁变更。

需求的层次

需求不是单一的东西，而是一个层次结构：

需求层次结构 ┌─────────────────────────────────────┐ │ 业务需求 (Business Requirements) │ ← 战略层面：公司为什么要做这个项目？ │ 例如：提升市场份额、降低运营成本 │ ├─────────────────────────────────────┤ │ 用户需求 (User Requirements) │ ← 用户层面：用户想要达成什么目标？ │ 例如：用户需要能快速搜索商品 │ │ 产出物：用户故事、用例 (Use Case) │ ├─────────────────────────────────────┤ │ 系统需求 (System Requirements) │ ← 系统层面：系统必须具备什么能力？ │ 分为两类： │ │ • 功能需求 (Functional) │ │ • 非功能需求 (Non-functional) │ ├─────────────────────────────────────┤ │ 需求规格 (Requirements Spec) │ ← 技术层面：精确、可验证的描述 │ 产出物：SRS 文档 │ └─────────────────────────────────────┘

功能需求 vs 非功能需求

这是需求工程中最基本的分类。混淆两者是新手最常犯的错误之一。

功能需求非功能需求
关注点 系统做什么 系统做得怎么样
示例 用户可以上传照片 照片上传响应时间 < 2 秒
表达方式 用例、用户故事、流程图 约束、指标、SLA
验证方式 功能测试 性能测试、安全审计、代码审查
优先级 功能需求决定"能不能用"，非功能需求决定"好不好用"。两者缺一不可。
常见陷阱：大多数项目只关注功能需求，忽视非功能需求。结果是"功能都能用，但性能太差没人用"。一个经典的反面案例是：某电商平台只关注"能下单"这个功能，却忽略了"并发处理能力"这个非功能需求，结果在大促期间系统崩溃 6 小时，损失数千万元。

需求获取

需求获取的目标是搞清楚用户真正需要什么。注意——"用户说的"和"用户需要的"往往是两回事。

获取方法

1

访谈 (Interview)

一对一或一对多深度交流。适合获取深层需求，但成本高、难以规模化。

2

问卷调查 (Survey)

适合大规模用户群体，获取量化数据。但难以挖掘深层动机。

3

观察 (Observation)

到用户实际工作环境中观察他们怎么做事情。能发现用户自己都没意识到的痛点。

4

原型法 (Prototyping)

快速做出可交互的原型让用户体验。用户看到东西才能说出真实感受。

5

头脑风暴 (Brainstorming)

召集利益相关者一起讨论。适合解决需求冲突和寻找创新方案。

需求获取的真实案例

有一家医院要开发一套患者预约系统。产品经理去问了医生："你们需要什么功能？"医生说："需要一个预约按钮。"产品经理就做了个预约按钮。

后来发现，医生真正的问题是：患者经常到了医院才说"我要挂号"，导致候诊室秩序混乱、医生大量时间花在分诊上。

正确的做法不是加一个"预约按钮"，而是重新设计就诊流程——在线分诊、智能排队、短信通知。这就是需求获取中"问对问题"比"得到答案"更重要的经典案例。

5 Whys 分析法：遇到需求时连续问 5 次"为什么"，找到根因。 
用户说："我想要一个导出 Excel 的功能"
为什么？ → "因为需要把数据拿去做报表"
为什么？ → "因为管理层每周要看销售趋势"
为什么？ → "因为现在靠人工汇总，经常出错"
为什么？ → "因为没有自动化的报表系统"
根因：不是要 Excel 导出，而是要自动化报表系统

需求分析

获取到需求后，需要进行分析、建模和优先级排序。

需求建模方法

建模方法用途适用场景
用例图 (Use Case) 描述系统与外部角色的交互 业务层面的功能梳理
用户故事 (User Story) As a [角色], I want [功能], so that [价值] 敏捷开发、产品 backlog
活动图 (Activity Diagram) 描述业务流程的每一步 复杂业务逻辑梳理
状态机图 (State Machine) 描述对象的状态转换 订单状态、审批流程等
数据流图 (DFD) 描述数据的流动和处理 数据处理类系统

需求优先级排序

需求永远做不完。关键在于排优先级。常用的方法有：

  • MoSCoW 法则：Must have（必须有）、Should have（应该有）、Could have（可以有）、Won't have（本次不做）
  • Kano 模型：基本型需求、期望型需求、兴奋型需求、无差异需求、反向需求
  • WSJF (Weighted Shortest Job First)：成本延迟 / 工作时长，常用于 SAFe 框架
MoSCoW 示例（电商购物车功能）：
  • Must：加入购物车、修改数量、删除商品、显示总价
  • Should：保存为收藏夹、分享购物车、库存预警
  • Could：智能推荐、购物车合并、跨店优惠计算
  • Won't：AR 试穿（放到下个版本）

需求规格说明书 (SRS)

SRS (Software Requirements Specification) 是所有需求分析的结晶。它是一份文档，描述系统必须具备的所有功能和非功能需求。

SRS 的标准结构（IEEE 830）

  1. 引言：目的、范围、定义、参考文献
  2. 总体描述：产品视角、产品功能、用户特征、约束、假设与依赖
  3. 具体需求：
    • 功能需求（按模块/用例描述）
    • 外部接口需求（UI、硬件、软件、通信）
    • 非功能需求（性能、可靠性、安全性、可维护性）
    • 设计约束
  4. 附录：数据分析、待确定问题清单

好的需求描述标准

每个需求都应该满足 INVEST 原则（用户故事）或 SMART 原则（一般需求）：

SMART 原则

  • Specific（具体的）：需求描述清晰，不含糊
  • Measurable（可衡量的）：有明确的验收标准
  • Achievable（可实现的）：技术上可行，资源上可达
  • Relevant（相关的）：与业务目标一致
  • Time-bound（有时限的）：有明确的完成时间或触发条件

需求描述的对比

差的描述好的描述
"系统应该快一点" "首页加载时间在 4G 网络下不超过 2 秒（P95）"
"用户友好的界面" "新用户首次使用无需培训，核心操作（注册、搜索、下单）可在 3 步内完成"
"支持高并发" "系统支持 10,000 个并发用户，CPU 使用率不超过 80%"
"安全可靠" "所有用户数据加密存储（AES-256），传输使用 TLS 1.3，攻击面扫描每月一次"

需求验证

需求验证的目的是确保需求是正确的、完整的、一致的、可实现的。常见的验证方法：

  • 需求评审 (Requirements Review)：召集开发、测试、产品三方一起过需求文档
  • 原型验证 (Prototype Validation)：用原型确认需求是否正确理解
  • 测试用例驱动 (Test-Driven Requirements)：为每个需求写测试用例，测试用例能通过 = 需求清晰
  • 可行性分析 (Feasibility Analysis)：技术、经济、操作三个维度的可行性评估

需求验证的检查清单

需求质量检查清单

  • [ ] 每个需求是否只有一个含义？（无歧义）
  • [ ] 每个需求是否都可验证？（有明确的验收标准）
  • [ ] 需求之间是否一致？（没有矛盾）
  • [ ] 需求是否完整？（覆盖了所有场景，包括异常场景）
  • [ ] 需求是否可实现？（技术、资源、时间上）
  • [ ] 需求是否必要？（不是"锦上添花"的伪需求）
  • [ ] 需求是否优先级清晰？（知道先做什么、后做什么）

需求管理

需求不是一次性的活。项目进行中，需求会不断变更。需求管理就是管这些变更。

变更控制流程

需求变更流程 1. 提交变更请求 (Change Request) ↓ 2. 影响分析 (Impact Analysis) - 对进度的影响 - 对成本的影响 - 对其他需求的影响 - 对架构的影响 ↓ 3. 变更控制委员会 (CCB) 评审 - 批准 / 拒绝 / 延期 ↓ 4. 更新需求文档 ↓ 5. 更新相关产物（设计、代码、测试用例） ↓ 6. 通知所有利益相关者
需求蔓延 (Scope Creep)：项目中最常见的问题之一——需求一点一点增加，没有人正式提变更，但项目范围已经远远超出了最初的计划。防止方法：每个变更都必须经过正式的变更控制流程，让团队清楚地看到变更的代价。

本章小结

  • 需求工程是软件工程的起点，决定了"做什么"
  • 需求分层次：业务需求 → 用户需求 → 系统需求 → 需求规格
  • 功能需求（做什么）和非功能需求（做得怎么样）同等重要
  • 需求获取要用多种方法，尤其要区分"用户说的"和"用户需要的"
  • 需求描述要满足 SMART 原则，避免模糊表述
  • 需求管理的关键是变更控制，防止需求蔓延
