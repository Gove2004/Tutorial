第 6 章：传输层原理 — Transport 抽象类与底层通信

RPC、SyncVar、Spawn——这些高层机制都建立在一个基础之上：数据如何在两台机器之间传输。 Mirror 通过 Transport 抽象层将这个问题隔离起来。理解 Transport 的原理， 你才能在网络状况不佳时做出正确的调优决策。

Mirror 96 API 更新
本章已全面适配 Mirror 96.x。主要变化包括： Transport 从接口（ITransport）改为抽象类（Transport）； 方法名从 Send/Connect/Disconnect 改为带前缀的 ServerSend/ClientSend/ServerStart/ClientConnect 等； 事件从 onMessage 改为 OnServerDataReceived/OnClientDataReceived 等； Transport.active 作为静态引用获取当前 Transport 实例。

6.1 Transport 抽象类的设计思想

Mirror 的架构是分层的：

┌─────────────────────────────────────┐
│         应用层（你的游戏逻辑）        │  Command / ClientRpc / SyncVar
├─────────────────────────────────────┤
│         消息层（Mirror 内部）        │  NetworkWriter / NetworkReader
├─────────────────────────────────────┤
│       Transport 抽象类              │  Transport（abstract class）
├─────────────────────────────────────┤
│   KCP   │   UTP   │   WS   │   ...  │  具体协议实现
├─────────────────────────────────────┤
│         操作系统网络栈               │  Socket API
└─────────────────────────────────────┘

在 Mirror 96 中，Transport 是一个抽象类（而非接口）， 所有具体的传输实现（KCP、UnityTransport、SimpleWeb 等）都继承自它：

using Mirror;

// Mirror 96 的 Transport 抽象类核心结构
public abstract class Transport
{
    // ===== 服务器端 API =====
    public abstract bool ServerActive { get; }           // 服务器是否在运行
    public abstract void ServerStart(string address);    // 启动服务器监听
    public abstract void ServerStop();                   // 停止服务器
    public abstract void ServerSend(int connectionId,    // 发送给指定客户端
        ArraySegment<byte> message, int channelId = 0);
    public abstract void ServerDisconnect(int connectionId); // 断开指定客户端
    public abstract string ServerGetClientAddress(int connectionId); // 获取客户端 IP

    // ===== 客户端 API =====
    public abstract bool ClientActive { get; }            // 客户端是否活跃
    public abstract void ClientConnect(string address);  // 连接到服务器
    public abstract void ClientConnect(Uri uri);         // 通过 URI 连接
    public abstract void ClientSend(                       // 发送数据到服务器
        ArraySegment<byte> message, int channelId = 0);
    public abstract void ClientDisconnect();              // 断开连接

    // ===== 事件（Action 类型） =====
    // 服务器端事件
    public Action<int> OnServerConnected;               // (connectionId)
    public Action<int, ArraySegment<byte>, int> OnServerDataReceived; // (connId, data, channelId)
    public Action<int> OnServerDisconnected;            // (connectionId)
    public Action<int, Exception> OnServerError;         // (connectionId, exception)

    // 客户端事件
    public Action OnClientConnected;                      // ()
    public Action<ArraySegment<byte>, int> OnClientDataReceived; // (data, channelId)
    public Action OnClientDisconnected;                    // ()
    public Action<Exception> OnClientError;               // (exception)

    // ===== 静态成员 =====
    public static Transport active;  // 当前活动的 Transport 实例

    // ===== 其他抽象成员 =====
    public abstract int GetBatchThreshold();  // 批处理阈值
    public abstract void Shutdown();          // 关闭并释放资源
}
Mirror 96 Transport API 变化
旧版 Mirror 使用 ITransport 接口，方法名为 Send、Connect、Disconnect 等， 事件为 onMessage。

Mirror 96 改为抽象类（非接口），方法名加 Server/Client 前缀， 事件改为 OnServer* / Client* 命名。 这使得服务器和客户端 API 更清晰、更不易混淆。

使用方式：你通常不需要直接调用 Transport 的方法——Mirror 的 NetworkServer/NetworkClient 会在内部调用它们。 你需要做的是在 NetworkManager 所在的 GameObject 上添加具体的 Transport 组件（如 KcpTransport）。

// 获取当前活动的 Transport
Transport transport = Transport.active;

// 检查服务器/客户端状态
bool serverRunning = transport.ServerActive;
bool clientActive = transport.ClientActive;

// 获取客户端地址（用于日志/反作弊）
string clientAddress = transport.ServerGetClientAddress(connectionId);
Debug.Log($"客户端 IP: {clientAddress}");

6.2 协议对比：TCP vs UDP vs KCP

Mirror 96 支持多种传输协议实现，每种都有各自的优劣：

6.2.1 TCP（Transmission Control Protocol）

特点：
• 可靠：保证送达
• 有序：保证顺序
• 面向连接：需要先建立连接
• 有头部开销：每个包 ~40 字节
• 头块堆积（HOL）：前一个包丢失会阻塞后续所有包

适用场景：聊天消息、交易确认、登录验证等低频但必须可靠的数据。

// TCP 的优势与劣势示例
// 假设你同时发送：[位置更新] [开火指令] [位置更新] [位置更新]

// TCP 处理：
// 如果 [开火指令] 因为网络问题丢失重传
// → [位置更新 #3] 和 [#4] 必须等待 #2 送达后才能交付给应用层
// → 这就是 HOL（Head-of-Line blocking）

// 结果：虽然 #3、#4 数据本身没丢，但你感受到了"卡顿"

6.2.2 UDP（User Datagram Protocol）

特点：
• 不可靠：不保证送达
• 无序：可能乱序到达
• 无连接：直接发送
• 头部开销小：~28 字节
• 无 HOL 问题
• 速度最快

适用场景：位置同步、输入流等高频、可容忍丢包的数据。

6.2.3 KCP（改善型 UDP）

KCP 是一个基于 UDP 的快速可靠传输协议。它在 UDP 的基础上添加了快速重传和滑动窗口， 同时保持低延迟。Mirror 的默认 Transport 就是 KcpTransport。

指标          TCP      UDP      KCP
-------------------------------------------------
可靠性         ★★★★★   ★★       ★★★★
速度          ★★★      ★★★★★   ★★★★★
延迟(低网络)   ★★★      ★★★★★   ★★★★★
延迟(高延迟)   ★★       ★★★★    ★★★★★
HOL 问题      有        无       可控
适用场景      聊天/交易  位置同步   竞技游戏（默认推荐）

为什么 Mirror 96 默认推荐 KCP Transport？

KCP 在 UDP 之上添加了可靠性保证（自动重传、滑动窗口）， 同时通过 NoDelay 模式关闭内部缓冲，让数据可以像 UDP 一样即时发送。 对于实时竞技游戏（FPS、格斗、MOBA），这是可靠性和延迟的最佳平衡点。

KCP Transport 在 Inspector 中可配置： Port（端口号，默认 7777）、NoDelay（无延迟模式，默认开启）、 Interval（更新间隔，默认 10ms）等。

6.2.4 Mirror 96 内置的 Transport 实现

Transport底层协议可靠性典型用途

6.3 消息的可靠性与传输

在 Mirror 96 中，所有 RPC 和 SyncVar 数据默认通过 Transport 的可靠通道发送 （KCP Transport 本身就是可靠的）。对于位置同步等高频数据， NetworkTransform 组件内置了插值和预测逻辑来处理网络波动。

不同数据的传输策略：
  • RPC / SyncVar：通过可靠通道传输，保证送达
  • NetworkTransform（位置/旋转同步）：通过 Transport 传输，内置插值处理丢包
  • 自定义消息：通过 Transport 的默认通道传输
Mirror 96 简化了通道管理——KCP Transport 统一使用可靠传输， NetworkTransform 通过应用层的插值来处理视觉平滑性。

6.4 MTU（最大传输单元）与分包

每个网络协议都有一个 MTU 限制——单次发送的最大数据包大小：

协议典型 MTU说明
以太网 (Ethernet)1500 字节标准局域网
IPv4 over PPPoE1492 字节宽带拨号
IPv61280 字节最小 MTU
WebSocket~1200 字节留余量给加密头部

如果你发送的消息超过 MTU，Transport 层需要分包（Fragmentation）：

// Mirror 96 的 Transport 抽象类提供最大包大小查询
Transport transport = Transport.active;
int maxPacketSize = transport.GetMaxPacketSize();  // 获取当前 Transport 的 MTU

Debug.Log($"当前 Transport 最大包大小: {maxPacketSize} 字节");
// 典型值：KCP ~1400, WebSocket ~1200

// Mirror 会自动处理分包——你不需要手动拆分
// 但要避免发送过大的消息：
// 单条消息超过 MTU → 触发分包 → 任何一个子包丢失都要重传全部
分包陷阱：如果一个大数据包被分成 3 个子包，只要其中 1 个丢失， 整个消息都无法重组——3 个子包全部丢弃。所以大数据包的可靠传输成本很高。 策略：把大数据拆成多条小消息发送，比发一条大数据包更高效。

6.5 选择和配置 Transport

在 Unity Editor 中配置 Transport 的步骤：

1

选择 NetworkManager 所在的 GameObject

在 Inspector 中可以看到 NetworkManager 组件。

2

添加 Transport 组件

Add Component → Mirror → Transport → 选择具体的 Transport（如 KcpTransport）。 Mirror 会自动发现并使用 GameObject 上的 Transport 组件。

3

配置 Transport 参数

在 Transport 组件的 Inspector 中设置端口、超时等参数。

KcpTransport Inspector 参数：

Port:         7777       （服务器监听端口）
NoDelay:      ✓          （关闭内部延迟累积，推荐开启）
Interval:     10         （KCP 更新间隔，毫秒，越小越实时）
Timeout:      10000      （连接超时，毫秒）
WindowSize:   4096       （滑动窗口大小）
MaxWindowSize: 4096     （最大窗口大小）

6.6 自定义 Transport

Mirror 96 允许你完全替换 Transport 实现。继承 Transport 抽象类并实现所有抽象成员即可：

using Mirror;
using UnityEngine;

// 自定义 WebSocket Transport 示例
public class CustomWebSocketTransport : Transport
{
    WebSocket websocket;

    // ===== 服务器端 =====
    public override bool ServerActive => websocket != null && websocket.IsListening;

    public override void ServerStart(string address)
    {
        // 启动 WebSocket 服务器
        int port = 7777; // 从配置中读取
        websocket = new WebSocket($"ws://0.0.0.0:{port}");
        websocket.OnMessage += (connectionId, data) =>
        {
            // 收到数据 → 触发 OnServerDataReceived 事件
            OnServerDataReceived?.Invoke(connectionId,
                new ArraySegment<byte>(data), 0);
        };
        websocket.OnConnect += (connectionId) =>
        {
            // 客户端连接 → 触发 OnServerConnected 事件
            OnServerConnected?.Invoke(connectionId);
        };
        websocket.OnDisconnect += (connectionId) =>
        {
            // 客户端断开 → 触发 OnServerDisconnected 事件
            OnServerDisconnected?.Invoke(connectionId);
        };
    }

    public override void ServerSend(int connectionId, ArraySegment<byte> message, int channelId = 0)
    {
        // 向指定客户端发送数据
        websocket.Send(connectionId, message.Array);
    }

    public override void ServerDisconnect(int connectionId)
    {
        websocket.CloseConnection(connectionId);
    }

    public override void ServerStop()
    {
        websocket?.Stop();
        websocket = null;
    }

    public override string ServerGetClientAddress(int connectionId)
    {
        return websocket.GetClientAddress(connectionId);
    }

    // ===== 客户端 =====
    public override bool ClientActive => websocket != null && websocket.IsConnected;

    public override void ClientConnect(string address)
    {
        // 连接到服务器（address 格式如 "ws://192.168.1.100:7777"）
        websocket = new WebSocket(address);
        websocket.OnMessage += (data) =>
        {
            // 收到数据 → 触发 OnClientDataReceived 事件
            OnClientDataReceived?.Invoke(
                new ArraySegment<byte>(data), 0);
        };
        websocket.OnOpen += () =>
        {
            // 连接成功 → 触发 OnClientConnected 事件
            OnClientConnected?.Invoke();
        };
        websocket.OnClose += () =>
        {
            // 连接断开 → 触发 OnClientDisconnected 事件
            OnClientDisconnected?.Invoke();
        };
        websocket.Connect();
    }

    public override void ClientConnect(Uri uri)
    {
        ClientConnect(uri.ToString());
    }

    public override void ClientSend(ArraySegment<byte> message, int channelId = 0)
    {
        websocket.Send(message.Array);
    }

    public override void ClientDisconnect()
    {
        websocket?.Close();
    }

    // ===== 其他抽象成员 =====
    public override int GetBatchThreshold() => 8192;  // 批处理阈值

    public override int GetMaxPacketSize() => 1200;  // WebSocket MTU

    public override void Shutdown()
    {
        ServerStop();
        ClientDisconnect();
    }
}
自定义 Transport 的关键：
1. 继承 Transport 抽象类，实现所有抽象成员
2. 在数据到达时触发对应的 OnServer* / OnClient* 事件
3. ServerSend / ClientSend 是发送数据的出口
4. Mirror 的 NetworkServer/NetworkClient 会自动调用这些方法

6.7 网络调优参数

不同游戏类型对网络的延迟和可靠性要求不同：

// 不同游戏类型的推荐配置

// FPS / 格斗游戏（追求最低延迟）
KcpTransport:
  NoDelay = true      // 关闭延迟累积
  Interval = 5        // 5ms 更新间隔（更激进）
  Timeout = 10000     // 10 秒超时

// 回合制游戏（可靠性优先）
KcpTransport 或 UnityTransport:
  NoDelay = false     // 允许延迟累积以合并小包
  Interval = 40       // 40ms 更新间隔足够了
  Timeout = 30000     // 30 秒超时

// 策略游戏（状态同步为主，玩家数多）
KcpTransport:
  NoDelay = false     // 合并小包节省带宽
  Interval = 50       // 50ms 更新间隔
  WindowSize = 8192   // 更大的窗口应对多客户端

// WebGL 浏览器游戏
SimpleWebTransport:
  使用 WebSocket（浏览器不支持原生 TCP/UDP）
  内置可靠传输

自测题

点击展开自测题
  1. 场景分析：一个 FPS 游戏中，位置同步和伤害计算的传输方案应该如何设计？为什么？
  2. 推理题：如果 MTU 是 1400 字节，你发送了一条 3000 字节的消息，会发生什么？Mirror 如何处理？
  3. 设计题：你需要为一个网页端的 Unity WebGL 客户端设计联网方案。Transport 层应该选什么？为什么？
  4. Mirror 96 变化题：旧代码使用了 class MyTransport : ITransport { ... }。 在 Mirror 96 中应该怎么修改？
参考答案：
1) 两者都通过 KCP Transport 的可靠通道传输。位置同步使用 NetworkTransform 组件 （内置插值处理丢包），伤害计算使用 SyncVar 或 RPC（保证送达）。 Mirror 96 简化了通道管理，KCP 统一提供可靠传输。

2) Mirror 会自动分包。但分包增加了复杂度和失败概率——任何一个子包丢失都需要重传全部。 策略：把大数据拆成多条小消息发送。

3) WebGL 只支持 WebSocket。使用 SimpleWebTransport。 WebSocket 本质上是基于 TCP 的，所以继承了 TCP 的 HOL 问题， 但对于 Web 游戏这是唯一选择。

4) 应改为 class MyTransport : Transport（继承抽象类而非实现接口）。 方法名需改为带前缀的版本：ServerSend、ClientConnect 等。 事件改为 OnServerDataReceived、OnClientConnected 等。
