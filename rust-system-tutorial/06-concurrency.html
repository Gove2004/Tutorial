第六章：并发编程

并发编程是系统编程的核心挑战。Rust 通过类型系统在编译期保证了内存安全和线程安全，让你可以"恐惧并发"（fearless concurrency）。本章将深入探讨 Rust 的并发原语、底层机制和最佳实践。

为什么 Rust 的并发如此特别？

在 C++ 中，数据竞争（data race）是未定义行为，编译器无法捕获。Go 的 goroutine 虽然轻量，但缺乏编译期的线程安全保证。Rust 的独特之处在于：它把并发安全变成了类型系统问题。Send 和 Sync 特质让编译器在编译期就能阻止 99% 的并发 bug。

6.1 Send 和 Sync：自动特质的精确语义

Send 和 Sync 是 Rust 并发安全的基础。它们是两个空特质（auto trait），由编译器根据类型的字段自动派生。理解它们的精确语义是编写安全并发代码的前提。

Send 特质

如果一个类型 T 实现了 Send，那么它的值可以在线程之间转移（ownership transfer）。换句话说，T 的所有权可以从一个线程移动到另一个线程。

// Send 的定义（空特质，没有关联项）：
pub unsafe auto trait Send {}

// 哪些类型是 Send？
// - i32, String, Vec<T>（当 T: Send）：✅ 所有权可以转移
// - &T（当 T: Send + 'static）：✅ 借用引用不拥有数据
// - &mut T（当 T: Send + 'static）：✅ 可变引用也可以转移
// - Rc<T>：❌ 引用计数不是线程安全的
// - Cell<T>：❌ 非线程安全的内部可变性
// - RefCell<T>：❌ 借用检查在运行时进行，不是线程安全的

Sync 特质

如果一个类型 T 实现了 Sync，那么它的引用可以在线程之间共享。形式化定义是：T: Sync ⇔ &T: Send。

// 哪些类型是 Sync？
// - i32, String：✅ 不可变数据可以安全共享
// - Mutex<T>（当 T: Send）：✅ 通过锁机制保护
// - Arc<T>（当 T: Send + Sync）：✅ 引用计数 + 共享所有权
// - Rc<T>：❌ 引用计数不是线程安全的
// - HashMap<K, V>：❌ 内部没有同步机制
// - atomic::AtomicBool：✅ 原子操作天然线程安全

6.1.1 什么时候需要手动实现 Send/Sync？

绝大多数情况下，不需要也不应该手动实现 Send/Sync。只有在以下场景才需要考虑：

1

包装了裸指针

裸指针 *const T 和 *mut T 既不 Send 也不 Sync。如果你的类型只包含裸指针，编译器会拒绝将其发送到其他线程。如果你能证明该裸指针指向的数据是线程安全的，可以手动实现：

struct SafePointer {
        ptr: *mut u8,
    }

    // 只有当你确认该指针的访问是线程安全的
    // （例如通过外部锁机制保护）时才这样做
    unsafe impl Send for SafePointer {}
    unsafe impl Sync for SafePointer {}
2

实现了 PhantomData 的特殊情况

当你的类型使用了 PhantomData 来标记生命周期或协变性时，Send/Sync 的自动派生可能不符合预期：

use std::marker::PhantomData;

    struct MyRef<'a, T> {
        data: *const T,
        _marker: PhantomData<&'a T>,
    }

    // *const T 不 Send 也不 Sync
    // 但如果我们知道 T 是线程安全的且指针不会跨线程转移
    // 可以手动实现
    unsafe impl<T: Send> Send for MyRef<'_, T> {}
    unsafe impl<T: Send + Sync> Sync for MyRef<'_, T> {}
3

第三方库的不兼容实现

某些 C 库的 FFI 封装可能需要手动实现 Send/Sync。此时应优先联系库作者修复，而不是自行实现。

危险警告：手动实现 Send/Sync 是 unsafe 操作。如果实现不正确，会导致数据竞争、内存安全漏洞甚至内核崩溃。只有在完全理解其语义且有充分测试的情况下才这样做。

6.1.2 Send/Sync 的继承关系

// 自动派生规则：
// 1. 结构体的所有字段都 Send → 结构体 Send
// 2. 结构体的所有字段都 Sync → 结构体 Sync

struct Container {
    a: String,       // String: Send + Sync
    b: Vec<i32>,     // Vec<i32>: Send + Sync
    c: Rc<str>,      // Rc<str>: 不 Send 也不 Sync
}

// Container 不 Send 也不 Sync（因为 Rc<str>）

// 泛型约束中的 Send/Sync：
fn spawn_send<T: Send + 'static>(t: T) {
    // 只有 Send 类型才能被 spawn 到其他线程
    std::thread::spawn(move || {
        drop(t);
    });
}

// 注意：'static 生命周期约束通常也需要，
// 因为线程可能在所有权归还之前一直持有数据

6.2 Arc<Mutex<T>> vs Arc<RwLock<T>>：锁的选择

6.2.1 Mutex 的深层机制

std::sync::Mutex 在底层使用操作系统的互斥量原语（pthread_mutex 在 Linux/macOS，CRITICAL_SECTION 在 Windows）：

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            // 临界区：锁在此期间保持持有
            *num += 1;
            // num 在此处被 drop，锁自动释放
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}

6.2.2 RwLock 的读者-写者模型

use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let data = Arc::new(RwLock::new(vec![1, 2, 3]));
    let mut handles = vec![];

    // 多个读者可以同时读取（不需要排队）
    for _ in 0..5 {
        let data = Arc::clone(&data);
        let handle = thread::spawn(move || {
            let read_guard = data.read().unwrap();
            // 多个 read() 可以同时持有
            println!("Read: {:?}", &**read_guard);
        });
        handles.push(handle);
    }

    // 写者独占访问
    let data = Arc::clone(&data);
    let handle = thread::spawn(move || {
        let mut write_guard = data.write().unwrap();
        write_guard.push(4);
    });
    handles.push(handle);

    for handle in handles {
        handle.join().unwrap();
    }
}

6.2.3 Mutex vs RwLock 性能对比

场景 Mutex RwLock 推荐
纯写操作（无竞争） ~50ns ~80ns Mutex
多读者并发 串行化所有读者 读者并行 RwLock
读写比 > 10:1 ❌ 不适合 ✅ 显著加速 RwLock
临界区 < 1μs ✅ 推荐 ❌ 开销更大 Mutex
写者饥饿风险 无 高（读者持续到达时写者等待） Mutex
死锁风险 低 较高（读写锁顺序） Mutex

6.2.4 避免死锁的策略

use std::sync::{Arc, Mutex, RwLock};
use std::thread;
use std::time::Duration;

fn main() {
    // 策略 1：try_lock — 避免永久阻塞
    let lock = Arc::new(Mutex::new(42));
    let lock2 = Arc::clone(&lock);

    let handle = thread::spawn(move || {
        match lock2.try_lock() {
            Ok(mut guard) => {
                println!("Acquired lock: {}", *guard);
            }
            Err(_) => {
                println!("Could not acquire lock, retrying...");
                thread::sleep(Duration::from_millis(10));
                // 重试逻辑
            }
        }
    });

    // 策略 2：timeout — 带超时的锁定
    let lock = Arc::new(Mutex::new(42));
    let lock2 = Arc::clone(&lock);

    let handle = thread::spawn(move || {
        // 注意：std::sync::Mutex 没有内置 timeout
        // 需要使用 parking_lot::Mutex 或 std::sync::Mutex::try_lock + sleep
        if let Ok(mut guard) = lock2.try_lock() {
            *guard += 1;
        }
    });

    // 策略 3：锁排序 — 始终按固定顺序获取多个锁
    // 假设有 lock_A 和 lock_B，永远先获取 lock_A 再获取 lock_B
    // 这样就不会出现 A→B 和 B→A 的死锁循环
}

锁竞争模型

Mutex 竞争模型：
┌──────────┐    lock()    ┌──────────┐
│ Thread A │ ────────────> │ Mutex    │
└──────────┘              │ (locked) │ ───> Thread A 等待
                          └──────────┘
┌──────────┐    lock()    ┌──────────┐
│ Thread B │ ────────────> │          │ ───> 阻塞等待
└──────────┘              └──────────┘

RwLock 竞争模型（读多写少）：
┌──────────┐    read()    ┌──────────┐
│ Reader 1 │ ────────────> │ RwLock   │ ───> ✅ 允许（读者计数+1）
└──────────┘              │ (1 reader)│
┌──────────┐    read()    ┌──────────┐
│ Reader 2 │ ────────────> │          │ ───> ✅ 允许（读者计数+1）
└──────────┘              └──────────┘
┌──────────┐    write()   ┌──────────┐
│ Writer   │ ────────────> │          │ ───> ❌ 阻塞（有读者）
└──────────┘              └──────────┘

6.3 通道通信：从 std::sync::mpsc 到 crossbeam

6.3.1 标准库通道

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    let handle = thread::spawn(move || {
        for i in 0..5 {
            tx.send(i * i).unwrap();
            thread::sleep(std::time::Duration::from_millis(100));
        }
        // tx 离开作用域时自动关闭通道
        // rx 的迭代器会在所有发送者 drop 后结束
    });

    handle.join().unwrap();

    for received in rx {
        println!("Received: {}", received);
    }
}

6.3.2 有界 vs 无界通道

use std::sync::mpsc;

// 无界通道：sender.send() 永远不会阻塞
// 缺点：内存可能无限增长
let (unbounded_tx, unbounded_rx) = mpsc::unbounded_channel();

// 有界通道：缓冲区满时 sender 阻塞
// 优点：背压（back pressure）保护
let (bounded_tx, bounded_rx) = mpsc::sync_channel(100);

// 性能对比（10^7 次 send 操作）：
// 无界通道： ~30ms（无阻塞，但可能 OOM）
// 有界通道： ~45ms（有背压，内存可控）
// 有界通道（满时）： ~500ms+（sender 被阻塞等待接收）
背压（Back Pressure）是什么？：当生产者速度快于消费者时，有界通道会让生产者阻塞等待。这防止了内存无限增长，代价是生产者可能需要等待。在系统编程中，背压是保证稳定性的关键机制。

6.3.3 crossbeam-channel：高性能替代方案

crossbeam-channel 使用 lock-free 队列实现，比标准库通道快 2-10 倍：

// Cargo.toml
// crossbeam-channel = "0.5"

use crossbeam_channel::{bounded, unbounded, Select};

fn main() {
    // 有界通道（带背压）
    let (tx, rx) = bounded(100);

    // 多发送者（天然支持，无需 Arc<Mutex<rx>>）
    let tx1 = tx.clone();
    let tx2 = tx.clone();

    std::thread::spawn(move || {
        for i in 0..500 { tx1.send(i).unwrap(); }
    });

    std::thread::spawn(move || {
        for i in 500..1000 { tx2.send(i).unwrap(); }
    });

    // Select：从多个通道中选择一个就绪的
    let mut sel = Select::new();
    sel.recv(&rx1);
    sel.recv(&rx2);
    let res = sel.select();

    // 性能对比（10^7 次消息传递）：
    // std::sync::mpsc:  ~120ms
    // crossbeam-channel: ~25ms（快 4.8x）
}

6.4 async/await：异步编程的底层机制

6.4.1 Future 的状态机转换

async/await 在编译时被转换为一个状态机（state machine），存储在实现了 Future trait 的结构体中。理解这一点对于调试异步代码至关重要：

// 异步代码：
async fn fetch_and_process(url: &str) -> Result<String, Error> {
    let response = reqwest::get(url).await?;     // 状态 0 → 1
    let body = response.text().await?;           // 状态 1 → 2
    Ok(body.to_uppercase())                      // 状态 2 → 3
}

// 编译器生成的状态机（伪代码）：
enum FetchAndProcessFut {
    Initial { url: String },
    WaitingGet { url: String, future: GetFuture },
    WaitingText { response: Response, future: TextFuture },
    Done { result: Result<String, Error> },
}

impl Future for FetchAndProcessFut {
    type Output = Result<String, Error>;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        match self.get_mut() {
            FetchAndProcessFut::WaitingGet { future, .. } => {
                match future.as_mut().poll(cx) {
                    Poll::Ready(Ok(response)) => {
                        // 推进到下一个状态
                        *self.get_mut() = FetchAndProcessFut::WaitingText {
                            response,
                            future: response.text(),
                        };
                        return self.poll(cx);  // 继续 poll
                    }
                    Poll::Ready(Err(e)) => return Poll::Ready(Err(e)),
                    Poll::Pending => return Poll::Pending,
                }
            }
            // ... 其他状态
        }
    }
}

6.4.2 Pin 和 Unpin 的精确语义

Pin<P> 确保被引用的数据在内存中的位置不会被移动。这对于实现自引用结构体和异步代码至关重要：

use std::pin::Pin;
use std::future::Future;
use std::task::{Context, Poll};

// Pin<&mut T> 保证 T 在 poll 之间不会被移动
// 这是 Future trait 签名要求的根本原因：
//   fn poll(self: Pin<&mut Self>, ...) -> Poll<Output>

// 为什么需要 Pin？
// 异步状态机可能包含自引用指针：
// struct SelfRefStruct {
//     data: String,
//     data_ptr: *const u8,  // 指向 data 的内部指针
// }
// 如果这个结构体被移动（如 swap、重新分配），data_ptr 会失效。
// Pin 阻止了这种移动。

// Unpin 是反向标记特质：
// - 大多数类型默认是 Unpin（可以被移动）
// - 只有明确实现 !Unpin 的类型才是 Pin 敏感的
// - Future trait 要求 Self: Unpin 才能在栈上移动

6.5 Tokio 运行时详解

6.5.1 单线程 vs 多线程运行时

// 单线程运行时（适合纯 IO 密集型）
#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        println!("Running on the main reactor thread");
    });
    handle.await.unwrap();
}

// 多线程运行时（适合混合负载）
#[tokio::main(flavor = "multi_thread", worker_threads = 4)]
async fn main() {
    // 4 个工作线程，每个都有自己的事件循环（reactor）
    // IO 事件分布到多个线程，避免单点瓶颈
}

// 性能对比（10^8 次异步操作）：
// 单线程：  ~50ms（受限于单个 CPU 核心）
// 4 线程：  ~15ms（充分利用多核）
// 8 线程：  ~10ms（IO 密集型场景收益递减）
// 16 线程： ~9ms（上下文切换开销开始抵消收益）

6.5.2 Tokio 最佳实践

use tokio::time::{timeout, Duration};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 最佳实践 1：使用 spawn_blocking 避免阻塞事件循环
    let result = tokio::task::spawn_blocking(|| {
        // 同步的 CPU 密集型操作
        expensive_computation()
    }).await?;

    // 最佳实践 2：使用 timeout 防止永久挂起
    let result = timeout(Duration::from_secs(30), fetch_data("https://api.example.com"))
        .await
        .map_err(|_| "Request timed out")?;

    // 最佳实践 3：使用 JoinSet 管理任务集合
    use tokio::task::JoinSet;
    let mut set = JoinSet::new();
    for url in &urls {
        set.spawn(fetch_data(url));
    }
    while let Some(result) = set.join_next().await {
        match result {
            Ok(data) => println!("Got: {}", data),
            Err(e) => eprintln!("Task failed: {}", e),
        }
    }

    Ok(())
}

fn expensive_computation() -> u64 {
    (0..10_000_000).fold(0u64, |acc, x| acc + x)
}

async fn fetch_data(url: &str) -> Result<String, reqwest::Error> {
    reqwest::get(url).await?.text().await
}

6.6 并发编程的高级优化

6.6.1 无锁数据结构和原子操作

use std::sync::atomic::{AtomicU64, Ordering};
use crossbeam::queue::ArrayQueue;

// 无锁队列：比 Mutex + Channel 快 5-10x
let queue = ArrayQueue::new(10000);

// 原子计数器：比 AtomicU64::fetch_add 更轻
static REQUEST_COUNT: AtomicU64 = AtomicU64::new(0);

fn handle_request() {
    REQUEST_COUNT.fetch_add(1, Ordering::Relaxed);
    // 处理请求...
}

// 原子操作的性能对比（10^9 次操作）：
// Ordering::Relaxed:     ~0.5ns（仅保证原子性）
// Ordering::Acquire:     ~1.0ns（读屏障）
// Ordering::Release:     ~1.0ns（写屏障）
// Ordering::AcqRel:      ~1.5ns（读写屏障）
// Ordering::SeqCst:      ~2.0ns（默认，最强一致性）

6.6.2 细粒度锁 vs 粗粒度锁

// 粗粒度锁：整个 HashMap 一把锁
use std::collections::HashMap;
use std::sync::{Arc, Mutex};

type SharedCache = Arc<Mutex<HashMap<String, String>>>;

// 细粒度锁：分片（sharded）锁，减少竞争
use std::sync::RwLock;

const NUM_SHARDS: usize = 16;

struct ShardedCache {
    shards: [Arc<RwLock<HashMap<String, String>>>; NUM_SHARDS],
}

impl ShardedCache {
    fn get(&self, key: &str) -> Option<String> {
        let shard = &self.shards[hash(key) % NUM_SHARDS];
        shard.read().unwrap().get(key).cloned()
    }

    fn set(&self, key: String, value: String) {
        let shard = &self.shards[hash(&key) % NUM_SHARDS];
        shard.write().unwrap().insert(key, value);
    }
}

// 性能对比（100 个线程并发读写 1000 个键）：
// 粗粒度 Mutex:   ~120ms（所有线程排队）
// 细粒度 RwLock:  ~35ms（16 个分片，竞争减少 16 倍）

6.7 本章小结

关键要点
  • Send/Sync：编译器自动派生的空特质，Send 表示可跨线程转移，Sync 表示可跨线程共享引用
  • Mutex vs RwLock：短临界区和写多读少用 Mutex；读多写少（>10:1）用 RwLock
  • 死锁预防：锁排序、try_lock、超时机制
  • Channels：std::sync::mpsc 够用，crossbeam-channel 快 4-10x
  • async/await：编译为状态机，需要 executor 驱动，Pin 保证内存位置不变
  • Tokio：多线程运行时适合混合负载，spawn_blocking 避免阻塞事件循环
  • 原子操作：Relaxed 最快（0.5ns），SeqCst 最安全（2.0ns）
  • 无锁数据结构：crossbeam::queue 比 Mutex 快 5-10x
