第 2 章：三大基石 — NetworkIdentity / NetworkServer / NetworkClient

如果说 Mirror 是一座建筑，那么这三者就是它的承重墙。 不理解它们的精确含义和行为边界，后续所有代码都会埋下隐患。 本章将逐一拆解，并给出真实项目中会遇到的陷阱。

2.1 NetworkIdentity：网络对象的身份证

NetworkIdentity 是附加在 GameObject 上的组件。 它的作用只有一个：告诉 Mirror"这个对象是网络对象"。

Mirror 通过它来区分：
• 这个对象需要通过网络同步吗？→ 有 NetworkIdentity → 需要
• 这个对象只是本地表现吗？→ 没有 NetworkIdentity → 不需要

2.1.1 关键属性

// 在 Inspector 中设置，或代码赋值
identity.isServer = true;   // 仅在服务器端有效
identity.isClient = true;   // 仅在客户端有效
identity.netId = 12345;     // 自动分配，唯一标识此网络对象

// 只读属性（运行时由 Mirror 自动管理）
identity.hasAuthority = false;   // 此客户端是否拥有此对象的所有权
identity.connectionToServer;     // 连接到服务器的 NetworkConnection
identity.connectionToClient;     // 服务器的连接引用（服务器端）

NetID（网络 ID）是什么？

每个被 Spawn 到场景中的网络对象都有一个唯一的 netId。 它是一个 uint 类型，由服务器分配，全局唯一。 你通过 netId 可以引用任何已 Spawn 的对象——无论它在哪个客户端上。

NetId 的生命周期：
• Spawn 时分配 → • 对象销毁时回收 → • 不会重复使用（在同一局游戏中）

2.1.2 Observed Components：谁在驱动同步？

NetworkIdentity 有一个 Observed 字段，通常会自动填入同一个 GameObject 上的 NetworkTransform 或其他同步组件。它的作用是：

"告诉服务器，这个对象的哪些组件需要被监控和同步。"

在大多数情况下，你不需要手动设置它——当你添加 NetworkTransform 时， Mirror 会自动将它加入 Observed 列表。但理解它的存在很重要，因为：

  • Observed 组件的 OnPreSend / OnPostSend 方法控制着同步频率和条件
  • 如果 Observed 组件返回 "没有变化"，Mirror 会跳过序列化，节省带宽

2.1.3 Asset ID：Prefab 层面的身份

每个 Prefab 在导出为 Asset Bundle 或通过 Resources.Load 加载时， 会有一个 Asset ID（一个 GUID）。Spawn 时，客户端收到的是 netId + assetId， 然后客户端根据 assetId 找到对应的 Prefab 实例化出来。

常见错误：在运行时用 Instantiate(prefab) 创建对象， 但没有通过 NetworkServer.Spawn() 注册。结果就是这个对象对所有客户端不可见—— 因为你创建了 GameObject，但没有告诉 Mirror 它是网络对象。

2.2 NetworkBehaviour：所有网络脚本的基类

在 Mirror 中，你不能直接把普通的 MonoBehaviour 放在网络对象上。 必须继承 NetworkBehaviour：

// ❌ 错误：普通 MonoBehaviour 不能放在网络对象上
public class PlayerController : MonoBehaviour { ... }

// ✅ 正确：继承 NetworkBehaviour
public class PlayerController : NetworkBehaviour { ... }

NetworkBehaviour 提供了几个关键属性，你在每个网络脚本中都会用到：

public class PlayerController : NetworkBehaviour
{
    void Update()
    {
        // 这些属性决定代码在当前实例上是否应该执行
        if (isServer)
        {
            // 这段代码只在服务器实例上运行
            ValidatePlayerInput();
        }

        if (isClient)
        {
            // 这段代码只在客户端实例上运行
            UpdateVisuals();
        }

        if (isLocalPlayer)
        {
            // 这段代码只对"玩家自己的角色"运行
            HandleLocalInput();
        }

        // 注意：hasAuthority 表示"我是否拥有这个对象的控制权"
        // 对于 Player 对象，拥有者通常是绑定它的客户端
        if (hasAuthority)
        {
            // 只有对象的拥有者才能操控它
            MovePlayer();
        }
    }
}
关键区别：isLocalPlayer vs hasAuthority
• isLocalPlayer：这个对象是"我的玩家角色"。
• hasAuthority：我有权控制这个对象。

对于 Player 对象，两者通常都为 true。但对于非 Player 的网络对象（如队友的角色、共享道具）， 可能有 authority 但不是 local player，或者反过来（某些特殊场景）。

2.3 NetworkServer：服务器端的上帝模式

NetworkServer 是服务器端的单例管理器。 它掌控着服务器上的一切网络状态：

// 核心属性
NetworkServer.connections       // 所有已连接的客户端
NetworkServer.localConnection   // 本地连接（Host 模式下使用）
NetworkServer.active            // 服务器是否正在运行

// 核心方法
NetworkServer.Listen(100);                    // 启动服务器，最大 100 连接
NetworkServer.Shutdown();                     // 关闭服务器
NetworkServer.Spawn(playerObject);            // 生成网络对象
NetworkServer.Destroy(playerObject);          // 从服务器上销毁对象
NetworkServer.RemoveConnection(client);       // 踢出客户端

// 注册自定义消息处理器
NetworkServer.RegisterHandler<MyMessage>(OnMyMessage, replace: true);

2.3.1 服务器上的对象管理

当一个对象通过 NetworkServer.Spawn() 生成后，Mirror 会在服务器内部维护一个字典： netId → NetworkIdentity。这个映射贯穿整个游戏生命周期。

// 在服务器端生成一个敌人
GameObject enemyPrefab = Resources.Load<GameObject>("Enemies/Boss");
GameObject enemyInstance = Instantiate(enemyPrefab);

// 关键：用 NetworkServer.Spawn 而不是 Instantiate
NetworkServer.Spawn(enemyInstance);

// 如果需要指定位置
NetworkServer.SpawnWithPosition(enemyInstance.transform.position, Quaternion.identity);
致命错误：以下代码在服务器上是无效的 Spawn： 
// ❌ 错误：只用 Instantiate，没调用 NetworkServer.Spawn
GameObject enemy = Instantiate(enemyPrefab, position, rotation);
这个对象存在于服务器的 GameObject 层级中，但 Mirror 不知道它的存在。 客户端永远不会收到它的 Spawn 消息，服务器上也无法对它调用 RPC。

2.4 NetworkClient：客户端的连接管理器

NetworkClient 是客户端端的单例管理器：

// 核心属性
NetworkClient.isConnected           // 是否已连接
NetworkClient.connection            // 主连接对象
NetworkClient.connections           // 多连接支持（高级用法）
NetworkClient.active                // 客户端是否活跃

// 核心方法
NetworkClient.Connect(new ConnectMessage
{
    host = "192.168.1.100",
    port = 7777,
    isAuthenticated = true,
    userId = 0
});

NetworkClient.Disconnect();                      // 断开连接
NetworkClient.PrepareToSpawnObjects();           // 准备 Spawn（场景切换时用）

2.4.1 客户端的对象接收

当服务器 Spawn 一个对象时，客户端并不会"手动创建"它。 流程是这样的：

1

服务器发送 Spawn 消息

服务器向所有客户端广播一条消息，包含：
• assetId（Prefab 标识）
• netId（对象唯一 ID）
• 初始状态数据（序列化后的 SyncVar 值）

2

客户端查找 Prefab

客户端收到消息后，根据 assetId 在已注册的 Prefab 池中查找对应模板。

3

客户端 Instantiate

用找到的 Prefab 模板实例化对象，设置 netId，初始化 SyncVar 值。

4

客户端回调

触发 OnStartServer、OnStartClient 等生命周期方法。

这意味着：客户端的 Spawn 对象必须是预制体注册过的。 你不能用 Resources.Load 动态加载一个从未注册过的 Prefab 然后 Spawn—— 客户端找不到 assetId 对应的模板。

2.5 NetworkManager：开箱即用的胶水

NetworkManager 是 Mirror 提供的最高层抽象。 它把连接流程、场景管理、Player Spawn、对象重置等琐碎工作都封装好了。

public class MyNetworkManager : NetworkManager
{
    [Header("Prefab 注册")]
    public GameObject playerPrefab;

    [Header("Spawn 点")]
    public GameObject[] spawnPoints;

    public override void StartServer()
    {
        base.StartServer();

        // 注册 Player Prefab
        // 这告诉 Mirror："当需要生成 Player 对象时，用这个 Prefab"
        AddPlayerPrefab();
    }

    public override void OnServerAddPlayer(NetworkConnection conn)
    {
        // 当新客户端连接时，生成它的 Player 对象
        GameObject player = Instantiate(playerPrefab, GetSpawnPosition(), Quaternion.identity);

        // 告诉 Mirror 这个对象属于哪个客户端
        NetworkServer.AddPlayerForConnection(conn, player);
    }

    Vector3 GetSpawnPosition()
    {
        // 随机选择 Spawn 点
        if (spawnPoints.Length == 0) return Vector3.zero;
        Vector3 pos = spawnPoints[Random.Range(0, spawnPoints.Length)].transform.position;
        return pos;
    }
}

2.5.1 NetworkManager 的生命周期钩子

钩子方法运行环境典型用途
OnServerStarted()服务器服务器启动后的初始化
OnServerConnect(NetworkConnection conn)服务器客户端连接时的回调
OnServerDisconnect(NetworkConnection conn)服务器客户端断开时的清理
OnServerAddPlayer(NetworkConnection conn)服务器为新客户端生成 Player 对象
OnClientConnected()客户端连接成功后的初始化
OnClientDisconnected()客户端断线清理
OnServerRemovePlayer(NetworkConnection conn)服务器移除玩家的 Player 对象

2.6 实战：从零搭建最小可运行联网项目

让我们把所有概念串起来，搭建一个最简单的可运行项目。

步骤 1：创建 Player Prefab

// PlayerController.cs
using UnityEngine;
using Mirror;

public class PlayerController : NetworkBehaviour
{
    [SerializeField] float moveSpeed = 5f;

    void Update()
    {
        // 只有本地玩家才能控制这个角色
        if (!isLocalPlayer) return;

        float h = Input.GetAxis("Horizontal");
        float v = Input.GetAxis("Vertical");

        // 移动 — 注意：这是客户端的"表现移动"
        // 真正的权威位置由服务器决定
        transform.Translate(h * moveSpeed * Time.deltaTime, 0, v * moveSpeed * Time.deltaTime);
    }

    // 服务器端调用的移动请求
    [Command]
    void CmdRequestMove(Vector3 direction)
    {
        // 服务器验证并执行移动
        if (direction.sqrMagnitude > 1f)
            direction.Normalize();

        transform.Translate(direction * moveSpeed * Time.deltaTime);

        // 同步新位置给客户端
        RpcUpdatePosition(transform.position);
    }

    [TargetRpc]
    void RpcUpdatePosition(Vector3 position)
    {
        transform.position = position;
    }
}

步骤 2：配置 NetworkManager

在场景中创建一个空的 GameObject，添加 NetworkManager 组件， 然后在 Inspector 中设置：

  1. Player Prefab：拖入你的 Player Prefab
  2. Offline Scene / Online Scene：设置离线和联机场景
  3. Port：默认 7777

步骤 3：配置 Transport

在 NetworkManager 的 Transport 组件中，选择传输协议。 对于开发阶段，推荐使用默认的 UnityTransport（基于 UTP）或 KCP with No Delay。

选择建议：
• TCP（HTTP/TCP） → 可靠、有序，但头块堆积（HOL）问题
• KCP → 可靠、快速重传，适合竞技游戏
• UDP（未加密） → 最快，但不保证送达和顺序
• WebSocket → 用于浏览器端客户端

步骤 4：运行测试

1

在 Unity Editor 中点击 "Host"

当前实例同时作为服务器和客户端启动。你可以看到自己的 Player 对象被生成了。

2

再打开一个 Editor 实例，点击 "Client"

第二个实例连接到第一个实例。现在你有两个 Player 对象了。

3

构建服务器

# 在 CI 或部署时编译专用服务器
BuildTarget ServerBuild
./YourGame.exe -batchmode -nographics -dedicated

2.7 常见陷阱与调试技巧

陷阱 1：在客户端修改了服务器上的数据

// ❌ 危险：没有环境检查
public void TakeDamage(float amount)
{
    health -= amount;  // 客户端也能调用！
}

// ✅ 正确：确保只有服务器能修改
public void TakeDamage(float amount)
{
    if (!isServer) return;  // 客户端调用直接返回
    health -= amount;
    RpcUpdateHealth(health); // 同步给客户端
}

陷阱 2：Spawn 顺序错误

// ❌ 错误：先添加子组件，后注册 Prefab
NetworkServer.Spawn(parent);       // 先生成父对象
// 此时子对象的 NetworkIdentity 还没准备好

// ✅ 正确：先确保所有 NetworkIdentity 都正确配置
// 然后在 NetworkManager 中注册 PlayerPrefab
manager.playerPrefab = playerPrefab;
NetworkServer.Listen(100);
// 连接后自动 Spawn

陷阱 3：IsServer / IsClient 在 Awake 时为 false

void Awake()
{
    // ❌ 这些在这里都是 false！
    Debug.Log(isServer);   // false
    Debug.Log(isClient);   // false

    // ✅ 正确的初始化时机：
}

void OnStartServer()
{
    // ✅ 服务器端初始化放这里
    Debug.Log(isServer);   // true
}

void OnStartClient()
{
    // ✅ 客户端端初始化放这里
    Debug.Log(isClient);   // true
}
为什么 Awake 时是 false？ 因为 NetworkIdentity 的网络状态是在连接建立后才设置的。 Awake 执行时，网络模块可能还没有初始化。 Mirror 专门设计了 OnStartServer / OnStartClient 等生命周期钩子， 保证在这些方法被调用时，网络状态已经就绪。

调试技巧：使用 Mirror 内置日志

Mirror 在 Console 中输出详细的网络日志。你可以在代码中控制日志级别：

// 开启详细日志
Logger.LogLevel = LogLevel.Debug;

// 常用级别
LogLevel.Fatal     // 致命错误
LogLevel.Error     // 错误
LogLevel.Warning   // 警告（默认级别）
LogLevel.Info      // 信息
LogLevel.Debug     // 调试（大量输出）

你还可以在 NetworkServer 和 NetworkClient 上注册自定义消息处理器来追踪数据流：

// 服务器端：打印所有收到的消息
NetworkServer.RegisterHandler<RpcMessage>(msg =>
{
    Debug.Log($"[Server] 收到 RPC 消息: {msg}");
}, replace: true);

2.8 本章小结

本章我们建立了 Mirror 的核心认知模型：

  • NetworkIdentity 是网络对象的身份证——没有它，Mirror 完全不知道这个对象的存在
  • NetworkServer 是服务器的上帝——管理所有连接和 Spawn 的对象，一切逻辑的权威
  • NetworkClient 是客户端的窗口——负责连接、接收消息、表现同步
  • NetworkBehaviour 是所有网络脚本的基类——提供 isServer / isClient / isLocalPlayer 等环境判断
  • NetworkManager 是胶水——把连接、Spawn、场景切换串联起来

下一章，我们将深入通信机制：RPC 和 SyncVar——这是你和服务器、客户端之间对话的语言。

自测题

点击展开自测题
  1. 代码分析：以下代码有什么问题？如何修复？ 
    public class HealthSystem : NetworkBehaviour
{
    public int health = 100;

    public void Damage(int amount)
    {
        health -= amount;
        if (health <= 0)
            Die();
    }
}
  2. 场景推理：服务器 Spawn 了一个对象 A，然后销毁了它。 此时客户端收到了 Destroy 消息但延迟了 500ms。在这 500ms 内， 客户端还能对对象 A 调用 RPC 吗？为什么？
  3. 设计题：你需要在一个网络对象上存储一个玩家的名字字符串。 这个名字在对象 Spawn 时由服务器设定，之后所有客户端都需要看到相同的值。 你会用 SyncVar 还是其他方式？为什么？
参考答案： 1) Damage 方法没有 isServer 检查，客户端可以直接调用并修改服务器状态。 修复：改为 [Command] 方法，或在方法开头加 if (!isServer) return; 2) 不能。客户端收到 Destroy 消息后，对象已从客户端的 Spawn 列表中移除， 调用 RPC 时会报 "unknown netId" 错误。 3) 用 SyncVar。名字是"状态数据"，不是"动作指令"——它需要在服务器修改后自动同步到所有客户端。
