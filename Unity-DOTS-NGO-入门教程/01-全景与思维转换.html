01　全景与思维转换：从 OOP 到 DOD

在写任何 ECS 代码之前，这一章只解决一件事：让你明白自己熟悉的那套写法在什么规模下会失灵，以及 DOTS 用什么思路替代它。概念看似“虚”，但后面所有 API 设计都是这些思路的直接结果——不懂这一章，写 ECS 会觉得处处别扭。

1.1 先看一个你写过一百遍的写法

假设做一款割草游戏，场景里有一万个敌人，每个敌人要移动、掉血、死亡。典型的面向对象写法是一个基类加一堆子类：

public abstract class EnemyBase : MonoBehaviour
{
    public float Health;
    public float MoveSpeed;

    protected virtual void Update()
    {
        Vector3 target = FindTarget();
        transform.position = Vector3.MoveTowards(
            transform.position, target, MoveSpeed * Time.deltaTime);
    }

    public virtual void TakeDamage(float damage)
    {
        Health -= damage;
        if (Health <= 0f) Destroy(gameObject);
    }
}

对象少的时候没有任何问题。但当数量从几十个涨到上万个，引擎会撞上三堵墙，而这三堵墙都不是“优化一下代码”能绕过去的，因为它们来自语言和硬件层面。

1.2 第一堵墙：CPU 缓存未命中

这是最反直觉、也最关键的一点。现代 CPU 的运算速度远远快于内存速度：一次 L1 缓存访问大约 1 纳秒，而一次主内存访问大约 100 纳秒，差距约百倍。CPU 并不会一次只取一个字段，而是以缓存行（cache line，通常 64 字节）为单位把相邻数据整块搬进缓存。

面向对象的内存布局是这样的：每个 EnemyBase 是堆上的一个独立对象，对象之间由谁先创建、GC 怎么移动决定，地址上互不相邻。更糟的是，一个对象里塞了它的全部字段——血量、速度、引用、状态机、缓存的组件引用。当 Update 只想读取 MoveSpeed 时，CPU 仍然把整个对象所在的缓存行拉进来，里面大半数据这次根本用不上。

关键认知：性能瓶颈往往不是“算得慢”，而是“等数据”

遍历一万个零散对象做简单的浮点运算，CPU 大量时间花在等待内存把数据送过来，真正的计算单元是空转的。这不是算法复杂度问题，O(n) 依然是 O(n)，常数项却被硬件延迟放大了。

数据导向设计（Data-Oriented Design，DOD）的对策是把同一种数据连续排列。如果一万个敌人的移动速度是一个连续的 float[]，CPU 读第一个元素时，会顺带把后面十几个速度一起搬进缓存，接下来的遍历几乎全部命中缓存。这就是 ECS 内存布局的底层逻辑，第二章会看到它具体怎么实现。

1.3 第二堵墙：GC 停顿

MonoBehaviour 是引用类型，运行在托管堆上，由垃圾回收器管理。游戏逻辑里常见的字符串拼接、Lambda 捕获、装箱、每帧 new 集合，都会产生垃圾。GC 触发时需要扫描堆、整理对象，表现为周期性的帧率尖峰——在动作游戏里就是“每隔几秒卡一下”。

DOTS 的应对分两层：

  • ECS 的组件默认是非托管的 struct，实体数据存在原生内存里，不经过 GC；
  • Burst 编译后的代码运行在原生层面，Unity.Collections 提供 NativeArray、NativeList 等非托管容器替代 List<T>。
注意一个正在收紧的趋势：Unity 6.6 已经把托管组件（class 形式、或含 string 等引用字段的 IComponentData）标记为弃用。官方给出的替代是 UnityObjectRef<T>、FixedString、DynamicBuffer 和 BlobAsset。这意味着从第一天起就该习惯“组件里只有非托管字段”这条纪律，第六章会逐项讲替代方案。

1.4 第三堵墙：主线程单线程

Unity 的 MonoBehaviour 回调全部在主线程执行，而现在的 CPU 早已不靠提升单核频率取胜，而是靠堆核心数——笔记本 8 核、台式机 16 核是常态。一万个敌人的移动逻辑彼此独立，天然可以并行，却被挤在一个线程里串行执行。

直接上手写 Thread 或 Task 是灾难性的：你要自己处理和引擎的同步、数据竞争、时序。DOTS 给出的方案是 C# Job System——把“对一批数据做同一件事”描述成一个 Job，由引擎配合安全检查调度到多核 Worker 线程，再加上 Burst 编译器把 IL 翻译成高度优化的原生 SIMD 机器码。第五章会详细展开。

1.5 数据导向设计到底是什么

一句话概括两种设计的提问顺序：

面向对象（OOP）问的是数据导向（DOD）问的是
这是个什么对象？它有哪些行为？它继承谁？

数据被封装在对象内部，按“名词”组织代码。 		程序要处理哪些数据？这些数据在内存里怎么布局？哪些线程在什么时机读写它们？

行为从数据中剥离，按“数据的变换过程”组织代码。

这不是说 OOP 错了。UI、编辑器工具、玩法原型、数量有限的管理器对象，OOP 的封装和多态依然是最顺手的工具。DOD 针对的是大规模、同质化、需要高性能的模拟数据。Unity 也没有让你二选一——GameObject 和实体可以在同一个项目里共存，这正是第三章 Baker 工作流和第十章混合工作流存在的意义。

1.6 DOTS 的组成全景

DOTS 不是一个单一插件，而是一组互相咬合的技术包：

flowchart TB
    subgraph DOTS["DOTS 技术栈"]
        ENT["Entities
ECS 运行时：实体、组件、系统"]
        JOB["C# Job System
多核任务调度（引擎内置）"]
        BURST["Burst Compiler

        COL["Collections
NativeArray / NativeList 等非托管容器"]
        GRAPH["Entities Graphics
面向实体的批量渲染"]
    end
    JOB --> BURST
    COL --> JOB
    ENT --> JOB
    ENT --> GRAPH
  • Entities：ECS 的核心运行时，负责实体的存储、查询与系统调度。
  • C# Job System：Unity 引擎内置的多线程作业系统，DOTS 复用它而不是另造一套。
  • Burst：基于 LLVM 的编译器，读取 Job 和 System 中的数学运算，生成利用 SIMD 指令集的原生代码，同时对非法写法做编译期检查。
  • Collections：非托管数据结构库，是 Job 之间传递数据的标准载体。
  • Entities Graphics：让渲染管线基于实体数据做 GPU 批量绘制，替代逐个 GameObject 的渲染开销。

1.7 澄清一个最容易混淆的问题：DOTS 和 NGO 是什么关系

这是本教程标题里两个名词的关系，必须先讲清楚，否则第十章会听得很混乱。Unity 目前有两套并存的多人网络栈：

Netcode for GameObjects（NGO）Netcode for Entities
面向的工作流 GameObject + MonoBehaviour Entities + ECS
抽象层级 高层 API：NetworkObject、NetworkBehaviour、RPC 底层框架：Ghost 快照、客户端预测、命令同步
适用规模 中小规模联机（合作、对抗房间） 大规模、高 tick 频率的多人模拟

注意命名：Netcode for GameObjects 不属于 DOTS，它是 GameObject 工作流的网络库；DOTS 原生的网络方案叫 Netcode for Entities。两者的关系在 2026 年又有了新变化——NGO 3.x 底层开始依赖 Netcode for Entities 包，并引入了连接两者的混合预制体（实验性）。这些细节第十章再讲，现在只要记住它们是两个层面的东西。

学习顺序建议：先学 DOTS（第 2–7 章），再学 NGO（第 8–9 章）。因为 NGO 3.x 已经建立在 Entities 包之上，理解了 ECS 再看它的依赖和混合方案不会发怵；反过来先学网络再补 ECS，会在第十章被概念债卡住。

1.8 需要提前建立的三个心理预期

1

不再有“挂在物体上的脚本”

ECS 里行为集中在 System 中，系统查询“所有满足条件的实体”然后批量处理。你不会再把脚本拖到某个物体上，取而代之的是写一个查询条件。

2

“改结构”是昂贵且需要报备的操作

增删组件、销毁实体属于结构变更，会影响内存布局，不能在并行 Job 里随手做，必须通过 EntityCommandBuffer 排队。这是第七章的主题，也是新手报错最多的地方。

3

编译器会变成你的同事

Burst 和 Job 安全系统会拒绝大量在 C# 里合法、但在多线程/原生环境下危险的写法（托管对象、静态变量、越界访问）。初期你会觉得被处处针对，但这些报错替你挡掉的是最难调试的竞态问题。

思考与练习

  1. 打开你自己的一个旧项目，找出三个“每帧遍历一批同类对象”的 Update。估算这批对象的数量级，判断它们是否属于 DOTS 适合接管的场景。
  2. 如果把一个敌人的 Transform、血量、AI 状态全存在同一个对象里，遍历移动速度时缓存行里浪费了哪些数据？试着在纸上画出 OOP 布局和连续 float[] 布局的对比。
  3. 用自己的话回答：为什么“把 Update 里的逻辑写得更高效”解决不了缓存未命中？

本章小结

  • 大规模 MonoBehaviour 模拟会撞上三堵硬件/语言层面的墙：缓存未命中、GC 停顿、单线程瓶颈。
  • DOD 的核心是先设计数据布局：同类数据连续存放、行为与数据分离、显式控制线程与时序。
  • DOTS = Entities + Job System + Burst + Collections + Entities Graphics，是一组协同技术而非单个插件。
  • NGO 是 GameObject 网络栈，Netcode for Entities 才是 DOTS 网络栈；NGO 3.x 开始在底层依赖后者。
  • DOTS 不要求推翻重写，GameObject 与实体可以混合共存。
