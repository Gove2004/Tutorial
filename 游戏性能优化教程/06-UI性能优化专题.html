UI 性能优化专题

模块二 · 优化策略实战 ｜ 对应原文策略 2、11，并结合 UGUI 机制展开

UI 是游戏里最容易被忽视的性能热点。逻辑上它只是“几个面板”，但在复杂项目里，UI 元素数量可能远超场景物体，且大量 UI 是半透明的，天然带来 Overdraw。本章先讲清楚 UGUI 最核心的 Canvas 重建机制，再覆盖 3D UI、管线分离、字体描边与图集治理。

6.1 Canvas 重建机制：一个元素变化，整个画布重算

UGUI 的更新遵循“脏标记 → 重建”模型。当一个 UI 元素变化时，它会被标记为布局脏（Layout Dirty）或顶点脏（Vertices Dirty），并向上冒泡。在 Canvas 触发重建（WillRenderCanvases）时，会遍历该 Canvas 下所有被标记的元素，重新计算布局并重建顶点缓冲。

关键陷阱：重建的成本与 Canvas 内元素总数相关，而不只是变化的元素。如果一个含上千元素的大 Canvas 里只有一个小图标在闪烁，每次闪烁都可能导致整个 Canvas 重新遍历。这就是 UI 卡顿最常见的根源。

Canvas 拆分原则

  • 静态与动态分离：不变的背景、装饰放进静态 Canvas；频繁变化的血条、计时器、动画放进独立小 Canvas，把重建范围限制在小画布内。
  • 按功能区域拆分：不同面板、不同 HUD 区域各自独立，避免打开一个面板影响到其他区域。
  • 嵌套 Canvas 用于隔离冒泡：子 Canvas 可以阻止脏标记继续向上传播。
Canvas 不是越多越好：跨 Canvas 的元素无法合批，每个 Canvas 至少产生独立批次，Canvas 过多会推高 Draw Call。拆分目标是隔离“高频变化”，而不是给每个元素都建 Canvas，需要在重建成本与批次数之间权衡。

6.2 策略 2：3D UI

部分 UI 可以用 3D 面片实现以替代传统 UGUI，从而直接复用引擎已有的材质系统、图集、合批机制与渲染管线。这种方式特别适合小地图以及一些特殊 UI——它们本质上更接近“贴在面片上的纹理”，没有复杂的布局与交互需求，用 3D 渲染反而能与场景对象一起合批，避免 UI 与 3D 两套体系的重复开销。

6.3 策略 11：UI 渲染管线分离

UI 渲染与 3D 场景渲染的需求差异明显：3D 需要完整的空间剔除、光照、阴影，而 UI 基本是屏幕空间的二维绘制。把 UI Camera 与 3D Camera 的渲染管线拆分，可以减少两条管线之间的重复计算。

  • UI 元素几乎都位于屏幕范围内，因此 UI 管线可以减少不必要的 Camera Culling 计算。
  • 独立的 UI 管线可以跳过光照、阴影等与 UI 无关的特性。
  • 避免 3D 场景的一些全屏 Pass 误作用于 UI 层。

6.4 字体、描边与顶点放大

文字组件上的视觉修饰会成倍增加顶点数，这是容易被忽略的隐性成本：

组件顶点放大说明
普通文本1 倍基准每个字符四边形
Shadow（阴影）约 2 倍额外复制一份偏移顶点
Outline（描边）约 5 倍四个方向各复制一份顶点

原文建议低端机降低字体描边质量甚至直接关闭。此外，动态字体图集在遇到图集外字符时会触发重建，运行时大量生僻字还可能撑爆图集；项目应尽量使用预生成字符集或 TextMeshPro 并固化字体资产。

6.5 UI Overdraw 与图集治理

UI 是半透明 Overdraw 的主要来源。常见问题包括：全屏不透明背景之上再叠多层半透明面板、用大尺寸透明图做 Mask、圆角矩形叠层。应在 Overdraw 调试视图中定位高重叠区域，移除不可见的底层背景，Mask 优先用矩形裁剪而非像素级透明遮罩。

  • 图集：同一面板、同一批次的 Sprite 必须打进同一图集，散图会打断合批。
  • 避免同一贴图被重复打进多个图集，造成内存翻倍。
  • 控制图集尺寸，移动端单张图集通常不超过 2048，超大图集既浪费内存又降低采样效率。

6.6 工程实现：节流的 UI 刷新

很多 UI 刷新是被数据变化事件高频触发的，但视觉上不需要这么快响应。对刷新做节流合并，可以把一帧内的多次变化收敛为一次重建：

using System;
using UnityEngine;

public class ThrottledLabel : MonoBehaviour
{
    private Action refresh;
    private bool queued;
    [SerializeField] private float interval = 0.1f;
    private float nextAllowed;

    public void Bind(Action onRefresh)
    {
        refresh = onRefresh;
    }

    public void RequestRefresh()
    {
        if (queued) return;
        queued = true;

        float wait = Mathf.Max(0f, nextAllowed - Time.unscaledTime);
        Invoke(nameof(Flush), wait);
    }

    private void Flush()
    {
        queued = false;
        nextAllowed = Time.unscaledTime + interval;
        refresh?.Invoke();
    }

    void OnDisable()
    {
        CancelInvoke();
        queued = false;
    }
}

6.7 原文归纳的三类 UI 性能问题

  1. 事件响应产生冗余：数据事件被重复监听、面板未取消订阅导致刷新放大。
  2. UI 重建产生额外开销：大 Canvas 内高频变化触发整画布重建。
  3. 面板更新存在冗余：隐藏面板仍在刷新、不可见区域仍在重算。

练习与思考

基础练习拆分 Canvas

检查项目中最大的一个 Canvas，列出其中的静态与动态元素，给出拆分方案，并用 Profiler 对比拆分前后 Canvas.BuildBatch 的耗时。

思考题顶点预算

一个带 Outline 的文本列表有 50 行，每行 10 个字符。估算描边让该列表的顶点数膨胀了多少，并判断在低端机上是否值得保留描边。

进阶挑战隐藏即停

实现一套机制，保证面板被关闭或移出屏幕时，其所有刷新请求与事件监听都被挂起，重新显示时再恢复。

本章小结

  • UGUI 采用脏标记重建，重建成本与 Canvas 元素总数相关；用静态/动态分离和子 Canvas 限制重建范围。
  • 3D UI 复用引擎材质与合批体系，适合小地图等二维面片型界面。
  • UI 与 3D 管线拆分，减少重复剔除与无关特性。
  • 描边/阴影成倍放大顶点；UI 半透明叠层是 Overdraw 重灾区；图集决定合批能否成立。
