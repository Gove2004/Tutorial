软件工程概述

软件工程是一门"用工程方法做软件"的学科。它不教你怎么写循环、怎么调 API，而是回答一个更根本的问题：如何让一群人稳定地、可预测地、高质量地做出复杂的软件系统？

什么是软件工程？

IEEE 标准定义：软件工程是将系统化、规范化、可量化的方法应用于软件开发、运行和维护的学科。换句话说，软件工程就是"把写软件这件事变成一门工程学科"。

为什么"写代码"不等于"做软件"

很多人认为"会写代码 = 会做软件"。这就像"会砌砖 = 会盖楼"一样荒谬。区别在于规模与复杂度。

维度写代码（编程）做软件（工程）
规模 几十行到几千行 百万行到亿行级代码
人员 一个人 几十人到几万人
时间跨度 几天到几周 几个月到几十年
核心挑战 语法、算法、数据结构 需求变更、团队协作、质量保障、运维
失败代价 重来一遍 经济损失、安全事故、人命伤亡
历史教训：1968 年 NATO 会议首次提出"软件工程"一词，原因是当时大量软件项目严重超预算、延期、质量低劣，被称为"软件危机"。这不是技术问题，是工程问题。

软件危机的典型案例

IBM System/360 操作系统项目（1960s）

这个项目最初计划 30 人、1 年完成。实际投入超过 4000 人、耗时 4 年，且初期版本存在大量缺陷。直接后果是 IBM 损失了数十亿美元的市场份额。

根本原因：没有需求管理、没有架构设计、没有测试体系、没有版本控制。完全是"作坊式"开发。

Healthcare.gov 网站上线事故（2013）

美国政府医保网站上线当天就崩溃了。测试覆盖率不足、代码质量差、缺乏集成测试，导致上线首月收到超过 10 万条用户投诉。

根本原因：外包管理失控、需求频繁变更、没有端到端集成测试、上线前没有压力测试。

Ariane 5 火箭爆炸（1996）

一枚价值 10 亿美元的火箭在发射后 37 秒自毁，原因是软件中的一个整数溢出异常未被处理。这段代码在 Ariane 4 中从未触发，因为 Ariane 4 的速度和加速度范围不会导致溢出。

根本原因：复用了未经充分测试的代码、异常处理不完善、系统集成测试不充分。

软件工程的生命周期

一个完整的软件项目通常经历以下阶段：

┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ 需求分析 │ -> │ 架构设计 │ -> │ 编码实现 │ └─────────────┘ └─────────────┘ └─────────────┘ ^ | | | v v | ┌─────────────┐ ┌─────────────┐ └─────────────│ 测试验证 │ <- │ 部署运维 │ └─────────────┘ └─────────────┘

但这不是单向流水线——每个阶段都可能产生反馈，推动前面的阶段修改。比如测试阶段发现的需求缺陷，会回到需求分析阶段。

软件工程的核心原则

工程师思维 Checklist

  • 可预测性：项目进度、成本、质量都应该可预估
  • 可重复性：同样的流程应该产生同样质量的产物
  • 可追溯性：每一行代码都应该能追溯到某个需求
  • 可维护性：软件不是写完就完了，而是要持续维护数年甚至数十年
  • 可扩展性：架构要能支撑未来的增长
  • 可靠性：软件要在预期场景下稳定工作
  • 经济性：工程质量要和投资回报匹配

软件工程 vs 其他学科

软件工程不是计算机科学，也不是项目管理，更不是艺术创作。它有自己独特的关注点：

学科关注点与软件工程的关系
计算机科学 理论、算法、计算模型 提供理论基础（算法、复杂度、形式化方法）
项目管理 计划、资源、风险、进度 软件工程是项目管理的特殊场景（无形、可变、复杂）
人机交互 用户体验、界面设计 软件工程的产品是"给人用的"，UX 是核心需求
质量管理 标准、流程、度量 ISO/IEC 25010、CMMI 等质量体系是工程化的重要支撑

现实中的软件工程困境

教科书和现实的差距，往往比代码和 bug 的差距还大。以下是一些真实场景中的两难问题：

经典困境：
  • 速度 vs 质量：老板说"下周必须上线"，但你知道代码质量撑不住——怎么办？
  • 完美 vs 完成：架构设计做到什么程度算够了？过度设计是常见问题
  • 技术债 vs 新功能：重构需要时间，但团队只考核新功能交付
  • 通用 vs 专用：做一套通用框架花 3 个月，但每个业务方都说"我们的场景不一样"

这些困境没有标准答案。但有了软件工程的方法论，你可以：做出有依据的决策，而不是凭感觉拍脑袋。

本章小结

  • 软件工程 = 用工程方法解决软件的规模、复杂度和协作问题
  • 软件危机的本质是"作坊式开发"无法应对"工业化规模"
  • 软件生命周期：需求 → 设计 → 实现 → 测试 → 部署 → 维护
  • 核心原则：可预测、可重复、可追溯、可维护、可扩展、可靠、经济
  • 现实中的工程决策需要在约束条件下做权衡
