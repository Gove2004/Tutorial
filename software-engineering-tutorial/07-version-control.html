版本控制与协作

版本控制是软件工程的"时间机器"。它让你能回溯到任何一个历史时刻，也能让多人同时修改同一份代码而不互相干扰。

Git 是目前最流行的版本控制系统。本章不只讲"怎么用 git"，而是讲在团队中怎么用 git 做好协作。

版本控制的发展

时代方法问题
石器时代文件命名：project_v1.py, project_v2_final.py, project_v2_reallyfinal.py找不到想要的版本
青铜时代CVS / SVN（集中式版本控制）单点故障、需要联网、分支操作重
铁器时代Git（分布式版本控制）学习曲线陡、概念多
现代Git + GitHub/GitLab + CI/CD流程复杂、需要纪律

Git 核心概念

Git 工作区模型 工作区 (Working Directory) │ git add ▼ 暂存区 (Staging Area / Index) │ git commit ▼ 本地仓库 (Local Repository) │ git push ▼ 远程仓库 (Remote Repository)

Git 最容易被误解的地方就是"工作区 → 暂存区 → 仓库"的三阶段模型。理解这个模型是掌握 Git 的关键。

操作命令说明

分支策略

分支策略决定了团队如何组织开发工作。选错了策略，Git 就会从"协作工具"变成"协作障碍"。

1. Git Flow

Git Flow 分支模型 main ────────────────────────────────────────●────●────● │ │ │ │ ┌── feature/login ───────────┘ │ │ │ │ │ ┌────┴────────────┐ │ │ │ │ │ ●────●────●────●────●─●────────────────────● release/v1.0 hotfix/security-fix
分支用途生命周期
main生产环境代码永久
develop开发集成分支永久
feature/*功能开发临时（功能完成后合并到 develop）
release/*发布准备临时（发布完成后合并到 main 和 develop）
hotfix/*紧急修复临时（修复后合并到 main 和 develop）

2. Trunk-Based Development (主干开发)

Trunk-Based 分支模型 main ──────────────────────────────────────────────●────●────● │ │ │ │ │ ┌──── feature/X ─────┐ │ │ │ │ │ (几天) │ │ │ │ ●────●────────────────────●●─────────────────●────●────● │ ┌──── feature/Y ─────┐ │ │ (几天) │ ●────●────────────────────●●─────────────────● │ │ ●────────────────────────────●─────────────────●

Trunk-Based 的核心思想：所有开发者直接从 main 分支检出短期分支，快速合并回来。分支生命周期以"天"为单位，不是"周"。

维度Git FlowTrunk-Based
理念分支隔离，稳定发布持续集成，快速合并
分支寿命周/月天
集成频率低（release 阶段才合入 main）高（每天多次）
适合团队传统发布节奏、大团队持续部署、DevOps 文化
复杂度高（5 种分支类型）低（只有 main + 短期 feature）
实践建议：如果你的团队在做持续部署（一天发布多次），选 Trunk-Based。如果你的团队是每月发布一次，Git Flow 更合适。对于大多数现代团队，GitHub Flow（只有 main + 短期 feature 分支 + PR）是最实用的折中方案。

GitHub Flow（推荐的入门方案）

1

从 main 创建一个功能分支

git checkout -b feature/add-login

2

提交代码到功能分支

git commit -m "feat: add user login page"

3

推送到远端并创建 Pull Request

git push origin feature/add-login → 在 GitHub 上创建 PR

4

代码审查

至少 1 人 review 通过后，合并到 main

5

合并后删除分支

保持仓库整洁

Commit Message 规范

好的 commit message 让代码审查和历史追溯变得容易。推荐使用 Conventional Commits 规范：

<type>(<scope>): <description>

[optional body]

[optional footer(s)]
Type含义示例
feat新功能feat(auth): add OAuth2 login
fix修复 bugfix(order): handle negative quantity
docs文档变更docs(readme): update installation guide
style代码格式（不影响逻辑）style: fix indentation in utils.py
refactor重构refactor(payment): extract charge logic
test测试相关test(cart): add unit tests for discount
chore构建/工具变更chore(ci): add lint step to pipeline

坏的 commit message 示例

差的 message好的 message
"fix" "fix(cart): calculate discount correctly for VIP users"
"update" "docs(api): add swagger documentation for user endpoints"
"wip" "feat(search): add fuzzy matching for product search"

代码评审 (Code Review) 文化

代码评审是团队协作中最重要的实践之一。它不只是"找 bug"，更是一种知识共享和质量文化。

好的代码评审应该

  • 关注重点：逻辑正确性、架构一致性、可读性，而不是缩进和命名风格（这些交给 lint）
  • 建设性语气：用"也许可以考虑..."而不是"你这样写是错的"
  • 及时回复：PR 创建后 24 小时内应该有人 review
  • PR 不要太大：一个 PR 最好不超过 400 行改动。太大的 PR 没人愿意认真看
  • 作者要主动：PR 描述要写清楚"做了什么"、"为什么这么做"、"怎么测试"

代码评审的检查清单

  • [ ] 代码是否实现了 PR 描述的功能？
  • [ ] 有没有明显的逻辑错误或边界情况遗漏？
  • [ ] 命名是否清晰？变量/函数/类名是否表达了意图？
  • [ ] 有没有硬编码的魔法值？
  • [ ] 错误处理是否完善？
  • [ ] 测试是否覆盖了新代码？
  • [ ] 有没有引入不必要的依赖？
  • [ ] 这段代码 6 个月后还能看懂吗？

协作中的常见陷阱

陷阱 1：Force Push
在共享分支上 force push 会覆盖他人的提交。永远不要在 main/master 或 shared branch 上 force push。
陷阱 2：大 PR (Big Pull Request)
一个 PR 改了 5000 行代码，涵盖 10 个功能。review 者要么没时间仔细看，要么看了也记不住。
对策：拆成多个小 PR，每个 PR 只做一件事。
陷阱 3：Merge Conflict 地狱
长时间不合并 main 到你的分支，导致 conflict 堆积如山。
对策：每天至少 rebase 一次 main，保持分支同步。
陷阱 4：忽略 .gitignore
把 node_modules、.env、__pycache__ 提交到仓库。
对策：项目初始化时就配好 .gitignore，并定期检查。

本章小结

  • Git 的三阶段模型（工作区 → 暂存区 → 仓库）是理解 Git 的基础
  • 分支策略要匹配团队节奏：Git Flow 适合月度发布，Trunk-Based 适合持续部署
  • GitHub Flow 是最实用的入门方案：main + 短期 feature 分支 + PR
  • Commit message 要规范，Conventional Commits 是行业标准
  • 代码评审是知识共享和质量控制的核心机制
  • 协作陷阱（force push、大 PR、merge conflict）需要纪律来避免
