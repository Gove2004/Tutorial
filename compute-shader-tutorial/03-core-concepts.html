Compute Shader 核心概念

本章是整本教程的理论核心。Thread Group、Dispatch、Shared Memory、Barrier 这四个概念构成了理解一切 Compute Shader 的基础。如果你能透彻理解本章，后面的实战和优化章节会轻松很多。

Thread Group：GPU 调度的最小单位

GPU 不会单独调度一个线程。它调度的最小单位是 Thread Group（线程组）。这是理解 Compute Shader 的第一步，也是最关键的一步。

Thread Group

Thread Group 是一组线程的集合，它们：

  • 被分配到同一个物理 SM（流式多处理器）上执行
  • 可以共享 Shared Memory（组内高速内存）
  • 可以相互同步（Barrier）
  • 在 Rendezvous（汇合点） 隐式同步——所有线程必须到达组尾，组才能结束

一个 Thread Group 的大小由 [numthreads(x, y, z)] 指定，常见的大小有：

大小线程数适用场景备注
(8, 8, 1)64图像处理、2D 数据并行2 个 Warp (NVIDIA)，对齐完美
(16, 8, 1)128中等并行度，Shared Memory 较大4 个 Warp
(256, 1, 1)2561D 数据流、粒子系统8 个 Warp，Warp 内数据局部性好
(512, 1, 1)512大规模 1D 并行16 个 Warp，最大化 Occupancy
(8, 8, 8)5123D 体积数据、3D 网格3D 空间局部性

为什么 256 和 512 是最常用的 1D 大小？

因为这些大小是 32（Warp Size）的整数倍：

256 / 32 = 8 个 Warp per Group
512 / 32 = 16 个 Warp per Group

NVIDIA GPU 一个 SM 最多驻留约 32 个 Warp。
如果用 numthreads(256, 1, 1)，一个 SM 可以同时驻留 32/8 = 4 个 Group。
如果用 numthreads(512, 1, 1)，一个 SM 同时驻留 32/16 = 2 个 Group。

更大的 Group 数 = 更好的延迟隐藏，但更少的 Occupancy。
不要随意选 numthreads：很多人随便选个 64 或 128，但这会导致 Warp 碎片化。比如 numthreads(64, 1, 1) = 2 个 Warp，一个 SM 驻留 16 个 Group。但如果 numthreads(96, 1, 1) = 3 个 Warp，16 个 Warp / 3 = 5 个 Group（余 1 个 Warp 浪费），Occupancy 很差。首选 32 的倍数。

Dispatch：从主机端发射计算

Dispatch 告诉 GPU 要创建多少个 Thread Group：

// DX12
commandList->Dispatch(groupCountX, groupCountY, groupCountZ);

// Vulkan
vkCmdDispatch(commandBuffer, groupCountX, groupCountY, groupCountZ);

总线程数 = groupCountX × groupCountY × groupCountZ × numthreadsX × numthreadsY × numthreadsZ

举例：一张 1024×1024 的图像，用 [numthreads(8, 8, 1)]：

每组处理 8×8 = 64 个像素
需要 1024/8 = 128 组（x 方向）× 128 组（y 方向）
Dispatch(128, 128, 1) → 16384 个 Group → 1,048,576 个线程

边界检查：线程数可能超过数据尺寸

如果图像是 1020×1020，Dispatch(128, 128, 1) 会产生 1024×1024 = 1,048,576 个线程，但只有 1,040,400 个有效像素。多出来的 8176 个线程需要做边界检查：

RWTexture2D<float4> output : register(u0);
Texture2D<float4> input : register(t0);
SamplerState samp : register(s0);

[numthreads(8, 8, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    // 边界检查——每个 Compute Shader 都必须做
    if (tid.x >= 1020 || tid.y >= 1020)
        return;

    output[tid.xy] = input.Sample(samp, tid.xy / 1020.0);
}
边界检查的性能影响：在组内如果部分线程越过边界提前返回，而另一部分还在计算，会导致 Warp 发散。缓解方法：让超出边界的线程也执行一个"空操作"（比如写入相同的值），保持所有线程同步执行。

Shared Memory：组内线程的高速通道

Shared Memory 是每个 Thread Group 私有的高速内存区域。它的特点：

属性值
容量每 SM 48KB-164KB（取决于 GPU 型号）
延迟1-3 个时钟周期（vs 全局内存 200-800 周期）
带宽约等于寄存器文件带宽，远高于全局内存
生命周期Group 存续期间，Group 结束后销毁
可见性仅同组线程可见，不同组之间隔离

Shared Memory 的典型用法：Tile-based 算法

最常见的 Shared Memory 使用模式是 Tile（瓦片）处理。以图像卷积为例：

// 5×5 高斯卷积：每个像素需要周围 2 个像素的值
// 如果每个线程直接读全局内存，一个像素需要 25 次全局读取

// 优化方案：用 Shared Memory 做 Tile 预取
#define KERNEL_SIZE 5
#define HALF_KERNEL 2

[numthreads(16, 16, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    // 1. 声明 Shared Memory（运行时分配）
    SharedMemory float4 sharedTile[32][32];       // 输入 Tile
    SharedMemory float4 sharedOutput[16][16];     // 输出 Tile

    // 2. 每个线程加载自己的全局像素到 Shared Memory
    int2 globalPos = tid.xy;
    if (globalPos.x < screenWidth && globalPos.y < screenHeight)
    {
        sharedTile[tid.xy] = inputTexture[globalPos];
    }
    else
    {
        sharedTile[tid.xy] = float4(0, 0, 0, 0);  // 边界填充
    }

    // 3. 加载 Halo 区域（相邻 Tile 的重叠部分）
    // 左 halo
    if (tid.x > 0)
    {
        sharedTile[tid.xy - int2(HALF_KERNEL, 0)] = inputTexture[globalPos - int2(HALF_KERNEL, 0)];
    }
    // 右 halo
    if (tid.x < 15)
    {
        sharedTile[tid.xy + int2(16 - HALF_KERNEL, 0)] = inputTexture[globalPos + int2(16 - HALF_KERNEL, 0)];
    }
    // 上 halo... 下 halo...（同理）

    // 4. ★ 关键：等所有线程都写完 Shared Memory 再读
    GroupMemoryBarrierWithGroupSync();

    // 5. 从 Shared Memory 做卷积计算（快 100x+）
    float4 result = float4(0, 0, 0, 0);
    for (int dy = -HALF_KERNEL; dy <= HALF_KERNEL; dy++)
    {
        for (int dx = -HALF_KERNEL; dx <= HALF_KERNEL; dx++)
        {
            int2 offset = int2(dx, dy);
            float weight = gaussianWeight(dx, dy);
            result += sharedTile[tid.xy + offset] * weight;
        }
    }

    // 6. 写回全局
    outputTexture[globalPos] = result;
}

Shared Memory 的 Bank Conflict

Shared Memory 被划分为若干个 Bank（存储体）。NVIDIA GPU 通常有 32 个 Banks，每个 Bank 每次服务一个线程请求。如果同一个 Warp 内的多个线程同时访问同一个 Bank 的不同地址，就会发生 Bank Conflict——这些访问被序列化执行。

32 Banks，每 Bank 4 字节（uint）：

Bank 0: [addr_0] [addr_32] [addr_64] ...
Bank 1: [addr_1] [addr_33] [addr_65] ...
Bank 2: [addr_2] [addr_34] [addr_66] ...
...
Bank 31: [addr_31] [addr_63] [addr_95] ...

无冲突：Warp 的 32 个线程分别访问 addr_0 到 addr_31
  → 每个线程访问不同的 Bank → 32 个访问同时完成

16 路冲突：Warp 的 32 个线程都访问 Bank 0
  → addr_0, addr_32, addr_64, ... 都在 Bank 0
  → 32 次访问被分成 2 次完成（每 2 个线程一组）
  → 性能下降 16x

避免 Bank Conflict 的方法：

// ❌ 有冲突：float3 导致偏移错开，32 个线程访问同一列时会冲突
SharedMemory float3 shared[32][32];

// ✅ 无冲突：加 padding 使每行对齐到 32 的倍数
SharedMemory float shared[32][33];  // 每行 33 个 float，跳过第 32 个

// ✅ 或者直接用 float4（4 × 32 = 128 字节 = 32 Banks × 4 字节，完美对齐）
SharedMemory float4 shared[32][32];  // 每个线程访问不同 Bank，无冲突

Barrier 与同步

Compute Shader 中有三种层次的同步机制：

2.1 Warp-level 同步

// 等待同一 Warp 内的所有线程到达
__syncthreads();  // CUDA 风格
// HLSL 中没有 warp-level barrier，但 __syncwarp() 可用（SM 6.0+）
// 或 waveBarrier()（SM 6.2+）

2.2 Group-level 同步（最常用）

// 等待同组所有线程完成对 Shared Memory 的写入
GroupMemoryBarrierWithGroupSync();
// 等价于：
//   GroupMemoryBarrier();  // 确保 Shared Memory 写入可见
//   barrier();             // 所有线程汇合

// 仅确保可见性，不等所有线程到达
GroupMemoryBarrier();
// 注意：后续代码可能在某些线程还没写完时就执行了！

2.3 全局同步（跨 Group）

// 所有 Group 的所有线程都到达此处
// 用于跨 Group 的数据依赖
// 在 DX12 中通过 Command List 的 Signal/Wait 实现
// 在 Vulkan 中通过 Fence/Semaphore 实现

Barrier 的语义分解

理解 Barrier 需要把它拆成两个正交的概念：

Memory Visibility（可见性）Synchronization（同步/汇合）
仅有可见性 GroupMemoryBarrier() 不等待其他线程，继续执行
可见性 + 同步 GroupMemoryBarrierWithGroupSync() 所有线程必须到达后才继续
全局可见性 DeviceMemoryBarrier() 确保所有设备内存操作完成
全局可见性 + 同步 DeviceMemoryBarrierWithGroupSync() 所有线程 + 所有内存操作完成
经典 Bug：写了 Shared Memory 后用了 GroupMemoryBarrier()（无 Sync）而不是 GroupMemoryBarrierWithGroupSync()。如果后续代码不依赖所有线程的数据，这没问题；但如果后续代码需要所有数据就绪，就会出 Bug。不确定就用 WithGroupSync。

Resource Binding：Shader 如何访问数据

Compute Shader 通过 Descriptor Heap（DX12）或 Descriptor Set（Vulkan）绑定资源。核心资源类型：

资源类型读写随机访问原子操作示例
Constant BufferSRV✗任意✗相机矩阵、场景参数
Structured BufferSRV✗任意✗顶点数据、粒子属性
RWStructured Buffer✓✓任意✓输出缓冲区、计数器
Texture2DSRV + Sample✗任意✗输入图像
RWTexture2D✓ (直接索引)✓任意部分输出图像、累加器
AppendBuffer✗✓ (追加)✗✓粒子生成、结果收集
ConsumeBuffer✓+✗ (原子弹出)✓ (删除)✗✓工作队列、任务分发

SRV vs UAV 的本质区别

这是 DX12 中最容易混淆的概念之一：

SRV (Shader Resource View)

只读视图。GPU 可以用 任意缓存策略读取（L1/L2 缓存命中率高）。绑定为 SRV 的资源，Shader 不能写入。

UAV (Unordered Access View)

读写视图。GPU 可以读和写。绑定为 UAV 的资源不使用缓存（uncached），因为写入需要同步保证可见性。UAV 还支持原子操作。

缓存策略的影响：SRV 走缓存，UAV 不走缓存。这意味着 读同一个位置多次，SRV 第二次命中 L1 缓存（~1 周期），UAV 要走全局内存（~200 周期）。所以只读资源一定要绑 SRV 而不是 UAV。

内存层级全景

理解 GPU 内存层级是编写高性能 Compute Shader 的关键。从快到慢：

层级延迟带宽容量/Group可见性
寄存器1 周期∞每线程 ~255 个私有
Shared Memory1-3 周期极高~48-164 KB/SM组内
L1 缓存~10 周期高~12-64 KB/SMSM 内
Texture Cache~10-20 周期高（空间局部性好时）~48 KB/SMSM 内
L2 缓存~50 周期中高~2-6 MB (全 GPU)全局
Global Memory200-800 周期~500 GB/s (RTX 4090)~24 GB (RTX 4090)全局

优化策略：尽量减少全局内存访问

一个简单的规则：

每次全局内存读 ≈ 200-800 周期
每次 Shared Memory 读 ≈ 1-3 周期
一次浮点加法 ≈ 1 周期

所以：把数据从全局内存搬到 Shared Memory，
      然后在 Shared Memory 中做 100+ 次计算，
      总体上是划算的。

Root Signature：DX12 的资源绑定契约

Root Signature 是 DX12 中 Shader 和资源之间的"契约"，它声明了 Shader 需要哪些资源、在哪里可以找到它们：

// DX12 Root Signature 构建
CD3DX12_DESCRIPTOR_RANGE srvTable({ D3D12_DESCRIPTOR_RANGE_TYPE_SRV, 1, 0 });
CD3DX12_DESCRIPTOR_RANGE uavTable({ D3D12_DESCRIPTOR_RANGE_TYPE_UAV, 1, 0 });

CD3DX12_ROOT_PARAMETER rootParams[2];
rootParams[0].InitAsDescriptorTable(1, &srvTable, D3D12_SHADER_VISIBILITY_COMPUTE);
rootParams[1].InitAsDescriptorTable(1, &uavTable, D3D12_SHADER_VISIBILITY_COMPUTE);

CD3DX12_ROOT_SIGNATURE_DESC rootSigDesc(2, rootParams, 0, nullptr,
    D3D12_ROOT_SIGNATURE_FLAG_ALLOW_INPUT_ASSEMBLER_INPUT_LAYOUT);

在 HLSL 中对应：

// rootParams[0] → descriptor table 0, slot 0 = SRV
StructuredBuffer<float> input : register(t0);

// rootParams[1] → descriptor table 0, slot 0 = UAV
RWStructuredBuffer<float> output : register(u0);

执行流全景：从 Dispatch 到结果

把所有概念串起来，一个完整的 Compute Shader 执行流程：

主机端 (CPU):
  1. 创建 Descriptor Heap（存放 SRV/UAV 描述符）
  2. 写入描述符（把 GPU 虚拟地址填入 Descriptor）
  3. 设置 Root Signature 和 Pipeline State
  4. 绑定 Descriptor Table 到 Pipeline
  5. cmdDispatch(128, 128, 1)

GPU 端 (硬件):
  6. 调度器将 16384 个 Group 分配到所有 SM
  7. 每个 SM 取 1-2 个 Group 驻留
  8. Group 拆分为 Warps (每组 16,16,1 → 4 Warps)
  9. Warps 从指令缓存取指执行
  10. 线程读取全局内存 → 写入 Shared Memory
  11. GroupMemoryBarrierWithGroupSync() — 所有线程汇合
  12. 从 Shared Memory 计算 → 写回全局内存
  13. 隐式 Rendezvous — 组尾同步
  14. Group 完成，释放 SM 资源
  15. 下一个 Group 被调度

主机端:
  16. cmdCopyResource（将 GPU 结果拷回 CPU 可读的 Readback Buffer）
  17. Map/Unmap 读取结果

练习与思考

1

概念题

为什么 Thread Group 必须在同一个 SM 上执行？如果允许跨 SM，Shared Memory 和 Barrier 还能工作吗？

2

分析题

一个 [numthreads(256, 1, 1)] 的 Shader 中，SharedMemory float shared[256]。Warp 0（线程 0-31）同时读取 shared[0..31]，会发生 Bank Conflict 吗？如果改成 SharedMemory float shared[32][8]，Warp 0 读取 shared[0..31][0] 呢？

3

代码题

写一个求数组最大值的 Compute Shader。提示：用 Shared Memory 做组内 Reduce（树形归约），最后每个 Group 输出一个局部最大值，主机端再做一轮归约。

本章小结

  • Thread Group 是 GPU 调度的最小单位，必须在同一个 SM 上执行
  • numthreads 首选 32 的倍数（256/512 最常用）
  • Shared Memory 比全局内存快 100x+，但要注意 Bank Conflict
  • Barrier 分两个正交概念：可见性 vs 同步
  • SRV 走缓存（读），UAV 不走缓存（读写+原子）
  • 内存层级决定了优化方向：尽量在 Shared Memory 中计算
