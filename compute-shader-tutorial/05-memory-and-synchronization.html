内存模型与同步机制

这是 Compute Shader 中最难、也最重要的章节。Barrier 的语义、Memory Model 的限定符、Shared Memory 的一致性——这些概念的错误理解是 GPU Bug 的最大来源。本章将逐个拆解。

为什么同步这么难？

在 CPU 多线程编程中，你至少可以假设："我写了一个变量，另一个线程一定能读到最新值"。但在 GPU 上，这个假设完全不成立。

原因有三：

  1. 写入延迟：GPU 指令执行是流水线的。一条 ST（存储）指令发出后，数据可能还在 L1 缓存中，尚未刷入全局内存。
  2. 指令重排：编译器/硬件可以对指令重排序以优化吞吐，只要单线程语义不变。
  3. 缓存一致性：Shared Memory 和 Global Memory 的缓存一致性模型在不同 GPU 上不同。

内存一致性（Memory Consistency）

内存一致性模型定义了："一个线程的写入，在什么条件下对其他线程可见"。强一致性（Sequential Consistency）最容易理解但性能最差；弱一致性（Weak Consistency）需要程序员显式同步但性能最好。GPU 采用弱一致性模型。

Barrier 的精确语义

很多人以为 Barrier 就是"等所有线程到齐"。这只是它的一半功能。Barrier 有两个正交的职责：

职责说明
内存屏障（Memory Barrier）确保之前的内存写入对所有线程可见
同步汇合（Synchronization Rendezvous）所有线程必须到达 Barrier 后才能继续

HSLS 中的 Barrier 家族

// 1. 组内 Shared Memory 屏障
// 确保：同组所有线程对 Shared Memory 的写入对其他线程可见
// 同步：所有线程必须到达
GroupMemoryBarrierWithGroupSync();

// 2. 仅可见性，不同步
// 确保：同组所有线程对 Shared Memory 的写入对其他线程可见
// 同步：不等待，线程可以继续执行
GroupMemoryBarrier();

// 3. 设备级全局内存屏障
// 确保：当前线程对全局内存的写入对其他线程/其他 Group 可见
// 同步：不同步
DeviceMemoryBarrier();

// 4. 设备级全局内存屏障 + 同步
DeviceMemoryBarrierWithGroupSync();

// 5. 资源屏障（DX12 层面，非 Shader 内）
// 转换 Resource State（如 UAV → COPY_SOURCE）
// 在 Command List 中通过 ResourceBarrier() 调用

最经典的 Barrier Bug

// ❌ 错误示例：没有 Barrier
[numthreads(256, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    // 线程 A 写入 Shared Memory
    sharedData[tid.x] = input[tid.x];

    // 线程 B 立即读取 Shared Memory —— 可能还没写完！
    // 因为写入还在 L1 缓存中，未刷入 Shared Memory
    result[tid.x] = sharedData[tid.x] * 2.0f;
}
// ✅ 正确示例：加上 Barrier
[numthreads(256, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    sharedData[tid.x] = input[tid.x];

    // 等所有线程写完 Shared Memory，再读
    GroupMemoryBarrierWithGroupSync();

    result[tid.x] = sharedData[tid.x] * 2.0f;
}
GroupMemoryBarrier() 还是 GroupMemoryBarrierWithGroupSync()？ 如果你不确定——用 WithGroupSync。它更安全。性能差异通常很小（Barrier 本身就是同步点，额外等待一个 Barrier 的成本远低于内存不一致导致的 Bug 修复成本）。

Memory Model 限定符（SM 6.0+）

SM 6.0 引入了 [shader("compute", model="xx")] 和 HLSL 中的 MemoryModel 限定符，让你可以精确控制内存一致性强度。

Memory Semantics 层级

HLSL 提供了 #pragma require 和 MemoryModel 注解来控制内存语义：

// 默认：宽松模型（Relaxed）
// 编译器/硬件可以自由重排内存操作

// 显式指定 Sequentially Consistent（顺序一致）
#pragma require(requireExplicitMemoryModel)
[shader("compute", model="6_0")]

// 使用 MemoryBarrier 时指定语义级别
// Acquire = 读/写屏障之前的操作不会被重排到屏障之后
// Release = 读/写屏障之后的操作不会被重排到屏障之前
// AcquireRelease = 两者兼有
// SequentiallyConsistent = 全局顺序一致（最严格，最慢）

Memory Semantics 的实际影响

以 GroupMemoryBarrier() 为例，不同 Memory Model 下它的行为：

Memory ModelBarrier 保证什么性能代价
Relaxed（默认）仅 Shared Memory 可见性最低
AcquireBarrier 前的读不会被重排到 Barrier 后低
ReleaseBarrier 后的写不会被重排到 Barrier 前低
AcquireRelease以上两者中
SequentiallyConsistent全局顺序一致，所有 GPU 看到的顺序相同高
实用建议：99% 的情况下，默认的 Relaxed 模型 + GroupMemoryBarrierWithGroupSync() 就够了。只有在跨 Group 同步（需要 DeviceMemoryBarrier）或有特殊数据依赖时，才需要考虑显式 Memory Model。

Resource Barrier vs Memory Barrier

这是 DX12 中最容易混淆的一对概念。它们在不同的层面工作：

Memory Barrier（Shader 内）Resource Barrier（DX12 API）
作用层面Shader 内部的内存可见性DX12 层面的资源状态转换
调用位置HLSL 代码中C++ 命令列表中
作用确保写入对其他线程可见转换资源的使用状态（如 UAV → COPY_SOURCE）
例子GroupMemoryBarrierWithGroupSync()commandList->ResourceBarrier(...)

一个完整的"写结果→拷回 CPU"流程需要两者配合：

1. Shader 内：GroupMemoryBarrierWithGroupSync()
   → 确保 Shared Memory 写入对所有组内线程可见

2. DX12 API：ResourceBarrier(UNORDERED_ACCESS → COPY_SOURCE)
   → 确保 GPU 完成了对 outputBuffer 的所有 UAV 写入
   → 允许 CopyResource 从 outputBuffer 读取

3. DX12 API：CommandQueue::ExecuteCommandLists()
   → 提交命令到 GPU

4. DX12 API：Fence 同步
   → 等待 GPU 完成所有命令

5. CPU：Map readbackBuffer 读取结果

Barrier 的粒度层次

Barrier 有不同的作用域，理解它们的区别对正确同步至关重要：

// 粒度 1：Warp 级别（最快）
// 仅等待同一 Warp 内的 32 个线程
// 不跨越 Group 边界
// 代价：~0 周期（硬件直接支持）
__syncwarp();  // SM 6.0+

// 粒度 2：Group 级别（常用）
// 等待同一 Thread Group 内的所有线程
// 仅影响 Shared Memory 可见性
// 代价：~10-50 周期
GroupMemoryBarrierWithGroupSync();

// 粒度 3：Device 级别（最慢）
// 等待整个 GPU 上所有线程
// 影响全局内存可见性
// 代价：~1000+ 周期（跨 SM 同步）
DeviceMemoryBarrierWithGroupSync();
避免 DeviceMemoryBarrier：它同步整个 GPU 上的所有线程，意味着所有 SM 都要停下来等最慢的那个。这在 Compute Shader 中几乎总是性能杀手。如果你发现自己需要 DeviceMemoryBarrier，重新思考算法——通常可以用多个 Dispatch + Fence 替代。

Vulkan 的 Memory Model

Vulkan 有自己的一套内存模型，与 DX12 不同但概念相似：

// Vulkan 使用 Memory Semantics 常量
// （在 SPIR-V 中指定，GLSL 中通过 layout 间接控制）

// vkCmdMemoryBarrier 的参数：
VkMemoryBarrier barrier = {};
barrier.srcAccessMask = VK_ACCESS_SHADER_WRITE_BIT;
barrier.dstAccessMask = VK_ACCESS_SHADER_READ_BIT;
// src/dst 定义了屏障前后的访问权限

// GLSL 中的 barrier()：
// 等价于 DX12 的 GroupMemoryBarrierWithGroupSync()
// 但它还包含了 VK_MEMORY_BARRIER_ALL_COMMAND_BIT 的效果
// 即 barrier() 是"全部屏障"——最安全但也最慢

Vulkan vs DX12 同步对比

功能DX12 / HLSLVulkan / GLSL
组内 Shared Memory 屏障GroupMemoryBarrierWithGroupSync()memoryBarrier() + barrier()
全局资源状态转换commandList->ResourceBarrier()vkCmdPipelineBarrier()
GPU-CPU 同步ID3D12FencevkQueueSubmit + vkWaitForFences
默认同步强度RelaxedSequentiallyConsistent

原子操作的内存语义

原子操作自带内存屏障语义，这是很多人不知道的：

// InterlockedAdd 不仅是原子加法，它还隐含一个 Release 语义
// 即：InterlockedAdd 之前的写入，在 InterlockedAdd 完成后对其他线程可见

RWStructuredBuffer<uint> counter : register(u0);
uint old;

sharedData[tid.x] = value;
GroupMemoryBarrierWithGroupSync();  // Shared Memory 可见

// InterlockedAdd 确保：
// 1. 对 counter 的加法是原子的
// 2. 之前的 Shared Memory 写入对其他线程可见（Release 语义）
InterlockedAdd(counter, 1u, old);
深层理解：原子操作的内存语义取决于 Memory Model。在 Relaxed 模型下，原子操作仅对该变量是原子的，不保证其他内存操作的顺序。在 SequentiallyConsistent 模型下，所有原子操作都有全局顺序。DX12 默认是 Relaxed，但 GroupMemoryBarrierWithGroupSync() 已经提供了足够的组内同步保证。

Barrier 最佳实践清单

Barrier 检查清单

每次使用 Barrier 时问自己：

  1. 我在同步什么？ Shared Memory？全局内存？资源状态？
  2. 同步的粒度是什么？ Warp？Group？Device？
  3. 需要可见性还是汇合？ 两者都需要吗？
  4. 有没有更轻量的替代方案？（比如用 Warp-level 代替 Group-level）
  5. Barrier 是否在分支内？ 分支内的 Barrier 可能导致死锁（如果分支发散）

常见 Barrier Bug 案例

点击展开：案例 1 — 分支内的 Barrier 死锁 
// ❌ 错误：如果线程 0-15 满足条件，线程 16-31 不满足
// 那么 16-31 跳过了 Barrier，0-15 在 Barrier 等不到所有人 → 死锁
[numthreads(32, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    if (tid.x < 16)
    {
        sharedData[tid.x] = input[tid.x];
        GroupMemoryBarrierWithGroupSync();  // 死锁！
        result[tid.x] = sharedData[tid.x] * 2;
    }
}

修复：确保所有线程都到达 Barrier，即使有些线程不需要屏障后的数据：

// ✅ 修复：所有线程都执行 Barrier
[numthreads(32, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    sharedData[tid.x] = input[tid.x];
    GroupMemoryBarrierWithGroupSync();  // 所有线程都到这里

    if (tid.x < 16)
    {
        result[tid.x] = sharedData[tid.x] * 2;
    }
}
点击展开：案例 2 — UAV 写入后忘记 Barrier 就读取 
// ❌ 错误：写入 UAV 后立即在同一 Shader 中读取
// GPU 可能缓存了旧值
[numthreads(256, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    outputBuffer[tid.x] = inputBuffer[tid.x] * 2;

    // 可能读到旧值！写入还在 L1 缓存中
    float val = outputBuffer[tid.x];
}

修复：写入 UAV 后读回，需要用 DeviceMemoryBarrier()：

// ✅ 修复：Barrier 确保写入可见
outputBuffer[tid.x] = inputBuffer[tid.x] * 2;
DeviceMemoryBarrier();  // 确保 UAV 写入对其他线程/后续读取可见
float val = outputBuffer[tid.x];

练习与思考

1

分析题

下面这段代码有什么问题？如果 numthreads(256, 1, 1)，Dispatch(2, 1, 1)，Group 0 和 Group 1 会互相干扰吗？为什么？

RWStructuredBuffer<float> sharedOutput : register(u0);

[numthreads(256, 1, 1)]
void CSMain(uint3 tid : SV_DispatchThreadID)
{
    sharedOutput[tid.x] = tid.x * 2.0f;  // 注意：tid.x 范围是 0-255
}
2

概念题

为什么 GroupMemoryBarrier()（无 Sync）在某些场景下比 GroupMemoryBarrierWithGroupSync() 更快？什么情况下可以安全地只用前者？

3

设计题

设计一个算法，让两个 Thread Group 协作处理一个数组：Group 0 处理偶数索引，Group 1 处理奇数索引，最后合并结果。你会用什么同步机制？为什么不用 DeviceMemoryBarrier？

本章小结

  • Barrier 有两个正交职责：内存可见性 + 线程汇合
  • GroupMemoryBarrierWithGroupSync() 是 Compute Shader 中最常用的屏障
  • Memory Model 限定符控制内存一致性强度，默认 Relaxed 就够了
  • Resource Barrier（DX12 API）和 Memory Barrier（Shader 内）是两个层面的概念
  • 避免 DeviceMemoryBarrier——它是跨 SM 的全局同步，代价极高
  • 分支内的 Barrier 可能导致死锁
  • 原子操作自带 Release 语义
