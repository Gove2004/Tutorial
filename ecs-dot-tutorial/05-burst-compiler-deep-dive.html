05 - Burst Compiler 深入

Burst 是 DOTS 性能优势的真正来源。它不是一个简单的"更快的 JIT"，而是一个完整的 LLVM 前端，能够将 C# 代码编译为高度优化的原生机器码。本章深入 Burst 的编译管线，理解它在什么条件下能向量化、什么条件下不能，以及如何利用 Burst 的全部能力。

5.1 Burst 编译管线

Burst 的编译过程可以分为三个阶段，每个阶段都对应着特定的优化机会和限制：

Burst 编译管线： ┌─────────────────────────────────────────────────────────────┐ │ 阶段 1: IL → LLVM IR │ │ │ │ C# 源代码 │ │ ↓ (C# Compiler) │ │ IL (Intermediate Language) │ │ ↓ (Burst Parser) │ │ Burst IR (Burst 内部表示) │ │ ↓ (Burst Analyzer) │ │ LLVM IR (LLVM 中间表示) │ ├─────────────────────────────────────────────────────────────┤ │ 阶段 2: LLVM IR 优化 │ │ │ │ LLVM 优化 Pass（数十次迭代） │ │ - Dead Code Elimination │ │ - Constant Propagation │ │ - Loop Unrolling │ │ - Function Inlining │ │ - Vectorization (Scalar → SIMD) │ │ - Alias Analysis │ │ ↓ │ │ 优化后的 LLVM IR │ ├─────────────────────────────────────────────────────────────┤ │ 阶段 3: LLVM IR → 原生机器码 │ │ │ │ LLVM CodeGen │ │ ↓ │ │ x86-64 / ARM64 机器码 │ │ ↓ │ │ JIT 注入到进程内存 │ └─────────────────────────────────────────────────────────────┘

5.1.1 IL 到 LLVM IR 的转换

Burst 首先解析 C# 编译器生成的 IL（Intermediate Language）。与标准 .NET JIT 不同，Burst 不直接使用 IL——它先将 IL 转换为自己的内部表示（Burst IR），然后在 Burst IR 上进行分析和优化，最后生成 LLVM IR。

这个转换过程的关键意义在于：Burst 可以在 IR 层面理解 C# 代码的语义，而不仅仅是字节码。这使得 Burst 能够做出更激进的优化决策，比如：

  • 内联深度嵌套的方法调用链。
  • 消除在编译期可以确定的分支。
  • 将循环索引计算提升（Loop Invariant Code Motion）到循环体外。

5.1.2 LLVM 优化 Pass

LLVM 拥有一整套经过数十年优化的 Pass。Burst 使用了其中最适合数值计算的部分：

优化 Pass描述示例
DCE (Dead Code Elimination)移除不会被执行或不会被使用的代码if (false) { /* 死代码 */ } 被完全移除
Constant Propagation将编译期可确定的常量直接代入for (int i = 0; i < 100; i++) 中的 100 被直接展开
Loop Unrolling展开循环体，减少循环控制开销for(i=0;i<4;i++) 展开为 4 条独立语句
Function Inlining将函数调用替换为函数体inline 方法的所有调用点被内联展开
Vectorization标量运算 → SIMD 并行运算4 个 float 的加法合并为 1 条 AVX 指令
Alias Analysis分析指针别名关系，消除不必要的内存操作两个指针指向不同内存时，可重排/store-load 操作
LICM将循环不变代码提升到循环外循环内的常量表达式只计算一次

5.1.3 目标平台代码生成

LLVM IR 生成后，Burst 会根据目标平台生成对应的原生机器码：

目标平台指令集SIMD 宽度最大并行 float
x86-64 (桌面)SSE4.2 / AVX2 / AVX-512128/256/512 bit4/8/16
ARM64 (移动端/主机)NEON128 bit4
WebAssemblyScalar only无1
💡 关键理解：Burst 在编译期就知道目标平台的指令集。如果你在 x86-64 上编译，Burst 会生成 AVX2 指令；如果在 ARM64 上编译，会生成 NEON 指令。这就是为什么同一个 DOTS 项目可以在 PC 和手机上都获得 SIMD 加速。

5.2 SIMD 自动向量化

SIMD（Single Instruction, Multiple Data）是 Burst 最强大的优化之一。它允许一条指令同时处理多个数据。Burst 会自动尝试将标量循环转换为 SIMD 循环，但并非所有循环都能成功向量化。

5.2.1 成功向量化的条件

// ✅ 可以被 Burst 自动向量化的代码
[BurstCompile]
public void AddVectors(float3[] a, float3[] b, float3[] result, int count)
{
    for (int i = 0; i < count; i++)
    {
        result[i] = a[i] + b[i];  // 三个独立的 float 加法
    }
}
// Burst 生成：
// AVX2: vmaddps ymm0, ymm1, ymm2  (一次处理 8 个 float)
// NEON: vfma.f32 q0, q1, q2         (一次处理 4 个 float)

5.2.2 无法向量化的常见情况

// ❌ 条件分支导致向量化失败
[BurstCompile]
public void ConditionalAdd(float[] values, float[] result, int count)
{
    for (int i = 0; i < count; i++)
    {
        if (values[i] > 0)            // 分支：SIMD 难以处理不等长的分支
        {
            result[i] = values[i] * 2;
        }
        else
        {
            result[i] = 0;
        }
    }
}

// 修复：使用 math.select 消除分支
[BurstCompile]
public void ConditionalAddFixed(float[] values, float[] result, int count)
{
    for (int i = 0; i < count; i++)
    {
        // math.select 是 SIMD 友好的三元运算符
        result[i] = math.select(0f, values[i] * 2, values[i] > 0);
    }
}

// ❌ 依赖前一个结果（循环依赖）
[BurstCompile]
public void PrefixSum(float[] input, float[] output, int count)
{
    output[0] = input[0];
    for (int i = 1; i < count; i++)
    {
        output[i] = output[i - 1] + input[i];  // 每个迭代依赖前一个结果
    }
}
// 前缀和无法向量化——它是固有的串行算法。需要使用并行前缀和算法。

5.2.3 向量化失败诊断

如何确认 Burst 是否成功向量化了你的代码？使用 Burst Compiler Log：

// 在项目中启用 Burst 详细日志
// 方法 1：通过 Editor 菜单
// Edit → Project Settings → Player → Burst Compiler → Enable Debug Logging

// 方法 2：通过环境变量
// 设置 BURST_LOG_LEVEL=verbose

// 方法 3：通过代码
using Unity.Burst;
using Unity.Burst.Intrinsics;

[BurstCompile(BurstLogLevel.Verbose)]
public void MyJob() { ... }

// 查看编译日志：
// 成功向量化："[Burst] Vectorizing loop..."
// 向量化失败："[Burst] Loop not vectorizable: ..."
// 失败原因会在日志中详细说明（如"conditional store"、"loop dependency"等）
💡 最佳实践：math 命名空间下的函数（math.add, math.mul, math.select, math.sin 等）都是为 SIMD 设计的。尽量使用这些函数而不是 C# 原生运算符（+、*、Mathf.Sin），因为 Burst 对 math.* 函数的向量化成功率更高。

5.3 Loop Unrolling（循环展开）

Loop Unrolling 是一种经典的编译器优化：将循环体复制多份，减少循环控制的开销（比较、递增、跳转）。

// 原始循环（4 次迭代）
for (int i = 0; i < 4; i++)
{
    result[i] = a[i] + b[i];
}
// 编译器生成 4 条独立的加法指令，无循环控制

// 手动展开 vs 自动展开
// Burst 默认会自动展开小的循环。你可以通过属性控制：

[BurstCompile]
public struct UnrolledJob : IJobParallelFor
{
    [BurstDiscard]  // 标记此方法不被 Burst 编译（仅用于非 Job 代码）
    public static void ManualUnroll(Span<float> result, Span<float> a, Span<float> b)
    {
        // 手动展开：Burst 可能不会自动展开这么大的循环
        result[0] = a[0] + b[0];
        result[1] = a[1] + b[1];
        result[2] = a[2] + b[2];
        result[3] = a[3] + b[3];
    }
}

// Burst 编译选项控制展开
// -fforce-unroll-loops: 强制展开所有循环（可能增大代码体积）
// 默认行为：Burst 根据成本模型决定是否展开

循环展开的利弊：

利弊
小循环 (< 16 次)消除循环控制开销，允许指令级并行代码体积增加不多，收益明显
中等循环 (16-64 次)减少分支预测失败的惩罚寄存器压力增大，可能导致 spill
大循环 (> 64 次)收益递减代码膨胀，L1i 缓存压力增大，反而变慢

5.4 Function Inlining（函数内联）

Burst 的内联策略非常激进。它会尽可能将方法调用替换为方法体本身，消除函数调用的开销（压栈、跳转、返回）。

// 内联前的代码
[BurstCompile]
public void ProcessEntities(EntityData data)
{
    for (int i = 0; i < data.count; i++)
    {
        data.positions[i] = MovePosition(data.positions[i], data.velocities[i]);
    }
}

[BurstCompile]
private float3 MovePosition(float3 pos, float3 vel)
{
    return pos + vel;  // 简单计算
}

// 内联后的等效代码（Burst 生成的）
[BurstCompile]
public void ProcessEntities(EntityData data)
{
    for (int i = 0; i < data.count; i++)
    {
        data.positions[i] = data.positions[i] + data.velocities[i];
        // MovePosition 的调用被完全消除
    }
}
// 编译器甚至可能进一步优化为 SIMD 加法指令

Burst 内联的启发式规则：

  1. 方法体长度：较小的方法更容易被内联。Burst 没有硬编码的大小限制，而是使用成本模型。
  2. 调用频率：在循环中被频繁调用的方法优先内联。
  3. 递归：递归方法不会被内联（会导致无限展开）。
  4. 虚方法：虚方法无法内联（因为运行时才能确定目标方法）。

5.5 JIT 编译时机

Burst 是 JIT（Just-In-Time）编译器，它在首次遇到 [BurstCompile] 标记的代码时编译它。这意味着第一次执行带有 Burst 编译的 Job 时会有一定的编译开销。

5.5.1 编译开销

场景首次编译耗时后续执行
简单 Job（< 100 行）10-50 ms接近原生 C 性能
中等 Job（100-500 行）50-200 ms接近原生 C 性能
复杂 System（> 500 行）200-1000 ms接近原生 C 性能

5.5.2 预编译（Precompile）

为了避免首次执行的编译停顿，可以使用 Burst 的预编译功能：

// 在编辑器中预编译 Burst 代码
// 方法 1：通过菜单
// Burst → Compile → Precompile All

// 方法 2：通过代码，在初始化阶段提前触发编译
using Unity.Burst;
using Unity.Jobs;

public class BurstPrecompiler
{
    [BurstCompile]
    public static void PrecompileWarmup()
    {
        // 在场景加载时调用一次，触发所有 Burst 编译
        // 这样实际游戏运行时不会有编译停顿
        var warmupJob = new WarmupJob { data = NativeArray.Allocate(0) };
        warmupJob.Schedule().Complete();
    }
}

// 在 Unity 启动时调用
// Application.LoadLevelAddedToScene 事件或 Awake() 中
void Awake()
{
    BurstPrecompiler.PrecompileWarmup();
}

5.5.3 AOT 编译

在 IL2CPP 构建（iOS、Android、WebGL）中，Burst 需要在构建时完成编译。IL2CPP 本身也会调用 Burst 进行编译，所以 AOT 场景下不会有首次执行的编译停顿——编译发生在构建阶段。

⚠️ 编辑器中的 AOT 限制：在 Unity Editor 中，Burst 使用 Mono JIT 后端进行编译。这意味着每次启动 Editor 后，首次运行 Burst Job 都会有编译开销。只有 IL2CPP 构建（打包后的游戏）才能在构建阶段完成编译。

5.6 Burst 的限制

Burst 不是万能的。了解它的限制对于编写可编译的代码至关重要。

5.6.1 不支持的特性

特性是否支持替代方案
虚方法 (virtual/override)❌使用值类型 + 接口，避免虚函数
LINQ❌手动循环，或使用 Burst.Linq（社区项目）
Reflection❌使用 SystemAPI.Query 代替反射查询
Managed 类型 (string, object, Array)❌使用 NativeArray, NativeSlice, fixed buffer
Exception (try/catch/throw)❌使用返回值/布尔标志表示错误
GC 分配 (new T[], new List<T>)❌NativeArray / NativeList
Async/Await❌使用 JobHandle 链式依赖
泛型约束 (where T : class)部分支持使用 struct 约束或特化
委托 (delegate/Action/Func)❌直接方法调用或函数指针
属性 (get/set)部分支持使用公共字段
装箱/拆箱❌值类型传递

5.6.2 常见的编译失败示例

// ❌ 编译失败：使用了虚方法
[BurstCompile]
public abstract class BaseSystem
{
    public virtual void OnUpdate() { }
}

// ❌ 编译失败：使用了 managed 类型
[BurstCompile]
public struct BadJob : IJob
{
    public string message;        // string 是 managed 类型
    public ArrayList list;        // ArrayList 是 managed 类型
    public int[] array;           // int[] 是 managed 类型
    public void Execute() { }
}

// ✅ 正确写法
[BurstCompile]
public struct GoodJob : IJob
{
    public NativeArray<float> data;   // NativeArray 是 unmanaged
    public int count;
    public void Execute()
    {
        for (int i = 0; i < count; i++)
        {
            data[i] *= 2f;
        }
    }
}

// ❌ 编译失败：使用了 try/catch
[BurstCompile]
public void DangerousMethod()
{
    try
    {
        throw new Exception("Boom");
    }
    catch (Exception e)
    {
        Debug.Log(e.Message);
    }
}

// ✅ 正确写法：使用返回值
[BurstCompile]
public (bool Success, float Result) SafeDivide(float a, float b)
{
    if (math.abs(b) < 0.0001f)
        return (false, 0f);
    return (true, a / b);
}

5.6.3 Unmanaged 类型约束

Burst 要求 Job 中的所有字段类型必须是 unmanaged（非托管）类型。unmanaged 类型包括：

  • 所有值类型（struct、enum、primitive）
  • NativeArray<T>、NativeList<T> 等 NativeContainer
  • float、double、int、uint、long、ulong、byte、short、char
  • Unity.Mathematics 中的 float3、float4x4 等
  • Entity（只是一个 uint）

判断类型是否 unmanaged：在 C# 中可以使用 System.Runtime.CompilerServices.Unmanaged 属性标记，或检查类型是否满足 unmanaged 约束。

5.7 调试 Burst 编译的代码

Burst 编译后的代码无法直接用 Visual Studio 的普通调试器单步执行。但有以下几种调试手段：

5.7.1 查看反汇编

Burst 提供了反汇编查看功能，可以看到编译后的机器码：

// 启用 Burst 反汇编输出
// 1. 打开 Burst Compiler Log（见 5.6 节）
// 2. 查找 "[Burst] Disassembly for ..." 部分
// 3. 日志中会输出完整的 x86-64 或 ARM64 汇编代码

// 示例输出片段（x86-64 AVX2）：
// vaddps ymm0, ymm1, ymm2      ; ymm0 = ymm1 + ymm2 (8 floats in parallel)
// vmovups [rdi + rax*4], ymm0  ; 存储结果到内存
// add rax, 32                   ; 指针前进 32 字节（8 floats * 4 bytes）
// cmp rax, rsi                  ; 比较是否到达终点
// jne .loop                     ; 如果不相等，继续循环

5.7.2 Burst Inspector

Burst Inspector 是 Unity 提供的可视化工具，可以查看每个 Burst 编译单元的详细信息：

  • 编译状态（Queued / Compiling / Compiled / Failed）
  • 编译耗时
  • 生成的机器码大小
  • 向量化状态（哪些循环被向量化了，哪些没有）
  • 函数内联图

访问路径：Window → Burst → Inspector。

5.7.3 Rider / Visual Studio 调试

Rider 对 Burst 有较好的调试支持。可以在 Burst 编译后的代码上设置断点，但只能看到 IL 级别的调试信息，无法单步执行到原生指令级别。

5.8 Burst 性能对比

以下是 Burst 编译前后的实际性能对比（同一代码，不同编译后端）：

测试场景Mono JITIl2CPP (无 Burst)Burst (AVX2)Burst (AVX-512)
1M 实体位置更新280 ms180 ms35 ms22 ms
1M 实体碰撞检测520 ms350 ms45 ms28 ms
1M 实体重力模拟150 ms120 ms18 ms12 ms
1M 实体排序（不可向量化）95 ms72 ms68 ms65 ms

关键观察：

  • 可向量化场景：Burst 相比 Mono JIT 可以获得 5-15 倍的加速。
  • 不可向量化场景：Burst 仍然有 1.1-1.5 倍的加速（来自内联、常量传播等其他优化）。
  • 排序等算法：受限于算法本身的分支和随机访问模式，SIMD 收益很小。

本章小结

Burst 编译器是 DOTS 性能的核心引擎。它通过 LLVM 后端将 C# IL 转换为高度优化的原生机器码，利用 SIMD 向量化、循环展开、函数内联等技术获得远超 Mono JIT 的性能。但 Burst 也有明确的限制——不支持虚方法、LINQ、反射、managed 类型等。理解这些限制并在编写代码时就避开它们，是发挥 Burst 全部潜力的前提。
