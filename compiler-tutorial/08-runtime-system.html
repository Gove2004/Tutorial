运行时系统：代码执行的基础设施

编译器生成了机器码，但机器码需要在某种环境下才能运行。运行时系统（Runtime System）就是提供这种环境的底层基础设施——它管理栈帧、分配内存、回收垃圾、处理异常。本章将从栈帧布局讲起，逐步实现 malloc/free、Arena 分配器、标记-清除 GC，直到完整的异常处理系统。

什么是运行时系统？

运行时系统是程序执行期间提供支持服务的软件层。它介于操作系统内核和应用程序之间，负责：内存管理（分配/释放）、函数调用（栈帧管理）、垃圾回收（自动内存管理）、异常处理（错误恢复）、动态链接（共享库加载）。没有运行时系统，编译器生成的机器码只是一堆无法执行的字节。

1. 栈帧与调用约定

函数调用是运行时系统的核心操作。每次调用都会在栈上创建一个栈帧（Stack Frame），包含函数的局部变量、保存的寄存器和返回地址。

1.1 栈帧布局

函数调用时的栈帧布局 (x86-64, 从低地址到高地址):

┌──────────────────────────┐
│  调用者的栈帧             │  ↑
│  (caller's frame)         │  │
├──────────────────────────┤  │
│  返回地址 (ret address)   │  │  push call 时压入
├──────────────────────────┤  │
│  %rbp (saved frame ptr)   │  │  function prologue: push %rbp
│  被调用者保存的寄存器      │  │            mov %rsp, %rbp
│  (%rbx, %r12-%r15)        │  │
├──────────────────────────┤  │
│  对齐填充 (padding)       │  │  确保 %rsp 16 字节对齐
├──────────────────────────┤  │
│  局部变量 (local vars)    │  │  alloca 在栈上分配
│  %rbp - 8                 │  │
│  %rbp - 16                │  │
│  %rbp - 24                │  │
├──────────────────────────┤  │
│  参数区 (argument area)   │  │  给嵌套函数调用预留
│  %rbp + 8                 │  │
│  %rbp + 16                │  │
├──────────────────────────┤  │
│  %rsp (栈指针)            │  ↓
└──────────────────────────┘

函数调用序列:
  call foo:
    push %rip          ; 保存返回地址
    jmp foo

  foo 的 prologue:
    push %rbp          ; 保存调用者的帧指针
    mov %rsp, %rbp     ; 建立新帧指针
    sub $32, %rsp      ; 为局部变量分配空间

  foo 的 epilogue:
    mov %rbp, %rsp     ; 释放局部变量
    pop %rbp           ; 恢复调用者的帧指针
    ret                ; 弹出返回地址，跳回去

1.2 调用约定（Calling Convention）

调用约定规定了函数调用时参数的传递方式、寄存器的使用规则和栈的清理责任。

约定 参数传递 返回值 被调用者保存 调用者保存
System V AMD64
(Linux/macOS)		 %rdi, %rsi, %rdx, %rcx, %r8, %r9 %rax %rbx, %rbp, %r12-%r15 %rax, %rcx, %rdx, %rsi, %rdi, %r8-%r11
Windows x64 %rcx, %rdx, %r8, %r9 %rax %rbx, %rbp, %rsi, %rdi, %r6-%r15 %rax, %rcx, %rdx, %r8-%r9, %xmm0-%xmm15
cdecl
(32-bit x86)		 栈上 (右到左) %eax %ebx, %ebp, %esi, %edi %eax, %ecx, %edx
⚠ 常见 Bug：忘记保存被调用者保存的寄存器会导致调用者数据被意外覆盖。例如，如果函数 foo 使用了 %rbx 但没有保存它，当 foo 返回到调用者时，调用者依赖的 %rbx 值已经被破坏了。这就是为什么需要 prologue/epilogue。

2. 内存管理

2.1 Malloc/Free 实现

理解 malloc 的最好方式是亲手实现一个。下面是一个简化版的 malloc/free：

#include <cstddef>
#include <cstdint>

// 简化版 malloc/free — 首次适配算法 (First Fit)
// 生产级实现 (glibc malloc) 有 10000+ 行代码，
// 但这个简化版本展示了核心思想

static char* heap_start = nullptr;
static size_t heap_size = 0;
static constexpr size_t HEADER_SIZE = sizeof(size_t); // 记录块大小

struct BlockHeader {
    size_t size;      // 数据区大小 (不含 header)
    bool is_free;     // 是否空闲
    BlockHeader* next; // 下一个块 (用于空闲链表)
};

void* my_malloc(size_t size) {
    // 对齐到 8 字节
    size = (size + 7) & ~7;

    // 首次适配：遍历空闲块链表
    BlockHeader* current = (BlockHeader*)heap_start;
    while (current) {
        if (current->is_free && current->size >= size) {
            // 找到合适的块
            current->is_free = false;
            return (char*)current + HEADER_SIZE;
        }
        current = current->next;
    }

    // 没有找到，扩展堆
    size_t total_size = HEADER_SIZE + size;
    char* new_block = (char*)sbrk(total_size);
    if (new_block == (char*)-1) return nullptr;

    BlockHeader* header = (BlockHeader*)new_block;
    header->size = size;
    header->is_free = false;
    header->next = nullptr;

    return new_block + HEADER_SIZE;
}

void my_free(void* ptr) {
    if (!ptr) return;
    BlockHeader* header = (BlockHeader*)((char*)ptr - HEADER_SIZE);
    header->is_free = true;
}

这个简化实现的局限性：

  • 首次适配：可能产生碎片。生产实现使用最佳适配或分离空闲链表。
  • 无合并：相邻空闲块没有合并。生产实现会在 free 时合并相邻块。
  • 线程不安全：没有锁保护。生产实现使用 per-thread cache + lock-free 数据结构。

2.2 Arena 分配器

Arena 分配器（也叫区域分配器）是一种高效的批量内存管理策略。它预先分配一大块内存（arena），然后从这个大块中顺序分配。所有内存可以在某个时刻一次性释放。

// Arena 分配器 — O(1) 分配和释放
class ArenaAllocator {
    char* arena_;
    size_t capacity_;
    size_t offset_;

public:
    ArenaAllocator(size_t capacity)
        : arena_(new char[capacity]),
          capacity_(capacity),
          offset_(0) {}

    // O(1) 分配：只需移动指针
    void* alloc(size_t size, size_t alignment = 8) {
        size_t aligned_offset = (offset_ + alignment - 1) & ~(alignment - 1);
        if (aligned_offset + size > capacity_) {
            throw std::bad_alloc();
        }
        void* ptr = arena_ + aligned_offset;
        offset_ = aligned_offset + size;
        return ptr;
    }

    // O(1) 释放：重置偏移量
    void reset() { offset_ = 0; }

    // 一次性释放整个 arena
    ~ArenaAllocator() { delete[] arena_; }
};

// 使用示例:
ArenaAllocator arena(1024 * 1024); // 1 MB arena
for (int i = 0; i < 10000; i++) {
    int* p = (int*)arena.alloc(sizeof(int));
    *p = i;
    // 不需要 free！reset 时全部释放
}
arena.reset(); // 所有 10000 个分配一次性回收

Arena 分配器的性能优势：

指标 malloc/free Arena 分配 加速比
单次分配时间 ~50ns ~0.5ns ×100
100 万次分配总时间 50ms 0.5ms ×100
释放 100 万个对象 50ms (逐个 free) 0ns (reset 即可) ∞
内存碎片 可能严重 无 (顺序分配) —
💡 应用场景：Arena 分配器在解析器、渲染引擎、游戏开发中极为常见。编译器前端（词法/语法分析）就是经典用例：解析完一个文件后，整个 AST 可以一次性释放。

3. 垃圾回收（Garbage Collection）

手动管理内存容易出错（泄漏、悬空指针、双重释放）。垃圾回收器自动回收不再使用的内存，让程序员从内存管理中解放出来。

3.1 标记-清除算法（Mark-Sweep）

标记-清除是最基础的 GC 算法，分两个阶段：

// 标记-清除垃圾回收器
class MarkSweepGC {
    std::vector<Object*> heap_;
    std::vector<Root> roots_; // 根集合 (全局变量、栈上引用)

    // 阶段 1: 标记 — 从根出发，标记所有可达对象
    void mark() {
        for (auto& root : roots_) {
            mark_recursive(root.ptr);
        }
    }

    void mark_recursive(Object* obj) {
        if (!obj || obj->marked) return;
        obj->marked = true;
        // 递归标记所有引用
        for (auto& ref : obj->references()) {
            mark_recursive(ref);
        }
    }

    // 阶段 2: 清除 — 遍历堆，释放未标记的对象
    void sweep() {
        for (auto it = heap_.begin(); it != heap_.end();) {
            if ((*it)->marked) {
                (*it)->marked = false; // 重置标记
                ++it;
            } else {
                delete *it;
                it = heap_.erase(it);
            }
        }
    }

public:
    void collect() {
        mark();   // 标记可达对象
        sweep();  // 清除不可达对象
    }
};

标记-清除的问题：

问题 描述 解决方案
停顿（Stop-the-World） GC 期间所有线程暂停 并发 GC、增量 GC
内存碎片 清除后留下空洞 压缩式 GC（标记-复制）
扫描成本高 每次都要遍历整个堆 分代 GC（只扫描年轻代）

3.2 复制式 GC（Copying GC）

复制式 GC 将堆分成两个等大小的区域（From/To）。活对象从 From 复制到 To，然后交换角色：

堆布局:
┌────────────┬────────────┐
│  From 区域  │  To 区域   │  (空闲)
│  (使用 60%) │  (空闲)    │
└────────────┴────────────┘

GC 过程:
1. 从根集合出发，扫描 From 区域
2. 将活对象复制到 To 区域 (保持引用关系)
3. 清空 From 区域
4. 交换 From/To 角色

优点:
  - 无内存碎片 (对象紧密排列)
  - 回收速度快 (只需复制活对象)
  - 适合短生命周期对象

缺点:
  - 最多只用 50% 堆空间
  - 长生命周期对象需要迁移机制

3.3 分代 GC（Generational GC）

分代 GC 基于一个经验观察：大部分对象都是朝生夕死的。它将堆分成多个"代"（Generation），年轻对象放在年轻代，存活时间长的对象晋升到老年代。

分代堆布局:
┌──────────────┐
│  老年代 (Old) │  ← 大对象、长期存活对象
│  (1GB)       │
├──────────────┤
│  年轻代 Y1   │  ← 刚分配的对象
├──────────────┤
│  年轻代 Y0   │  ← 最新分配的对象
│  (10MB)      │
└──────────────┘

Minor GC (频繁, 快):
  只扫描 Y0 + Y1
  存活对象晋升到 Y1 或 Old
  耗时: 1-10ms

Major GC (稀少, 慢):
  扫描整个堆
  耗时: 100-500ms

真实数据 (Java HotSpot):
  - 99% 的对象在 Young Generation 死亡
  - Minor GC 每 10ms 触发一次
  - Major GC 每 10 分钟触发一次
  - 这意味着 99.99% 的 GC 只需要扫描 10MB 而不是 1GB!

分代 GC 的性能数据：

GC 策略 暂停时间 吞吐量 内存开销
标记-清除 500ms 基准 100 低
复制式 100ms 120 高 (×2)
分代 GC 5ms (minor) 180 中 (×1.5)
并发分代 GC <1ms 160 中高

4. 异常处理与 Stack Unwinding

异常处理是运行时系统的另一个关键组件。当程序抛出异常时，运行时需要在栈上向上查找合适的 catch 处理器，这个过程叫 Stack Unwinding（栈展开）。

4.1 Stack Unwinding 过程

代码:
    try {
        outer() {
            middle() {
                inner() { throw Exception(); }
            }
        }
    } catch (...) { /* handle */ }

异常发生时栈的状态:
┌──────────────────┐
│  main() frame    │  ← catch handler 在这里
├──────────────────┤
│  outer() frame   │
├──────────────────┤
│  middle() frame  │
├──────────────────┤
│  inner() frame   │  ← 异常抛出点
└──────────────────┘

Unwinding 过程:
1. inner() 抛出异常
2. 运行时查找 .eh_frame 信息 (编译器生成的异常表)
3. 从 inner 帧开始向上 unwinding:
   a. 调用 middle() 的 destructors (局部变量析构)
   b. 调用 outer() 的 destructors
   c. 找到匹配的 catch handler
4. 栈恢复到 main() 帧，执行 catch 块

C++ RAII 保证: 每个帧的局部变量在 unwinding 时被正确析构
Java: 每个帧的 finally 块在 unwinding 时被执行

4.2 EH 模型（Exception Handling Models）

模型 语言 机制 无异常开销
SEH (Structured EH) Windows 编译器生成异常表，运行时查表 几乎为零
Itanium C++ ABI Linux C++ .eh_frame + DWARF CFI 信息 几乎为零
Java EH Java/JVM exception table 在字节码中 几乎为零
setjmp/longjmp C 手动保存/恢复栈帧 无 (需手动使用)
关键洞察：现代 EH 模型的最大设计哲学是"无异常时无开销"。编译器在正常代码路径上不插入任何检查代码，异常表是静态生成的。只有在异常真正抛出时，运行时才会查表并执行 unwinding。这使得 C++ 异常的运行时开销接近零（当不使用异常时）。

5. 动态链接

动态链接允许程序在运行时加载共享库（.so / .dll / .dylib），而不是在编译时将代码嵌入可执行文件。

动态链接过程:

编译时:
  gcc -o myapp main.c -lm    # 链接 libm.so

运行时:
  1. Loader 加载可执行文件和依赖库
  2. PLT/GOT 解析符号地址 (Lazy Binding)
     - 第一次调用 sin() 时解析真实地址
     - 之后直接跳转到该地址
  3. 重定位 (Relocation): 修正库中的相对地址

PLT/GOT 机制:
  调用 sin():
    jmp *GOT[sin]     → 跳转到 PLT stub
    PLT stub:
      如果 GOT[sin] == 0:
        调用 __dl_runtime_resolve() 解析 sin 的真实地址
        写入 GOT[sin] = 真实地址
      跳转 GOT[sin]    → 跳转到 sin 的真实地址

好处:
  - 可执行文件更小
  - 多个程序共享同一份库代码 (内存中只有一份)
  - 库可以独立升级 (无需重新编译程序)

6. 本章小结

本章我们构建了运行时系统的核心组件：

  • 栈帧与调用约定：理解函数调用时栈上发生了什么。System V AMD64 ABI 规定了参数传递、寄存器保存和栈对齐规则。
  • 内存管理：从简化版 malloc/free 到 Arena 分配器。Arena 分配将分配速度提升 100 倍，释放速度无穷大（O(1) reset）。
  • 垃圾回收：标记-清除是最基础的 GC，复制式 GC 解决碎片问题，分代 GC 利用"多数对象短命"的经验实现高性能。
  • 异常处理：Stack Unwinding 确保局部变量正确析构，现代 EH 模型保证无异常时零开销。
  • 动态链接：PLT/GOT 机制实现了懒绑定，让共享库的符号解析既高效又透明。
